## 1. 项目背景

### 1.1 项目背景

密码是用户最敏感的数据之一，但主流密码管理服务普遍把（加密后的）数据托管在服务端，客户端形态、存储位置、同步方式均由服务方决定。对合规受限、离线作业或高度重视数据主权的用户而言，需要一个**数据完全留在本地、且"不联网"可被技术审计验证**的密码管理器。Coffer 面向的就是这个需求。

### 1.2 本项目定位

> **一个完整移除网络能力的本地密码管理器。**

三个关键词的分量：

- **功能完整**：条目模型、密码生成、自动填充、TOTP、安全体检、搜索、附件、Passkey，一个不少。
- **完整移除网络**：App 不含对云端/远程服务的通信能力——禁止外部网络连接，数据不出本机。不是"默认不联网"，是**根本没有联网的能力**（本机内进程间通信 UDS / 本机回环不在禁止范围，见 NFR-SEC-07 与 docs/27 D-4）。这一条要能被技术审计验证（见 NFR-SEC-07）。
- **自研实现**：存储格式、加密方案均为自研设计并文档化；对外数据交换通过公开格式（1PUX / CSV / opvault）的导入导出实现互操作。

> **另有一个已裁定、排在 v2.x 的后置需求域**：**Agent 凭据域**（Secret Broker / Credential Gateway for AI Agents）。**它不在本文 §7 MoSCoW 表内，也不进入 v0.1–v1.0.0 任何一版的出口判据**，故本文 §1.2 / §1.3 / §7 的定位、目标用户与需求全集（**110 个原子 ID**，r1.4 起含 FR-15）**均不因它改变**。需求正文见 **`10-Agent凭据域.md`**。

### 1.3 目标用户

| 画像 | 特征 | 核心诉求 |
| --- | --- | --- |
| **合规受限者** | 就职于不允许密码离开内网的机构（军工、金融、涉密研发） | 数据物理不可外流，可接受无跨端同步 |
| **隐私偏好者** | 不信任任何云密码服务，包括标榜零知识的 | 完全掌控数据与备份，自行决定搬运方式 |
| **旧密码库持有者** | 已有存量密码数据，可导出为 1PUX / CSV / opvault | 平滑迁入，字段逐项可核对 |
| **离线环境用户** | 常在无网络环境作业（野外、封闭实验环境） | 离线可用是第一需求，不是附加项 |

### 1.4 最核心的矛盾与它的解决方式

需求提出时存在一个内在矛盾：

> "要本地版、无网络" **且** "要 Android 端 + macOS 端"

两端之间如何交换数据？**决策结论：不交换。本项目是纯单机应用。**

- Android 端只管理 Android 上的数据库；
- macOS 端只管理 macOS 上的数据库；
- 两端之间**不存在任何同步机制、配对机制、连接机制**；
- 数据若要跨端，唯一方式是**人工导出加密文件 + 人工搬运 + 导入**（AirDrop、U 盘、用户自选的任意通道）。App 不参与、不知情、不提供便利。

这个决策使架构从"分布式系统"降级为"单机应用"，复杂度降低约一个数量级，也让"零网络"这一承诺在技术上变得可证明——没有同步需求，就没有联网理由。

### 2.2 明确排除（Out of Scope）

以下功能**不实现，且不预留接口**。列入此表的意义在于：防止后续需求蔓延，并在评审时能明确回答"这个功能为什么没有"。

| 编号 | 排除项 | 排除理由 |
| --- | --- | --- |
| X-01 | 云端同步、云账号、订阅体系 | 与"零网络"根本冲突 |
| X-02 | 端到端设备间同步（含局域网直传） | 本项目定位为纯单机，见 §1.4 |
| X-03 | 家庭 / 团队 / 企业共享 | 需服务端协调权限与密钥分发 |
| X-04 | SSO / SCIM / 目录集成 | 企业级能力，依赖外部身份提供方 |
| X-05 | 审计日志上报、事件订阅 | 需服务端 |
| X-06 | 浏览器扩展（Chrome / Safari 插件） | 与系统级自动填充功能重叠，且引入独立发布与维护成本。**列为 v2 候选** |
| X-07 | 在线泄露库查询（HIBP 等） | 需联网。替代方案见 FR-6.5 |
| X-08 | 密码紧急联系人 / 遗产继承 | 需服务端验证与延迟机制 |
| X-09 | 实时协作与变更通知 | 需服务端 |
| X-10 | 遥测、崩溃上报、使用统计 | 与"零网络"根本冲突。崩溃日志一律本地留存 |
| X-11 | 自动更新检查 | 与"零网络"根本冲突。更新由用户手动下载安装包 |
| X-12 | 在线激活 / 许可证服务器 | 与"零网络"根本冲突（C-01）。采用离线签名序列号（FR-15.3），见 §12 Q-14 |
| X-13 | 反破解技术对抗（反调试、代码混淆、二进制完整性自校验） | 与开源模式冲突且成本高。商业模式约束官方分发渠道，不做技术对抗（见 FR-15 诚实声明） |

> ⚠️ **X-11 的连带影响**：由于 App 不联网，**无法自动更新**。这意味着安全补丁必须由用户主动获取。此项需在发布说明中显著告知用户，否则安全风险会随时间累积。缓解措施见 §10 风险 R-06。

## 3. 术语表

| 术语 | 定义 |
| --- | --- |
| **保险库（Vault）** | 密码条目的逻辑容器。一个 App 可含多个保险库，每个保险库独立加密 |
| **主密码（Master Password）** | 用户设定的唯一口令，用于派生解密密钥。**遗失不可恢复** |
| **主密钥（Master Key）** | 由主密码经 KDF 派生的加密密钥，仅存在于内存 |
| **安全核心（Vault Core）** | Rust 实现的加密 + 存储 + 业务逻辑库，两端共用 |
| **1PUX** | 1Password Unencrypted Export，1Password 8 导出的 ZIP 归档格式 |
| **opvault** | 1Password 7 及更早版本的本地加密保险库目录格式 |
| **自动填充（Autofill）** | 由系统或 App 将凭据注入到目标输入框的过程 |
| **TOTP** | 基于时间的一次性口令（RFC 6238） |
| **Passkey** | 基于 FIDO2/WebAuthn 的可同步凭据，替代传统密码 |
| **序列号（Serial）** | 离线签名的授权凭证：载荷（版本、机器指纹、签发时间）+ Ed25519 签名，经 Base32 编码供用户输入（FR-15） |
| **试用期（Trial）** | 未激活状态下自首次启动起 7 天的全功能窗口（FR-15.1） |
| **只读模式（Read-only Mode）** | 试用到期未激活后的降级形态：可查看 / 搜索 / 复制，一切写路径与数据出口被拒（FR-15.2） |

## 4. 用户角色与场景

### 4.1 主要角色

本产品为单用户单机软件，**无多角色权限模型**。角色仅按使用阶段划分：

| 角色 | 描述 | 关键活动 |
| --- | --- | --- |
| **首次使用者** | 全新安装，无历史数据 | 创建保险库 → 设定主密码 → 录入或导入条目 |
| **迁移者** | 从旧密码管理器迁出（可导出 1PUX / CSV） | 导出 1PUX → 导入 Coffer → 校验完整性 → 删除导出文件 |
| **日常使用者** | 已建库，日常填充 | 解锁 → 自动填充 → 新增/修改条目 |
| **维护者** | 定期整理与备份 | 跑安全检查 → 处理告警 → 导出加密备份 → 搬运到离线介质 |

### 4.2 关键场景

**场景 1：从旧密码管理器迁移（核心场景）**

1. 在原密码管理器中执行导出，得到 `xxx.1pux`；
2. 在 Coffer 中创建保险库，设定主密码；
3. 选择"从 1PUX 导入"，选中该文件；
4. 系统显示导入预检报告：将导入 N 个条目、M 个附件、K 个无法识别的字段；
5. 用户确认后完成导入，逐条抽查核对；
6. 用户按提示**删除导出的 1PUX 文件**（该文件为明文，是最大的瞬时风险点）。

**场景 2：日常填充（高频场景）**

1. 在目标 App 或浏览器触发登录框；
2. 系统弹出 Coffer 的填充建议（Android：Autofill 建议条；macOS：快捷键唤起面板）；
3. 用户通过生物识别或主密码确认身份；
4. 凭据填入。若条目含 TOTP，验证码可一并填入或复制。

**场景 3：主密码遗失（灾难场景）**

1. 用户忘记主密码 → **数据不可恢复**；
2. 系统不提供任何重置、找回、后门；
3. 唯一恢复路径：用此前导出的加密备份 + 当时记录的主密码；或重新开始。

> 此场景必须在**创建保险库时**以强制确认方式告知，不能隐藏在帮助文档里。

> **FR-4.6 平台限制与已定方案**
>
> macOS 不像 Android 有系统级 Autofill 框架，第三方 App **无法在其他 App 的输入框中直接注入文本**（除非申请辅助功能权限模拟键盘）。两种可行方案：
>
> | 方案 | 做法 | 权限 | 结论 |
> | --- | --- | --- | --- |
> | **剪贴板** | 写入剪贴板 + 提示粘贴 + 定时清除 | 无额外权限 | ✅ **采用** |
> | 辅助功能模拟键盘 | 申请 Accessibility 权限模拟键盘输入 | 高权限 | ❌ 不采用。权限过重，与"最小权限"原则冲突，用户信任成本高 |
>
> **已定**：v1.0.0 及后续版本均采用剪贴板方案。体验确实比 Android 端差一档（用户需多按一次粘贴），这是平台能力的硬限制，不是实现缺陷。**该差距需在用户文档中明确说明**，避免用户误判为 bug。

### G. 数据导入（FR-7）

这是本项目的**命脉功能**。用户从旧密码管理器迁出后，能否完整落地，决定产品成败。

| 编号 | 需求 | 验收要点 | 来源 |
| --- | --- | --- | --- |
| FR-7.1 | 导入 1PUX | 解析 ZIP 归档，读取 `export.attributes`、`export.data`、`files/` 目录 | 1PUX 规范 |
| FR-7.2 | 导入 CSV | 解析 9 列 CSV 导出格式（字段有限，见下） | CSV 格式规范 |

| FR-7.5 | 导入模式 | 支持"新建保险库导入"与"导入到已有保险库"；后者提供"跳过重复项 / 覆盖 / 全部新建"策略 | UX 关键 |

| FR-7.8 | 导入后风险提示 | 强制提示删除源导出文件（明文风险） | 安全要求 |

**FR-7.2 能力边界（必须明示）**：该 CSV 导出格式**仅包含**：标题、网址、用户名、密码、一次性密码、收藏状态、归档状态、标签、备注。**不包含**：安全问题、关联项、自定义字段、附件。因此 CSV 导入必然是降级导入，UI 中需明确提示"建议使用 1PUX 以获得完整数据"。

**FR-7.1 格式要点**（来源：1PUX 格式规范，见引用来源清单 [1]）：

```
xxx.1pux  (ZIP 归档)
├── export.attributes    # JSON：version / description / createdAt
├── export.data          # JSON：accounts → vaults → items 三级嵌套
└── files/               # 附件实体文件（export.data 中以 path 引用）
```

`export.data` 结构：

```json
{
  "accounts": [{
    "attrs": { "accountName", "name", "avatar", "email", "uuid", "domain" },
    "vaults": [{
      "attrs": { "uuid", "desc", "avatar", "name", "type" },
      "items": [{
        "uuid", "favIndex", "createdAt", "updatedAt", "state",
        "categoryUuid", "overview": { "title", "url", "urls", "tags", "subtitle" },
        "details": { "loginFields", "notesPlain", "sections", ... },
        "file": { "attrs", "path" }
      }]
    }]
  }]
}
```

其中 `type` 取值：`P`（个人库）、`E`（共享库）、`U`（用户自建库）。`state` 取值：`active` / `archived`。

> | Android | `CredentialProviderService` + `androidx.credentials` | **API 34（Android 14）** | Android 官方文档：Credential Manager 自 Android 14 引入；`CredentialProviderService` 标注 Added in API level 34 |
> | macOS | AuthenticationServices 凭据提供者扩展（App Extension） | **macOS 14（Sonoma）** | Apple Platform Security 文档：macOS 13 起可指定第三方凭据提供者；自 macOS Sonoma（14）起开放第三方**存储** Passkey |
>
> **两条必须处理的限制**：
>
> 1. **macOS 端没有 Passkey 数据源**：据 1PUX 格式导出说明（见引用来源清单 [2]），**Passkey 仅能在 iOS 和 Android 端导出**，桌面端导出的 1PUX 不含 Passkey。因此 macOS 端首次建立 Passkey 只能靠两条路：① 在网站重新注册 Passkey 并选择 Coffer；② 从 Android 端的库文件（密文）搬运过来。**这条限制无法通过技术手段绕过**，必须在用户文档中说明。
> 2. **Passkey 私钥在库文件中是可导出的**：FIDO 规范的本意是私钥不可导出，但所有密码管理器为支持跨设备同步都必须存储可迁移的私钥。本项目遵循同一惯例：Passkey 私钥加密存储在库内，随库文件一起搬运。这意味着**库文件一旦外流，Passkey 私钥也随之暴露**——与其他条目面临的威胁等级一致，但用户应当知情。
>
> **Android 官方对密码管理器的硬性要求**：官方文档明确 "For passkeys, private keys must be encrypted"。本项目的字段级加密设计天然满足该要求。
>
> ⚠️ **本功能是本项目唯一一项"平台能力做不到就只能砍掉"的技术依赖。** 因此它的平台可行性验证已**列为 M0 阶段必须完成的事项**（见 `04-系统设计.md` §10.1），不允许拖到编码阶段才暴露。

### Q. 主密码恢复（FR-17）—— 新增（2026-10-09）

> **背景（2026-10-09，用户裁定）**：用户提出「本地主密码忘记如何恢复」——Coffer 零知识设计下主密码是唯一解锁凭据（VaultSetupView 明示「遗失后无法找回」），**无恢复码/应急密钥机制**（全仓 grep 证实），改密 `changePassword` 强制旧密码重验证（错 → 1002），备份恢复也需同一主密码 → **主密码遗忘 = 数据不可恢复**（唯一幸存通道：已启用 Touch ID 时可解锁读数据，但不能重置密码）。用户裁定（2026-10-09，选项 C「A+B 都做」）立项双通道恢复。技术基础：三路解锁（password/biometric/MCP）recover 的都是 **DEK**（数据密钥）——重置主密码 = 新密码 KDF 派生 KEK **重新包裹 wrapped_dek + 重算 verifier + 原子重写 header**；DEK 不变则条目数据不重加密，bio_wrap / mcp_wrap / recovery_wrap 全部保持。存储格式 = header 新增**可选** `recovery_wrap` 字段（向后兼容，dev-architect 设计定夺是否 bump FORMAT_VERSION）。

| 编号 | 需求描述 | 验收要点 | 来源 |
| --- | --- | --- | --- |
| FR-17.1 | **生物识别重置主密码**（A 方案） | 已启用 Touch ID（`bio_wrap` + Keychain bio 项）时，锁态 LockView「忘记密码 → Touch ID 验证 → 设新密码」，**免旧密码**重置主密码。新增 Rust API `reset_password_with_bio`：bio 解锁会话已持 DEK → 新密码重包 `wrapped_dek` + 重算 `verifier` → 原子重写 header。验收：重置后旧密码失效、Touch ID / MCP escrow / 恢复码全部仍可用（DEK 不变）；生物识别重验失败不重置；写入审计。**归属 v2.5.0** | 用户 2026-10-09 裁定（A+B 都做）；BUG-17 动机延伸（主密码可能遗忘，Touch ID 应始终可解锁） |
| FR-17.2 | **离线恢复码**（B 方案） | VaultSetup / 设置生成一次性**高熵恢复码**（≥128-bit 随机，仅展示一次需抄写留存），header 存 `recovery_wrap`（恢复码 KDF 派生 KEK 包裹 DEK）。遗忘主密码 → 锁态「忘记密码 → 输入恢复码 + 新密码」→ 重包 `wrapped_dek` + 重算 `verifier`。验收：恢复码仅展示一次、可主动重新生成（旧码随即失效）；正确恢复码 + 新密码可重置；错误恢复码失败且文案与格式错误**不可区分**（同 FR-1.4 纪律）；恢复码明文永不落盘（仅 wrap 密文存 header）。**归属 v2.5.0** | 用户 2026-10-09 裁定（A+B 都做） |

### 6.1 安全（NFR-SEC）

| 编号 | 需求 | 依据 |
| --- | --- | --- |
| NFR-SEC-01 | 加密算法：XChaCha20-Poly1305 做 AEAD，Argon2id 做 KDF | RFC 9106（Argon2，2021-09）；draft-irtf-cfrg-xchacha（2019）；RFC 8439（ChaCha20-Poly1305，2018-06） |

| NFR-SEC-03 | 无服务端额外熵因子（Secret Key 类机制）情况下的爆破成本补偿：通过提高 Argon2id 内存参数实现，代价是解锁延迟 | 本项目架构约束 |

| NFR-SEC-05 | 敏感数据不进入崩溃报告、系统日志、系统备份 | 安全要求 |
| NFR-SEC-06 | 所有加密实现使用经过审计的成熟库，**禁止自实现密码学原语** | 通用工程原则 |
| NFR-SEC-07 | "零网络"可被技术验证（**边界 = 无外部网络、数据不出本机**；本机内进程间通信 UDS / 本机回环允许，docs/27 D-4）：Android 侧 `AndroidManifest.xml` 不含 `INTERNET` 权限；macOS 侧二进制不链接网络框架，签名时启用 Hardened Runtime 并关闭网络客户端权限 | 可审计性要求 |
