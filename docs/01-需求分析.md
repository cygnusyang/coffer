## 1. 项目背景

### 1.1 一个被厂商自己删掉的产品

Coffer 要解决的问题，不是"再做一个密码管理器"，而是填补一个**明确存在的功能真空**。

事实链条（均有来源，见 §12）：

1. 1Password 在 7.x 及更早版本中提供 **standalone vault（独立保险库）** —— 完全本地存储、可由用户自行备份、可用 Dropbox/iCloud 等第三方通道同步。
2. **1Password 8 于 2021 年发布时移除了 standalone vault 支持**，转为纯云架构（Electron 客户端 + 订阅制）。官方社区代表的原话是"standalone vault 不会成为 1Password 8 的一部分"。
3. 到 2025 年，第三方评测（WIRED）仍将"无法本地托管任何保险库"列为 1Password 的主要缺陷之一，并明确对比指出 Bitwarden 有自托管、KeePassXC 类开源方案需要用户自行解决托管。
4. 官方社区中长期存在用户因此流失的讨论，迁移终点集中在 KeePassXC、Bitwarden、Strongbox 等。

**结论**：市场存在一批"要 1Password 的体验，但不要 1Password 的云"的用户，而 1Password 官方已明确放弃服务这批人。这是本项目的立足点。

### 1.2 本项目定位

> **一个功能对齐 1Password 8、但完整移除了网络能力的本地密码管理器。**

三个关键词的分量：

- **功能对齐**：条目模型、密码生成、自动填充、TOTP、安全体检、搜索、附件、Passkey，一个不少。
- **完整移除网络**：App 不含任何网络通信代码路径。不是"默认不联网"，是**根本没有联网的能力**。这一条要能被技术审计验证（见 NFR-SEC-07）。
- **不是 1Password 的复刻品**：因为 1Password 8 已无本地实现可参照，本项目在存储格式、加密方案、导入路径上均为自研。1Password 只作为**功能对标基线**与**数据来源**。

### 1.3 目标用户

| 画像 | 特征 | 核心诉求 |
| --- | --- | --- |
| **合规受限者** | 就职于不允许密码离开内网的机构（军工、金融、涉密研发） | 数据物理不可外流，可接受无跨端同步 |
| **隐私偏好者** | 不信任任何云密码服务，包括标榜零知识的 | 完全掌控数据与备份，自行决定搬运方式 |
| **1Password 7 留守者** | 仍在用旧版本，担心 macOS 升级后彻底失效 | 平滑迁出，保留原有使用习惯 |
| **离线环境用户** | 常在无网络环境作业（野外、封闭实验环境） | 离线可用是第一需求，不是附加项 |

### 1.4 最核心的矛盾与它的解决方式

需求提出时存在一个内在矛盾：

> "要本地版、无网络" **且** "要 Android 端 + macOS 端"

两端之间如何交换数据？**决策结论：不交换。本项目是纯单机应用。**

- Android 端只管理 Android 上的数据库；
- macOS 端只管理 macOS 上的数据库；
- 两端之间**不存在任何同步机制、配对机制、连接机制**；
- 数据若要跨端，唯一方式是**人工导出加密文件 + 人工搬运 + 导入**（AirDrop、U 盘、用户自选的任意通道）。App 不参与、不知情、不提供便利。

这个决策使架构从"分布式系统"降级为"单机应用"，复杂度降低约一个数量级，也让"零网络"这一承诺在技术上变得可证明——没有同步需求，就没有联网理由。

以下功能**不实现，且不预留接口**。列入此表的意义在于：防止后续需求蔓延，并在评审时能明确回答"这个功能为什么没有"。

| 编号 | 排除项 | 排除理由 |
| --- | --- | --- |
| X-01 | 云端同步、云账号、订阅体系 | 与"零网络"根本冲突 |
| X-02 | 端到端设备间同步（含局域网直传） | 本项目定位为纯单机，见 §1.4 |
| X-03 | 家庭 / 团队 / 企业共享 | 需服务端协调权限与密钥分发 |
| X-04 | SSO / SCIM / 目录集成 | 企业级能力，依赖外部身份提供方 |
| X-05 | 审计日志上报、事件订阅 | 需服务端 |
| X-06 | 浏览器扩展（Chrome / Safari 插件） | 与系统级自动填充功能重叠，且引入独立发布与维护成本。**列为 v2 候选** |
| X-07 | 在线泄露库查询（HIBP 等） | 需联网。替代方案见 FR-6.5 |
| X-08 | 密码紧急联系人 / 遗产继承 | 需服务端验证与延迟机制 |
| X-09 | 实时协作与变更通知 | 需服务端 |
| X-10 | 遥测、崩溃上报、使用统计 | 与"零网络"根本冲突。崩溃日志一律本地留存 |
| X-11 | 自动更新检查 | 与"零网络"根本冲突。更新由用户手动下载安装包 |

> ⚠️ **X-11 的连带影响**：由于 App 不联网，**无法自动更新**。这意味着安全补丁必须由用户主动获取。此项需在发布说明中显著告知用户，否则安全风险会随时间累积。缓解措施见 §10 风险 R-06。

## 3. 术语表

| 术语 | 定义 |
| --- | --- |
| **保险库（Vault）** | 密码条目的逻辑容器。一个 App 可含多个保险库，每个保险库独立加密 |
| **主密码（Master Password）** | 用户设定的唯一口令，用于派生解密密钥。**遗失不可恢复** |
| **主密钥（Master Key）** | 由主密码经 KDF 派生的加密密钥，仅存在于内存 |
| **安全核心（Vault Core）** | Rust 实现的加密 + 存储 + 业务逻辑库，两端共用 |
| **1PUX** | 1Password Unencrypted Export，1Password 8 导出的 ZIP 归档格式 |
| **opvault** | 1Password 7 及更早版本的本地加密保险库目录格式 |
| **自动填充（Autofill）** | 由系统或 App 将凭据注入到目标输入框的过程 |
| **TOTP** | 基于时间的一次性口令（RFC 6238） |
| **Passkey** | 基于 FIDO2/WebAuthn 的可同步凭据，替代传统密码 |

## 4. 用户角色与场景

### 4.1 主要角色

本产品为单用户单机软件，**无多角色权限模型**。角色仅按使用阶段划分：

| 角色 | 描述 | 关键活动 |
| --- | --- | --- |
| **首次使用者** | 全新安装，无历史数据 | 创建保险库 → 设定主密码 → 录入或导入条目 |
| **迁移者** | 从 1Password 迁出 | 导出 1PUX → 导入 Coffer → 校验完整性 → 删除导出文件 |
| **日常使用者** | 已建库，日常填充 | 解锁 → 自动填充 → 新增/修改条目 |
| **维护者** | 定期整理与备份 | 跑安全检查 → 处理告警 → 导出加密备份 → 搬运到离线介质 |

### 4.2 关键场景

**场景 1：从 1Password 迁移（核心场景）**

1. 在 1Password 8 中执行导出，得到 `1PasswordExport-xxx.1pux`；
2. 在 Coffer 中创建保险库，设定主密码；
3. 选择"从 1PUX 导入"，选中该文件；
4. 系统显示导入预检报告：将导入 N 个条目、M 个附件、K 个无法识别的字段；
5. 用户确认后完成导入，逐条抽查核对；
6. 用户按提示**删除导出的 1PUX 文件**（该文件为明文，是最大的瞬时风险点）。

**场景 2：日常填充（高频场景）**

1. 在目标 App 或浏览器触发登录框；
2. 系统弹出 Coffer 的填充建议（Android：Autofill 建议条；macOS：快捷键唤起面板）；
3. 用户通过生物识别或主密码确认身份；
4. 凭据填入。若条目含 TOTP，验证码可一并填入或复制。

**场景 3：主密码遗失（灾难场景）**

1. 用户忘记主密码 → **数据不可恢复**；
2. 系统不提供任何重置、找回、后门；
3. 唯一恢复路径：用此前导出的加密备份 + 当时记录的主密码；或重新开始。

> 此场景必须在**创建保险库时**以强制确认方式告知，不能隐藏在帮助文档里。

## 5. 功能需求

编号规则：`FR-<组>.<序号>`。每条含**需求描述**、**验收要点**、**来源**（对应 1Password 功能解剖的哪一项）。

### A. 保险库与访问控制（FR-1）

| 编号 | 需求 | 验收要点 | 来源 |
| --- | --- | --- | --- |
| FR-1.1 | 支持创建本地保险库 | 指定名称与主密码即可创建；库文件落在本地指定目录 | 1P 保险库 |
| FR-1.2 | 支持创建多个保险库 | 至少支持 10 个库并存；各自独立主密码 | 1P 多库 |
| FR-1.3 | 主密码强度校验 | 创建时给出熵评估；弱密码需二次确认（非强制阻止） | 1P 同类 |
| FR-1.4 | 解锁保险库 | 输入主密码解锁；错误密码只返回统一失败提示，不区分"密码错"与"文件损坏" | 1P 解锁 |
| FR-1.5 | 生物识别解锁 | 支持 Android BiometricPrompt / macOS Touch ID 作为**解锁快捷方式**（主密钥仍由主密码派生，生物识别仅解锁本地缓存的密钥封装） | 1P 生物识别 |
| FR-1.6 | 自动锁定 | 支持"空闲 N 分钟锁定"与"应用退到后台立即锁定"，N 可配置，默认值见 §6.5 | 1P 自动锁定 |
| FR-1.7 | 手动立即锁定 | 提供一键锁定入口 | 1P 同类 |
| FR-1.8 | 修改主密码 | 支持更换主密码，需先验证旧密码；换密后全库重新加密 | 1P 同类 |
| FR-1.9 | 保险库元信息 | 记录创建时间、条目数、最后修改时间、格式版本 | 1P 同类 |

**FR-1.2 补充说明**：既然不联网，"密钥派生移除 Secret Key"是本项目与 1Password 的关键安全差异。1Password 的 Secret Key 是一个 128 bit 的额外随机因子，用于显著抬高离线爆破成本。Coffer 无服务端，无法保管 Secret Key，因此**必须靠 KDF 参数补偿**（见 NFR-SEC-02）。

| 编号 | 需求 | 验收要点 | 来源 |
| --- | --- | --- | --- |
| FR-2.1 | 支持 1Password 全部条目类型 | 至少覆盖：Login、Password、Secure Note、Credit Card、Identity、Document、API Credential、Bank Account、Crypto Wallet、Database、Driver License、Email Account、Medical Record、Membership、Outdoor License、Passport、Reward Program、SSH Key、Server、Social Security Number、Software License、Wireless Router | 1P 22 类条目 |

| FR-2.3 | 自定义字段 | 支持在任意条目上添加自定义字段，类型含文本、密码、URL、日期、布尔、多行文本 | 1P 自定义字段 |
| FR-2.4 | URL 与多 URL | Login 类支持多个 URL，每个带标签（如"登录页""管理后台"） | 1P urls 数组 |
| FR-2.5 | 标签 | 一条目可打多个标签；标签可筛选 | 1P tags |
| FR-2.6 | 收藏 | 条目标记为收藏，可在独立视图查看 | 1P favIndex |
| FR-2.7 | 归档 | 条目可归档，归档后不出现在默认列表 | 1P archived |
| FR-2.8 | 回收站 | 删除先进回收站，可恢复；回收站可清空 | 1P Recently Deleted |
| FR-2.9 | 条目历史版本 | 每次修改留存历史快照，可查看与回滚 | 1P item history |
| FR-2.10 | 新建 / 编辑 / 复制 / 移动条目 | 完整 CRUD；复制可跨库复制 | 1P 同类 |
| FR-2.11 | 附件挂载 | 条目可挂载文件附件 | 1P attachments |

**FR-2.1 落地说明**：22 类条目需逐一确定字段清单。此清单在详细设计阶段以**字段映射表**形式落地（`03-详细设计.md` §6.3），本阶段只锁定类型范围。

| 编号 | 需求 | 验收要点 | 来源 |
| --- | --- | --- | --- |

> **FR-4.6 平台限制与已定方案**
>
> macOS 不像 Android 有系统级 Autofill 框架，第三方 App **无法在其他 App 的输入框中直接注入文本**（除非申请辅助功能权限模拟键盘）。两种可行方案：
>
> | 方案 | 做法 | 权限 | 结论 |
> | --- | --- | --- | --- |
> | **剪贴板** | 写入剪贴板 + 提示粘贴 + 定时清除 | 无额外权限 | ✅ **采用** |

| 编号 | 需求 | 验收要点 | 来源 |
| --- | --- | --- | --- |
| FR-7.1 | 导入 1PUX | 解析 ZIP 归档，读取 `export.attributes`、`export.data`、`files/` 目录 | 1PUX 规范 |

| FR-7.4 | 导入预检 | 导入前展示报告：条目数、按类型分布、附件数、无法映射的字段清单、冲突项 | UX 关键 |
| FR-7.5 | 导入模式 | 支持"新建保险库导入"与"导入到已有保险库"；后者提供"跳过重复项 / 覆盖 / 全部新建"策略 | UX 关键 |

**FR-7.2 能力边界（必须明示）**：1Password 的 CSV 导出**仅包含**：标题、网址、用户名、密码、一次性密码、收藏状态、归档状态、标签、备注。**不包含**：安全问题、关联项、自定义字段、附件。因此 CSV 导入必然是降级导入，UI 中需明确提示"建议使用 1PUX 以获得完整数据"。

**FR-7.1 格式要点**（来源：1Password 官方 1PUX 格式说明页）：

```
xxx.1pux  (ZIP 归档)
├── export.attributes    # JSON：version / description / createdAt
├── export.data          # JSON：accounts → vaults → items 三级嵌套
└── files/               # 附件实体文件（export.data 中以 path 引用）
```

`export.data` 结构：

```json
{
  "accounts": [{
    "attrs": { "accountName", "name", "avatar", "email", "uuid", "domain" },
    "vaults": [{
      "attrs": { "uuid", "desc", "avatar", "name", "type" },
      "items": [{
        "uuid", "favIndex", "createdAt", "updatedAt", "state",
        "categoryUuid", "overview": { "title", "url", "urls", "tags", "subtitle" },
        "details": { "loginFields", "notesPlain", "sections", ... },
        "file": { "attrs", "path" }
      }]
    }]
  }]
}
```

其中 `type` 取值：`P`（个人库）、`E`（共享库）、`U`（用户自建库）。`state` 取值：`active` / `archived`。

> **FR-10 范围已定：完整能力，条件性进 v1.0**（C-04 v1.2）
>
> **⚠️ 条件性交付修订（C-04 v1.2，2026-09-24）**：完整交付以 **D-11（macOS 凭据提供者扩展，见 `04-系统设计.md` §14.1）在 M0 验证打通**为前提——打通则「导入/查看/创建/使用/删除」完整交付；未打通则 macOS 端「创建/使用」延 v1.1，**首版保留导入/查看/删除**。这是对原 ADR-10 的条件性修订。Android 端不受此影响。
>
> 覆盖全部 Passkey 凭据的导入、查看、创建、使用、删除。两端技术路径均已确认可行：
>
> | 平台 | 技术路径 | 最低版本 | 依据 |
> | --- | --- | --- | --- |
> | Android | `CredentialProviderService` + `androidx.credentials` | **API 34（Android 14）** | Android 官方文档：Credential Manager 自 Android 14 引入；`CredentialProviderService` 标注 Added in API level 34 |
> | macOS | AuthenticationServices 凭据提供者扩展（App Extension） | **macOS 14（Sonoma）** | Apple Platform Security 文档：macOS 13 起可指定第三方凭据提供者；自 macOS Sonoma（14）起开放第三方**存储** Passkey |
>
> **两条必须处理的限制**：
>
> 1. **macOS 端没有 Passkey 数据源**：据 1Password 官方导出说明，**Passkey 仅能在 iOS 和 Android 端导出**，桌面端导出的 1PUX 不含 Passkey。因此 macOS 端首次建立 Passkey 只能靠两条路：① 在网站重新注册 Passkey 并选择 Coffer；② 从 Android 端的库文件（密文）搬运过来。**这条限制无法通过技术手段绕过**，必须在用户文档中说明。
> 2. **Passkey 私钥在库文件中是可导出的**：FIDO 规范的本意是私钥不可导出，但所有密码管理器为支持跨设备同步都必须存储可迁移的私钥。本项目遵循同一惯例：Passkey 私钥加密存储在库内，随库文件一起搬运。这意味着**库文件一旦外流，Passkey 私钥也随之暴露**——与其他条目面临的威胁等级一致，但用户应当知情。
>
> **Android 官方对密码管理器的硬性要求**：官方文档明确 "For passkeys, private keys must be encrypted"。本项目的字段级加密设计天然满足该要求。
>
> ⚠️ **本功能是本项目唯一一项"平台能力做不到就只能砍掉"的技术依赖。** 因此它的平台可行性验证已**列为 M0 阶段必须完成的事项**（见 `04-系统设计.md` §10.1），不允许拖到编码阶段才暴露。

## 6. 非功能需求

### 6.1 安全（NFR-SEC）

| 编号 | 需求 | 依据 |
| --- | --- | --- |
| NFR-SEC-01 | 加密算法：XChaCha20-Poly1305 做 AEAD，Argon2id 做 KDF | RFC 9106（Argon2，2021-09）；draft-irtf-cfrg-xchacha（2019）；RFC 8439（ChaCha20-Poly1305，2018-06） |
| NFR-SEC-02 | Argon2id 参数需按设备实测标定，**目标：在目标设备上单次派生耗时 0.5–1.0 秒**，内存占用不超过设备可用内存的合理比例。**具体参数（m/t/p）待阶段 3 基准测试后锁定**，不预设数值 | OWASP Password Storage Cheat Sheet 的调参方法论；RFC 9106 §4 参数建议 |
| NFR-SEC-03 | 无 Secret Key 情况下的爆破成本补偿：通过提高 Argon2id 内存参数实现，代价是解锁延迟 | 本项目架构差异 |
| NFR-SEC-04 | 内存中密钥使用后清零，避免被换页到磁盘 | 通用密码学工程实践 |
| NFR-SEC-05 | 敏感数据不进入崩溃报告、系统日志、系统备份 | 安全要求 |
| NFR-SEC-06 | 所有加密实现使用经过审计的成熟库，**禁止自实现密码学原语** | 通用工程原则 |
| NFR-SEC-07 | "零网络"可被技术验证：Android 侧 `AndroidManifest.xml` 不含 `INTERNET` 权限；macOS 侧二进制不链接网络框架，签名时启用 Hardened Runtime 并关闭网络客户端权限 | 可审计性要求 |

> **NFR-SEC-07 是本项目的核心可信度来源。** "我们不会联网"是承诺；"我们**没有能力**联网"是可验证事实。后者才值得信任。Android 的 `INTERNET` 权限缺失会让操作系统直接阻止任何 socket 创建，这是不可绕过的。

| --- | --- | --- |
| AC-01 | 创建保险库并解锁 | 能创建、能解锁、错误密码被拒且无信息泄露 |
| AC-02 | 录入并检索条目 | 22 类条目各录一条，均可搜索到 |
| AC-03 | 从 1PUX 完整导入 | 使用真实 1PUX 样本导入，条目数与源文件一致，抽查 20 条字段无错位 |
| AC-04 | Android 自动填充（v1.1，第二批交付） | 在真实 App 与浏览器中成功填充登录信息 |
| AC-04b | macOS 快捷键唤起 + 剪贴板填充 + 自动清除闭环 | 全局快捷键唤起快速搜索 → 选中条目复制密码 → 粘贴登录 → 剪贴板按时自动清除 |
| AC-05 | TOTP 正确性 | 生成验证码与标准 TOTP 工具（如 `oathtool`）输出一致 |
| AC-06 | 导出后可恢复 | 导出加密备份 → 删除库 → 从备份恢复 → 数据完全一致 |
| AC-07 | 零网络验证 | Android 安装包经反编译确认无 `INTERNET` 权限；macOS 二进制经 `otool -L` 确认无网络框架链接 |
| AC-08 | 安全检查可用 | 构造含弱密码、重复密码、http 站点的库，全部被检出 |

### 8.2 安全验收

| 编号 | 验收项 | 通过标准 |
| --- | --- | --- |
| AC-SEC-01 | 加密正确性 | 使用标准测试向量验证 Argon2id 与 XChaCha20-Poly1305 实现 |
| AC-SEC-02 | 锁定后内存无残留 | 锁定后堆转储中检不到明文密码 |

## 10. 风险登记册

| 编号 | 风险 | 影响 | 概率 | 缓解措施 |
| --- | --- | --- | --- | --- |
| R-01 | **Passkey 平台实现打不通**（Android API 34 凭据提供者 / macOS 凭据提供者扩展） | **高：macOS 端「创建/使用」无法交付（延 v1.1），首版降级为部分交付** | 中 | **已列入 M0 必验项**（见系统 §10.1）：用最小 Demo 在真机跑通 Passkey 的创建与断言。**该验证为 macOS 首版门禁**：若不通过，macOS 端「创建/使用」延 v1.1，首版保留导入/查看/删除（FR-10 条件性交付） |
| R-01b | macOS 端 Passkey 无数据源（桌面端 1PUX 不含 Passkey） | 中：macOS 端 Passkey 初始为空 | 高（确定） | **macOS 首版时 Android 端尚不存在，缓解路径②（从 Android 端库文件搬运）在首版不成立，路径①（网站重新注册）为主要路径。** 已定缓解路径：在网站重新注册 + 从 Android 端库文件搬运。**无法技术绕过，需在用户文档中说明** |
| R-02 | **主密码遗忘即数据永久丢失** | 高：用户数据灾难 | 中 | 强制创建时告知；提供备份提醒；提供"恢复演练"引导 |
| R-03 | **无自动更新**导致安全补丁滞后 | 中高：长期安全风险 | 高（确定性） | 发布说明显著提示；提供版本检查的手动路径；核心加密逻辑尽量少变更 |
| R-04 | 自研容器格式存在设计缺陷 | 高：数据泄露或不可恢复 | 低中 | 使用成熟原语；格式规范文档化；第三方审计（建议 v1.0 前） |
| R-05 | 1PUX 导入字段映射不全 | 中：迁移体验受损 | 中 | 导入预检报告明示未映射项；建立样本回归测试集 |
| R-06 | macOS 无系统级填充，体验明显弱于 1Password | 中：macOS 端吸引力下降 | 高（确定） | 已定采用剪贴板 + 全局快捷键把摩擦降到可接受；**辅助功能模拟键盘方案已明确不采用**（权限过重，与最小权限原则冲突）。**首版直接体验差距，用户文档必写（提前至首版）** |
| R-07 | 密码学实现被误用（如 nonce 复用） | 极高：加密体系崩塌 | 低 | 严格 code review；使用库的高层 API 而非手工拼装；nonce 由 CSPRNG 生成并纳入测试 |
| R-08 | 范围蔓延（用户后续追加同步 / 共享需求） | 中：架构返工 | 中 | §2.2 已明确排除，作为评审基线 |
