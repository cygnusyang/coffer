# 运营门槛与就绪度（Coffer）

> 目的：把「能不能对外推」从感觉变成可判定的清单。每条标准都必须**能指着一份证据说通过或没通过**，否则不算标准。
> 审计时点：2026-10-25（v2.13.3 已发布）。

## 1. 三档门槛

### T1 可发布（工程侧硬门槛）

| # | 标准 | 判定方法 |
| --- | --- | --- |
| 1.1 | 可复现构建 | 干净机器上 `tools/build_macos_app.sh` 一次通过；CI 用同一脚本 |
| 1.2 | 测试门禁 | 全部 harness + `cargo test` 绿；测试计数逐版本只增不减 |
| 1.3 | 版本纪律 | 三位版本号 + CHANGELOG 段 + tag 触发自动发布 |
| 1.4 | 产物签名 | `codesign --verify --strict` 通过；entitlement 最小化 |
| 1.5 | 治理文件 | LICENSE / CONTRIBUTING / CODE_OF_CONDUCT / SECURITY / CLA 齐备 |
| 1.6 | 更新通道 | OTA 可用且清单验签（Ed25519 + SHA256） |
| 1.7 | 无阻断缺陷 | Issue 与 KNOWN-ISSUES 中无未处置的 S1/S2 |

### T2 可推广（首批外部用户）

| # | 标准 | 判定方法 |
| --- | --- | --- |
| 2.1 | 非技术用户能装上 | 下载后**不需要**命令行；Gatekeeper 阻断必须有一步式指引或已公证 |
| 2.2 | 首屏能说清是什么 | README 首屏有：一句话定位 + 截图/GIF + 安装入口 + 许可证 |
| 2.3 | 目标语言覆盖 | UI 与 README 双语；文档至少有一份英文导览 |
| 2.4 | 反馈有去处 | Issue 模板 + Discussions + SECURITY 私密渠道；有 triage 约定 |
| 2.5 | 可信度可核验 | CI 徽章绿 + 测试证据可查 + 设计文档公开 |
| 2.6 | 主分发渠道 ≥1 | Homebrew Cask 或等价的一键安装入口（不能只有 Releases 页） |
| 2.7 | 有过一次正式曝光 | ≥1 个社区渠道（HN / Reddit / V2EX / 少数派 / MCP 目录）的正式介绍 |

### T3 可持续运营

| # | 标准 | 判定方法 |
| --- | --- | --- |
| 3.1 | 可预期的发布节奏 | 明示节奏（如双周/月度），且最近 3 个版本间隔符合 |
| 3.2 | 兼容策略成文 | 破坏性变更走 MAJOR + 迁移说明；schema 变更需迁移脚本 |
| 3.3 | 缺陷响应分级 | S1/S2/S3 定义 + 响应时限，Issue 上可见处置记录 |
| 3.4 | 渠道数据可观测 | 下载量/版本分布有口径与刷新机制（GitHub `download_count` 已具备） |
| 3.5 | 单点风险可控 | ≥2 名维护者，或交接文档 + 一键恢复流程齐备 |
| 3.6 | 安全披露闭环 | SECURITY.md 有渠道 + 响应承诺 + 已演练一次 |
| 3.7 | 反馈闭环 | Issue → 版本 → CHANGELOG 双向可追溯 |

## 3. 结论

- **T1 达标**：工程侧随时可以发版。
- **T2 差 3 项**：公证（连带 Cask 一起解）、主分发渠道、一次正式曝光。前两项受 $99 证书阻塞；曝光需要先有 2.1/2.6 落地，否则推了也是拉低转化。
- **T3 明显不达标**：缺成文节奏与响应时限、bus factor = 1。这三条不是「写文档」能解决的，属于运营投入问题。

**一句话**：**能发版，还不能推；推得动，撑不住。** 现在的瓶颈不在代码质量，在分发与持续性。
