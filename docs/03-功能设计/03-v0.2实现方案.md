## 0. 结论先行

1. **八项需求全部可进 v0.2，无需顺延大项**。唯一裁定的顺延子项：FR-8.2（1PUX 导出，Should 级）推 v0.3，理由见 §2.1。
2. **FR-1.8 修改主密码在本架构下不需要"全库重新加密"**——只重封装 header 中的 DEK（约 1 天工作量，而非数天的重加密工程）。需求措辞与本架构的偏差裁决见 §3.2 D-2。
3. **加密备份 = 现有工作目录的 ZIP 打包**（docs/01-需求与架构/03-详细设计.md §1.4 既定格式），零新增加密设计；密钥不出会话的约束被**结构性满足**（打包根本不需要密钥）。FR-8 的回环验证（导出 → 恢复 → 解锁 → 数据一致）作为验收测试落进 cf-exporter。
4. **并行分组四组**：G1 exporter（cf-exporter）、G2 audit（cf-audit）、G3 session（cf-session + cf-store history 仓库 + cf-crypto SubKeys 增一把子密钥）、G4 串行接线（cf-ffi + macos + docs）。三组并行组的文件范围**互斥矩阵见 §6**，接口契约在本文档冻结（§3 各节签名），G1/G2/G3 可同时开工，合并顺序 G1/G2 → G3 → G4。
5. **唯一动到格式冻结边的改动**：`SubKeys` 新增第 8 把子密钥 `audit_key`（HKDF label `cf/audit/v1`）。**不涉及 DDL、不涉及任何落盘数据**（纯运行时派生），不触发 schema 迁移；按不可逆决策流程仍列出待人类确认（§3.5 D-5）。

## 2. 技术选型裁决

### 2.1 顺延裁定：FR-8.2 1PUX 导出 → v0.3

**备选**：A) 本版实现 1PUX 导出；B) 顺延。
**选择 B**。理由：① 1PUX 导出依赖 `categoryUuid` 反向映射表，而正向映射尚卡在 M0-③（`004`/`112` 两类待库主确认）——先导出再返工映射表是双重浪费；② 1PUX 导出在 MoSCoW 为 Should（docs/01-需求与架构/01-需求分析.md §7），不阻塞交付；③ 加密备份（FR-8.1）已覆盖"数据可搬运可恢复"的核心诉求。**风险**：用户迁移回 1Password 的路径推迟——缓解：CSV 导出是 1Password 可导入的保底格式。

### 2.2 备份提醒（FR-8.5）：可选项

Should 级。若 G4 排期富余则做（纯 Swift：记录 `last_backup_at` 到 UserDefaults，超过 N 天在主窗口横幅提醒）；否则顺延，不阻塞任何验收。

## 3. 各需求设计

> 以下签名即 **G1/G2/G3 并行开发的冻结契约**。签名改动必须回到本文档走评审，不得在实现中静默变更。

### 3.1 FR-8.1 / 8.3 / 8.6 —— 导出与备份（G1：cf-exporter）

#### D-1 备份格式：复用 docs/01-需求与架构/03-详细设计.md §1.4 交换形态（结论）

**备选**：
| 方案 | 做法 | 评估 |
| --- | --- | --- |
| **A. ZIP 打包工作目录（采用）** | `wal_checkpoint(TRUNCATE)` → 打包 `header.json` + `db.sqlite`（排除 -wal/-shm）→ 结构校验 | 内容已字段级 AEAD 加密，ZIP 仅容器；恢复 = 解包 → `open_container` → 用主密码解锁。与 docs/01-需求与架构/03-详细设计.md §1.4 完全一致，零新格式 |
| B. 自研单文件加密容器（类似 KDBX） | 设计新 header + 流式加密 | 违背"不推翻既有决策"；需新格式文档、新审计面、新迁移策略。否决 |
| C. 逐表导出再整体加密 | 导出 JSON → AEAD 加密 | 多一次序列化映射 = 多一类数据丢失 bug；且与库文件格式分叉。否决 |

**安全性论证**：密钥不出会话的约束被结构性满足——打包过程**不接触任何密钥**（`header.json` 只含公开参数与密文）。导出文件可用应用重新打开（FR-8.1 验收）= 解包后主密码解锁，回环测试见下。

**⚠️ 不可逆决策标注**：备份文件格式是用户会长期留存的产物，一旦用户开始归档 `.coffer` 备份文件，格式即事实冻结（后续只能向后兼容）。**请主理人确认后落定**：备份文件扩展名定为 `.coffer`（替换 docs/01-需求与架构/03-详细设计.md 中 `.lvvault` 旧称，后者是改名前遗留），格式 = docs/01-需求与架构/03-详细设计.md §1.4 ZIP 容器。

### 3.2 FR-1.8 修改主密码（G3：cf-session）

#### D-2 架构裁决：只重封装 DEK，不重加密全库

**依据**：本架构中条目数据由 DEK 经 HKDF 派生的 SubKeys 加密（docs/01-需求与架构/03-详细设计.md §2.4），主密码只经 Argon2id 生成 KEK 封装 DEK（docs/01-需求与架构/03-详细设计.md §2.2）。**换主密码 = 换 KEK = 只需重封装 header 中的 `wrapped_dek` 与 `verifier`**，db.sqlite 一个字节都不用动。

**备选**：
| 方案 | 做法 | 评估 |
| --- | --- | --- |
| **A. 只重封装 header（采用）** | 旧密码解出 DEK → 新 salt + 新 KEK → 重封装 wrapped_dek/verifier → `cf_format::write_header` 原子重写 | 数百毫秒完成；失败面小；与 Touch ID 封装（K_bio 直接封装 DEK）天然解耦——**bio 封装不受换密影响** |
| B. 字面执行"全库重新加密" | 换新 DEK → 全表逐字段重加密 | 数十分钟级（大库）；中途断电需复杂恢复协议；收益为零（威胁模型无差异）。否决 |

**需求文档裁决**：docs/01-需求与架构/01-需求分析.md FR-1.8 验收要点"换密后全库重新加密"描述的是 1Password 式实现（数据直接由口令派生密钥加密）的需求意图，其**本质是"换密后旧密码失效"**——方案 A 完全满足该本质。裁决：**改文档不改实现**（G4 任务：docs/01-需求与架构/01-需求分析.md §5-A FR-1.8 与 docs/01-需求与架构/03-详细设计.md §2.7 各补一句"本架构下仅重封装 header"备注）。

#### 接口签名

```rust
// core/cf-session/src/change_password.rs（新模块）
impl VaultSession {
    /// 修改主密码。
    /// 门禁：需解锁态（1001）——与 enable_biometric 一致（设置页在解锁后可达）。
    /// 流程：new_password 过 zxcvbn 门禁（<3 → 1010，先于任何文件操作）
    ///   → recover_dek(old_password) 重验证旧密码（错 → 1002，header 未动）
    ///   → salt' = random_salt()；KEK' = derive_key(new, salt', header.kdf)
    ///   → wrapped_dek' = seal(KEK', aad=uuid‖"wrapped_dek", DEK)
    ///   → verifier'    = seal(KEK', aad=uuid‖"verifier", VERIFIER_PLAINTEXT)
    ///   → header.modified_at 更新 → write_header 原子重写 → 内存 header 副本更新
    /// bio 封装（wrapped_dek_bio）不动：K_bio 封装的是 DEK 本身。
    /// 可选参数支持顺带升级 KDF 档位（M0-② 标定后的补偿路径）：
    pub fn change_password(
        &self,
        old_password: &str,
        new_password: &str,
        new_kdf: Option<KdfParams>,
    ) -> SessionResult<()>;
}
```

#### 文件清单（G3）

- `core/cf-session/src/change_password.rs`（新）
- `core/cf-session/src/vault.rs`（挂接方法，~20 行）
- `core/cf-session/src/lib.rs`（模块声明）

#### 测试要点

1. 换密 → lock → 旧密码解锁 **失败**（1002）、新密码解锁成功；换密后 bio 解锁仍成功（若已启用）。
2. 旧密码错 → 1002 且 header 字节不变（读文件比对）。
3. 新密码弱 → 1010 且 header 字节不变。
4. 换密中途注入失败（write_header 前打桩）→ 旧 header 完整、旧密码仍可解锁（原子性）。
5. 换密后立即导出备份 → 恢复 → 新密码可解锁、旧密码不可。
6. `new_kdf` 传入新档位 → header.kdf 更新且解锁走新参数。

#### 风险

低。唯一注意点：`recover_dek` 已在 docs/03-功能设计/02-TouchID解锁设计.md 拆分出（bio 通道复用），此处直接复用，无新密钥代码路径。

### 3.3 FR-2.9 条目历史版本（G3：cf-session + cf-store）

#### D-3 快照语义

**数据**：`history` 表已冻结（uuid / item_uuid / version / created_at / enc_snapshot BLOB），快照载荷 = 既有的 `cf_domain::snapshot::ItemSnapshot`（CBOR 序列化 → `hist_key` AEAD 加密，AAD = `build_table_field_aad("history", history_uuid, "enc_snapshot")`，与现有仓库层模式一致）。

**触发**：`update_item_with_totp` 事务内、替换前，读当前完整状态构造快照写入（同事务，满足 NFR-REL-01）。**内容无变化不写**（CBOR 字节与最新版本比对）——防高频保存把库撑爆。

**回滚语义**：以历史快照构造 `ItemDraft` 走**正常 update 路径**——即"回滚"本身也是一次修改，当前状态先成为新版本（1Password 同语义，用户可"回滚回滚"）。

**保留策略**：v0.2 不限量（表有 `idx_history_item`，查询按 version DESC 分页）；保留上限（1Password 约 1 年）列为 v0.3 备选，不做隐性清理。

**备选**：
| 方案 | 评估 |
| --- | --- |
| **A. 修改前全量快照（采用）** | 简单、恢复语义直观；空间代价 = 每次真实修改一份全量 CBOR（条目级 KB 量级，可接受） |
| B. 字段级 diff | 省空间但回滚需重放逻辑，快照含 Concealed 值的 diff 构造复杂。否决（YAGNI） |
| C. 触发器实现（SQLite trigger） | 加密在 Rust 侧，触发器拿不到明文快照。否决 |

#### 接口签名

```rust

    pub fn list(&self, item_uuid: &str) -> CfStoreResult<Vec<HistoryMeta>>;   // version DESC
    pub fn snapshot(&self, history_uuid: &str) -> CfStoreResult<Option<ItemSnapshot>>; // 解密

// Repos 聚合体新增字段 pub history: HistoryRepo<'a>（repo/mod.rs）

// core/cf-session/src/usecase/history.rs（新）

pub fn list_history(store: &ItemStore, item_id: &str) -> SessionResult<Vec<HistoryEntry>>;
```

#### 文件清单（G3）

- `core/cf-store/src/repo/history.rs`（新）、`core/cf-store/src/repo/mod.rs`（聚合体 + 重导出）、`core/cf-store/src/lib.rs`（pub use 一行）
- `core/cf-session/src/usecase/history.rs`（新）、`usecase/mod.rs`、`usecase/items.rs`（update 路径插快照，**本组内唯一触碰点**）、`src/lib.rs`

#### 测试要点

1. 创建 → 编辑 2 次 → history 有 2 个版本，version 递增，created_at 单调。
2. 快照密文落盘断言（BLOB ≠ CBOR 明文；跨行搬运解密失败——沿 totp 仓库测试模式）。
3. 回滚：编辑改标题+删字段+换 TOTP → 回滚到 v1 → 当前条目与 v1 逐字段相等，且 history 多出一条新版本。
4. 内容无变化的 update 不新增版本。
5. 同事务原子性：update 中注入失败 → history 与主表同时回滚。
6. 硬删条目 → history 级联消失（FK ON DELETE CASCADE 已建）；软删/恢复不动 history。
7. 1000 条目 × 平均 3 版本的 list 性能 < 200ms 基线。

#### 工作量与风险评估

**约 2.5–3 天，是本版最大单项**。风险：① `update_item_with_totp` 是 v0.1 QA 反复打磨过的路径，插快照必须以最小侵入实现（改动集中在函数开头读快照、事务闭包内写一行）；② 快照需读 TOTP secret（`ItemSnapshot.totp` 含 secret）——secret 只在 Rust 事务内流转，不跨 FFI，符合既有纪律；③ 库体积增长——内容去重已缓解，v0.2 观察不设限。

### 3.4 FR-3.3 密码短语生成（G2：cf-audit）

#### 接口签名

```rust
// core/cf-audit/src/passphrase.rs（新）
pub struct PassphraseOptions {
    pub word_count: usize,     // 3..=10（默认 5，约 64 bit 熵 @7776 词表）
    pub separator: String,     // 默认 "-"；限 1..=3 个打印字符（防注入与失控长度）

}
```

**随机源（硬约束落实）**：`rand`（0.8，MIT/Apache）+ `rand::rngs::OsRng`，逐词 `SliceRandom::choose`。不自实现 RNG（NFR-SEC-06）；与现有 `passwords` crate 的 CSPRNG 同根（getrandom）。词表 7776 词（每词 ≈ 12.9 bit）经 `include_str!` 嵌入 `assets/`。

**FFI**（G4）：`generate_passphrase(opts: FfiPassphraseOptions) -> String`，挂 VaultSession 与 CofferApp 双入口（生成器在解锁前后都可用，镜像 `generate_password` 的做法）。

#### 文件清单（G2）

- `core/cf-audit/src/passphrase.rs`（新）、`core/cf-audit/src/lib.rs`（模块声明 + 重导出）
- `core/cf-audit/assets/eff_large_wordlist.txt`（新资产）
- `core/cf-audit/Cargo.toml`（新增 rand）

#### 测试要点

1. 形状：词数精确、分隔符精确、capitalize 生效；词均在词表内。
2. 参数越界（word_count 2/11、空分隔符超长）→ 拒绝。
3. 熵底线：word_count=5 时不同输出分布抽样断言（同一词不重复出现在单次短语中——choose 放回问题：采用**不重复抽样** `choose_multiple`，熵按 7776·7775·… 计算仍 ≥ 目标）。
4. 10 万次生成无 panic（模糊边界）。

**词表许可证**：EFF Diceware 词表按 CC-BY 类许可发布（要求署名），与 NFR-LEGAL-02（禁 GPL/AGPL）不冲突，但需在 `assets/` 附 LICENSE 头与 NOTICE。**备选**：若评审认为署名义务不可接受，换用自建 7776 词表（从公开领域词典过滤 3–8 字母词，工作量 +0.5 天）。**此为许可合规决策，请主理人确认 EFF 词表方案**。 passphrase 不落盘，词表更换对格式零影响（非不可逆）。

### 3.5 FR-6.2 / FR-6.3 —— Watchtower 重复密码与弱 URL（G2 纯函数 + G3 编排）

#### D-4 分层：cf-audit 纯函数、cf-session 编排

cf-audit **不依赖 cf-store**（保持纯计算层），解密与取数在 cf-session。重复密码判定**不得明文比较**（docs/01-需求与架构/03-详细设计.md §8 AUD-02）：用 HMAC-SHA256 指纹比对。

#### D-5（⚠️ 不可逆决策标注）SubKeys 新增 audit_key

`SubKeys` 增加第 8 把子密钥：`audit_key = derive_subkey(dek, vault_uuid, "cf/audit/v1")`（`cf-crypto/src/subkeys.rs`，G3）。

**为什么不能复用现有 7 把**：HMAC key 与字段加密 key 一钥多用违背 docs/01-需求与架构/03-详细设计.md §2.4 "一钥一用"；为什么不是存储格式问题：HKDF 派生是运行时行为，不落盘、不改 DDL、旧库打开时多派生一把即可——**但 `SubKeys` 是跨 crate 公共类型，签名变更影响 cf-store/cf-session 编译**，且"子密钥清单"实质构成密钥体系契约的一部分。**请主理人确认后落定**。若否决，备选方案：在 cf-session 内对 `field_key` 再做一次 HKDF-expand（`"cf/audit/v1"` label）派生——不加类型字段，但派生链多一跳。

#### 接口签名

### 3.6 FR-11.2 模糊匹配搜索（G3：cf-session）

#### D-6 算法

**备选**：
| 方案 | 评估 |
| --- | --- |
| **A. 多字段子串 + 词级编辑距离 ≤ 1（采用）** | 覆盖"子串与近似匹配"验收要点；1000 条量级实测毫秒级；无索引复杂度 |
| B. n-gram / BM25 | 引入分词与打分体系，200ms 预算下收益不明。否决（v0.3 观察误报率再议） |
| C. SQLite FTS5 | 加密列无法建索引（明文不可落盘），FTS 需密文索引方案。否决（架构冲突） |

扩展范围：搜索字段从仅标题扩到 **标题 + 用户名 + URL + 标签**（全量解密内存搜索的既定方案 A，docs/01-需求与架构/03-详细设计.md §3.3，无新增性能面）。近似匹配限词级（token）Damerau-Levenshtein ≤ 1、且词长 ≥ 4 才启用（短词误报爆炸）；实现用 `strsim`（MIT/Apache，新增依赖）而非自写 Unicode 编辑距离。

```rust

///   命中 = 子串包含 OR 与该字段任一 token 的编辑距离 ≤ 1（词长 ≥ 4）
pub fn search(store: &ItemStore, query: &str) -> SessionResult<Vec<ItemSummary>>;
```

#### 测试要点

1. 子串回归（既有测试全绿）。
2. 近似：`githb` 命中 `github`；`ab` 不触发近似（词长 < 4）；中文字段近似按词长规则自然关闭（CJK 单 token 长词除外，逐用例验证）。
3. 多字段：按用户名 / URL / 标签命中。
4. 性能：1000 条 × 4 字段 < 200ms 基线（更新既有基线测试）。
5. NFC：组合/分解形式一致命中（沿用现有归一化测试模式）。
