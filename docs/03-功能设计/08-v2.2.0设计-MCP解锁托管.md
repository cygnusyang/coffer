# 29 · v2.2.0 设计——MCP 解锁托管与设置页收口

## 0. 结论先行

**路线（lead 2026-10-07 已裁定，本文细化）**：App 解锁后 `HKDF(DEK, salt=vault_uuid, info="cf/mcp/v1")` 派生 `mcp_key` 托管进 macOS 数据保护 Keychain；库 header 新增可选字段 `mcp_wrap`（复用 `biometric_wrap` 先例，**零 format_version 变更、零 DDL 变更**）承载 `AEAD(mcp_key, DEK)` 封装密文。MCP 进程只拿 `mcp_key` 解封 DEK 开库——获得「此库解锁能力」而非可复用主密码；删除 Keychain 条目即独立吊销；换主密码（重封装 D-2，DEK 不变）**不自动吊销**托管，吊销走设置页开关显式执行。

关键裁定建议（需用户/lead 确认项见 §8）：

1. **派生分层**：HKDF 原语（label + `derive_mcp_key`）落 `cf-crypto`；编排（recover_dek → 派生 → 封/解封 DEK）落 `cf-session`（镜像 `unlock_bio` 通道）。
2. **`mcp_wrap` 存 header**，不存第二 keychain 条目——与 `wrapped_dek_bio` 同型，单 keychain 条目（只存 `mcp_key`）。
3. **CLI 取密顺序**：托管条目 → `COFFER_VAULT_PASSWORD` env 兜底 → 都无则配置错误退出 1。**env 不覆盖托管**（托管存在即可用）；env 仅当托管不存在（`Ok(None)`）时兜底；托管读取失败/解锁失败 → **fail-closed 报错退出 1**，不回退 env（防止掩盖签名/ACL 配置问题）。
4. **Keychain 条目无 biometry ACL**（仅 `WhenUnlockedThisDeviceOnly`，共享 access group）——CLI 无法交互认证，ACL 必触发弹窗/失败（既有坑，见 §6 风险 1）；**coffer CLI 必须与 App 同 Apple Development 身份 + 同 `keychain-access-groups` entitlement 签名**，组内读取静默无弹窗。
5. **UI**：provider 下拉放开 coffer 切换；自家库配置（vault 目录来自当前打开的库）；注册命令随 provider 生成（coffer 版**不含密码 env**，只带 `COFFER_VAULT_DIR`）；op 告警/「链接 1Password」仅 provider==op 时呈现；新增 MCP 解锁托管三态开关（镜像 Touch ID 三态 + D-9 顺序裁定）。

## 2. 关键机制：mcp_key 封装通道（镜像 bio 通道）

解锁能力等价于「能拿到 DEK」。主密码路径 = 密码 → Argon2id KEK → 解封 `wrapped_dek`（`cf-session/src/unlock.rs:277 recover_dek`）。`mcp_key` 无法反向推出 DEK（HKDF 单向），因此需要一条**独立的 DEK 封装副本**，与 Touch ID 的 `wrapped_dek_bio` 完全同构（`cf-session/src/unlock_bio.rs`）：

```text
enable（App 侧，镜像 unlock_bio D-9 顺序）:
  derive_mcp_key(password)         // recover_dek → HKDF(DEK, uuid, "cf/mcp/v1") → mcp_key
  Swift 写 Keychain               // service="cn.coffer.mcp-escrow" account=vault_uuid（先 Keychain 后 header）
  enable_mcp_escrow(password, mcp_key)  // recover_dek → seal(mcp_key, aad=uuid‖"wrapped_dek_mcp", DEK)
                                        // → 原子重写 header.json 的 mcp_wrap 段
  失败 → Swift 补偿删除 Keychain 项（不留半启用态）

unlock（CLI 侧）:
  read_mcp_key(vault_uuid)          // VaultEscrowStore：Keychain 读 mcp_key
  unlock_store_with_mcp_key(mcp_key) // open(mcp_key, aad=uuid‖"wrapped_dek_mcp", mcp_wrap.wrapped_dek_b64)
                                       // → DEK → finish_unlock（与主密码/bio 路径共享收尾）
```

**与 bio 通道的关键差异**（本文唯一有意偏离）：

| 维度 | wrapped_dek_bio（Touch ID） | wrapped_dek_mcp（MCP 托管） | 理由 |
| --- | --- | --- | --- |
| 封装钥 | K_bio = **随机** 32B（CSPRNG） | mcp_key = **DEK 派生**（确定性） | 派生钥无随机存储需求，且「删条目即吊销」；确定性使重启用幂等（无需新随机钥） |
| Keychain ACL | `biometryCurrentSet`（读取须生物认证） | **无 ACL**（仅 WhenUnlockedThisDeviceOnly） | MCP 进程为后台 spawn，无法交互认证；组内读取靠共享 access group 静默放行 |
| 重启用 | 生成新 K_bio，旧项作废 | 重派生同一 mcp_key，幂等覆盖 | 确定性派生属性 |

**派生位置**：`mcp_key` **不进 `SubKeys` 容器**（`cf-crypto/src/subkeys.rs`）。容器语义 = 「库内使用密钥」；`mcp_key` 是 escrow 出库密钥，生命周期与在库子密钥不同（只在 enable 时派生一次、交给平台存储），放入容器会在每次解锁多派生一把且语义混淆。label 常量与派生函数仍**同文件共置**（subkeys.rs），保证 label 可发现性。

## 3. mcp_key 派生规格

### 3.1 HKDF 输入

与既有全部子密钥**同一方案**（`cf-crypto/src/kdf.rs:319 derive_subkey`）：

| 参数 | 值 |
| --- | --- |
| 算法 | HKDF-SHA256（`Hkdf::<Sha256>`） |
| salt | `vault_uuid` 16 字节原始形式（同 `SubKeys::derive`） |
| ikm | DEK（32 字节） |
| info | `"cf/mcp/v1"` |
| 输出 | 32 字节 |

### 3.2 purpose 标签与既有编号关系

- 新标签：`LABEL_MCP: &str = "cf/mcp/v1"`（`cf-crypto/src/subkeys.rs`，与 `LABEL_META`…`LABEL_PASSKEY_IDX` 同文件）。
- 既有 10 个 label：`cf/meta/v1` `cf/item/v1` `cf/field/v1` `cf/file/v1` `cf/history/v1` `cf/manifest/v1` `cf/attach-mac/v1` `cf/audit/v1` `cf/root-mac/v1` `cf/passkey-idx/v1`。`cf/mcp/v1` 与前缀**无碰撞** → 派生的第 11 把独立密钥，与其他子密钥互不相同（一钥一用保持）。
- **不冲突**：方案（salt + label）未变，仅新增 label；`SubKeys` 容器字段不动（§2）。已托管条目的解锁只依赖「header 里的 wrapped_dek_mcp + Keychain 里的 mcp_key」，与既有 10 把子密钥零耦合。

### 3.3 接口与测试（cf-crypto）

```rust
// cf-crypto/src/subkeys.rs（新增，不放 SubKeys 容器）
pub const LABEL_MCP: &str = "cf/mcp/v1";
/// HKDF(DEK, uuid, "cf/mcp/v1") → 32B（escrow 用，不进 SubKeys 容器）
pub fn derive_mcp_key(dek: &[u8; 32], vault_uuid: &[u8; 16]) -> Result<[u8; 32], CfCryptoError>;
```

测试（镜像 `audit_key`/`root_mac_key`/`passkey_idx_key` 先例，subkeys.rs:230-330）：
1. **KAT 已知答案**：固定 dek=`0x42…`、uuid=`0x11…` → 冻结 hex（实现时按既有「独立 Python 实现首算」惯例计算，测试注释记录输入与先例交叉验证）。
2. **与既有 10 把子密钥两两互异**（label 分离）。
3. **确定性** + **跨库不同**（uuid 变 → mcp_key 变）。

### 3.4 不可逆性

label 一旦随 v2.2.0 发布并托管了用户条目，**改 label 会使全部已托管条目失配**（无法解封 wrapped_dek_mcp），用户须重开开关。属**外部可观察契约** → 列入 §8 不可逆清单（D-1）。

## 5. Keychain 条目规格

### 5.1 条目定义（对齐 `BiometricKeychain.swift` 先例，关键差异见 §2 表）

| 属性 | 值 | 依据 |
| --- | --- | --- |
| class | `kSecClassGenericPassword` | BiometricKeychain 同款 |
| service | `"cn.coffer.mcp-escrow"` | 与 `"cn.coffer.biometric"`（BiometricKeychain.swift:28）平行命名空间，互不干扰 |
| account | `vault_uuid` 文本 | 多库天然隔离（BiometricKeychain 同款，docs/03-功能设计/02-TouchID解锁设计.md §3.3） |
| accessible | `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` | **绝不随 iCloud 同步**；CLI 为登录态后台进程，可读 |
| accessControl（ACL） | **无**（不设 `kSecAttrAccessControl`，只设 accessible） | **关键差异**：CLI 无法交互认证，任何 ACL（biometry 等）都会弹窗或失败（既有坑 memory `coffer-real-machine-keychain-acl-consent`） |
| access group | `A6DS985SJJ.app.coffer.Coffer` | 与 App entitlement 同组（Coffer.entitlements:27）；组内二进制读取静默放行，无跨组同意弹窗 |
| 数据保护钥匙串 | `kSecUseDataProtectionKeychain=true` | 同 BiometricKeychain（macOS 10.15+ 语义） |

> `kSecAttrAccessControl` 与 `kSecAttrAccessible` **互斥**（BUG-2 实证，BiometricKeychain.swift:104-109）——本条目不设 ACL，直接设 `accessible`，无此冲突。

### 5.2 生命周期（设置页开关 ↔ 条目绑定，镜像 Touch ID D-9 顺序裁定）

| 动作 | 顺序 | 失败语义 |
| --- | --- | --- |
| **启用**（开关 ON，需内联主密码确认，D-6 同款） | ① FFI `derive_mcp_key(password)`（Rust：recover_dek → 派生，~1s Argon2id）→ ② Swift `McpEscrowKeychain.save(mcp_key)` → ③ FFI `enable_mcp_escrow(password, mcp_key)`（Rust：recover_dek → seal → 原子重写 header `mcp_wrap`） | ②/③ 任一失败 → Swift 补偿删除 Keychain 项（不留半启用态；AppModel.swift:795-801 同款 catch） |
| **关闭**（开关 OFF，二次确认） | ① Swift `McpEscrowKeychain.delete`（幂等）→ ② FFI `disable_mcp_escrow`（header 原子重写 `available=false`） | ② 失败非致命（Keychain 已删，MCP 实际已不可用；AppModel.swift:817-842 同款） |
| **stale**（header `available=true` 但 Keychain 项缺失） | 三态渲染「重新启用」入口 | 重启用 = 重派生同 mcp_key，幂等覆盖（比 Touch ID 的随机 K_bio 更干净，无需新钥） |

三态判定纯函数（镜像 `TouchIDStatus.resolve`，TouchIDStatus.swift:39-55）：

```text
resolve(headerMcpWrapAvailable, keychainItemExists, sessionOpen) →
  sessionOpen ∧ headerAvailable ? (keychainItemExists ? enabled : stale) : disabled
```

### 5.3 吊销语义（lead 要求落档）

- **删除 Keychain 条目 = 吊销**：CLI 无法再解封 `mcp_wrap`（无 DEK 无法重派生 mcp_key）。
- 已外泄的 mcp_key（如被攻破的 CLI 进程）在进程存活期内仍可用——标准吊销语义（文档声明，非缺陷）。
- **确定性派生**：重启用恢复同一 mcp_key，幂等；吊销后可随时重开。
- **换主密码不自动吊销**（重封装 D-2，DEK 不变 → mcp_key 不变 → wrapped_dek_mcp 不变）：**落档三处**——本文 §5.3、McpSettingsView footer 文案（用户可见：「换主密码不影响 MCP 解锁托管；如需吊销请在设置页关闭」）、docs/01-需求与架构/05-Agent凭据域.md MCP 域。

## 6. CLI 取密顺序（core/cf-mcp）

### 6.1 现状

`coffer_config_from_env()`（cli.rs:208-235）要求 `COFFER_VAULT_DIR` + `COFFER_VAULT_PASSWORD` 双 env，缺任一 → 退出 1；`CofferStoreProvider::open(vault_dir, password)`（cli.rs:569）一步开库+解锁。

### 6.2 新取密流程（`--provider coffer`）

```text
1. COFFER_VAULT_DIR 必填（缺 → 配置错误退出 1，维持现状）
2. open_vault(vault_dir) → header（锁定态，无需密码；读出 vault_uuid）
3. escrow.read_mcp_key(header.vault_uuid)：
     Ok(Some(mcp_key)) → unlock_with_mcp_key(mcp_key)
         Ok → 就绪（日志 source="keychain-escrow"）
         Err → 报错退出 1（托管条目存在但解锁失败：可能已吊销/损坏，提示在 App 设置页重新启用托管）【fail-closed】
     Ok(None)（托管不存在）→ env 兜底：
         有 COFFER_VAULT_PASSWORD → unlock(password)（日志 warning source="env-fallback"）
         无 → 配置错误退出 1（提示：启用 MCP 解锁托管，或提供 $COFFER_VAULT_PASSWORD）
     Err（读取失败：ACL/签名/长度）→ 报错退出 1（可操作消息，fail-closed，不回退 env）
4. 成功会话 → CofferStoreProvider::new(session)（复用既有构造，coffer.rs:65）
```

**取密只影响解锁来源**；解锁后的 `CofferStoreProvider` 行为不变（SecretProvider 4 方法 + 8 操作同现状）。

### 6.3 env 是否覆盖托管的裁定建议

**建议：env 不覆盖托管；env 仅在托管不存在（`Ok(None)`）时兜底。**

| 备选 | 说明 | 结论 |
| --- | --- | --- |
| **A（推荐）** 托管优先，env 仅兜底，不覆盖 | ① 目的 = 消除明文密码落盘——env 覆盖会让启用托管的用户仍暴露明文；② 兜底兼容无 App 场景（headless/CI）；③ 托管存在但不可用 → fail-closed 报错，不静默回退（防掩盖签名/ACL 问题） | **采纳** |
| B：env 覆盖托管 | 兼容旧行为，但削弱托管价值，且用户无法觉察托管已失效 | 否决 |
| C：任何托管失败都回退 env | 掩盖签名/ACL 配置问题，违背「显式错误处理」纪律 | 否决（部分采纳为 A 的 env-兜底分支） |

> 例外澄清：本建议的「fail-closed」仅针对**托管条目存在但不可用**（read Err / unlock Err）——此时回退 env 会掩盖真实问题。托管**不存在**（`Ok(None)`）是合法「未启用托管」态，env 兜底属正常兼容路径。

### 6.4 read 门裁定（lead 2026-10-07，补 §6.2 流程的可用性前提）

**裁定**：CLI **read 门** = header `mcp_wrap.available`（**意图源语义**）——仅当 `available == true`
（用户经 App 显式启用托管）才读 Keychain；`available == false`（用户显式停用托管）= 语义即「托管
不存在」→ **直接 env 兜底，不触 Keychain read**。孤儿条目边界：header 禁用 + keychain 残留 →
**env 兜底而非 fail-closed**（header = 意图源；`unlock_with_mcp_key` 对该态本就 1002，不构成凭据
风险）。已由测试 **`orphan_item_ignored_when_header_disabled`**（`core/cf-mcp/src/cli.rs` 单测）锁定
——`available=false` 必须跳过 read（mock 即便返回可解锁的 key 也不得被读）。
