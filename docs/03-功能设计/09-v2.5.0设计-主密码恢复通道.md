## 1. header recovery_wrap 存储格式

### 1.1 字段形态（决策 D-2）

Header 新增可选字段，与 McpWrap（core/cf-format/src/header.rs:151-162）同构：

```rust
#[derive(Clone, Default, Serialize, Deserialize)]
#[serde(default)]
pub struct RecoveryWrap {
    pub available: bool,
    /// b64( nonce(12B) ‖ ciphertext(DEK) )
    pub wrapped_dek_b64: String,
}
```

Header 上挂载：`#[serde(default)] pub recovery_wrap: Option<RecoveryWrap>`。

**不设独立 salt 字段**：恢复码密钥派生用 HKDF，salt 由 vault_uuid 充当（镜像 derive_mcp_key 的 derive_subkey(dek, vault_uuid, label) 模式，core/cf-crypto/src/subkeys.rs:120-132）。code 本身含 128-bit 熵，无彩虹表/预计算风险，固定 salt 成立。备选（任务文本字面形态 salt/nonce/ciphertext 三字段）被否决：多两个必填字段、校验更繁琐、且与既有 McpWrap 形态不一致。

向后兼容三面验证：
1. 旧库（无此字段）→ 反序列化为 `None`，`has_recovery_wrap()=false`，行为不变
2. 新库打开旧 header → `recovery_wrap=None`，正常解锁
3. 旧 App 打开新 header → 反序列化不开启 `deny_unknown_fields`（header.rs:9-11 设计意图），未知字段被忽略；旧 App 重写 header 会丢弃 recovery_wrap——既有接受残余，与 McpWrap 同风险、同先例

### 1.2 密钥派生与密封（决策 D-4）

- `K_recovery = HKDF-SHA256(ikm=code, salt=vault_uuid, info="cf/recovery/v1")`，经 subkeys 扩展（新增 `LABEL_RECOVERY="cf/recovery/v1"`）
- 密封：AES-256-GCM，random nonce 12B，`aad = header_aad(vault_uuid, b"wrapped_dek_recovery")`（复用 core/cf-session/src/unlock.rs:399-404 header_aad）
- `wrapped_dek_b64 = b64(nonce ‖ ct)`；`available=true`

### 1.3 validate_header 增补

header.rs validate_header 增加：recovery_wrap 存在时，`available==true` 则 wrapped_dek_b64 非空且可 base64 解码为 ≥28 字节（12B nonce + 16B tag）；`available==false` 等价 None。解码失败 → 读路径 1005 Corrupted；重置路径归 1002（与 FR-1.4 合并，见 §3.5）。

### 1.4 FORMAT_VERSION（决策 D-1，已落定）

**落定：不 bump（保持 1）**。依据：header.rs:26 注释「仅在容器结构发生不兼容变更时递增」；本字段纯可选、向后兼容；G1b/McpWrap 已建立「可选字段不 bump」先例且已过评审（FORMAT_VERSION=1 加 McpWrap 未 bump）。风险：旧 App 重写 header 丢字段（接受残余，先例一致）。

> bump 分支（FORMAT_VERSION=2 + validate_header version 分支，破坏面从「旧 App 静默丢字段」升级为「旧 App 拒绝打开」）已于 2026-10-09 落定时作废，不作实现。

## 2. 恢复码规范

### 2.1 熵与生成

- 熵：128-bit CSPRNG（OsRng 16 字节）
- `generate_recovery_code()`：**只返回 code（内存），不触发任何落盘**。用户放弃时旧 wrap 不受影响（安全顺序，见 §2.4）

### 2.2 编码（决策 D-3，已落定）

| 方案 | 长度 | 校验 | 依赖 | 优点 | 缺点 |
|------|------|:---:|------|------|------|
| BIP39-12 | 12 词 | 4-bit 校验和 | 新增 bip39 crate（纯 Rust、无传递依赖） | 抄写/朗读友好、校验和可纠错 | 英语词表、词长、新增依赖 |
| base32(RFC4648) | 26 字符 | 无 | 零新增（cf-totp 已有 decode，需补 encode 纯函数 ~30 行） | 紧凑、零依赖 | 无校验、抄错即整体失败且与格式错误不可区分 |

**落定：BIP39-12**。依据：恢复码核心场景是「抄写一次、长期保存」，校验和显著降低抄写事故；FR-17.2 要求错误码与格式错误不可区分——无校验方案下抄错一个字符即整个恢复码作废且无法定位。base32-26 备选（依赖最小化优先）已作废。

### 2.3 存储

- **明文（code）永不落盘**：磁盘上仅 §1 的 wrap 密文
- 内存卫生：Rust 侧生成/接收 code 用 zeroizing 缓冲；FFI 传 String 是残余面（Swift 侧以会话局部 `[UInt8]` 持有，流程结束即置空）。Swift 无法保证零化——FR-17.2 只承诺「明文不落盘」，内存零化为 best-effort，如实记录（不声称强零化）
- **Keychain 侧：无恢复码存储**。区别于 k_bio（存 Keychain + Secure Enclave + LAContext 生物验证，unlock_bio.rs BIOMETRIC_PROVIDER_TOUCH_ID）：恢复码是**用户持有**的秘密，存 Keychain 等于把重置钥匙与设备绑定，拿到设备即能重置——反目的。故恢复码无 Keychain 侧信息

### 2.4 生成 / 重生成语义（FR-17.2：仅展示一次、重生成旧码失效）

1. `generate_recovery_code()` → 返回新 code（无落盘，旧 wrap 不变）
2. Swift 一次性展示 code（大号字体 + 复制按钮 + 剪贴板 30s 自动清空）
3. 用户确认「我已抄写保存」→ 输入主密码（D-6：先验证身份再写 header）
4. `enable_recovery_code(password, code)` → recover_dek → K_recovery=derive → seal → 原子写 header（覆盖旧 recovery_wrap 槽位）
5. 新 code 生效即旧 code 失效（同一槽位被覆盖，不可回滚）
6. 任一步取消 → header 未写 → 旧 wrap 保持有效，新 code 作废

重生成 = 同流程，UI 前置确认对话框「旧恢复码将立即失效」。

## 3. Rust API 契约

### 3.1 关键依据：DEK 获取（决策 D-7）

任务文本「bio 解锁会话已持 DEK」与 v2.4.0 现状**不符**：retention 层（retain_dek_with_bio / dek_retained / unlock_with_dek）已裁除（9fde5c4），session 解锁后不持 DEK。

设计：reset-with-bio 复用 `recover_dek_bio(k_bio)`（unlock_bio.rs:212-239，k_bio → 打开 wrapped_dek_bio）；reset-with-recovery 新增 `recover_dek_recovery(code)`。**不重建 DEK retention**。与 D-6「enable 传 password/凭证、不传 DEK」一致。

### 3.2 公共 helper 重构（先于一切 reset 实现）

从 change_password_impl（core/cf-session/src/change_password.rs:54-130）抽取：

```rust
/// ① zxcvbn 门禁(1010) → ② new_kdf 校验(5002) → ③ 新 salt + derive_key
/// → ④ 重包 wrapped_dek + verifier → ⑤ 保留 bio/mcp/recovery wraps（不动）
/// → ⑥ write_header 原子写
pub(crate) fn repack_dek_with_new_password(
    header: &mut Header,
    dek: [u8; 32],
    new_password: &Password,
    new_kdf: Option<KdfParams>, // None → default_kdf_params
) -> CfResult<()>
```

change_password_impl = recover_dek(old_password) + repack；reset 三兄弟共享之（change_password 的 ①④⑤⑥⑦ 步即 repack 主体）。

### 3.3 新增 API（VaultSession 层；facade 见 §3.6）

```rust
// recovery.rs（新文件，impl 层）
pub fn has_recovery_wrap(&self) -> bool
pub fn generate_recovery_code(&self) -> CfResult<String>                              // 无落盘
pub fn enable_recovery_code(&self, password: &Password, code: &str) -> CfResult<()>  // write_guard（解锁态）
pub fn reset_password_with_recovery_code(&self, new_password: &Password, code: &str) -> CfResult<()> // license_guard（锁定态）
// unlock_bio.rs 增
pub fn reset_password_with_bio(&self, new_password: &Password, k_bio: &[u8]) -> CfResult<()>         // license_guard
```

- reset 两函数从**锁定态**执行：仅 license_guard（§3.4），**不** finish_unlock（重置后保持锁定，由 Swift 决定是否用新密码解锁，D-9）
- enable 从解锁态执行：write_guard（原样）
- 与 changePassword 关系：changePassword 需旧密码；reset 不需要——这正是恢复通道的价值。二者共享 repack helper，语义正交

### 3.4 门禁拆分（决策 D-6）

write_guard（core/cf-session/src/vault.rs:1145-1157）= unlocked(1001) + license(6002/6003)。拆出：

```rust
fn license_guard(&self) -> CfResult<()>          // 仅 6002/6003
fn write_guard(&self) -> CfResult<()> { self.ensure_unlocked()?; self.license_guard() }
```

reset 用 license_guard（锁定态可写 header）；enable/change 仍 write_guard。

### 3.5 错误码（决策 D-5，已落定）

| 场景 | 码 | 说明 |
|------|----|------|
| 恢复码错误 / wrap 损坏 / header 损坏 | 1002 | 与 FR-1.4 / FR-17.2 不可区分纪律统一（三态合并先例） |
| recovery_wrap 缺失（defensive；UI 有 has_recovery_wrap 门） | **4003 RecoveryUnavailable** | 镜像 4001 BiometricUnavailable 先例（D-8：bio 不可用 → 4001，unlock_bio.rs） |
| 新密码弱 | 1010 | repack 内 zxcvbn 门禁 |
| license 阻断 | 6002 / 6003 | license_guard |

4003 已落定加入 CfError（error.rs 无 `_` 兜底分支——新增变体编译器强制在 code() 补码）+ FFI 映射 + docs/01-需求与架构/03-详细设计.md §12 表登记（2026-10-09，v2.5 修订行）。错误码属公共契约，新增为**可逆增量**（不破坏既有码）。

### 3.6 backoff 与审计（facade 层，vault.rs）

- **reset-with-recovery**：try_acquire（共享密码 oracle 计数器）+ 失败 on_failure——对恢复码在线爆破的纵深防御（128-bit 熵下攻击不可行，防御成本≈0）；副作用：密码爆破触发 backoff 期间恢复码也被临时封锁，可接受（且 Touch ID 仍豁免，正当用户总有出路）
- **reset-with-bio**：**免** backoff（k_bio 非密码 oracle，镜像 unlock_with_biometric 完全豁免）；不 acquire
- **审计**（core/cf-store/src/repo/audit.rs 新事件）：
  - `PasswordResetByBio`（"password_reset_bio"）
  - `PasswordResetByRecovery`（"password_reset_recovery"）
  - `RecoveryCodeEnabled`（"recovery_code_enabled"，detail 区分 initial/regenerated）
  - 写路径：reset 从锁定态写审计 → `AuditRepo::new(conn)` 仅需 Connection（audit_local 表为明文、无需 subkeys，audit.rs:99,107）→ reset 内开**瞬态 Connection** 追加后关闭（镜像 unlock.rs:448 cleanup_orphans_best_effort：`Connection::open(vault_dir.join(DB_FILE))`）
  - `as_str`/`parse` + 往返测试（audit.rs:232-241 穷举断言）同步更新
- `has_recovery_wrap` 免审计

### 3.7 零网络复核（C-01 / NFR-SEC-07）

recovery/reset 全链路：CSPRNG、HKDF、AEAD、header 原子写、本机 Keychain（bio 路径 LAContext）——**无任何网络 API**。设计不引入网络路径，零网络硬承诺保持。

### 5.3 与 FR-17.1 关系
