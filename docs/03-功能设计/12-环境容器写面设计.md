# 36 · v2.8.0 设计——环境容器写面（CLI `set-env` + App 编辑保护）

## 0. 背景与目标

环境容器（Environment）是 v2.x 挂起模型（U-4）的临时载体：`SecureNote` 条目 + 保留标签
`coffer:environment`（`core/cf-mcp/src/provider/coffer.rs:63`，`ENV_TAG`），字段 = `NAME`/`VALUE`
对，`resolve_env` 按标题精确匹配。MCP 侧 `inject_environment`（coffer.rs:402）把容器**全部字段名**
当环境变量名注入子进程 env。

现状写面极窄：CLI 只有 `mcp`（读）+ `set-password`（写）；`set-password` **拒绝写环境容器**
（`set_password.rs` `EnvContainer` 分支）。App 走通用条目编辑（ItemEditView）——最宽写面但
**无环境容器意识**：标签是自由文本，改条目可能误删 `coffer:environment` 标签 → 静默破坏容器
契约（容器从 MCP env 清单 / `set-env --scope` 解析中消失）。

目标（三项 v2.8.0 裁定已锁）：
1. **CLI 新写子命令 `coffer set-env`**：在环境容器内写 `NAME`/`VALUE` 字段对；
2. **App 环境容器友好编辑**：评估并落地最小改动（保护标签 + 识别/校验，不做大 UI）；
3. **MCP 保持只读**（无任何写工具，不实现）。

本文档产出 = 设计决策 + 改动清单（含并行/串行分组）+ 待 lead 确认的不可逆决策。**不写实现代码**。

## 2. 范围

### 2.1 In（本版）

- **CLI 通道**：`coffer set-env` 写子命令（`coffer-store` feature 门控，镜像 `set-password` 纪律）。
- **App 通道**：环境容器标签保护 + 识别 + NAME 校验（最小改动，见 §5）。
- 两通道共享既有 Rust 写内核（item update + FR-2.9 历史 append），**无 schema / 无 FORMAT_VERSION
  变更**；环境容器映射仍是 U-4 临时约定（coffer.rs 模块文档明示「可逆、可整体替换」）。

### 2.2 Out（明确不做）

- MCP 写工具（R2）；多级/嵌套作用域（R1 扁平）；App 侧全新「环境容器」专用编辑器或侧栏分组
  （§5 评估为成本高、非必需，顺延）；`NAME` 多行值（POSIX env 惯例单行；见 §4.4）；`set-env`
  与 `set-password` 之外的任何新 CLI 写面。

## 3. 安全与纪律（两通道共用）

- **VALUE 是秘密载荷**：环境容器值的典型用途 = API key（MCP `inject_environment` 直接注入子进程
  env）。故 set-env 沿用 `set-password` 的「值不落 argv」纪律——敏感值走 stdin 隐藏输入
  （§4.4 两档值来源）。
- **值不进日志 / 审计 / stdout 回显**：stderr 诊断、stdout 成功消息只含 NAME 与容器名，**不含 VALUE
  明文**（载荷纪律，docs/03-功能设计/06-MCP设计.md §3.5-4 同界）。
- **一次 update_item 原子写**：多条 NAME/VALUE + `--unset` 同一次 `update_item` 整换重建 →
  FR-2.9 自动 append 一条历史（可回滚），失败不落库。
- **失败 fail-closed**：解锁失败 / 目标未命中 / NAME 非法 → 不写库、明确报错（CLI 退出码映射
  对齐 docs/03-功能设计/10-v2.5.0设计-密码更新写面.md §5.2 一次性写命令映射）。
- **明文临时缓冲用后 zeroize**：draft 内 VALUE 副本成功/失败分支一致清零（镜像 `set_password.rs`
  `apply_update` 的 M-3 纪律）。

## 4. CLI 通道——`coffer set-env`

### 4.1 命令签名（推荐形态，§7 待 lead 确认）

```
coffer set-env --scope <owner> NAME=VALUE [NAME=VALUE ...] [--id <UUID>]
coffer set-env --scope <owner> NAME [--id <UUID>]              # 该 NAME 的值从 stdin 读（TTY 隐藏）
coffer set-env --scope <owner> --unset NAME [NAME ...] [--id <UUID>]
```

- **`--scope <owner>`**（必填）：owner = 容器标题（R1 扁平）。与 `--id` 互斥。
- **`--id <UUID>`**：UUID 兜底定位（名称歧义/改名场景），镜像 `set-password --id` 纪律。
- **`NAME=VALUE`**：按**第一个** `=` 分割（VALUE 可含 `=`）；`NAME=` 空值 = 显式置空串（合法，
  env 空值有语义，与 set-password 空密码**不同**——VALUE 空不是错误）。**至多一个裸 `NAME`**
  （stdin 值来源歧义约束，见 §4.4）。
- **`--unset NAME [NAME ...]`**：删除字段（清空/删除语义显式化，见 §4.3）。与 `NAME=VALUE` 对
  **互斥**（本版每次调用一个意图，简化契约）。
- 未知 flag / 缺值 / 多余位置参数 / `--scope`+`--id` 并存 / `--unset`+对并存 → 用法错误退出 4。

### 4.2 目标定位（owner 解析）

镜像 `set_password::resolve_by_name` 的严格语义，**不**复用 `provider::resolve_env`（后者首个命中、
无歧义检测，是 MCP 只读语义）：

| 情况 | 行为 | 退出码 |
| --- | --- | --- |
| 命中恰 1 个环境容器（Active + SecureNote + `coffer:environment`） | 目标 = 该条目 | — |
| 0 命中且**无任何条目**同名 | **自动建容器**（SecureNote + ENV_TAG，复用 `create_environment` 语义） | 0（首写即建） |
| 0 命中但有**非环境容器**条目同名 | 报错「标题已存在但不是环境容器」，**不自动建**（避免标题撞车混淆） | 2 |
| >1 命中 | 歧义报错，提示 `--id` | 2 |
| `--id` 命中但非环境容器 | 报错（`EnvContainer` 反向：目标须是容器） | 2 |
| `--id` 未命中 | ItemNotFound | 2 |

**自动建容器语义（§7 待 lead 确认）**：owner 不存在 = 首次写入即初始化。理由：空容器无害且可删
（App 可见）、`create_environment` 重复拒绝天然充当并发守卫、语义贴合「给某 owner 写变量」。
反例已拒：同名非容器条目不得覆盖/撞车（必须显式报错）。

> **并发自愈（H-1，dev-reviewer 闭环）**：`auto_create_environment` 双守卫——① 查重挡顺序重复；
> ② 建后 `prune_race` 按 uuid 字典序收敛，**赢家只硬删空容器**；输家容器已有字段（已提交写入）
> 跳过删除、留双容器（可恢复歧义，`--id` 可救，**无数据丢失**）。残余仅两类且均不丢数据：
> 输家已提交写入窄窗口（双容器）/ 双 SIGKILL 毫秒窗口（双空容器）。彻底修（会话层原子
> create-if-absent）后置。**busy_timeout**：vault 连接未设，并发写以 `database is locked` 有界
> 重试（10×20ms）缓解；`is_busy` 依赖错误文案，若未来加 busy_timeout 可整体移除重试层（LOW）。
>
> **Trashed/Archived 同名注记（L-3）**：`resolve_by_scope` 只按 Active 过滤——已删除/归档的同名
> 条目不阻止自动建容器（0 命中 → 直接建）。该废弃条目日后恢复即出现同名歧义，属边缘接受
> 残余（可用 `--id` 定位），文档明示。

### 4.3 写入语义（整换重建，一次 update_item）

- 模板 = `set_password::apply_username_field` 同款：遍历 draft 字段按 `name == NAME` 命中 →
  更新现值；未命中 → append `FieldDraft{ name: NAME, value, field_type: Text, designation: None,
  position: max+1 }`。
- **字段形态固定**：`FieldType::Text` + `designation: None`——与 MCP `username_value`「纯 Text
  不参与伴随注入」、`secret_value`「Text 不参与取密」两处只读语义对齐（写侧不引入 designation，
  避免破坏「环境容器不是 secret/username」的既有边界）。命中既有字段时**不改其 field_type /
  designation**（用户手编字段不静默重写）。
- **`--unset`**：按 name 删除字段（`draft.fields.retain`）。删除缺失的 NAME = 幂等成功（与
  `revoke_secret` 幂等纪律同）。
- 重建经 `draft_from_details`（`pub(crate)`，set-password 同源），TOTP 恒 `None`（`update_item`
  默认 Keep 不丢既有 TOTP）。

### 4.4 值来源与校验

- **两档值来源（§7 待 lead 确认）**：
  - 内联 `NAME=VALUE`：方便，供**非敏感**值（`LOG_LEVEL=debug`）与脚本使用——显式用户选择，
    值仍在 argv/ps 可见（用户知情的逃生口，不设静默）；
  - 裸 `NAME`：该值走 stdin（TTY 下 `rpassword::read_password` 隐藏输入，复用 set-password 读密
    机制；管道模式读一行、剥离结尾换行）——供敏感值（API key）使用。**至多一个裸 NAME**，
    保证 stdin 值归属无歧义。
- **NAME 校验**：复用 `is_valid_env_name`（`core/cf-mcp/src/provider/mod.rs:107`，`pub(crate)`，
  同 crate 直接可用）——`[A-Za-z_][A-Za-z0-9_]*`。非法 → 用法错误退出 4、整命令不写库。
- **VALUE 校验**：拒 NUL（用法错误 4）；空串合法；**多行不支持**（POSIX env 单行惯例；stdin
  档已按行读）。
- 校验顺序（镜像 `set-password` L-3）：**用法校验最先**（无需解锁即可判定，先验用户输入、再动
  钥匙链），再取密解锁，再定位，再写。

### 4.5 退出码（一次性写命令映射，镜像 docs/03-功能设计/10-v2.5.0设计-密码更新写面.md §5.2 / `set_password.rs::exit_codes`）

| 码 | 语义 | 对应分支 |
| --- | --- | --- |
| 0 | 成功（写入/更新/删除 + 历史 append；含首写自动建容器） | — |
| 1 | 解锁失败 fail-closed（escrow 与 env 均无 / escrow 存在但解锁失败**不回落 env** / vault 定位失败）；会话层存储错误；**stdin 读取失败**（裸 NAME 取值 IO 错误，dev-reviewer L-4 补注） | `unlock_vault` 复用 |
| 2 | 目标未命中 / 歧义 / 目标非环境容器（含「标题存在但非容器」） | `TargetNotFound` / `Ambiguous` / `NotEnvContainer` |
| 3 | **保留槽位，不适用**（set-password 3 = 强度不足；set-env 无强度门禁，保留该码位维持跨写命令映射对齐，文档明示） | — |
| 4 | 参数/用法错误（未知 flag / 缺 `--scope` / `--id` 格式错 / NAME 非法 / VALUE 含 NUL / `--unset` 与对并存 / 多余位置参数） | — |

> 本版不新增错误码；一次性写命令码位（0/1/2/4 + 3 保留）与 docs/03-功能设计/06-MCP设计.md §5.3 的 MCP 服务器进程码
> （0/1/2/3）**按子命令上下文区分**（docs/03-功能设计/06-MCP设计.md r0.14 补注纪律）。

### 4.6 解锁与接线

- 取密链完全复用 `cli::unlock_vault`（escrow → env 兜底 → fail-closed 1），与 `set-password`
  同构（D-4 纪律，docs/03-功能设计/08-v2.2.0设计-MCP解锁托管.md §6.2 / docs/04-测试与验收/10-v2.2.0验收判据骨架.md §1.3 六条已核销先例）。
- `cli.rs::run` 分派：`#[cfg(feature = "coffer-store")]` 块内新增 `set-env` → `set_env::run(&args[1..])`；
  `lib.rs` 同 feature 门控注册 `pub mod set_env`。
- **零新增依赖**：rpassword / zeroize / uuid / cf_domain / cf_session / cf-audit 均已在
  `coffer-store` feature 依赖树（set-password 同款），依赖方向 cf-mcp → 下（docs/03-功能设计/06-MCP设计.md §2.2 只下不上）
  不新增边。

### 4.7 输出

- stdout 只写成功消息（本命令非协议会话），如：`已写入环境容器 <owner>（NAME1, NAME2）· 旧版本
  可在 App 历史中回滚` / `已从环境容器 <owner> 移除（NAME1）…`。**不含 VALUE 明文**。
- 诊断/错误经 `Logger` 走 stderr（`Logger::stderr()`，同 set-password）。

## 5. App 通道——环境容器编辑保护（最小改动方案）

### 5.1 现状覆盖度评估（已读 `macos/Coffer/`）

- **写路径已全覆盖**：`ItemEditView`（新建/编辑，含 tags 逗号文本 + 通用字段行）+ `ItemStore`
  `createItem`/`updateItem`（FFI）已通；用户今天即可手工建容器（建 SecureNote + 加标签）并编辑
  NAME/VALUE 字段。**无需新增写内核**。
- **三个缺口**：
  1. **标签即身份，无保护**：编辑容器时 `coffer:environment` 出现在 tagsText 自由文本里，误删即
     静默失格（容器从 MCP env 清单 / `set-env --scope` 解析消失）——数据完整性风险；
  2. **无识别**：`FfiItemSummary` 无 tags 字段（cf_ffi.swift:5113）、`FfiItemFilter` 无标签过滤 →
     App 列表层无法分辨容器，只能逐条查详情（N+1）；
  3. **无 NAME 校验**：App 可写非法 NAME（如含 `-`），MCP `inject_environment` 防御性跳过 →
     App 所见与注入行为静默分歧。

### 5.2 推荐方案（最小改动，§7 待 lead 确认）

**采纳「智能通用编辑」，不新建专用编辑器、不做侧栏分组**（本版）：

| 改动 | 文件 | 性质 |
| --- | --- | --- |
| 容器识别辅助 | `macos/Coffer/Support/EnvironmentContainer.swift`（新） | 新增：`isEnvContainer(details.tags)` + `isValidEnvName(_:)`（Swift 本地复刻 `[A-Za-z_][A-Za-z0-9_]*`，注释链 provider/mod.rs:107 同源） |
| 标签保护 | `macos/Coffer/Views/ItemEditView.swift` | 修改：编辑容器时 `coffer:environment` 从 tagsText 剔除，渲染为**锁定徽章**（不可编辑/不可删），保存时恒回写该标签 |
| 识别展示 | `macos/Coffer/Views/ItemDetailView.swift` | 修改：容器条目详情页头部加「环境容器」徽章（识别友好，成本≈0） |
| NAME 校验 | `macos/Coffer/Views/ItemEditView.swift` | 修改：编辑容器时对字段行 name 做 `isValidEnvName` 实时告警（红字「不是合法环境变量名」，不阻断保存——防御在注入侧，App 校验是提前告知） |

- **检测入口**：`FfiItemDetails.tags`（FFI 明文 `[String]`，cf_ffi.swift:4695）`contains
  "coffer:environment"`；ItemEditView 编辑模式与 ItemDetailView 均已持有 details，检测零额外调用。
- **不做**：侧栏「环境容器」分组（需 FFI 标签过滤或逐条查详情 N+1，成本高收益低，顺延）；
  专用键值对编辑器（通用编辑 + 标签锁已覆盖核心需求）。
- **校验实现裁决**：Swift 本地复刻 `is_valid_env_name` 而非 FFI 导出——该规则冻结且 ~6 行；
  FFI 导出需把 `pub(crate)` 提升 + cf-ffi 引 cf-mcp 的可见性/依赖面改动（cf-mcp → 下不成立），
  得不偿失；且即便 App 放行非法名，注入侧防御性跳过兜底，最坏是用户困惑非破坏。**漂移风险
  低**（规则冻结 + 注入侧兜底）。

## 7. 不可逆决策清单（待 lead 确认，确认前不落定实现）

> 存储格式层面：set-env/App 均**不改变** U-4 临时映射（SecureNote + 标签 + Text 字段），本就
> 可逆。下列为**行为契约 / API 签名**级别的不可逆项（一旦发布，脚本与用户习惯依赖之）。

| # | 决策点 | 候选 | 本设计推荐 | 理由/风险 |
| --- | --- | --- | --- | --- |
| D-36.1 | `--scope <owner>` 定位形态 | A. `--scope` flag（本推荐）；B. 位置参数 `<owner>` | A | B 下 owner 与 NAME=VALUE 需判别（标题可含 `=`）；A 无歧义且贴合 lead 拟形态 |
| D-36.2 | **自动建容器** | A. owner 缺失自动建（本推荐）；B. 缺省失败 + `--create`；C. 缺省失败 + 显式建容器命令 | A | 首次写入即初始化最顺手；空容器可删；同名非容器已设防。反例：手误 scope 产生垃圾容器（App 可见可删，可接受） |
| D-36.3 | **值来源两档** | A. 内联 + 裸 NAME stdin（本推荐）；B. 全内联；C. 全 stdin | A | 内联 = 非敏感值逃生口（显式知情）；裸 NAME = 敏感值隐藏输入。B 泄露 secret 至 ps/历史（违背 §3 纪律）；C 牺牲脚本便利 |
| D-36.4 | **`--unset` 同命令** | A. 同命令 `--unset`（本推荐）；B. 独立 `coffer unset-env`；C. 本版不做删除 | A | 一个写内核/一次 update_item/一条历史；与对互斥保持意图单一。C 会让写面不完整 |
| D-36.5 | **退出码 3 保留** | A. 保留槽位不适用（本推荐）；B. 复用 3 作他义 | A | 维持跨写命令映射对齐（set-password 3=强度）；脚本按类别判断不混淆 |
| D-36.6 | **App 校验实现** | A. Swift 本地复刻 `is_valid_env_name`（本推荐）；B. FFI 导出 | A | 规则冻结 ~6 行；B 需提 `pub(crate)` + cf-ffi 引 cf-mcp 依赖面改动，破坏 cf-mcp → 下 |
| D-36.7 | **App 编辑形态** | A. 智能通用编辑 + 标签锁（本推荐）；B. 专用键值对编辑器 + 侧栏分组 | A | 写内核已通、缺的是保护非编辑器；B 成本高（FFI 标签过滤/N+1）收益低，顺延 |
| D-36.8 | **App 是否自动补标签** | A. 编辑容器标签恒回写（本推荐）；B. 仅警告允许移除 | A | B 允许一次手误静默失格；A 锁死契约 |

> **lead 裁定（2026-10-10）**：D-36.1~D-36.8 **全部采纳推荐项 A**。8 项均不违反已裁定
> 纪律（R1 扁平 owner / R2 MCP 只读 / 值不落 argv / 依赖方向只下不上），属 API 契约级
> 决策，由 lead 依设计推荐定谳。**特别提示 D-36.2（自动建容器）**：手误 scope 会产生
> 空容器（App 可见可删），为接受残余；同名非容器条目拒绝不覆盖（防撞车）为硬约束。
