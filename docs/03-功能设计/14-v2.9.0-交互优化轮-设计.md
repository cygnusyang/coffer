### 2. P2-A 首启引导合并（FW-01）

#### 2.1 现状与问题
- `RootView.swift:19-38` 两个独立 sheet：bio 引导（`pendingBioOffer`）+ 恢复码引导（`pendingRecoveryOffer && !pendingBioOffer`），均 `interactiveDismissDisabled`，bio 先、恢复码后，同一会话连续两弹。
- 两引导均为**可选**（都有「以后再说」跳过），`AppModel.createVault`（`AppModel.swift:532-536`）成功时置位。

#### 2.2 设计（合并为一个「首启引导」向导）
- **触发**：`phase == .unlocked && (pendingBioOffer || pendingRecoveryOffer)` 时呈现**单个 sheet 向导**，替代现有两个 sheet。`interactiveDismissDisabled` 保留（结构型引导）。
- **步骤模型**（最多两步，按置位情况裁剪）：
  - Step 1「启用 Touch ID 解锁？」：仅 `pendingBioOffer` 时出现。内容沿用 `VaultBioEnableOfferView` 的现有结构（图标 + 说明 + 主密码确认行 + 启用/跳过）。
  - Step 2「生成恢复码？」：仅 `pendingRecoveryOffer` 时出现。内容沿用 `RecoveryCodeOfferSheet` 的现有结构（说明 + 「生成恢复码」进入既有 RecoveryCodeSetupSheet 流程 / 跳过）。
  - 只有一步时向导单步直出，无步骤指示器。
- **步骤流转（状态机）**：

```
[未置位 或 已处理] ─→ 不出现在任何引导
[bio 置位] ──Step1─┬─ 启用成功/跳过 → 清 pendingBioOffer → 进 Step2（若 pendingRecoveryOffer）
                   │                    └→（无恢复码置位）→ 关闭向导
[recovery 置位] ──Step2─┬─ 生成成功（hasRecoveryWrap）→ 清 pendingRecoveryOffer → 关闭向导
                        └─ 跳过 → 清 pendingRecoveryOffer → 关闭向导
```

- **步骤级可跳过保留**（硬约束「勿砍可跳过」）：Step1「以后再说（可在安全设置中开启）」、Step2「以后再说（可在安全设置中开启）」，文案逐字保留现有。
- **实现建议**：AppModel 的 `pendingBioOffer` / `pendingRecoveryOffer` 作为步骤级状态**原样保留**（最小改动纪律），向导容器根据两者派生单一 `showOnboarding` 绑定（`pendingBioOffer || pendingRecoveryOffer`），步骤内部完成后清各自旗标；两旗标均清即自动收口。恢复码生成流程仍以**嵌套 sheet**（RecoveryCodeSetupSheet，现状）呈现，返回后 `hasRecoveryWrap` 已置位则一并收口。
- **不破坏既有确认点**：Step1 的主密码确认（D-6）不动；Step2 进入的 RecoveryCodeSetupSheet 完整四步不动（P6 会在其内部加验证步，见 P6）。

#### 2.3 线框（合并向导，两步场景）

#### 2.5 设置页首次高亮兜底（硬约束「保留设置页首次高亮兜底」）
- **兜底含义**：两步骤均被跳过时，用户仍须能在设置页找到对应入口。设计：为设置页「安全」节的 Touch ID 行与恢复码区加**一次性首次高亮**（accent 圆点 + 「未完成设置」footnote），仅当对应引导步骤被跳过且功能未启用时出现；启用对应功能后清除。
- 实现建议：UserDefaults 记录 `bio_offer_skipped` / `recovery_offer_skipped`（跳过 Step1/Step2 时置位；启用对应功能即清）。
- **已定案（lead 裁定⑤）**：首启引导的「设置页首次高亮兜底」为正式纳入项，非可选增强——跳过引导后设置页「安全」节必须提供一次性高亮入口，直至用户完成对应功能设置。实现优先级与 P2-A 向导本体同级。

### 3. P2-B 设置窗口锁定态关闭（FW-02/REV-03）

#### 3.1 现状与问题
- 设置独立窗口（`CofferApp.swift:72-75`，Window id "settings"）不随 phase 拆除；`AppModel.lock()`（`AppModel.swift:601-618`）不置 session=nil，锁定态设置窗口内 `guard let session` 仍通过 → 改密 / Touch ID enable / MCP enable / 审计日志均吃 1001（REV-03）。
- `DataCommands` 设置项 `.disabled(phase != .unlocked)`（`CofferApp.swift:112-114`）与「窗口常驻」自我矛盾（FW-02）。

#### 3.2 设计（锁定时关闭设置窗口）
- **主案（lead 裁定）**：phase 离开 `.unlocked`（→ `.locked` / `.noVault`）时关闭设置窗口。设置窗口生命周期与主窗口 RootView 随 phase 拆树同语义——设置是「解锁态表面」，锁定即拆。
- **触发实现建议（两候选，dev-team 择一）**：
  1. 设置窗口 scene 内容包一层 host 视图，`onChange(of: model.phase)` 中 phase != .unlocked → `@Environment(\.dismissWindow) dismissWindow(id: "settings")`（自包含，推荐）；
  2. 若自窗口内 dismiss 不可靠（SwiftUI 对正在拆树的 scene 调 dismiss 的已知边界），改由**主窗口 scene**（RootView）`onChange(of: model.phase)` → `dismissWindow(id: "settings")`（跨 scene dismiss 另一窗口，语义合法）。
- **菜单纪律修正**：保留「设置… / ⌘,」的 `.disabled(phase != .unlocked)`——锁定态设置窗口已关闭 + 菜单禁用，二者**一致**，自相矛盾解除（现状锁定态本就无法经菜单/⌘, 打开设置，非回归）。
- **过时注释修复**：`ChangePasswordView.swift:121`「设置页仅在解锁态可达」在本案下**恢复为真**，注释保留并注明「v2.9.0 锁定态关闭设置窗口后此不变量成立」。
- **联动**：锁定态若由菜单栏「锁定全部」/ ⌘L（P7）触发，设置窗口同时关闭（同走 phase 变更）。

#### 3.3 回退条件（必须标注，lead 指示）
> 若 dev-team 确认 Window scene 关闭 API **不可行**（无法在 phase 变更时可靠关窗），降级为**行级禁用**：
> - 设置菜单恢复为锁定态可用（去掉 `.disabled(phase != .unlocked)`）；
> - 设置窗口内容按 phase 渲染：锁定态在窗口顶部显示锁定提示条，并对 **5 个 session 依赖行** `.disabled(phase != .unlocked)`：修改主密码 / Touch ID 启用·重启用 / MCP 启用（McpSettingsSection）/ 审计日志 / 从备份恢复；
> - 此降级即「维护第二份 session 依赖清单」，仅在主案不可行时启用，须向 lead 报备。

#### 3.4 线框（P2-B 状态序列）

```
解锁态                          自动锁定 / ⌘L / 菜单栏锁定
┌──────────┐  打开   ┌──────────────┐   phase→.locked   ┌──────────┐
│ 主窗口     │ ──────▶ │ 设置窗口(解锁) │ ─────────────────▶│（关闭）    │
│ MainView  │         │ 9 节全可用     │                    └──────────┘

#### 3.5 状态与负路径（P2-B）
| 状态 | 处理 |
|---|---|
| 设置窗口开着 → 自动锁定 | 窗口关闭；session 依赖操作不可能再触发 1001 |
| 设置窗口开着 → 手动锁定（⌘L / 工具栏锁定 / 菜单栏锁定全部） | 同上 |

| noVault 态（无库） | 无设置窗口（从未打开 / 已关闭） |

### 2. 设计（共享导入向导壳）

- **壳职责**（`ImportWizardShell`，消除 ~1200 行重复的脚手架部分）：
  - 头部：`title` + 「关闭」按钮（导入执行中禁用，`.keyboardShortcut(.cancelAction)`）；
  - 状态机框架：`pick → report → importing → done`（OPVault 扩展为 `pickDirectory → password → precheck → importing → done`）；
  - 选文件步骨架（图标 + `pickTitle` + `pickDescription` + `pickButtonLabel` + NSOpenPanel 配置）；
  - 导入进度步骨架（ProgressView + `importingCopy` 逐字）；
  - 结果页骨架（checkmark.circle + `doneHeadline` + `doneFooter`（可空）+ 路径行（lineLimit 2 / truncationMode .middle）+ 「完成」按钮 `.defaultAction`）；
  - 预检失败 alert（`precheckErrorAlertTitle`）；导入失败恢复策略（`failureRecovery`）+ 失败追加文案（`failureSuffix`，逐字）；
  - 共享子件：`statLabel`、`failureList`、`pathLine`、`ffiErrorAlert` 接线。
- **格式配置**（每格式提供一个 `ImportFormatConfig`，含全部下述字段）——**报告正文仍按格式私有**（以 builder/内容闭包注入壳），壳收敛的是脚手架而非报告内部结构（报告差异天然巨大，强行统一反会抹平语义）。
- **事务语义参数化**（lead 硬约束落点）：`transactionSemantics: allOrNothing | perItem` 驱动 importing/失败文案的**默认值**，但每格式可提供**逐字覆盖**（CSV 与 OPVault 同为 all-or-nothing 但 importing 文案不同，见 §3 对照表）——一律以各格式逐字覆盖值为准。

### 2. P5-A 剪贴板单点化（CO-01）

#### 2.1 现状
- `ClipboardManager`（`Platform/Clipboard.swift`）统一档位 + changeCount 守卫 + clearOnLock。
- `RecoveryCodeSetupSheet.copyCode()`（`RecoveryCodeSetupSheet.swift:238-258`）**手写** NSPasteboard 写入 + DispatchWorkItem 固定 30s + 自持 changeCount——守卫逻辑与 ClipboardManager 重复，有漂移风险。

#### 2.2 设计
- **新增 API**（ClipboardManager）：
  - `func copyWithAutoClear(_ value: String)` —— 现状，跟随用户档位（不变）。
  - `func copyWithAutoClear(_ value: String, clearSecs: TimeInterval)` —— **新**：本次复制以 `clearSecs` 覆盖用户档位调度清除；changeCount 守卫与 `schedulePendingClear` 同纪律（清除任务闭包内**局部捕获**写入时 changeCount，不依赖单例槽位）；`clearOnLock` 覆盖（经单例槽位记录本次写入，锁定时若仍为本内容即清）。
  - 参数纪律：`clearSecs == 0` 视作「本次不清除定时路径」但保留锁定兜底（与档位 0 同语义，勿 asyncAfter(0)）。
- **RecoveryCodeSetupSheet.copyCode() 重写**：删除手写 NSPasteboard 代码与 `clipboardClearItem` 状态，改为 `ClipboardManager.shared.copyWithAutoClear(code, clearSecs: Self.clipboardClearSecs)`（`Self.clipboardClearSecs = 30`，常量保留并注释「FR-17.2 一次性纪律，不受用户档位影响」）。
- **副作用（安全增强）**：恢复码复制现纳入 `clearOnLock` 覆盖——锁定时刻剪贴板仍是恢复码则立即清空（现状手写路径不覆盖锁定，仅等 30s 到点）。与 FR-17.2 一次性纪律一致，属净改进，标注于判据。
- **多次复制 / 视图消失后到点执行**：由 ClipboardManager 既有 DispatchQueue 持有语义保证（视图消失仍到点执行 + changeCount 守卫不误清），与现状手写行为一致。

#### 2.3 状态与负路径（P5-A）
| 状态 | 处理 |
|---|---|
| 用户复制后 30s 内未动剪贴板 | 到点清空（changeCount 未变） |
| 30s 内用户复制了别的内容 | 绝不误清（changeCount 守卫） |
| 复制后锁定 | `clearOnLock` 立即清（若仍为本内容）——**新增覆盖** |
| 多次点击复制 | 取消旧未到点任务，只保留最近一次 |
| 用户档位 = 从不 | 恢复码仍 30s 清（不入参覆盖为空） |
| sheet 关闭后 | 清除任务由 DispatchQueue 持有，到点仍执行 |

### 3. P5-B 成功反馈矩阵（CO-02，交 ui-standard 并入 DESIGN.md）

> 以下为「建议内容」，供 ui-standard 在 DESIGN.md（G1 骨架）内组织。矩阵与决策规则即本项规格的权威建议。

#### 3.1 决策规则（规范）
对一次操作，**只选一种反馈形态，不叠加**（结果页不再额外弹 alert；就地更新不叠加结果页）。按操作性质选型：
- **A · 结果页**：操作产出「需用户查看/决定下一步」的报告或结果（导入报告/导出路径/跨库复制落点/恢复引导）→ 流程末步即成功面。
- **B · 就地状态更新**：操作后界面就地反映新持久状态（开关/设置项）→ 不额外弹层。
- **C · alert**：仅用于安全关键流需强制显式下一步（改密后须重解锁）——**最小化使用**，HIG 不鼓励成功 alert。
- **D · 瞬时反馈**：轻量瞬时动作（复制）→ 控件内「已复制」短暂态。

#### 3.2 反馈形态矩阵（现状盘点 + 目标一致化）

| 操作 | 现状形态 | 目标形态 | 依据 / 反例 |
|---|---|---|---|
| 复制（字段/TOTP/恢复码） | 控件瞬时「已复制」 | **D 瞬时反馈**（保留） | 无结果可报告 |
| 导入（CSV/1PUX/Bitwarden/OPVault） | 结果页 | **A 结果页**（保留） | 含报告 + 删源建议 |
| 导出 / 备份 | 结果页 | **A 结果页**（保留） | 含路径/报告 |
| 跨库复制 | 结果页 | **A 结果页**（保留） | 显示落点库 |
| 恢复备份 | 结果页/引导解锁 | **A 结果页**（保留） | 引导下一步 |

#### 3.4 文案结构模板（三种形态，进 DESIGN.md 固化）
每种形态给**结构骨架 + 填空位 + 一句话书写规则**；dev-team 写新成功文案时按模板填空，不允许自由发挥。

**A · 结果页（headline / body / footer）**
```
headline =  <动词已完成>           例：「导入完成」
body     =  <计数摘要> + <下一步建议>   例：「成功 8 / 跳过 1 / 失败 0；建议在确认后删除源文件。」
footer   =  <单出口动作>           例：「关闭」（或「前往 X」）
规则：headline 只报完成态，不堆细节；计数摘要一条写完，失败为 0 也要写明；

```

```
title   =  <已完成的状态名>         例：「主密码已修改」
message =  <强制下一步的原因> + <用户须做什么>  例：「将立即锁定密码库，请用新主密码重新解锁。」
按钮    =  <主动作>（必要）+ <次动作>（可选）    例：「好」

纯确认型成功（无下一步）不得用 alert。
```

**D · 瞬时反馈（inline 控件内）**
```

## P6 恢复码抄写确认步（SEC-04）

### 1. 目标与判据锚点

| 锚点 | 内容 |
|---|---|
| SEC-04（docs/13 §2.5） | 恢复码生成「我已抄写保存」单按钮直过，无抄写验证；与 FW-04 互为放大 ⇒ 忘抄恢复码 = 永久锁死 |
| lead 裁定（docs/13 §3 P6） | 建议含「重生成」旁路降低确认摩擦；不破坏既有安全确认点（主密码确认步等） |

**恢复码格式（已实读确认）**：`core/cf-session/src/recovery.rs` —— BIP39-12，**12 个英文小写词**（空格分隔，约 60–80 字符）。此事实决定验证形态。

### 2. 设计

- **位置**：在 `RecoveryCodeSetupSheet` 的 ② 展示步与 ③ 主密码确认步之间**插入验证步**（新 `Step.verify`）。流程变为：`intro → showCode → verify（新增）→ confirm（主密码确认，原样）→ enable → 关闭`。
- **验证形态（推荐）**：**随机 3 词验证**。进入验证步时从 12 词中随机抽 3 个不同位置，提示「请输入恢复码第 N₁、N₂、N₃ 个词」（本次实例内固定，不随失败重试变化；仅「重新生成」后重抽）。
- **代码隐藏（关键安全语义）**：验证步**不再显示恢复码**（showCode 步的码区在本步消失）。用户在无码可看的情况下输入，必须依赖其已抄写/保存的副本——这才是「抄写确认」的本质。**不提供「返回查看」**（否则验证形同虚设）。
- **旁路（lead 要求）**：验证步提供「重新生成」次级按钮 → `startGenerate()` 生成新码 → 回 showCode → 再入验证（重抽词位）。由于此时 header 尚未写入（enable 在确认步之后），重新生成非破坏性：setup 流程无旧码可失效；regenerate 流程旧 wrap 仍有效，不受影响。**主流程无需破坏性确认**（与本步处于 enable 前一致），但**「重新生成」点击后须就地确认行**（REV2-06）：确认文案「将重新生成新恢复码，当前显示的恢复码将无法再次查看」，提供「重新生成」/「取消」两个内联动作；理由：旧码一旦被新码替换即不可再看（恢复码一次性纪律），用户若在 showCode 步刚抄写到一半、误点重新生成即前功尽弃，须给一次低成本反悔。
- **退出出口保留**：验证步保留「取消」（Esc / 关闭）→ 整体放弃（header 未写，旧 wrap 不受影响）。满足「不破坏既有安全确认点」。
- **不得可跳过**：验证步**不可跳过**（SEC-04 的意义即取消单按钮直过）；旁路只能是「重新生成」或整体取消，不能「直接确认」。

### 3. 线框（verify 步）

```
┌──────────────── RecoveryCodeSetupSheet（宽 440） ────────────────┐
│  [key 图标]                                                       │
│  确认抄写恢复码                                                     │
│  请在下方输入恢复码第 3、7、11 个词（恢复码已隐藏，请对照你保存的副本）  │
│                                                                    │
│   第 3 个词  [  TextField（普通非掩码）  ]                            │
│   第 7 个词  [  TextField（普通非掩码）  ]                            │
│   第 11 个词 [  TextField（普通非掩码）  ]                            │
│   （输入不符时橙色提示）与恢复码不符，请对照抄写内容再试。             │
│                                                                    │
│        [取消]     [重新生成]          [确认抄写]（borderedProminent） │
└────────────────────────────────────────────────────────────────────┘
```
- **固定为普通非掩码 `TextField`（非 `SecureField`）**。理由：恢复码是用户**已保存副本**的对照抄写，非新输入秘密；掩码只增加打字摩擦（自可见性差），且肩窥场景在此步无收益（旁边不显示参考码，窥屏者看到的也只是用户自己打的 3 个词）。掩码纪律（SEC-02）针对「显示/复制敏感值」场景，此处输入的是用户自己保存的副本，不适用。若 dev-team 出于统一输入框风格倾向 `SecureField`，须先向 lead 报备——本规格定为普通 TextField。
- 输入归一化：小写、折叠连续空格、trim；比较时大小写不敏感（接受用户误输大写）。
- 「确认抄写」在三个输入框均非空时可用。
- 错误处理：不符 → 就地橙色提示，**清空输入**，保留本步（词位不变）；「重新生成」随时可用。
- **verify 步剪贴板粘贴路径（lead 裁定方案 (b)）**：进入 verify 步时，若剪贴板当前持有一项恢复码复制项（来自 showCode 步的「复制」），**立即清除该项**（复用 P5-A 的统一剪贴板清除任务，changeCount 守卫同套）。由此 verify 步不允许「粘贴回填」——用户必须自己抄写/回忆已保存副本，粘贴路径被显式封死，剪贴板成为死数据。
- **分层安全声明（避免实现方误加防暴）**：verify 步是**抄写摩擦门**（让「我没抄写」无法直过），不是安全门。真正的高强度安全确认点仍是：③ 主密码确认步（D-6 密码重验证）+ enable 时的全码校验。因此 verify 步**不设输入次数上限、不加失败锁定/延时/防暴**——加了会与本步「纯摩擦门」定位冲突，也让误输 N 次的用户无路可退。

### 4. 状态与负路径（P6）
| 状态 | 处理 |
|---|---|
| 三词输入正确 | 进 ③ 主密码确认步（原样，含 D-6 密码重验证） |
| 输入不符 | 就地错误提示 + 清空 + 保留本步重试（无次数上限；旁路 = 重新生成） |
| 用户未保存副本 | 无法答出 → 「重新生成」旁路或「取消」整体放弃；不产生死胡同 |
| 用户点击「取消」 | 整体放弃，header 未写，旧 wrap（regenerate 场景）不受影响 |
| 重新生成 | 点击后先出**就地确认行**（「将重新生成新恢复码，当前显示的恢复码将无法再次查看」+ 重新生成/取消）；确认 → 生成新码 → showCode → 新 verify（词位重抽）；取消 → 原样留在 verify 步 |
| 恢复码含歧义字符 | BIP39 词表为英文小写词，无 0/O/1 混淆问题（词为单位，天然无歧义）——无需额外处理 |
| 长内容 | 12 词展示步保留现状（monospaced、可滚动/复制）；验证步仅 3 词输入，无滚动 |
| 深色/窄窗 | 固定宽 sheet，无特殊处理 |

### 5. 涉及文件范围（P6）
- `RecoveryCodeSetupSheet.swift`（Step 增 `.verify`；showCodeStep 的「我已抄写保存」改指向 verify 而非直接 confirm；新增 verifyStep；copyCode 走 P5-A 统一 API 已另列）

### 6. 实现验收要点（P6）
1. 「我已抄写保存」不再直过——必须先通过三词验证。
2. 验证步恢复码隐藏；无「返回查看」入口。
3. 随机抽 3 个词位，本实例内固定；「重新生成」后重抽且生成新码。
4. 输入错误就地提示 + 清空 + 可重试；「重新生成」与「取消」旁路可用。
5. ③ 主密码确认步原样保留（D-6 安全确认点未破坏）。
6. 验证通过前 `enable_recovery_code` 不可达（header 未写）。
7. 与 FW-04 文案修复（P1，不在本项）组合后，忘抄恢复码的死锁链被拆解。
8. 三词输入框为**普通非掩码 TextField**（REV2-04）；若实现改为 SecureField 须先报备 lead。
9. 进入 verify 步时清除恢复码剪贴板项（REV2-05，复用 P5-A 统一清除 + changeCount 守卫）；verify 步无「粘贴回填」路径。
10. 「重新生成」先出就地确认行（REV2-06），确认后才生成新码；verify 步**无次数上限/无失败锁定**（摩擦门，非安全门）。
11. 重新生成后 showCode 步显示的码为新码（旧码作废且不可再看），verify 词位重抽。

#### 3.3 全局键冲突警示（进 DESIGN.md G9）
1. **应用级 ⌘N/⌘L/⌘⇧C/⌥⇧C 均为 app-local**（CommandGroup），仅在 Coffer 激活前台时生效——**不与系统全局快捷键冲突**；唯一真全局键是既有 ⌥⌘P（HK-1，HotKeyMonitor），保持现状。
2. **第三方全局工具**（剪贴板管理、截图工具常注册 ⌘⇧C / ⌥⇧C 类全局键）：用户在 Coffer 前台按这些键时 Coffer 优先响应（macOS 前台 app 菜单快捷键优先），第三方工具通常自行检测冲突并提示；设计上无需代码处理，仅在 CHANGELOG 发版说明提示用户可自行改第三方快捷键。**⌘⇧C 冲突概率偏高**（REV2-10）：⌘⇧C 是部分剪贴板/截图工具（如 Clipy、个别截图工具）的**默认全局键**，用户装有此类工具时前台行为虽不受影响、后台全局呼出仍可能两者抢键——发版说明须**明确列出可能冲突的工具类**（剪贴板管理、截图），并提示：用户若在 Coffer 侧改键，须**同步修改第三方工具的同一快捷键**，否则第三方工具前台内按 ⌘⇧C 仍触发其自身动作（Coffer 的 CommandGroup 只在 Coffer 前台生效，不会拦截第三方 app 内部的键）。
3. **裸方向键 / 回车严禁注册为应用级**（§2.2 理由），避免与系统文本编辑/默认按钮语义冲突。
4. **⌘N 与 Window scene**：Coffer 为单窗口 WindowGroup，无 File 菜单；以 `CommandGroup(replacing: .newItem)` 注册 ⌘N 覆盖隐式「新建窗口」绑定，须回归确认不会额外开窗。
5. **回归要求**：⌘L 与菜单栏「锁定全部」语义（factory.lockAll + model.lock）不同——⌘L 仅锁当前库（model.lock()），菜单栏保留全局锁定全部，二者并存不冲突，需在实现注释与菜单文案区分。
