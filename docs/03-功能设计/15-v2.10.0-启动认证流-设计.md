## 0. 结论速览

- **目标 A**：现状首次建库后的启动会话内主密码输入 **3 次**（解锁 → 向导 bio 确认 → 恢复码确认），计入建库本身为 **4 次分钟级连续输入**（同串字符重复敲 4 遍）。方案空间 A0（基线）/ A1（向导内密码归一，3→2）/ A2（链式授权，3→1）/ A3（DEK 会话驻留，docs/02 Q-4 已裁定排除，仅记录）。
  - **推荐**：v2.10.0 先落 **A1**（纯 UI、低风险、零模型存储偏差，立竿见影 3→2）；**A2** 为体验最优目标（3→1），其中「首启解锁并入向导」形态（A2b）零模型存储、但改首启流程，**已裁顺延（§7-OP1：A1 先行）**；「AppModel 瞬态槽」形态（A2a）含模型持密码偏差，不推荐。
- **目标 B**：授权点矩阵 9 行，结构性结论——**(a)「仅需授权」类（主库解锁、跨库复制目标库解锁、忘记密码 bio 重置）Touch ID 已全面优先**；**(b)「必须主密码本身」类（Touch ID / 恢复码 / MCP 托管启用·重启用、修改主密码）因 Rust `recover_dek(password)` 需主密码作 KDF 输入派生 DEK、Touch ID 只能释放已存密钥材料而无法「说出」主密码，结构性无法替代**——不能糊成「全部优先 Touch ID」。可落地强化点 = ① 确认 (a) 类无遗漏；② 减少 (b) 类触发频率（配合目标 A）；③ 面告知消除认知落差（AUTH-5）。
- **KDF 成本如实声明**：除被排除的 A3 外，3× Argon2id（~3s）不可消除（docs/02 Q-4）。「收敛输入次数」优化的是打字与打断，不是耗时；进度反馈须如实呈现（不误导「更快」）。
- **偏差登记 2 处**：D-A1（向导 @State 跨步暂存密码）、D-A2（瞬态授权链，推荐形态不落模型）。均为一次性、即用即清、不落盘/日志。
- **目标 C（r0.2 新增）**：交互摩擦全检 23 条新发现（FRICT-01~23，主列表/详情/编辑/导入/设置/数据面），**0 CRITICAL / 0 HIGH / 12 MEDIUM / 11 LOW**。TOP-5：① 自定义字段保存后无法删除/改名（编辑死路）；② 次 URL 编辑面不可见不可管；③ 编辑 Esc/取消无未保存守卫；④ CSV 导入失败丢弃有效预检报告全量重走；⑤ MCP 数据源选择不持久化（重开设置静默重置、复制注册命令 provider 错误）。docs/13 已覆盖项 + v2.9.0 已落地项一律不重报；图标 bug（vault→archivebox）按已修复态不重报。

## 2. 目标 A：启动链路密码输入收敛

### 2.1 方案空间与安全代价对比

> 硬边界（全部方案的共同前提）：**DEK 不驻留解锁态**（docs/03-功能设计/02-v0.2.0-TouchID解锁-设计.md:58 D-6「不把 DEK 常驻解锁态，enable 传主密码」+ :428 Q-4「DEK 已 drop，维持现状」；辅 docs/09 §3.1 D-7）。任何 enable 都要 `recover_dek(password)` 重派生 DEK。因此「收敛输入」只能优化**打字与打断**，不能消除 KDF。

| 方案 | 启动会话输入次数 | KDF 次数 | 安全代价 | 纪律偏差 | 风险 / 备注 |
|---|---|---|---|---|---|
| **A0 基线**（现状） | 3 | 3 | 0（每次独立重确认，D-6 字面语义） | 无 | 用户直接投诉项，不做 |
| **A1 向导内密码归一** | **2**（解锁 + 向导一次输入复用于 Step1/Step2） | 3（不变） | **低**：向导 @State 持密码跨 Step1→Step2（**分钟级窗口**——Step2 含恢复码展示/12 词抄写/3 词验证；confirm 提交即清，§2.2）；每次 `recover_dek` 仍校验（1002 纪律保留）；「重确认」从「逐次重输」降为「一次输入、每步显式授权」 | **D-A1**（§2.2）：docs/07「提交即清」放宽为「跨步暂存、confirm 提交即清 + 向导关闭即清」 | 改动面小（向导内 + RecoveryCodeSetupSheet 加一次性授权入参）；不触 AppModel / 不改流程 |
| **A2 链式授权** | **1**（解锁输入即完成全部设置） | 3（不变） | **中**：授权窗口从「向导会话」扩到「解锁后瞬时窗口」；「证明身份」由刚完成的解锁满足（同会话、解锁刚完成、意图新鲜；暂存量级与 A1 相同——分钟级 + confirm 提交即清）；1002 校验保留 | **D-A2**（§2.3）：两形态——A2a 模型瞬态槽（不推荐，模型持密码）；A2b 首启解锁并入向导（推荐，密码只在向导 @State→Task 闭包） | A2b 改动首启流程（create→locked→unlock 变为 create→「解锁+设置」向导）；A2a 触 AppModel 瞬态存储 |
| **A3 DEK 会话驻留** | 1（且免 KDF） | 1 | **高**：DEK 是主密钥，驻留内存延长暴露窗口；与 Q-4 明确冲突 | 推翻 docs/02 D-6 | **已裁定排除，仅记录**。若要彻底免 KDF 需新开设计论（防篡改内存持 DEK 方案），不在本轮 |

**推荐**：
- **v2.10.0 落 A1**——安全默认、纯 UI、低偏差、直接回应用户投诉（3→2）。
- **A2b（首启解锁并入向导）作为体验最优目标**——3→1 且零模型存储，但改首启流程语义；**已裁顺延（§7-OP1）：A1 先行**，A2b 前置 M-3 相位机制设计（§2.3）。A2b 与 A1 不互斥：A1 是 A2b 的基础归一（向导内复用），A2b 把「解锁」也并入同一输入。

> 所有方案下 3× Argon2id（~3s）不变（A3 除外）。设计须在向导进度反馈中如实呈现（§2.2 线框「正在启用…密钥派生约需 1 秒」× 步数），不得暗示「更快」。

### 2.2 A1 向导内密码归一（推荐安全默认）

#### 设计
- **OnboardingWizard 持有单个跨步密码暂存**：Step1 bio 的 SecureField 输入（`OnboardingWizard.swift:86`）启用成功后**不再清空**，而是保留为「本向导会话已确认的主密码」（向导 `@State`，生命周期 = 向导展示期）。
- **Step2 显式授权复用**：进入嵌套 `RecoveryCodeSetupSheet` 时传入该值作为**一次性授权**（非预填文本、非静默自动提交）：
  - confirmStep（`RecoveryCodeSetupSheet.swift:391-421`）在「已携带向导授权密码」时，文案改为「将使用你刚输入的主密码完成此设置」（替代现状「出于安全考虑…重新输入一次」），主按钮改为「继续」（替代「启用恢复码」+ 空 SecureField）；
  - 用户可点「改为手动输入主密码」旁路（恢复原 SecureField 形态）——**授权是显式动作，不是替用户做主**；
  - 授权值仅存在于确认步提交闭包，`confirmEnable`（`:428-443`）仍走「拷贝进 Task 闭包、随即清空」纪律（**DESIGN.md D-2.4 密码生命周期**——提交瞬间进入调用链随即清空、不预填不落状态，L-1）。
- **D-2.3 对齐（一次确认边界，L-2）**：A1 把「Step1/Step2 各自重输」归一为「向导内一次输入 + 每步显式授权」——同一会话内同一操作（首次启用安全功能）只确认一次，符合 DESIGN.md D-2.3「同一流程内不得二次要求重输」（改密类安全门禁除外）。
- **D-2.1 登记待办（L-3）**：新 confirm 文案「将使用你刚输入的主密码完成此设置」须并入 DESIGN.md D-2.1 统一文案源（单一常量 + 用途参数），**不得**作为手写变体落地——随 G2 组件化（D-2.2）一并实现。
- **清空时机（关键缓解）**：**confirmStep 授权提交后立即清空**——`enableRecoveryCode` 触发（暂存值已拷入其 Task 闭包）即清暂存，**无论成败**，不等到 `onDisappear`（Step2 含恢复码展示/12 词抄写/3 词验证，为分钟级流程，驻留必须收敛到「提交即清」而非「流程结束才清」）；Step1/Step2 均跳过、任一启用失败需重输、向导 `onDisappear`、`lock()` 相变——同样一律清空（兜底防残留）。
- **RecoveryCodeSetupSheet 从设置页进入（无向导授权）**：行为与现状完全一致（独立 SecureField）。新增一个可空「授权密码」入参，nil = 现状路径。
- **失败语义**：Step1 启用失败（1002）→ 暂存密码判定为不可用，清空并回到 Step1 手动重输（现状可重试语义保留）；Step2 若授权密码同样失败（理论不可能——同串密码，除非数据损坏）→ 回手动输入旁路。


#### 偏差登记 D-A1
- **条款**：DESIGN.md D-2.4（submit-then-clear，源出 docs/07 §2.4）「主密码提交即清、不落 @State 之外」在**首启引导向导会话内**放宽为「跨步暂存、向导关闭即清、每次提交仍即时清空 Task 闭包副本」。
- **安全论证**：① 暂存值仍在视图 `@State`（不落 AppModel / 不落 @Published / 不落盘 / 不进日志——D-2.4 纪律）；② 生命周期 = 单向导会话展示期跨 Step1→Step2——**分钟级**（Step2 含恢复码展示/12 词抄写/3 词验证，RecoveryCodeSetupSheet 五步流），**缓解**：confirm 提交（`enableRecoveryCode` 触发）后无论成败立即清空暂存，实际最长驻留 =「输入 → confirm 提交」之间（12 词抄写/3 词验证恰在这一窗口内，如实涵盖），**不随 confirm 提交后的启用流程与向导收口拉长**；收口路径全覆盖清空兜底；③ 每次 enable 仍独立 `recover_dek` 校验（1002 纪律、错误文案不可区分纪律不变）；④ 「重确认」语义从「逐次重输」降为「一次输入 + 每步显式授权」，但解锁本身就是新鲜意图（用户刚输入同串密码），D-6「证明身份 + 重验证」被满足而非削弱。
- **判定**：A1 落地后，向导内 grep 不得出现密码落 AppModel/@Published/UserDefaults/日志；`onDisappear`/skip/lock 全路径清空可断言行成立。

### 2.3 A2 链式授权（体验最优，已裁 A1 先行、A2b 顺延）

> **顺延前置（M-3，记录即可）**：OP1 已裁 A1 先行、A2b 顺延（§7）。A2b 启动前须先补**相位机制**设计——`showOnboarding` 要求 `.unlocked`、Step0（解锁步）无法经现状 sheet 形态呈现、「以后再说」对解锁步语义冲突（解锁不可跳过）；归 dev-team 实现 A2b 时前置补齐，不阻塞 A1。

目标形态：启动会话内**只输一次密码**（解锁），bio + 恢复码 enable 全部用该值。两种实现形态：

#### A2a — AppModel 瞬态槽（**不推荐**）
- `unlock(password:)`（`AppModel.swift:701-728`）成功后将 password 拷入 **非 @Published** 的瞬态槽（`private var lastUnlockPassword: String?`），供紧接的向导消耗一次后清空；`lock()` 清空。
- **偏差 D-A2a**：模型短暂持主密码（违反「不落任何 @State/@Published 属性」的字面与精神）。安全代价 > A2b（模型是全局单例，驻留窗口不可控于单一视图）。
- 结论：不推荐，除非 A2b 因故不可行，且须 lead + 安全评审通过。

#### A2b — 首启解锁并入向导（**推荐形态**）
- 建库成功后（`createVault`，phase 置 locked 前），**首启不再回 LockView**，而是直接呈现「首启解锁 + 设置」向导：
  - **Step0「解锁」**：复用 LockView 密码框（`LockView.swift:54` 同构），输入主密码 → `unlock(password)`（phase → .unlocked，1001 门禁解锁后 enable 可达）；
  - **Step1 bio / Step2 恢复码**：同 A1 的向导内复用（密码在向导 `@State` 跨步）；
  - 密码只在向导 `@State` → Task 闭包 → `unlock` / `enableTouchID` / `enableRecoveryCode` 调用链中流动，**零模型存储**。
- **语义变化（OP1 已裁顺延）**：A2b 若实现，现状「建库 → 强制回锁定页证明记住密码」改为「建库 → 解锁+设置一步完成」。「首启证明记忆」属性 = 弱化为 Step0 仍需输入（用户仍证明记住了密码）但不再有独立锁定页；A1 先行下该属性保留（解锁仍回 LockView）。
- **与 AUTH-4 的关系**：A2b 顺带解决「建库后连输两遍」——建库（①）与解锁（②）之间的重复被消除为一次输入（Step0）。
- **失败路径**：Step0 解锁失败（1002/退避门禁）→ 向导内就地呈现、保留可重试（现状 LockView 语义）；用户中途想「先去主界面再说」→ 向导每步保留「以后再说（可在安全设置中开启）」（P2-A 硬约束「勿砍可跳过」逐字保留）。

#### 偏差登记 D-A2
- A2b：无模型存储偏差（密码仅向导 @State + 调用链）。与 DESIGN.md D-2.4 的关系 = 同 D-A1（跨步暂存，范围从 Step1→Step2 扩为 Step0→Step2，生命周期仍是单向导展示期）。
- A2a：见上（不推荐形态，若启用需单独安全评审）。

### 2.4 负路径（目标 A）

| 状态 | 处理 |
|---|---|
| Step0/Step1 启用失败（1002 密码错 / 数据损坏） | 就地 `ffiErrorAlert` 呈现（不可区分文案纪律不变）；清密码暂存，保留可重试（重输） |
| 用户中途锁定 / 关窗 / 切库 | phase 离开 .unlocked → 向导随 RootView 拆树拆除（RootView.swift:21-28 现状同语义）；密码暂存随视图销毁释放 |
| 跳过 Step1 或 Step2 | 「以后再说（可在安全设置中开启）」逐字保留；跳过即清对应旗标 + 记 `*_offer_skipped`（设置页首次高亮兜底 P-2.1 触发） |
| 恢复码流程整体放弃（cancel） | header 未写、旧 wrap 不受影响（RecoveryCodeSetupSheet.cancelFlow:455-458）；暂存密码保留供 Step2 重试 |

### 2.5 验收判据（草案，转 dev-team）

1. 首次建库后启动会话主密码输入次数 = **2**（A1）或 **1**（A2b）。（对比基线 3；以 Touch ID 解锁则各减 1，判据按主密码解锁路径口径）
2. 每次 enable 仍独立 `recover_dek` 校验：任一密码错 → 1002 就地呈现、不可区分文案不变、可重试。
3. 向导收口（跳过 / 成功 / onDisappear / lock）后，暂存密码无任何残留（grep 无落 @Published/盘/日志；断言行可测）。
4. Step2 confirm 授权形态：默认「继续」、旁路「改为手动输入主密码」、旁路后清暂存。
5. P2-A 硬约束不回归：每步可跳过、「以后再说」文案逐字、设置页首次高亮兜底（P-2.1）触发/清除语义不变。
6. （A2b，顺延后适用）Step0 解锁失败可重试、退避门禁期按钮防呆（LockView 语义对齐）；「首启证明记忆」属性按 OP4 终态落实（A1 保持现状；A2b 实现时若需变更须显式声明偏离）。
7. **无授权密码回退（M-4①）**：无 Touch ID 设备或 Step1 已跳过 → Step2 无授权密码 → 回退手动形态（nil 授权入参，行为与现状完全一致——独立 SecureField、逐字文案）。
8. **Step2 授权密码失败（M-4②）**：数据损坏理论路径 → 清暂存 + 回「改为手动输入主密码」旁路（旁路后暂存即清，可重试）。
9. **D-A1 grep 门禁正式化（M-4③）**：向导内 grep 不得出现主密码落 AppModel / @Published / UserDefaults / 日志；清空全路径（confirm 提交即清 / skip / onDisappear / lock / 旁路）断言行成立。
10. **向导置位设置窗门控（M-2 验收）**：首启向导置位期间（`pendingBioOffer || pendingRecoveryOffer`）「设置…」入口两处（⌘, 菜单栏 + 工具栏按钮）均禁用、设置窗不可开；向导收口（旗标全清）后恢复可开（CofferApp.swift:154-156 / MainView.swift:159 同谓词生效）。

## 3. 目标 B：Touch ID 优先授权矩阵

### 3.1 授权点全量盘点

> 分类：**(a) 仅需授权**（证明「是本人」，Touch ID 满足，可替代密码）；**(b) 必须主密码本身**（需要主密码作 KDF 输入派生/封装 DEK，Touch ID 只能释放已存密钥材料、无法「说出」主密码）；**(c) 第三方通道**（恢复码）；**(d) 无需凭据授权**（仅确认）。

| # | 授权点 | 触发场景 | 现认证方式 | 分类 | 能否 Touch ID | 为什么（每行给出理由，不糊） |
|---|---|---|---|---|---|---|
| B-1 | 主库解锁 | 启动 / 锁定 | 主密码 / Touch ID（按钮 + 启动自动弹窗） | (a) | ✅ **已是 Touch ID 优先** | Touch ID 释放 K_bio → FFI `unlockWithBiometric` 解 DEK（cf_ffi.swift:1590）；只需「是本人」，密码知识非必需。启动自动弹（`maybeAutoPromptBiometric` AppModel:559-572，PL-7 瞬时失败降级） |
| B-2 | 跨库复制目标库解锁 | 跨库复制 | 目标库主密码 / Touch ID | (a) | ✅ **已是** | K_bio 按 vault_uuid 定位目标库（CrossCopySheet.swift:213-220/295-314）；CO-04 已让弹窗指明目标库名 |
| B-3 | 忘记主密码 → bio 重置 | 锁定页「忘记主密码？」 | Touch ID（`resetPasswordWithBio`）或恢复码 | (a) | ✅ **已是** | `recover_dek_bio(k_bio)` 复用已存密钥解 DEK（RecoveryResetSheet.swift:135-158；docs/09 §3.1）——忘记密码场景 Touch ID 反而优先于密码 |
| B-4 | Touch ID 启用 / 重启用 | 设置 / 首启引导 | 主密码（D-6） | (b) | ❌ **结构性不能** | 启用 = 生成 K_bio 并 `enableBiometric(password:kBio:)`（cf_ffi.swift:1185）内部 `recover_dek(password)` 派生 DEK 再封装。**鸡生蛋**：K_bio 尚不存在，Touch ID 无从释放；即使重启用（K_bio 已存在），仍需主密码作 KDF 输入重派生 DEK——Touch ID 释放 K_bio 只给出一个尚待封装的密钥，无法「说出」主密码 |
| B-5 | 恢复码启用 / 重生成 | 设置 / 首启引导 | 主密码（confirm 步） | (b) | ❌ **结构性不能** | `enableRecoveryCode(password:code:)`（cf_ffi.swift:1220）内部 recover_dek(主密码) → 派生 K_recovery → 封装 DEK。恢复码的 KDF 输入是主密码，不是任何 Keychain 项；Touch ID 无法代派生 |
| B-6 | MCP 解锁托管启用 / 重启用 | 设置 | 主密码（deriveMcpKey + enableMcpEscrow） | (b) | ❌ **结构性不能** | `derive_mcp_key(password)` = recover_dek(主密码) → HKDF 派生 mcp_key（cf_ffi.swift:1137/1204）。mcp_key 是「主密码派生值」，Touch ID 释放的 K_bio 与其无关 |
| B-7 | 修改主密码 | 设置 | 旧主密码（changePassword，D-2.3 安全门禁） | (b) | ❌ **结构性不能** | 改密必须证明「知道旧密码」：旧密码 → KEK → DEK 校验（ChangePasswordView.swift:3-8）。Touch ID 证明生物特征非密码知识；允许 Touch ID 改密 = 生物特征可重置密码 = 降权到「任何人持有本机 + 指纹即可改密」。1002 语义（旧密码错）也必须来自密码路径 |
| B-8 | 忘记主密码 → 恢复码重置 | 锁定页 | 恢复码（非主密码） | (c) | 不适用 | 用恢复码本身；主密码已知且 Touch ID 可用时走 B-3（RecoveryResetSheet 两分支堆叠，bio 在上） |
| B-9 | 关闭 Touch ID / MCP 托管 | 设置 | 二次确认（无密码） | (d) | 不适用 | disable 不重派生 DEK，仅删 Keychain 项 + 改 header（`disableBiometric`/`disableMcpEscrow` cf_ffi.swift:1156/1165）；现状二次确认已足够，无密码可「优先」替换 |

### 3.2 结构性结论（为什么不能糊成「全部优先 Touch ID」）

1. **「仅需授权」类（B-1/2/3）Touch ID 已全面优先**：主库解锁（启动自动弹 + LockView 按钮）、跨库复制目标库解锁、忘记密码 bio 重置。三者均已支持且默认优先。**此类的"尽可能优先"已达成**，无新增入口需求。
2. **「必须主密码本身」类（B-4/5/6/7）结构性无法用 Touch ID 替代**，根因 = **D-6 的 `recover_dek(password)` 需要主密码作为 KDF 输入**，而 Touch ID 的能力边界是「释放已存的密钥材料」，不是「说出」任何值：
   - 启用类（B-4/5/6）：需要主密码派生/封装 DEK → 无密码 = 无 DEK = 无法写入 wrap。
   - 改密（B-7）：需要证明密码知识本身；Touch ID 化 = 生物特征可重置密码，降权不可接受。
3. **唯一能让 (b) 类走生物识别的路径 = 引入可被 Touch ID 释放的「授权密钥」，但该密钥仍需主密码在启用时刻生成——即又回到 B-4**。不存在「Touch ID 首启后一切免密」的闭合环（除非 DEK 驻留，Q-4 已排除）。
4. 因此目标 B 的正确落地 = **不新增 Touch ID 入口，而是**：① 维持/确认 (a) 类优先（回归检查）；② 减少 (b) 类触发频率（目标 A 收敛输入）；③ 面告知消除 AUTH-5 认知落差。
