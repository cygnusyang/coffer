| 用户三问 | 结论 |

| 要不要加？ | **要加（裁定 YES）**，以受限形态加入：三入口 → VaultManagementView 库管理面——设置页「密码库」区「管理密码库…」主入口 + 库切换 sheet 底部深链 + LockView「管理密码库…」（第三入口，忘密废库/单库忘密，工厂级）；确认门 = 输入库名逐字符确认（**无任何密码步**，UDR-3 采纳）；删除操作工厂级（锁定态/忘密废库均可删，与 restore 同构）；删当前库可删（先锁旧，落最近库锁定态 / `.noVault`）；导出前置步（推荐先导出后删除，C8 参数化导出目标库）；CLI 删除命令**不新增**（六裁定 #6 取消）。理由与完整方案见 §3 / §4 |

## §2 现状与历史裁定

### 2.1 历史裁定链（为什么一路「没有」）

| 时点 | 裁定/证据 |
|---|---|
| v0.2.0+ | 删除库登记为未来项：docs/02-TouchID解锁设计.md §3.3「删除库（未来 delete_vault）时必须同步删除对应 Keychain 项」，**已预写实现约束** |
| v0.4 | docs/04 §3.2.1「明确不做：删除库、库重命名、库间数据合并」；§9 顺延清单再列「多库子项：删除库」 |
| v2.9.x 交互审查 | FW-04（HIGH）死胡同 + SEC-04（MEDIUM）互为放大 → lead 裁定「FW-04 出路先改文案，不补删除库能力」，提供库删除列为独立设计决策点（docs/13 §5 裁定 4 / §9.3） |
| v2.9.1 | FW-04 文案缓解落地：RestoreBackupView 的 1004 专属文案不再引导「先删除现有库」（现状见 RestoreBackupView.swift 恢复错误分支） |
| v2.9.0 | SEC-04 由 P6 恢复码抄写确认步收口（docs/14 P6）——放大链已断一半：忘抄恢复码不再单靠删除兜底 |

### 2.2 现状能力审计（本文结论的事实基础）

- **无删除入口**：VaultSwitcherView.swift 文件头注释明示「明确不做：删除库」；SettingsView「数据」区现仅「从备份恢复… / 审计日志…」，无密码库管理面。
- **core 无 delete 能力**：cf-ffi 库管理面仅 `list_vaults` / `create_vault` / `open_vault`（core/cf-ffi/src/api.rs），**无 `delete_vault`**；CLI 子命令仅 `mcp` / `set-password` / `set-env`（core/cf-mcp/src/cli.rs 文件头）——删除库属**新增核心能力**（实现契约见 §5 C1）。
- **导出能力工厂级可用**：FFI `export_backup(vault_dir:, out_path:)`（core/cf-ffi/src/api.rs）收任意 vault_dir、**锁定态可用（TC-EXP-08）**——非当前/锁定库的加密备份可在删除向导内直接导出（C8 前提）；但 ExportView 现无目标库参数（恒导当前库），是 UDR-1 隐患源，须参数化。
- **许可门禁接缝已备**：cf-domain/src/license.rs `LicensedOp::VaultWrite` 已列 `delete_vault`（库级写组，与 create_vault/change_password 同组）——新增 delete_vault 天然过许可门禁（TC-GATE-12 结构性保证），无新增门禁面。
- **既有删除语义只有条目级**：软删进回收站 + 清空回收站（TrashView，FW-03 聚合反馈已按 DESIGN.md D-8.2 落地）。**库删除是库文件级操作，与条目级删除语义不同**（条目删除在库内事务，库删除销毁整库），文档须显式区分，见 §3.5。
- **恢复备份冲突文案已改**：RestoreBackupView 1004 专属文案现为「库已存在即无需恢复，或改选其他备份文件」，不再引导删除——剩余缺口 = **冲突库的清理能力**（本文补上后，1004 场景出路 = 删除冲突库 → 重试恢复，见 §4.1 分支）。
- **多库状态机**：单活跃会话不变量，切换 = 先开新、成功才锁旧（docs/04 §3.2.1）——删除当前库必须考虑此不变量，见 §4.2。
- **空态首屏**：`.noVault` 相位 → VaultSetupView（RootView 相位拆树）——删除最后一座库的落点。
- **恢复的工厂级可达面（restore 同构基准）**：RestoreBackupView 仅自 SettingsView（解锁态）与 VaultSetupView（.noVault 工厂级）两处呈现，全程不读会话（RestoreBackupView.swift / VaultSetupView.swift 恢复入口注释）；LockView 无恢复入口——删除管理面的可达面与之一致（见 §4.2 / 附 C 边界）。

### 2.3 FW-04 / SEC-04 演进与本功能的关系

- FW-04 死胡同三出路：① 改文案（**已做**，v2.9.1）；② 提供删除库能力（**本文 = 根治**）；③ 恢复前自动改名/合并（维持不做——docs/04 §3.2.1 库重命名/合并仍不做）。
- SEC-04 已由 P6 收口。删除能力补上后，追加效果：忘密码/库被污染/冗余测试库等场景获得「归零重来」正路。**注意**：删除重建 = 数据销毁，不等于数据保全，恢复码纪律与备份纪律仍须维持（删除只提供归零路径，不替代备份）。

## §3 裁定（是否加 + 形态限定，lead 六裁定终版）

### 3.1 裁定：加，但限定形态

1. **入口 = 设置页「密码库」区「管理密码库…」主入口 + 库切换 sheet 底部深链 + LockView「管理密码库…」低存在感链接**（破坏性操作放低频路径更稳，深链补可发现性；LockView 工厂级入口收口单库忘密死路，与 restore 同构；lead 裁定 r0.4 / UDR-2，标签经 R-A 与设置/切换器同文案——「忘记主密码？」留给既有恢复入口 RecoveryResetSheet）。管理面 = 新增 VaultManagementView（列全库，行内删除）。删当前库可删后，当前库行同样有入口。
2. **确认门 = 输入库名逐字符确认，无任何密码步**（UDR-3 采纳，推翻 lead 前期主密码裁定）；**比对前输入与库名各 trim**（防首尾空格库名确认永不过 = 删不掉死路，UDR-1 必改，Swift 侧）。§3.4 的「验证用当前库密码」设计点随主密码验证一并撤下；孤儿库/忘密库删除不受影响（无需任何库密码）。
3. **锁定态可删（非当前库）**：删除操作工厂级（无解锁会话依赖、无密码门），与 restore 同构；忘密废库 UI 直接可删。锁定态下导出前置 = 加密备份（工厂级可用），plaintext（CSV/1PUX）需解锁目标库，不在向导内嵌解锁（C8 限定加密 tab）。
4. **允许删除当前库**；先锁旧再删 → 多库落最近库锁定态 / 单库落 `.noVault` 空库首屏（对齐 docs/04 §3.2.1 bootstrap 语义；UDR-5 空态分支由此可达）。
5. **导出前置步**：向导内置「先导出加密备份再删除（推荐）/ 直接删除」双选；导出走 C8 参数化 ExportView（targetVaultDir/targetVaultName + **全目标仅加密备份** + **显式展示正在导出哪座库**）——对非当前/锁定库目标同样开放（加密备份工厂级可用），必落非可选项（S-6）；明文导出不在删除向导内提供，用户可事后自行解锁导出（UDR-3）。
6. **CLI 删除命令不新增**（六裁定 #6 取消）：随「无主密码验证」失去必要性，孤儿/忘密废库 UI 直接可删，无需 CLI 兜底。
7. **删除库 ≠ 卸载 App**：文案与文档显式区分两种语义（对齐系统设计 §7.4 前置要求，且不能假设系统备份兜底）。
8. **不做的边界（重申 v0.4 裁定）**：库重命名、库间数据合并、多会话并存 UI——仍不做。
9. **判定锚点**：AC-06「导出加密备份 → 删除库 → 从备份恢复 → 数据完全一致」端到端可走通（真机判据）。

### 3.2 裁定理由

- **为什么现在加**：FW-04 是 docs/13 遗留的唯一 HIGH 死路（文案只缓解未根治）；AC-06 验收前置假设此能力；系统设计 §7.4 明确要求删除流程；删除是忘密码/被污染库/清理测试库的唯一正路。
- **为什么不是更早**：v0.4 时建/切/复/备份优先级更高，删除非首版必备；物理语义（文件族 + Keychain 清理面）当时未定，且安全设计（确认强度）需先立。
- **为什么入口在设置「管理密码库…」+ 库切换深链（lead 六裁定 #1）**：破坏性操作放**低频路径**（设置「数据」区，与「从备份恢复… / 审计日志…」同级管理面）比放高频路径更稳——库切换器是日常高频入口，行内直接挂删除易误触、且破坏性动作与高频动作同层，违反「破坏性操作不与普通操作同层级」纪律；设置页主入口 + 库切换 sheet 底部深链兼顾**可发现性**。管理面 = VaultManagementView 列全库（含当前库），与恢复入口（设置 + 空态首屏）可达面同构。
- **为什么确认门只需输入库名（UDR-3 采纳）**：见 §3.4 理由重构。

### 3.3 确认强度权衡与裁定（lead 六裁定终版 / UDR-3 采纳）

| 候选要素 | 裁量 | 裁定 |
|---|---|---|
| 破坏性确认弹窗 | **要**（误触防护基线） | 含库名 + UUID + 不可逆声明 + 导出前置步 |
| 「输入库名」逐字符确认 | **要**（确认门，防误触/防错目标；非认证门） | 全部删除路径统一；**比对前双方 trim**（UDR-1）；同名库 Step3 尾显 masked UUID 消歧（UDR-7）；忘密库无需任何密码即可删 |
| 主密码重验证 | **不要** | 撤下（UDR-3 采纳，推翻 lead 前期主密码裁定）；理由见 §3.4 |
| 失败锁定 / 延时 | **不要** | 那是防暴拆解路径；确认失败只可能「库名不符」，无凭据攻击面 |
| 强制先导出才能删 | **半强制** | 「先导出加密备份再删除」为推荐项（默认选中），但允许「直接删除」（合法清库场景）——软性约束，不堵死归零需求 |

**权衡结论**：删除库 = 不可逆数据销毁，确认强度取「弹窗 + 输入库名逐字符确认」档——与行业惯例（GitHub / Apple / 1Password 删除 = 输入名称确认）一致；不引入主密码步，因其在已解锁会话上不构成安全边界（§3.4），且会堵死忘密废库清理（FW-04 死路换形式回归）。

### 3.4 为什么无主密码验证（UDR-3 理由重构）

删除「当前库结构性不可删」支柱后（当前库可删、导出前置步开放全目标），主密码验证的深层支柱不存在了，理由重构如下：

- **解锁态攻击者本具全量破坏力**：已解锁会话下，攻击者可浏览全部秘密、明文导出（CSV/1PUX）、改主密码、删除条目——拒绝「删库」这一项不降低其实际破坏面（机密性已失）。主密码门此时只保「完整性」一维，且是虚假完整（删库不是攻击者获得新能力的必要路径）。
- **锁定态攻击者有 FS 访问权**：锁定态下删除是文件级操作，UI 验证拦不住绕过 App 的直接目录删除（安全边界在文件系统/密钥层，不在 UI 弹窗）。
- **忘密废库清理是真实高频维护需求**：用户弃库忘密极常见（docs/01-需求与架构/04-系统设计.md §1「忘记主密码 = 永久不可恢复」）；主密码门会把它堵死 = 删不掉也解不开 = **FW-04 同类死路换形式回归**。六裁定 #2 + **LockView「管理密码库…」工厂级入口**（lead 裁定 r0.4 / UDR-2，标签经 R-A 改判）后无死路：忘密废库（含单库忘密锁定态）UI 直接可删，删后落 `.noVault` 自然衔接 VaultSetupView 恢复面。
- **一致性**：D-2 密码确认先例用于「开启能力」（启用 TouchID / MCP / 恢复码）；删除是「销毁既有对象」，行业惯例不要求密码（GitHub / Apple / 1Password 均输入名称确认）。无人值守 Mac 上他人借删除作恶 = 蓄意多步行为且机密性已失，登记为接受残余（§4.4）。

### 3.5 库删除 vs 条目删除（语义显式区分）

| 维度 | 条目删除（既有） | 库删除（本文） |
|---|---|---|
| 作用域 | 库内单条目事务 | 整库文件族销毁 |
| 可逆性 | 软删进回收站可恢复；清空回收站不可逆 | 不可逆（无回收站层级） |
| 安全确认 | 清空回收站 = 确认弹窗（无密码验证） | 确认弹窗 + 输入库名逐字符确认（终局操作） |
| 数据保全 | 不涉备份 | 删除前引导导出加密备份（推荐步） |
| 会话依赖 | 库内（解锁态） | 工厂级（锁定态/忘密库均可删，与 restore 同构） |

### 3.6 孤儿库 / 忘密废库清理（单通道 = UI 直接可删）

| 场景 | 通道 | 说明 |
|---|---|---|
| 已有任一库解锁 | GUI：设置「管理密码库…」/ 库切换深链 → 管理面行内删除 | 输入库名即删，无需任何库密码 |
| 忘密废库（含孤儿） | 同 GUI | 密码门撤下后无死路；导出可选（加密备份仍需其自身主密码才可恢复，仅对密码可寻回者有用） |
| 单库忘密想清库重来 | **GUI：LockView「管理密码库…」**（lead 裁定 r0.4 / UDR-2，R-A 改判标签） / 恢复码 / 重装走 restore | 工厂级入口收口单库忘密死路，删后落 `.noVault` 衔接 VaultSetupView 恢复面（UDR-2）；真机可达性待实现轮验证 |

## §4 交互方案

### 4.0 信息架构

```
设置「数据」区「管理密码库…」（主入口，解锁态）──────┐
库切换 sheet 底部「管理密码库…」（深链，解锁态）──────┤
LockView「管理密码库…」（工厂级，锁定态；lead 裁定 r0.4 / UDR-2，R-A 改判标签）┼→ VaultManagementView（库列表，全库）
（VaultSetupView .noVault 工厂级，restore 同构，可选）──┘
   └─ 行内 [删除…] → DeleteVaultConfirmSheet（多步向导）
        Step1 目标与方式（库名+UUID+不可逆声明；双选：先导出再删 / 直接删）
        Step2 [先导出再删时] 导出（C8 参数化 ExportView，加密 tab，显式目标库）
        Step3 输入库名逐字符确认
        Step4 执行（当前库先锁旧）→ Step5 完成反馈 + 落位引导
```

### 4.1 完整用户流程（含分支）

**主流程（删非当前库，含忘密孤儿库）**
1. 解锁态：设置「数据」区「管理密码库…」或库切换 sheet 底部「管理密码库…」→ VaultManagementView（库列表，onAppear `reloadVaultBriefs`）。
2. 目标库行 `[删除…]`（destructive）→ DeleteVaultConfirmSheet Step1：库名 + UUID + 不可逆声明 + 操作方式双选（「先导出加密备份再删除」默认选中 /「直接删除」）。
3. 选「先导出加密备份再删除」→ Step2 导出（参数化 ExportView：显式展示目标库名 + masked UUID，**全目标仅加密备份**，工厂级）→ 导出成功 → Step3；选「直接删除」→ 直接 Step3（明文导出不在删除向导内提供，用户可事后解锁导出，UDR-3）。
4. Step3 输入库名逐字符确认（**输入与库名各 trim 后精确匹配**，UDR-1；同名库尾显 masked UUID，UDR-7）→ 匹配后 `[确认删除]`（destructive）可用。
5. 执行（`Task.detached`，工厂级 FFI delete_vault，无密码/会话门）→ Step5 完成反馈 → 目标库从管理列表消失。

**主流程（删当前库，叠加先锁旧 + 落位）**
1-4 同（目标 = 当前库，行内同样有 `[删除…]`）。
5. 执行前**先锁当前会话**（防在打开连接上删库导致 WAL/SHM 半删）→ 删除 → 落位：多库 → 切剩余库中 createdAt 最近者 `.locked` 解锁引导；单库 → `.noVault` 空库首屏。

**管理面生命周期（UDR-4）**：删除成功后先关闭确认 sheet；目标库从管理列表消失、列表刷新。删光全库 → VaultManagementView 一并关闭，落 `.noVault` 首屏（VaultSetupView）；删非当前库 → 管理面保持打开（列表刷新）。真机核销加「删光全库无残留 sheet/卡死」。

**分支（负路径）**
- 库名确认不符 → 就地错误提示，保留重试。
- 导出失败 → 错误经 ffiErrorAlert，确认流留驻；「先导出再删除」路径导出未成功不得进 Step3（强制先保数据）。
- 删除失败（文件占用/磁盘只读/沙盒 I/O）→ 错误经 ffiErrorAlert，确认流留驻可重试；部分删除提示「部分文件已删除，请重试或检查文件权限」；list_vaults 对损坏目录跳过（cf-ffi api.rs 既有韧性）。
- 1004 恢复冲突 → 经设置/管理删除冲突库 → 回恢复流程重试（出路闭环）。
- 最后一座库删除 → 落 `.noVault` → VaultSetupView（空库首屏）。
- 任一环节取消 → 无任何变更（删除前无破坏性副作用）。
- 只读许可用户 → 「管理密码库…」入口及行内 `[删除…]` 整体隐藏/禁用（UDR-7，对齐 create_vault 拒绝口径）——不在向导内逐项报错。

### 4.2 状态矩阵（lead 六裁定终版）

| 状态 | 删除入口 | 确认门 | 删除后落位 |
|---|---|---|---|
| 解锁态 | ✅ 设置「管理密码库…」+ 库切换深链 → VaultManagementView 行内 | 输入库名逐字符确认（无密码） | 见下行 |
| 锁定态 | ✅ **操作工厂级**：不依赖解锁会话、无密码门（与 restore 同构）；**当前锁定库经 LockView「管理密码库…」**（lead 裁定 r0.4 / UDR-2，R-A 改判标签）；非当前库入口见附 C | 输入库名（trim 后精确匹配，UDR-1） | 删当前锁定库 → `.noVault`；删非当前库 → 目标库消失 |
| `.noVault` 空态 | ✅ 工厂级（VaultSetupView「管理密码库…」，restore 同构入口；服务孤儿目录清理） | 输入库名 | 目标库从管理列表消失 |
| booting / fatal | ❌ 不可达 | — | — |
| 多库 · 删非当前库 | ✅ | 输入库名 | 当前会话不变；目标库从管理列表消失 |
| 多库 · 删当前库 | ✅（先锁旧） | 输入库名 | 切剩余库中 createdAt 最近者 → `.locked` 解锁引导（对齐 docs/04 §3.2.1 bootstrap 语义） |
| 单库 · 删当前库 | ✅（先锁旧） | 输入库名 | `.noVault` 空库首屏（VaultSetupView） |
| 孤儿库 / 忘密库 | ✅（无密码即可删） | 输入库名 | 同删非当前库 |

> 落位原则：删除后**不自动解锁**新库（安全默认，回主窗口走 LockView 解锁引导）；删除后成功反馈与落位引导文案见 §4.3。
> 管理面生命周期：删光全库 → sheet 自动关闭落 `.noVault` 首屏；删非当前库 → sheet 保持、列表刷新（UDR-4，见 §4.1）。

### 4.4 负路径清单

| 负路径 | 处理 |
|---|---|
| 库文件被外部占用 / 删除失败 | 错误经 ffiErrorAlert，确认流留驻可重试；部分删除提示「部分文件已删除，请重试或检查文件权限」；list_vaults 对损坏目录跳过（cf-ffi api.rs 既有韧性） |
| 磁盘只读 / 沙盒 I/O 拒绝 | 同上；沙盒 I/O 走既有降级通道（cf-exporter EPERM 先例，见附 C） |
| 导出未完成即被引导删除 | 不可能：「先导出再删除」路径导出成功才放行 Step3（强制保数据） |
| 删除中 App 退出 | 建议 rename-then-delete 原子化（重命名 = 库即刻「不可见」，物理删除后台收尾，见 §5 C5）；中断后 list_vaults 跳过损坏目录，不产生承诺外的状态 |
| 删除中在「FFI 删文件」与「Keychain 双清」之间退出 | 残留 orphan Keychain 项 / 文件（对已删库无泄露面、无害，仅数据卫生）——**接受为已知限制，登记归 backlog**（UDR-2），不做启动期差集清扫；见 §5 C2 注 |
| 当前库删除失败（已先锁） | 用户处锁定态，可重解锁重试，无数据丢失 |
| 库名确认不符 | 就地错误提示，保留重试 |
| 他人在场 / 无人值守已解锁 Mac（SEC-01 关窗驻留面） | 无人值守残留登记为接受残余：该场景下全库机密性已失（可解锁浏览），删除不新增泄露面；删除为蓄意多步行为（UDR-3 理由重构，§3.4） |
| 只读许可用户 | 「管理密码库…」入口 + 行内 `[删除…]` 隐藏/禁用（UDR-7）——不在向导内逐项报错 |

## §5 实现契约（core 缺口标注，C1–C8）

**core 缺口**：无 `delete_vault`（cf-ffi 库管理面仅 list/create/open；CLI 无删除子命令且按六裁定 #6 **不新增**）。以下为给 dev-team 的实现契约，不写实现代码：

- **C1 · 核心能力**：cf-session use case 层 `delete_vault(base_dir, uuid)` → cf-ffi 暴露 `FfiCofferApp::delete_vault`（**工厂级**：不依赖解锁会话，与 restore 同构——锁定态/忘密库可删）。校验：uuid 合法（防路径拼接逃逸，对齐 open_vault 既有先例）。文件族范围 = 工作目录 `<base>/<uuid>/` 整目录（header.json / db.sqlite / db.sqlite-wal / db.sqlite-shm（运行时）/ attachments/ / thumbnails/ / MANIFEST.json（可选），docs/03-详细设计.md §1.2；**目录布局经 R-B 裁定（lead，C1 布局实测）定为 `<base>/<uuid>/`，改文档不改代码，实现轮由 dev-team 对齐**）。
- **C2 · Keychain 双清（Swift 侧既有接缝，非新增 Rust 面）**（docs/02-TouchID解锁设计.md §3.3 已登记实现约束）：Touch ID K_bio 经 `Platform/BiometricKeychain.delete(vaultUUID:)`、MCP escrow 经 `Platform/McpEscrowKeychain.delete(vaultUUID:)`（service cn.coffer.mcp-escrow，docs/05-Agent凭据域.md §6）——**均已现成且按 vault_uuid 幂等**。清理归属 **AppModel 编排层**；Rust 侧只删文件族。恢复码 wrap 在 header.json 内，随目录删除自动清除。**残余**：FFI 删文件与 Keychain 双清间强退 → orphan Keychain 项 / 文件（无害，接受为已知限制，见 §4.4，UDR-2）。
- **C3 · forget_session**：删除前将目标库从 factory 注册表移除（切换/打开过的库可能留有**已锁定**会话对象）——防注册表残留、uuid 复用混乱。
- **C4 · lastVaultUUID 清键**：删除成功 → 若 UserDefaults `lastVaultUUID` 指向被删库则清除 → reloadVaultBriefs → 落位。
- **C5 · 当前库先锁旧 + 原子化**：删除当前库须先锁当前会话（防 WAL/SHM 半删）；建议 rename-then-delete（同盘 rename 原子，rename 成功 = 库即刻不可见，物理删除后台收尾）——提升「删除中退出」鲁棒性。
- **C6 · 许可门禁**：`delete_vault` 已归 `LicensedOp::VaultWrite`（license.rs 库级写组），调用侧过门禁；**只读许可用户隐藏/禁用「管理密码库…」入口 + 行内 `[删除…]`**（对齐 create_vault 拒绝口径，UDR-7）。
- **C7 · 测试**：core 单测（删除后目录消失 / 损坏目录跳过）、FFI 测试、UI 冒烟、Keychain 双清幂等回归、真机 E2E（AC-06：导出 → 删除 → 恢复 → 数据一致）、**独立判据「删除当前库后正确落位」**（先锁旧 + 多库最近库 / 单库 `.noVault`，一等公民，不留暗坑）、**库名确认 trim 比对（Swift UI 层，UDR-1）**、**删光全库无残留 sheet**（UDR-4）。
- **C8 · 导出前置步参数化（UDR-1，lead 六裁定 #5 / S-6 强调必落，非可选项）**：ExportView 增 `targetVaultDir` / `targetVaultName` 入参；向导导出步**全目标仅加密备份**（明文 CSV/1PUX 不在删除向导内提供，用户可事后解锁导出，UDR-3）；**导出面显式展示正在导出哪座库（库名 + masked UUID）**；factory 级 export_backup（api.rs）已支持任意 vault_dir，无需新增 FFI。r0.2 的 CLI delete-vault 契约（旧 C8）已按六裁定 #6 删除。**Step3 库名确认的 trim 比对为 Swift UI 层行为（UDR-1），不触本组 core 契约**；core 侧「库名允许首尾空格 / 无长度上限」经 **G-D 裁定（r0.5）** 补 create 校验（拒 `name != name.trim()` + `len > 128`，仅约束 create、不影响既有库打开），详见附 C。

### UDR-1 HIGH —— 输入库名逐字符确认的空白/长度死结（长库名必查点）

- **证据**：core/cf-session/src/unlock.rs `create_vault` 仅以 `name.trim().is_empty()` 拒绝全空白名——**含首尾空格的库名合法、无长度上限**。Step3 逐字符精确匹配对「 我的密码库 」这类名近乎不可达 → 确认永不过 → 该库删不掉 = FW-04 式死路换形式回归（正冲本文根治目标）。
- **处置**：①**比对前双方 trim**（输入与库名各 trim 后比较；库名语义不含首尾空白，无损）——必改；②建议建库侧补「禁首尾空白 / 长度上限」校验（对齐 `InvalidArgument` 拒绝口径）——可选；③超长库名给「复制名称」辅助或明示逐字要求——可选。
- **状态**：改动在 Swift 侧确认步 + cf-session 建库校验，不触 C1~C8 core 契约。

### UDR-2 MEDIUM —— 「忘密废库无死路」表述与附 C 可达性边界未对齐

- **证据**：§3.4「主密码门会把它堵死 = FW-04 同类死路换形式回归」与 §3.6「无死路」在附 C 已登记的「纯锁定态 GUI 无可达删除入口」下**不成立**：单库忘密锁定用户 App 内无法删除（无设置、非 `.noVault`），只能恢复码 / 重装走 restore。六裁定 #3「锁定态可删」的 GUI 兑现面 = 有另一库解锁 或 `.noVault`。
- **处置**：二选一——(a) LockView 补工厂级「管理密码库…」入口（全额兑现六裁定 #3，与 restore 同构语义一致）；或 (b) 收敛 §3.4/§3.6 为「可达即无死路」并维持附 C 边界。倾向 (b) 先低成本收口，LockView 入口归 lead 裁定。

### UDR-3 MEDIUM —— 向导导出步「限定加密 tab」与「CSV/1PUX 提示需解锁」双读歧义

- **证据**：C8 与 §3.1.5 明确「限定加密 tab」；§4.3 Step2 文案「plaintext tab 对非当前/锁定库提示『需先解锁该库才能导出此格式』」与 §4.5 Step2 线框「（非当前/锁定库仅此 tab；CSV/1PUX 提示需解锁）」**暗示当前库（解锁态）目标时 plaintext 可在向导内导出**——与「向导仅加密」矛盾，实现者无所适从。
- **处置**：统一「向导导出步**仅加密备份 tab（全目标一致）**；plaintext 走切换后库内导出」（§6.2 已登记此边界）——删「非当前/锁定库仅此 tab」条件句式。

### UDR-4 MEDIUM —— 删光全库后 VaultManagementView sheet 生命周期未定义

- **证据**：删当前库（单库）→ 落 `.noVault`；设置「管理密码库…」/ 深链弹出的 VaultManagementView sheet 后续行为（自动关？留在删光的空管理列表？）未指定。附 A「sheet 出口」仅覆盖「显式出口 + Esc」，未覆盖「落位导致 sheet 失联」。
- **处置**：§4.1 补「删除成功后关闭确认 sheet；落 `.noVault`/切库时管理面一并关闭，下次进入重载列表」；真机核销加「删光全库无残留 sheet/卡死」。

### UDR-5 LOW —— 「唯一身份门」措辞过载

- 输入库名确认是**防误触/防错目标**门（库名在管理列表与 Step1 均可见、读屏者可复制），非身份门。§3.4 理由重构本身已正确（UX 门非认证），仅 §3.3 表格标签「唯一身份门」过载 → 改「确认门（防误触/防错目标）」。

### UDR-6 LOW —— 库切换 sheet 深链的呈现方式未定义

- 库切换 sheet 底部「管理密码库…」若 sheet 内再弹 VaultManagementView（SwiftUI sheet-on-sheet 层级限制），建议「先关切换 sheet → 从主窗弹管理面」；实现细节，登记提示。

### UDR-7 LOW —— 同名库的 Step3 心疑

- `create_vault` 无库名唯一约束，多库可同名；Step1 已用 UUID 消歧（目标固定），功能无误。建议 Step3 提示保留已选目标 UUID 尾显（「正在确认删除：『名称』（UUID…）」），防用户输对名字却疑删错目标。

### UDR-1 HIGH —— 「导出前置复用 ExportView（预选本库）」不成立；naive 复用会导出当前库而非待删库

- **证据**：`ExportView.swift` 仅 `@EnvironmentObject model`，无任何目标库参数；导出走 `model.vaultDirPath`（AppModel，注释明示该值即当前库目录）+ `model.vaultName`（建议文件名）；加密/CSV/1PUX 三 tab 全部硬编码当前库。并行方案删除入口只对**非当前库**开放——照「复用不新建」实现，① 步导出的将是**当前库**，用户误以为已备份待删库、随后永久删除目标库 = **假备份保障下的数据丢失**。
- **能力面澄清**：FFI `export_backup(vault_dir:, out_path:)`（core/cf-ffi/src/api.rs）是工厂级、收任意 vault_dir、锁定态可用（TC-EXP-08），导出**目标**库在能力上可行——缺的只是 ExportView 的「目标库」参数化，并非零改造。
- **r0.3 处置**（并入主本体）：C8 导出前置步参数化（targetVaultDir/targetVaultName + 限定加密 tab + 显式展示目标库），对非当前/锁定库开放（S-6 必落）——见 §4.1/§4.5/§5 C8。

### UDR-2 MEDIUM —— 「强退 → 下次启动自动收敛」无支撑机制

- **证据**：清理顺序「FFI delete（含 forget）→ Keychain×2 → lastVaultUUID」非原子；App 在 FFI 删文件后、Keychain×2 前强退 → 残留 orphan Keychain 项。`AppModel.swift` / `Platform/` 全量 grep 无 orphan 清扫/reconcile 逻辑——「强退 → 下次启动自动收敛」**无实现依据**；Rust 侧无法触 Keychain，不存在真原子事务。
- **r0.3 处置**（并入主本体）：删「自动收敛」表述，登记为**已知限制**（orphan K_bio/escrow 密文对已删库无泄露面、无害，仅数据卫生；低成本，倾向此方案）——§4.4 / §6.2；真清扫（启动期差集）归 backlog。

### UDR-3 MEDIUM（裁定记录）—— 破坏性确认取舍：维持「输入库名确认」，否决主密码验证

- **并行方案裁定**：设计 §3.3 的「输入库名逐字符精确匹配」为足够强确认，**不引入主密码验证**。理由：① 解锁态攻击者已具全量读写（ExportView CSV 明文导出、条目软删/硬删、改主密码），拒绝删库不降其实际破坏面；② 主密码验证会破坏「锁定态可删 / 工厂级 / 不触碰密钥材料 / 与 restore 同构」的前提，并制造第 5 处主密码确认面；③ 行业惯例（GitHub / Apple / 1Password 删除 = 输入名称确认）。
- **r0.3 覆盖**（editor 注）：**lead 六裁定 #2 正式采纳 UDR-3**——仅输入库名逐字符确认、无任何密码步；理由重构见 §3.4（深层支柱：删除「当前库结构性不可删」后，解锁态攻击者本具全量破坏力 + 锁定态攻击者有 FS 访问权，UI 验证不构成安全边界；忘密废库清理无死路）。
