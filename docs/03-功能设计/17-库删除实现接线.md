## §1 结论总览

- **core 只加两个函数**：cf-session `delete_vault`（文件族物理删除，**三步链**：rename → remove_file(header.json) → remove_dir_all，§2.1）+ cf-ffi `CofferApp::delete_vault`（许可门禁 + uuid 校验 + 会话注册表 lock+forget + 委托）。**不新增 `forget_session` 独立 FFI**——C3「forget_session」并入 `delete_vault` 内部实现（见 §2.3，偏差与理由）。错误面复用既有码位（5002 / 5001 / 6002 / 6003），无新错误码、无错误码表改动。
- **AppModel 编排单点收敛**：新增 `deleteVault(uuid:) async -> Result<DeleteVaultLanding, Error>`。删当前库 = 先锁旧 → FFI delete（内含 forget）→ Keychain 双清 → lastVaultUUID 清键 → reload → 落位（多库切 createdAt 最近者锁定态 / 单库 `.noVault`）；删非当前库 = **会话不变** → FFI delete → Keychain 双清 → reload 列表刷新 + 反馈（**不做落位**，lead 裁定，§3.3）。
- **Swift 新增 2 个视图文件**（VaultManagementView / DeleteVaultConfirmSheet），**改动 5 个既有文件**（SettingsView / VaultSwitcherView / LockView / ExportView / AppModel）；MainView 与 RestoreBackupView 不动。
- **并行 = 2 轨**：Track A（Rust，串行 A1→A2）与 Track B（Swift，B1 串行头 → C1~C6 并行尾），**两轨零文件交集**；Swift 组内 C1/C2（新视图）先落，C3/C4/C5（入口接线）后接。
- **5 项设计对齐冲突**（F1~F5，§6）：F1（docs/16 C1 路径写错 `vaults/` 子目录）裁定改文档；F2（LockView「忘记主密码？」与既有 RecoveryResetSheet 入口撞名）**已裁定 r0.1.3：独立低存在感链接「管理密码库…」，二选 sheet 否决**；F4（core 库名校验收紧）建议本轮并入但**只收紧建库写侧、读侧严禁加校验**。
- **无不可逆存储决策**：本功能不涉存储格式、无数据迁移。唯一接近不可逆的是 `delete_vault` FFI 签名与错误面（一经 v2.10.0 发版即冻结给 Swift 绑定）——但它完整对齐 `create_vault` 既有惯例，风险低，实现前经 lead 确认签名即可（§2.1）。

## §2 core 接线（C1/C3/C5 落点）

### 2.1 delete_vault 落点与签名（近不可逆 API，发版前冻结）

**cf-session 层**（core/cf-session/src/unlock.rs，紧邻 `create_vault` / `open_vault`）：

```rust
pub fn delete_vault(base_dir: &Path, vault_uuid: &str) -> SessionResult<()>
```

- **uuid 校验**：`uuid::Uuid::parse_str`，非法 → `CfError::InvalidArgument`（码 5002）——逐字镜像 `open_vault` 既有防路径拼接逃逸先例（core/cf-ffi/src/api.rs `CofferApp::open_vault`）。
- **目录解析**：`vault_dir = base_dir.join(uuid.to_string())`（注意：**无 `vaults/` 中间子目录**，见 F1）。文件族范围 = 该整目录：`header.json` / `db.sqlite` / `db.sqlite-wal` / `db.sqlite-shm`（运行时）/ `attachments/**` / `thumbnails/**` / 可选 `MANIFEST.json`（与 cf-exporter/src/backup.rs `collect_vault_files` 枚举一致）。
- **目录不存在 → `Ok(())`（幂等）**：对齐「list_vaults 对损坏/缺失目录跳过」韧性，且删一半重试语义友好（§2.2 决策记录）。
- **三步链（C5，lead 裁定 + core coder 实测修正）**：① `fs::rename(vault_dir, tombstone)`（tombstone = base_dir 内 `.coffer-deleted-<uuid>-<epoch>`）→ ② `fs::remove_file(tombstone/header.json)`（**header 在库目录根部，rename 连它一起进 tombstone——单靠 rename 不构成对 list_vaults 不可见**，open_container(tombstone) 会成功 → 幽灵库被枚举；故必须显式移除 header）→ ③ `fs::remove_dir_all(tombstone)` 物理收尾。**不变式**：header 一旦移除，tombstone 对 list_vaults 必不可见（open_container 读 header.json 必败，`CofferApp::list_vaults` 零改动）。② 对本来无 header 的孤儿目录 remove_file 报 NotFound → 视为 no-op（与目录不存在幂等一致）。①/②/③ 任一失败 → 报错可重试，重试收敛；仅 ① 成功而 ② 失败时 tombstone 仍可能被枚举（幽灵），重试 ②③ 收敛（§6.3）。
- **不做 header 解析**：删除按 uuid 路径直删，不读 header——不产生 1005 路径，也与「孤儿库/忘密库无密码即可删」语义一致。

**cf-ffi 层**（core/cf-ffi/src/api.rs，`CofferApp` 工厂，紧邻 `create_vault`）：

```rust
pub fn delete_vault(&self, base_dir: String, vault_uuid: String) -> Result<(), FfiError>
```

执行序列：
1. `self.license_check(LicensedOp::VaultWrite)?`——与 `create_vault` 同门禁同组（license.rs `LicensedOp::VaultWrite` 已列 delete_vault，TC-GATE-12 结构性保证）；
2. uuid 校验（非法 → 5002，复用 `open_vault` 先例）；
3. `self.sessions_lock().remove(&key)` 命中 → `session.inner.lock()`（**防御性锁定，幂等**，防「Swift 侧漏锁导致在打开连接上删库致 WAL/SHM 半删」，C5；`lock_all` 同型调用先例，core/cf-ffi/src/api.rs `CofferApp::lock_all`）→ drop；
4. `session_call(AssertUnwindSafe(|| cf_session::delete_vault(Path::new(&base_dir), &key)))`。

### 2.2 错误面（复用既有码位，零错误码表改动）

| 场景 | 码 | 依据 |
|---|---|---|
| uuid 非法（路径拼接逃逸） | 5002 InvalidArgument | 镜像 `open_vault`；cf-ffi/src/error.rs 冻结测试 |
| 目录不存在 | **Ok（幂等）** | 决策：对齐 list_vaults 韧性；删除天然幂等，第二次删同库不报错 |
| 文件族删除 I/O 失败 / 部分删除 | 5001 Io | 透传 `CfError::Io`；UI 侧「部分文件已删除，请重试或检查权限」 |
| 只读许可拒绝 | 6002 / 6003 | `license_check` 既有映射（`CfError::LicenseTrialExpiredWriteDenied` / `LicenseStateWriteDenied`） |
| panic 兜底 | 5999 | `session_call` 既有 |

**决策记录（备选对比）**：目录不存在返回 `VaultNotFound`（1003）——备选，UI 层可显式提示「库不存在」；但删除是幂等操作、向导只对 list_vaults 呈现的真实库放行，1003 在「删一半重试」路径反而制造噪音。**取幂等 Ok**。此项可逆，实现时可再议。

### 2.3 C3「forget_session」并入 delete_vault（设计偏差，需 lead 知悉）

- 设计 docs/16 C3 将 forget_session 列为独立契约项。**实读结论**：会话注册表是 cf-ffi `CofferApp.sessions`（Mutex<HashMap<uuid, Arc<VaultSession>>>，core/cf-ffi/src/api.rs 结构体字段），属 cf-ffi 内部状态，cf-session 层不存在该注册表——「forget」只能在 cf-ffi 内做。
- **裁定**：不新增独立 `forget_session` FFI，在 `delete_vault` 步骤 3 内联完成「lock + remove + drop」。理由：① 注册表 remove 是 CofferApp 自有状态，delete_vault 天然有权限做；② 少一个 FFI 面 = 少一套 Swift 绑定 + 单测；③ AppModel 编排序列相应简化为「锁旧 → FFI delete → Keychain 双清 → …」（见 §3），team-lead 消息中的「session forget」步由 FFI delete 内部消化。**若 lead 坚持独立 FFI（如未来需「忘库但不删文件」场景），加一个 `forget_session(vault_uuid:)` 三行即可，不构成返工**——登记为待 lead 知悉的偏差。

## §3 AppModel 编排（C2/C4/C5 落位）

### 3.1 新增 API（macos/Coffer/AppModel.swift）

```swift
enum DeleteVaultLanding: Equatable {
    case switchedToMostRecent(FfiVaultBrief)   // 删当前库·多库：切 createdAt 最近者，锁定态
    case noVault                               // 删当前库·单库：空库首屏（VaultSetupView）
    case sessionUnchanged                      // 删非当前库：会话不变 + 列表刷新 + 反馈（lead 裁定，§3.3）
}

func deleteVault(uuid: String) async -> Result<DeleteVaultLanding, Error>
```

### 3.2 删当前库流程（C5 先锁旧 + 落位）

1. `guard !isBusy`，置 isBusy（防并发删/切/建）；
2. `isCurrent = (uuid == vaultUUID)`；
3. 若 isCurrent：`lock()`（锁 Rust 会话 + 清 items/currentDetails/剪贴板 + phase → .locked，AppModel `lock()` 既有语义）；
4. `Task.detached`：`factory.deleteVault(baseDir:, vaultUuid: uuid)`（内含 registry lock+forget + 文件删除）；
5. 成功 → **Keychain 双清**（C2，归属 AppModel）：`BiometricKeychain().delete(vaultUUID: uuid)` + `McpEscrowKeychain().delete(vaultUUID: uuid)`——**best-effort**（catch → DiagLog，orphan Keychain 无害为已登记接受残余，docs/16 §4.4/§6.2）；
6. isCurrent → `session = nil; vaultUUID = ""; vaultName = ""; lockBackoffDeadline = nil`；
7. `UserDefaults.lastVaultUUID == uuid` → remove（C4）；
8. `reloadVaultBriefs()`；
9. 落位（纯函数可测）：`remaining = vaultBriefs.filter { $0.vaultUuid != uuid }`；`remaining.max(by createdAt)` → `openSession(brief)`（phase → .locked）返回 `.switchedToMostRecent`；空 → `phase = .noVault` 返回 `.noVault`。

### 3.3 删非当前库流程（lead 裁定 2026-10-13：落位仅对删当前库生效）

isCurrent 为 false：**跳过步骤 3**（单活跃不变量保证非当前会话恒锁定，且目标库可能从未 open 过——无会话可锁）；**跳过步骤 6**（当前会话状态不清零）；**跳过步骤 9 落位**。执行步骤 4 FFI delete（含 registry forget + 文件删除）→ 步骤 5 Keychain 双清（best-effort）→ 步骤 7 lastVaultUUID 清理（仅当 `lastVaultUUID == target`；常规下 lastVaultUUID 指向当前库，本路径不触发）→ 步骤 8 reloadVaultBriefs 刷新列表 → 返回 `.sessionUnchanged`（UI 仅给「已删除 + 列表已刷新」反馈）。

**不做落位**：当前会话不变（解锁态保持、不切库、不重建 session、不重写 lastVaultUUID）。依据 docs/16 §4.2 状态矩阵 + 判据 DL-6「删非当前库：会话不变 + 列表刷新 + 反馈」；最少意外原则。冲突反例（lead 裁定）：当前 A(2020) 删非当前 B(2021) 时 `.max(by createdAt)` 切到 C(2022) 属**无来由跳变**——即使 `remaining.max` 恰为当前库自身，切回也是无意义自切。故 §3.3 不再需要「openSession 防同库自切」补丁；该防御仅在 §3.2 步骤 9 保留为纯防御（删当前库时 remaining 恒不含目标 uuid，无自切可能）。

### 3.4 错误恢复语义

| 失败点 | 语义 | 呈现 |
|---|---|---|
| FFI delete 失败（5001 / 部分删除） | 确认流留驻可重试；已删部分 → tombstone 语义，重试收敛 | ffiErrorAlert（code+message 直出），wizard 留驻 |
| 删当前库失败（已先锁） | 用户处锁定态，可重解锁重试，无数据丢失（docs/16 §4.4） | settings 窗口已随 phase 离开 .unlocked 自关（F3），错误经主窗 LockView 的 ffiErrorAlert 呈现 |
| Keychain 双清失败 | 非致命：库已删，orphan Keychain 无害 | DiagLog，不弹错 |
| 任一环节取消 | 删除前无任何破坏性副作用 | 无变更 |

- **终版裁定（lead，r0.1.3；T4 已实现 6c3511b）**：LockView 新增**独立低存在感链接「管理密码库…」** → VaultManagementView；既有 `[忘记主密码？]` → RecoveryResetSheet **原样保留不动**。**「二选 sheet」方案正式否决**，理由：① 恢复主路径（RecoveryResetSheet）不应为删除副路径多垫一层选择；② 独立链接用不同标签已消除同名歧义，二选 sheet 的立论前提（双入口歧义）不再成立；③ 独立链接与设置页/切换器「管理密码库…」文案一致（单一口径）。
- 实现（coder 已落 6c3511b）：LockView 改动点 = 次级链接「管理密码库…」（低存在感，置于「忘记主密码？」同区相邻，含 UDR-7 只读隐藏）→ 主窗 sheet 弹 VaultManagementView；「忘记主密码？」入口语义不变（FR-17.1/17.2）。
- 锁定态深链弹 VaultManagementView 在主窗 sheet 呈现（LockView 为主窗 RootView 相内，phase 变化随拆树）：删当前锁定库 → 单库 `.noVault`（LockView 随拆树到 VaultSetupView）；多库 → 落位 `.locked`，管理面保持打开列表刷新（UDR-4）。

### 4.6 ExportView 参数化（macos/Coffer/Views/ExportView.swift，C8 必落）

- 新增 init 参数（默认 nil / false，现有调用点零改动）：`targetVaultDir: String?`、`targetVaultName: String?`、`targetVaultMaskedUUID: String?`、`encryptedOnly: Bool`。
- `encryptedOnly == true`：顶部三入口 Picker 隐藏/锁定为 `.encrypted`，CSV/1PUX 分支不可达（UDR-3 全目标仅加密备份）。
- `suggestedFileName()`：`targetVaultName ?? model.vaultName`（现硬编码 model.vaultName，ExportView.swift 同名函数）。
- `doExport`：`targetVaultDir ?? model.vaultDirPath`（现硬编码 model.vaultDirPath，ExportView.swift `doExport`——**UDR-1 隐患根因：naive 复用会导当前库而非待删库**，docs/16 附录 D UDR-1；本参数化根治）。

### 6.2 F4 评估：core 库名校验收紧（并入 vs 顺延）

- **现状缺陷**：`create_vault_with_kdf` 只拒全空白名——含首尾空格的库名合法、无长度上限（docs/16 附 C 登记）。Swift 侧 Step3 trim 比对（UDR-1）是**必改兜底**（文档判据，交付前必做）。
- **并入建议（推荐，低成本）**：建库写侧新增——`name != name.trim()` → 5002（禁首尾空白，语义无损，UDR-1 已证）；`name.trim().len() > 上限（建议 64 字符，与 UI lineLimit 展示协配）` → 5002。**只改写侧 create_vault**。
- **兼容红线（必须遵守）**：① **读侧（open_container / validate_header / list_vaults / open_vault）严禁加任何 display_name 校验**——既有含首尾空格/超长库名必须照常打开，否则「既有合法库打不开」回归（docs/16 §6.1「不得让既有合法库打不开」）；② 长度上限只拦新建，不迁移既有；③ cf-format `validate_header` 是否已对 display_name 有约束需 A1 实现时先核对（未发现即不动）。若实现时发现 validate_header 读侧有长度隐含约束，**放弃收紧、登记顺延**（Swift trim 兜底已足够，本项为可选硬化）。
- **备选**：本轮不动 core，仅 Swift trim 兜底，core 收紧顺延 v2.11.0。**推荐并入**——因为删库向导 Step3 的 trim 比对是硬需求，若核心不收紧，「 我的密码库 」这类库删除确认仍靠 trim 才可达，核心校验缺失会让创建侧继续产生此类名，属同一缺陷两面。
