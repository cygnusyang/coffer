## 0. 一句话结论与待确认

**结论**：用系统原生 .lproj 做语言匹配，用**中文原文当 key**，只发 en.lproj；中文侧零改动、缺键自动回落中文，因此 666 处字面量 Text 一行不改，现有断言中文的测试全部保持绿。真正的成本不在改代码，在**写约 660 条英文译文**和**172 处非字面量 Text 的人工分诊**。

**需用户确认（§10，逐条给了选项与影响）**：D-6 中文原文当 key ｜ D-7 资源布局（只 en、不声明 CFBundleLocalizations、保留 CFBundleDevelopmentRegion=zh_CN）｜ D-8 strings 源分片布局 ｜ D-9 语言偏好存储形态 ｜ D-10 错误文案口径由「码 + 原始 message」改为「码优先，载荷降为日志」。

### 1.2 不改什么（明确非目标，防范围蔓延）

- **不引第三方依赖**：抽取/校验脚本用 bash + python3 标准库 + plutil（均为系统自带或仓内既有能力）。
- **不改 Rust 核心**：不新增 lang 参数、不改 FfiError 契约、不做核心内 i18n（§7.2 方案 B 被否）。
- **不改符号 key 体系**：不把 666 处 Text("中文") 改成 Text("settings.title")（§10 D-6）。
- **不建 zh-Hans.lproj**：中文由 key 回落承担（§4.2）。
- **不翻 Help Center 长文**（3487 字，Views/HelpCenterContent.swift）：v2.13.0 明确不翻，英文界面加一行说明（§5.7）。
- **不翻 CLI / MCP 协议输出**：cf-mcp 的 stdout 是协议面与脚本面，不属本次 UI 范围。
- **不做一键重启**：沙盒内启动自身被实证不可靠（§6.6），v2.13.0 只提示手动重启。
- **不做单位/日期本地化**：只翻文案，不引入 formatted() 改造，登记为后续项。

### 1.3 最大风险三条

1. **静默失败**：占位符写错（%d vs %lld、漏占位符、多占位符）**不崩不报**，只是显示错值/丢值 [实测]。→ 必须做构建期占位符校验（§4.5 G3），这是本设计里唯一「不做就等于没做」的门禁。
2. **文案与数据混淆**：把用户数据（库名、条目名、文件名）当文案翻，会造成**数据被改写**；把文案当数据，则永久不翻。→ §5.5 分界规则 + §5.4 统一入口。
3. **覆盖率幻觉**：Text 字面量自动生效 ≠ 英文界面干净。真正的验收是 **AX 抓取 5 个核心面文本后扫 CJK**（§9 L10N-02），不是数 .strings 条数。

## 3. 已确立的技术事实

> 前 8 条来自上游调研 [实测]；F9–F11 为本设计阶段新增实测（/tmp/l10n-lab/L3，同一套 swiftc + 手写 Info.plist + ad-hoc 签名的手工 bundle，与 Coffer 构建方式一致）；F12 为仓内既有实证。

| # | 事实 | 证据 | 设计含义 |
| --- | --- | --- | --- |
| F1 | Contents/Resources/*.lproj/Localizable.strings 即可被 Bundle.main 解析，**不需要** Xcode 工程、**不需要**改 Info.plist | 玩具 bundle 基线：localizations=[en, zh-Hans]，lookup[hello]=你好 | 不必为 i18n 引入 Xcode 或 plist 声明 |
| F2 | 所选语言**缺 key 时回落到 key 本身**，不跨 .lproj 借别的语言的译文 | lookup[only_en]=<MISS>（系统语言 zh，key 只在 en 里有） | **中文原文当 key 的技术前提**；也意味着「键级 zh→en 回落」不存在（§6.5） |
| F3 | CFBundleDevelopmentRegion 会被无条件注入 bundle 本地化列表，并决定「用户语言不在支持列表」时回退到谁 | 删掉该键后 ja 用户 preferred 变 en；保留时拿到 zh-Hans（V10） | **必须保留 zh_CN**，否则日语法语用户落到英文而非中文，违背「中文优先」 |
| F4 | CFBundleLocalizations 与 .lproj 同时声明 → 本地化列表出现**重复项**（[en,en,zh-Hans,zh-Hans]） | V7 | **不声明**该键（只在「没有 .lproj 也要声明语言」时才需要） |
| F5 | 签名后再加资源 → codesign --verify --strict 由 exit 0 变 "a sealed resource is missing or invalid" | V12 | 拷贝必须插在签名之前（build_macos_app.sh:150-166 区间） |
| F6 | Text("中文字面量") 查 Localizable 表；Text(verbatim:)、Text(String)、Text(AttributedString) **不查**；Button / Label / Toggle / .alert / .navigationTitle / .help(字面量) 同 Text | 渲染宽度指纹（verbatim 42pt vs 命中 26pt） | 322 处字面量 Text + 其余 6 类 API 零改动；183 处非字面量必须人工处理 |
| F7 | 插值键形态（2026-10-24 实测修正）：Int/Int64 → %lld、Int32 → %d、UInt32/UInt16 → %u、UInt64 → %llu、String → %@、Double → %lf；源码字面量里的 % 在键里转义成 %% | String(localized:) 打印键：计数 %lld 项 等 | 75 处插值文案的键必须按规则推导，不能照抄原文 |
| F8 | 占位符写错的三种形态**全部静默**：%d 侥幸显示 3（UB）、漏占位符静默丢值、多占位符填垃圾值，均不崩 | 渲染实测表 | 必须构建期静态校验（§4.5 G3） |
| F9 | 向**App 自己的偏好域**写 AppleLanguages 后，**下一个进程**立即按该值解析（无需重装、无需重启系统） | CFPreferencesSetAppValue 后新进程 preferred=[en] lookup=HELLO_EN；清除后回到 zh-Hans | 这是「App 内手动覆盖」的落地机制，也是 macOS 13+「系统设置 → 应用程序」语言项同一底层 |
| F10 | **当前进程内不生效**：写入后同进程与新建的 Bundle(path:) 实例仍按旧语言解析 | 同进程内 after live set: preferred=[zh-Hans] lookup=你好；fresh Bundle 同 | 「需重启」不是懒惰，是系统缓存行为；必须如实告知用户（§6.3） |
| F11 | 读偏好**不能**用 UserDefaults.standard.object(forKey:"AppleLanguages")：无 app 域值时它会读到**全局域**的系统语言，无法区分「用户显式选了中文」与「跟随系统」 | 无 app 域值时 UserDefaults.standard 与 CFPreferencesCopyAppValue 都返回 zh-Hans-CN，而 persistentDomain(forName:) 返回 nil | 判定「是否被显式设置」只能读 persistentDomain；写用 CFPreferencesSetAppValue + CFPreferencesAppSynchronize |
| F12 | 沙盒 App 内 NSWorkspace.openApplication 启动辅助程序被实证为**静默 no-op**（回调 error=nil 假成功） | Updater/OTAInstaller.swift:272-283（BUG-29 真机全链路） | 不做「切换后自动重启」；只提示手动重启（§6.6） |

**待验证（[推断]，实现期必须复核）**：系统设置「语言与地区 → 应用程序」列表对我们这种「只有 en.lproj + CFBundleDevelopmentRegion=zh_CN」的 bundle 是否展示两项且去重；沙盒容器内 CFPreferencesSetAppValue 写自身域是否有额外限制（玩具 bundle 未沙盒）；真实 Coffer.app 加 .lproj 后 codesign --verify --strict 的端到端（本机当前无可用 codesigning 身份）。

## 4. 资源布局与构建装配

### 4.1 目录树

**源（入库）**：

~~~text
macos/Coffer/Resources/

  Localization/
    en/
      00-common.strings     # 跨组复用条目（约 17 条：回收站/设置/保存/彻底删除/历史版本/安全体检/导入…）
      10-ui-a.strings       # impl-ui-a 独占
      20-ui-b.strings       # impl-ui-b 独占
      30-support.strings    # impl-support 独占（Support/Platform/Updater/Dropzone/AppModel/CofferApp）
      40-errors.strings     # impl-support 独占（25 错误码文案）
    InfoPlist.strings       # 权限提示文案（en）
~~~

**产物（构建生成，不入库）**：

~~~text
Coffer.app/Contents/Resources/
  en.lproj/Localizable.strings   # 由 5 个分片按文件名序 cat 合并
  en.lproj/InfoPlist.strings     # 直接拷贝
  Coffer.icns
~~~

### 4.2 只建 en.lproj（不建 zh-Hans.lproj）

| 项 | 方案 A：只 en（**推荐**） | 方案 B：zh + en 双语都建 |
| --- | --- | --- |
| 中文来源 | key 本身（源码原文） | zh-Hans.lproj 的 503 条 |
| 中文侧回归风险 | **零**（永远等于源码，不可能漏条、不可能与源码漂移） | 漏一条 → 该条回落 key（仍中文，无害）；但两份文案会漂移（改了源码没改 zh） |
| 维护成本 | 503 条 × 1 语言 | 503 条 × 2 语言 + 每次中文改动双写 |
| 「键存在性」校验 | 只需 en 一侧 | 两侧都要，且要交叉校验 |
| 键分叉（同一中文两义） | 分叉键的中文侧自动正确（就是源码那串） | 分叉键须在 zh 里再补一条 |
| 未来中文改词 | 改源码即生效（一次 sed） | 改 zh.strings，源码不动（优点是文案与代码解耦） |
| 结论 | **采用** | 仅在「中文文案要脱离源码单独维护」时才需要；当前 503 条全在源码里，不成立 |

> 注意：不建 zh-Hans.lproj **不影响**系统语言列表里出现中文——CFBundleDevelopmentRegion=zh_CN 会被注入（F3），列表是 [en, zh_CN]，中文项命中的是「无 .lproj → 回落 key → 中文原文」，行为正确。

### 4.3 为什么译文源要分片

Localizable.strings 是**单一表**（SwiftUI Text 没有指定 table 的入口 [实测：非 Localizable 表回落 key]），所以产物必须是一个文件。但**源**若也只有一个文件，四个实现组会写同一个文件 → 文件级冲突，与「组间文件范围互斥」直接矛盾，也让「可并行」成为纸面承诺。

分片 + 构建期合并解决这个问题：

- 每组只写自己的分片，**源文件级互斥**成立；
- 合并时检测**跨分片重复键**：两个组独立翻了同一条中文且译文不同 → 构建直接失败并报「key 已定义于 X」，这是特性不是噪音（§5 的冲突规避靠它兜底）；
- 合并顺序固定（文件名序），产物可复现。

00-common.strings 的存在是为了让复用条目（17 条）有唯一归属，减少跨片重复。

### 4.4 构建装配点

插入位置：tools/build_macos_app.sh 的 **step 3/4 组装 bundle**，在 cp Coffer.icns（第 161-163 行）之后、写 PkgInfo（164 行）之前，**在 step 3.5 签名之前**（F5 硬约束）。

### 4.5 门禁（tools/check_l10n.sh）

硬门禁失败即 exit 1，构建中止；软报只输出清单，不阻断（渐进翻译）。

| ID | 检查 | 硬/软 | 失败后果（不做会怎样） |
| --- | --- | --- | --- |
| G1 | 每个分片存在且 plutil -lint 通过；合并后文件非空 | 硬 | 语法错的 .strings 整表静默失效（所有 key 回落中文，英文界面全中文且无报错） |
| G2 | 跨分片**无重复键**（同键同值也报，强制归一到 00-common） | 硬 | 后写覆盖先写，两组译文互相踩 |
| G3 | 每条 "key" = "value" 的 printf 占位符**数量与顺序一致**；键侧类型可判定时类型也要一致 | 硬 | F8 三种静默错误直接进用户界面 |
| G4 | en/InfoPlist.strings 存在且 lint 通过；含 NSCameraUsageDescription | 硬 | 英文用户看到中文权限弹窗（系统弹窗无法回落） |
| G5 | 已声明键（tools/l10n_keys_allow.txt）必须能在源码中找到出处，否则报「死键」 | 硬 | 死键堆积，无人敢删 |
| G6 | 源码字面量 key（启发式抽取）与 en 键集 diff → 「未翻译清单」+ 覆盖率数字 | 软 | 无法量化进度；但启发式有假阳性，不能当门禁 |
| G7 | 输出分片归属统计（每个分片条数） | 软 | 无（用于工作量可见） |

**G6 的诚实边界**：源侧键抽取靠正则 + 插值类型推断（\(n) 是 Int 还是 String 需看表达式），**必然有假阳性**（多行字符串、嵌套括号、计算属性）。因此 G6 只报数不进硬门禁；真正卡住英文界面质量的是 §9 L10N-02 的 AX 扫描（运行时真相，不依赖静态推断）。占位符校验（G3）完全基于 .strings 自身，**零假阳性**，所以可以硬。

### 4.6 格式规范

- 编码 UTF-8 **无 BOM**（实测 UTF-8 正常，不需要 UTF-16）。
- 每条一行："键" = "值";；键/值内的双引号转义为 \"，换行转义为 \n。
- 分片可用 /* 段注释 */ 分组（按钮 / 空态 / 错误 / 表头）；注释不参与去重。
- 不排序：每组在自己的文件尾部追加，避免无意义 diff；同组分片内允许按功能聚簇。

## 5. 文案抽取策略

### 5.1 key 的五种形态

| 形态 | 源码 | .strings 键 | 说明 |
| --- | --- | --- | --- |
| K1 普通 | Text("保存") | "保存" = "Save"; | 绝大多数（约 428 条） |
| K2 插值 · Int | Text("共 \(n) 条") | "共 %lld 条" = "%lld items"; | 75 处插值里最多的一类 |
| K3 插值 · String | Text("名称 \(name) 无效") | "名称 %@ 无效" = "Invalid name: %@"; | 英文可重排占位符位置，**不算失效** |
| K4 含字面 % | Text("已完成 100% 共 \(n) 项") | "已完成 100%% 共 %lld 项" = "100%% done (%lld items)"; | 只对**带插值**的键生效；纯 Text("完成率 100%") 的键就是原文 [实测] |
| K5 分叉 | 同一中文两种英文语义 | 第二处改源码为 Text("打开（文件）")，键随之 | 见 §5.3 |

**推导规则（给抽取脚本与人工）**：

1. 取源码字面量的原文，保留原有标点与空格（键必须与 Swift 生成的键逐字节相等）。
2. 每个插值**按声明类型**替换（**不得按 Int 猜**，2026-10-24 ui-b 实测 Swift 6.3.1 修正）：`Int` / `Int64` → `%lld`；`Int32` → `%d`；`UInt32` / `UInt16` → `%u`；`UInt64` → `%llu`；`String` 及所有非数值类型（枚举 rawValue、URL、UUID）→ `%@`；`Double` / `CGFloat` → `%lf`。类型无法判定时抽 `%?` 并**列入人工复核清单**（脚本输出 Top-N 文件）。**教训**：原稿写「UInt → %lld」是错的——20 条 UInt32/UInt64 键（导入条数、回收站计数、附件数、非 SHA-1 TOTP 位数）会静默回落中文，而 G3 只校验键↔值一致，抓不到。
3. 字面量内既有的 %，在**该条含插值**时转义为 %%；不含插值时原样。
4. 空字符串 "" 与纯符号（"·"、"…"）不入表（无法翻译且无信息）。
6. **码位类数字一律不用 Int 插值**（2026-10-24 support 实测）：`Int` 插值走本地化数字格式，`1005` 会显示 `1,005`、OSStatus `-34018` 会显示 `-34,018`。错误码 / OSStatus / 退出码 / errno 一律 `\(String(x))` → 键侧 `%@`。G3 只校验键↔值一致，抓不到这类错，只能靠口径。

5. 译文侧占位符**不得重排、不得增删**（与 G3 的「数量与顺序一致」保持一致；此条 2026-10-24 冻结——原稿写「可任意重排」与门禁互斥。若将来确需重排，只能用位置参数 `%1$@` 形态并同步改 G3）。

**已批准的分叉写法（2026-10-24）**：同一中文在不同语境需要不同英文时，用
`String(localized: "登录（类别）", defaultValue: "登录")` —— 键分叉、中文侧仍显示「登录」、英文侧 `Login`。
优先于「改源码中文加限定语」，因为后者会破 AC-L10N-05（中文逐字不回归）。


**字段名落库口径（2026-10-24 裁定）**：`ItemTemplates.fields(for:)` 在**新建条目时按当前语言**生成字段显示名并写进草稿/落库；`designation`（username / password / notesPlain / cc-number…）才是语义锚点，**严禁翻译**。因此英文界面新建的条目字段名是英文，存量中文条目不受影响；切换语言不回溯已落库字段名。这是显式接受的行为变化（与 1Password 同类行为），不属于缺陷。
### 5.2 例外清单制度

tools/l10n_exceptions.txt（入库，行格式：文件:模式 # 理由）—— 三类必须登记：

| 类别 | 例子 | 处理 |
| --- | --- | --- |
| 用户数据（永不翻译） | Text(meta.filename)、Text(brief.displayName)（库名）、Text(failure.itemTitle)（导入条目名）、Text(verbatim: brief.vaultUuid) | 保持 verbatim，登记「数据」 |
| 非语言内容 | 版本号、路径、命令串、TOTP 位数/周期数字 | 保持 verbatim |
| 已知不翻（v2.13.0 范围外） | HelpCenterContent 长文 | 登记后 G6 报表不再计为缺口 |

例外清单是 **G5 死键校验的对偶**：没有它，G6 的「未翻译清单」会永远混着不可翻项，报表失去意义。

### 5.3 冲突规避（同一中文、不同英文）

规则：**优先分叉键，不改符号体系**。

1. 第一发现者保持原文（打开）。
2. 第二处改源码字面量为「原文 + 中文括号限定语」：打开（文件选择）、删除（永久）。限定语必须是人能读的中文短语，且**不得**引入英文、下划线或数字（保证回落时用户看到的是可读中文）。
3. 分叉同时在 l10n_exceptions.txt 登记理由（为什么不能共用）。
4. 分叉键两处都要人工核对英文：打开 = "Open"、打开（文件选择）= "Open File…"。

现状有利：503 条去重里跨 API 复用的 17 条（回收站 / 设置 / 保存 / 彻底删除 / 历史版本 / 安全体检 / 导入…）**语义全部一致**，暂无必然分叉项——但这是今天的快照，不是契约，制度要留。

同一中文、不同词性/大小写（句首 vs 按钮）：走分叉。保存 = "Save"，保存更改 = "Save Changes" 属不同串，天然不冲突。

### 5.4 非 Text 场景的统一入口

**总原则：本地化发生在 String 的产生点，不发生在使用点。** 一旦 String 已经拼好，任何 View 都救不回来（Text(String) 不查表 [实测]）。

| 场景 | 手段 | 归属层 | 备注 |
| --- | --- | --- | --- |
| 字面量 Text / Button / Label / Toggle / .alert / .navigationTitle / .help(字面量) / Window(标题) | **不动**（自动查表） | — | 666 处 |
| Text(<已本地化 String>) | 保持 Text(String) 或 Text(verbatim:) | View | 例：Text(errorMessage ?? "") 合规前提是 ErrorPresenter 已本地化 |
| Text(<未本地化拼接串>) | 重构为**带插值的字面量**：Text("已选择 \(n) 项") | View | 约 45 处，需逐条判语序 |
| Text(<动态 key>，key 运行时决定) | Text(LocalizedStringKey(keyVar)) [实测有效] | View | 少；须保证 keyVar 是稳定中文串 |
| Text(verbatim: <数据>) | 保持 + 登记例外 | View | 文件名 / 库名 / UUID |
> **字段名裁定（2026-10-24）**：`ItemTemplates.fields(for:)` 的 `name` 在**创建时**本地化并随草稿落库——英文界面新建的条目字段名是 `Username`/`Password`，一旦落库即为数据、不再随语言变化（存量中文条目不受影响）。理由：字段名同时是展示标签与落库值，拆「显示层 vs 持久化层」需要动条目 schema，超出 v2.13.0（UI 多语言）范围；`designation`（cardholder / cc-number 等）是持久化契约，**严禁翻译**。

| 纯函数返回展示串（MenuStatusText、PasswordStrength.label、ItemTemplates.displayName、McpStatus 状态词） | 返回值处 String(localized:)；调用方 Text(verbatim:) 或直接用于 NSMenuItem(title:) | Support | 关键：返回 String 的纯函数**在返回时**翻 |
| 拼接串（MenuStatusText.openTitle = "打开 " + statusLine） | 改单串 + 占位符：String(localized: "打开 %@")，参数传已本地化的 statusLine | Support | 英文语序需重排，不能靠 + |
| AppKit：NSMenuItem(title:)、NSSavePanel.message/prompt、NSOpenPanel.message | String(localized:) | Platform / View | F6 不覆盖 AppKit |
| 错误展示 | ErrorPresenter 统一出口（§7） | Support | D-12.3 单一来源不变 |
| NSAlert | **仓内 0 处**（grep 证实），不设规范 | — | 未来引入时走 String(localized:) |

**禁止**：自建 L10n.t(key:) 包装 Text——Text(L10n.t(...)) 会退化成 Text(String)，**反而丢失本地化**。只在 String 返回值场景用 String(localized:)，不新增抽象层。

### 5.4.1 `String(localized:)` 与插值（2026-10-24 实测裁定，取代早期误报）

**结论：`String(localized:)` 在缺键时会把插值代入，中文侧不露占位符。** 实测（swiftc 5 / macOS 27，无资源 + 空 `.strings` 两种上下文各跑一遍）：

```text
A: 长度 12 个字符      <- String(localized: "长度 \(n) 个字符")，缺键
B: 名称 甲 无效        <- String(localized: "名称 \(name) 无效")，缺键
C: 无插值常量
D: 模板 12             <- String(format: String(localized: "模板 %lld"), n)
E: 长度 12 个字符      <- NSLocalizedString 同样代入
```

早期一条报告称「缺键返回未格式化的键（显示 %u/%@）」，**本机两次复测不复现**；该现象对应的是 `NSLocalizedString` 被误当作 `String(localized:)`，或命中了一条占位符与调用点不一致的 `.strings` 条目（那是 G3 的职责）。

**规则**：
1. `String(localized:)` 直接带插值 —— **允许**，与 `Text(LocalizedStringKey)` 行为一致。
2. `String(format: String(localized: "模板 %lld"), v)` —— 同样**允许**（等价写法，已按此改的代码不必回退）。两种写法二选一即可，不强制统一。
3. 真正的风险不在写法，而在**键里的占位符类型与调用点类型不一致**（§4 规则 2）——那会静默显示错值，由 G3 卡。

### 5.4.2 装置边界：裸 CLI 二进制 vs 真 .app（2026-10-24 复现）

同一条 `String(localized: "缺键 \(n) 个")`：

| 执行上下文 | 缺键返回 |
| --- | --- |
| 裸 CLI 可执行文件（Bundle.main 无 .lproj） | **未格式化**：`缺键 %lld 个` |
| 真 .app（Contents/MacOS + Info.plist + en.lproj） | 已格式化：`缺键 12 个`（zh/en 一致） |

**对测试的影响（AC-L10N-10 按两档核对）**：
- 无插值键：裸二进制里键 == 原文，**断言应保持原样通过**；
- 带插值键：裸二进制里会吐 `%lld`/`%@`，若某断言变红，**先判断该文件是否编进了裸二进制**——那是装置问题，不是产品回归。
- 凡要验证插值结果，一律用 .app + `-AppleLanguages` 跑，或让被测函数走 `String(format:)` 便于断言。

### 5.5 文案 vs 数据分界

| 判据 | 结论 |
| --- | --- |
| 字符串来自用户输入 / 库文件 / 文件系统 / 导入源 | **数据**，永不翻译 |
| 字符串由 Swift 代码字面量产生、仅用于展示 | **文案**，必须翻译 |
| 枚举 → 展示名（FfiItemCategory.displayName、AuditEvent.displayName） | **文案**（不落库，纯派生） |
| 枚举 → 持久化值（rawValue、标签 coffer:environment） | **数据**，严禁翻译（翻了会破坏解析） |
| 拼接后的句子（"打开 " + name） | 骨架是**文案**、参数是**数据**，必须拆成占位符 |

落地检查：任何 String(localized:) 的参数不得把外部输入编进键（只有字面量里的插值骨架才是 key）。

## 6. 语言选择

### 6.1 模型

三态，值域与 AppleLanguages 对齐：

~~~swift
enum AppLanguage: String, CaseIterable {   // Support/LanguagePreference.swift
    case system            // "跟随系统" —— app 域无 AppleLanguages
    case zhHans = "zh-Hans"
    case en = "en"

    var displayName: String { get }        // 自身也需本地化："跟随系统"/"System"、"简体中文"/"Chinese, Simplified"
}

enum LanguagePreference {
    static var current: AppLanguage { get }              // 读 app 域（persistentDomain 判定）
    static var launchLanguage: AppLanguage { get }       // 进程启动时解析出的实际生效语言（快照常量）
    @discardableResult
    static func apply(_ language: AppLanguage) -> Bool   // 写入/移除 app 域；返回「是否需要重启才能生效」
}
~~~

### 6.2 存储：单源 = app 域 AppleLanguages

| 项 | 方案 A：直接用 app 域 AppleLanguages（**推荐**） | 方案 B：自建键 cofferLanguage + 启动时回写 AppleLanguages |
| --- | --- | --- |
| 与系统设置的关系 | 同一底层（macOS 13+「应用程序」语言项写的就是它），两处天然一致 | 两处会打架：系统设置写 AppleLanguages，我们写自己的键，谁赢需额外规则 |
| 状态数量 | 1（有值 / 无值） | 2（自建键 + AppleLanguages），可能出现「自建键=跟随系统 但 AppleLanguages=en」 |
| 读取正确性 | 需 persistentDomain(forName:) 才能区分「显式」与「全局」（F11） | 自建键判定简单 |
| 迁移成本 | 0 | 首启需迁移（把系统设置里已有的值读进来） |
| 结论 | **采用** | 否 |

写入用 CFPreferencesSetAppValue(_:value:appID:) + CFPreferencesAppSynchronize（F9 实测路径）；「跟随系统」= 写入 nil（移除该键）。

读取判定：

- UserDefaults.standard.persistentDomain(forName: Bundle.main.bundleIdentifier!)?["AppleLanguages"] 为 nil → .system；
- 数组首元素前缀 en → .en；zh 开头 → .zhHans；其它值 → 视为 .system（**不覆盖**用户在系统设置里选的第三语言，如 ja）。

> F11 的坑必须写进代码注释：用 UserDefaults.standard.object(forKey:) 会在无显式值时读到全局域，导致 Picker 永远显示「简体中文」而不是「跟随系统」。

### 6.3 生效时机

**下次启动生效**（F10：同进程内即使新建 Bundle 实例也不改解析结果）。

交互：Picker 变更后立即弹一次性提示（.alert 或行内提示条）：标题「需要重新启动」、正文「语言将在 Coffer 下次启动时生效。」、按钮「好」。**不静默生效**——静默会让用户以为切换失败。

### 6.4 入口位置

**设置 → ① 通用节，自动锁定行之后的第二行**：

~~~text

┌─────────────────────────────────────────┐
│ ⏱  自动锁定            [ 5 分钟      ▾ ] │
~~~

- Label：Label("语言", systemImage: "globe")（与现有 Label+systemImage 行形态一致）。

### 6.5 回退链的正确表述（对任务书的一处修正）

任务书写「回退链 zh-Hans → en → 开发语言」。**这在 CFBundle 里不存在键级跨语言回落**（F2：所选 .lproj 缺键直接回落 key，不去别的 .lproj 找）。真实机制是两层，本设计按真实机制表述：

| 层 | 顺序 | 本仓落点 |
| --- | --- | --- |
| L1 语言级（选哪个 .lproj） | 用户偏好（app 域 > 全局域）→ 与 bundle 本地化列表匹配（精确 en / zh-Hans，再退化前缀）→ CFBundleDevelopmentRegion（zh_CN）→ 列表首个 | 中文用户 → 无 zh lproj → 落 key（中文）；英文用户 → en.lproj；日语法语用户 → dev region → key（中文） |
| L2 键级（该语言里这条有没有） | 有 → 译文；无 → **key 本身**（中文原文） | 英文漏翻 → 显示中文；中文永远显示中文 |

即：产品语义上的「中文优先、英文次之、最后中文兜底」成立，但**不是**「英文缺了就退到另一个语言文件」，而是「英文缺了就露出中文原文」。任何实现都不要写「查 en 失败再查 zh」的逻辑——那是多余且错的行为。

### 6.6 不做一键重启（附条件）

沙盒内 NSWorkspace.openApplication 已被实证静默失败（F12）。可行的替代（/usr/bin/open -n <自身>）会**先起第二个实例再杀第一个**，带来状态栏双图标、钥匙串并发、相位重入等风险，收益不抵成本。

v2.13.0：只提示手动重启。登记 **P-19.2**：一键重启（复用 CofferUpdater.app 的 relaunch 通道或新增最小 helper），触发条件 = 用户反馈「切换太麻烦」。

## 7. Rust 错误码 → 用户文案

### 7.1 现状（证据链，结论：**中英混排直出 UI**）

1. core/cf-domain/src/error.rs:56-175：25 个变体的 Display **全是英文**（vault is locked / corrupted container: {0} …）。
2. 载荷在各自 crate 构造，**大量中文**：cf-crypto/src/error.rs:18「KDF 参数非法：{0}」、cf-crypto/src/opvault.rs:110「OPVault 密码错误或数据损坏」、cf-format/src/header.rs:262「KDF 参数非法：…」。
3. core/cf-ffi/src/error.rs:78-85：From<CfError> → Coffer { code, message } **直传**；同文件 :60 注释写的是「错误摘要（日志用；UI 按 code 本地化，不解析本字段）」——**契约与实现不符**（本设计把实现拉回契约）。
4. Support/ErrorPresenter.swift:56：return "错误 \(code)：\(message)"；:102 Text(errorMessage ?? "")（String 入参，连自动本地化都不触发）。
5. 用户今天实际看到：错误 1005：corrupted container: KDF 参数非法：…

### 7.2 四方案对比

| 方案 | 做法 | 代价 | 风险 | 结论 |
| --- | --- | --- | --- | --- |
| **A 码映射优先** | Swift 按 code 查表得用户文案；原始 message 只进 DiagLog / 诊断页 | 写 26 条中英文案 | 信息量下降（排障看日志） | **采用** |
| B 核心内 i18n | Rust 按 locale 选文案 | 25 条 Display + 567 条中文串双份；错误跨层要带语言上下文 | 与「核心不依赖 UI 语言」分层纪律冲突；CLI/MCP 语言与 App 不同；**破坏 FFI 契约（MAJOR）** | 否 |
| C 结构化 payload | FfiError::Coffer { code, params } | 契约变更（MAJOR）、25 变体逐个改 | 收益接近 A，成本高一个量级 | 否（登记 P-19.5） |

### 8.4 对已建任务的分组意见（结论：不调整，但补两条边界）

维持 impl-infra(11) / impl-ui-a(12) / impl-ui-b(13) / impl-support(14)。需要显式写进任务卡的两条边界：

1. **Views/SettingsView.swift 归 ui-a，但语言入口的 UI 实现在 infra 的 LanguageSection.swift**。ui-a 只加一行 LanguageSection() 与节内注释，不自己写 Picker；否则 Settings 文件被两组共享。

## 10. 不可逆决策（**需用户确认**）

> 分级依据 docs/02-研发计划与决策/02-版本开发计划.md §9：存储格式 / API 签名 / 数据迁移类须用户确认后冻结。以下五条按同样纪律提交；确认后应追认进 docs/02-研发计划与决策/03-不可逆决策追认表.md（本文不改该表）。

### D-6 中文原文当 key（最高不可逆度）

| 选项 | 影响 |
| --- | --- |
| **A 中文原文当 key（建议）** | 666 处调用零改；缺键回落中文，中文侧不可能漏条；测试零改。代价：键可读性靠制度（分叉键「打开（文件）」）；同一中文要给不同译文只能继续分叉；改中文 = 改 key = 译文的键失效，需同步改 .strings |
| B 符号 key（settings.title） | 键稳定、可重构、可 grep、可做键级完整度校验。代价：666 处改写 + 503 条中文搬进 zh-Hans.lproj + 断言中文的测试成批改 + 必须建 zh-Hans.lproj（漏一条中文界面显示 settings.title） |

**裁决建议：A。** 本仓 UI 文案 1528 条、Views 层 1097 条，l10n 是 Could 级需求（NFR-UX-04「架构上预留多语言」），B 的成本是 A 的 3–4 倍且收益主要在「长期重构便利」，当前不成立。**这是「实际不可逆」的一条**：一旦落地，日后再改符号 key 等于重写全部文案层。

| 选项 | 影响 |

### D-8 strings 源布局（分片合并 vs 单文件）

| **A 源分片（5 个文件）+ 构建合并（建议）** | 四组文件级互斥、可并行；跨片重复键被构建抓住；代价是多一个脚本与「产物不入库」的心智 |
| B 单文件 + 分段注释 | 简单直接、少一个脚本；代价：四组写同一文件 → 冲突/覆盖，并行退化为串行 |

**裁决建议：A。** 可逆（合并即可回单文件），但多组并行落地后再改回会产生大量重排 diff。

### D-9 语言偏好存储（app 域 AppleLanguages 单源）

| 选项 | 影响 |
| --- | --- |
| **A 直接读写 app 域 AppleLanguages（建议）** | 与系统设置同源、无迁移、无二源冲突；代价：读取必须用 persistentDomain 区分显式值（F11）；用户在系统设置里改，App 内 Picker 随之变化（正确行为，但需在 UX 上说清） |
| B 自建 cofferLanguage 键 + 启动回写 | 状态自洽；代价：与系统设置二源，规则复杂（谁赢、何时写回），首启需迁移 |

**裁决建议：A。** 逆向成本：若改 B，已选过语言的用户设置会丢（需读 A 的值迁移），**属于用户持久状态**，故标不可逆。

### D-10 错误文案口径（码优先 + 载荷降为日志）

| 选项 | 影响 |
| --- | --- |
| **A 码映射优先，原始 message 只进日志/诊断页（建议）** | 英文界面干净；中文可见文案变短（唯一中文行为变化）；排障需看诊断页；契约回到 cf-ffi/src/error.rs:60 注释的原意 |
| B 保持 code+message 直出 | 零行为变化；代价：英文界面永久混入中文载荷（KDF 参数非法：…），验收必挂 |
| C 结构化 payload（params 数组） | 信息量与本地化兼得；代价：FFI 契约 MAJOR 变更、25 变体逐个改、跨版本兼容 |

**裁决建议：A**（成本最小且与 LicenseError 先例一致）。若用户不接受「细节降级」，退 B 并把 en 验收范围缩到「无 code+message 拼装串」——那等于放弃错误面英文化，不建议。
