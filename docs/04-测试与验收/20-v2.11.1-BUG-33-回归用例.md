## §0 范围与不变量

**本次修复的一行意图**：CLI 读取托管条目时，access group 从「只查改名前的旧组」改为「先查当前组、旧组兜底」——即**只扩大读取面**。

**非目标（判据不得据此判红）**：不迁移/不删除历史 Keychain 条目；不改 Keychain 条目格式（service `cn.coffer.mcp-escrow` / account `<vault_uuid>` / 32B 载荷 / 无 ACL）；不改 App 写入组；不改 CLI entitlements（已双组共存）。

**必须保持不变的不变量**（任一被破坏即判红，即使解锁变「能用」）：

| ID | 不变量 | 依据 |
|---|---|---|
| INV-1 | `Ok(Some(key))` → 用 key 解锁，日志 source=`keychain-escrow` | `cli.rs` 取密顺序（D-4） |
| INV-2 | `Ok(None)`（**全部**候选都无条目）→ 才走 env 兜底 | D-4「仅 Ok(None) 降级」 |
| INV-3 | `Err(..)` → fail-closed 退出 1，**绝不**回落 env（防掩盖缺 entitlement / ACL / 签名问题） | D-4 / docs/30 §1.3 |
| INV-4 | 错误对象与日志不含任何密钥材料 | docs/30 §1.2 |
| INV-5 | `mcp_wrap.available=false` → 不触 Keychain，直接 env 兜底 | 意图源语义（lead 裁定） |

## §3 构建产物判据（自动）

| 用例 | 判据（可判定） | 预期 | 实际 | 验证方式 | 分级 | 状态 |
|---|---|---|---|---|---|---|
| **TC-B33-06** 产物代码段含两组名 | **去签名后**逐字面量计数：新组 `A6DS985SJJ.top.cygnusyang.coffer` ≥1 **且** 旧组 `A6DS985SJJ.app.coffer.Coffer` ≥1 | 1/1 或以上 | 新构建 release 1/1、debug 1/1（2026-10-22）→ PASS；旧 helper 0/1 → 先红成立 | 见下方三步 | 构建产物 | ✅ |

**验证方式（三步，可直接粘贴；`<bin>` = `core/target/release/coffer` 或打包 helper `.../Helpers/coffer.app/Contents/MacOS/coffer`）**：

```bash
cp <bin> /tmp/coffer-nosig
codesign --remove-signature /tmp/coffer-nosig        # 已签名产物必做；cargo 直出未签名产物可跳过（失败无妨）
for g in A6DS985SJJ.top.cygnusyang.coffer A6DS985SJJ.app.coffer.Coffer; do
  printf '%-32s occ=%s\n' "$g" "$(grep -o -a "$g" /tmp/coffer-nosig | wc -l)"
done
```

**判据边界（三条，均为实测踩过的坑）**：

1. **必须先去签名**。签名产物的 embedded entitlements 里本身就列着两组名（`codesign -d --entitlements :- <bin>` 可见），**直接 grep 原文件会假绿**——实测旧 helper 去签名前新组 2 / 旧组 4，看着「两组都在」，实际代码段只有旧组。去签名后才是 0/1 的真红。
2. **不要用 `strings | grep -o 'A6DS985SJJ[.A-Za-z]*'` 分组计数**。字符串表会把相邻常量粘连成一行（实测输出 `A6DS985SJJ.top.cygnusyang.cofferA6DS985SJJ.app.coffer.Coffernot`），第二组被前一组吃掉 → 单组「0 命中」是假红；同理不要用 `grep -c A6DS985SJJ` 总数判定（1 次时无法区分是哪一组，正是 BUG-33 修复前的情形）。
3. **优化不得判红**。若某组名在 release 因内联/折叠缺失：先换 debug 构建或打包 helper 复核，两处都缺才算缺陷（实测 release 优化后仍各 1 次，无此问题）。
4. **本用例的能力上界**：只证「候选表进了产物」，**不证**读取行为正确。行为正确性 = read_with 的顺序与 fail-closed（主组命中即停 / `Ok(None)` 才继续 / `Err` 立即返回）——只有单元 02~05 能证，两者互不替代。06 绿而 02~05 红仍判红。

## §4 真机判据（人工核销）

### TC-B33-07 启用托管后 `coffer mcp` 能解锁（BUG-33 主症）

**前置**：Apple Development 签名产物（ad-hoc 必 -34018）+ 已嵌入未过期 provisioning profile（本机 profile 授权 `A6DS985SJJ.*`，覆盖新旧两组）；库已由 App「设置 → MCP / Agent 协作 → MCP 解锁托管」启用（header `mcp_wrap.available = true`）。

**步骤**：

1. 确认意图源：`python3 -c 'import json,sys;print(json.load(open(sys.argv[1]))["mcp_wrap"])' <vault>/header.json` → `available` 为 `true`。
2. 不带 env 密码执行（**关键**：带上 `$COFFER_VAULT_PASSWORD` 会遮住 escrow 失败——回落 env 后「看起来成功」，造成假绿）：

```bash
COFFER_VAULT_DIR=<库目录> \
  /Applications/Coffer.app/Contents/Helpers/coffer.app/Contents/MacOS/coffer \
  mcp --provider coffer
```

3. 观察：进程**不退出 1**，进入 MCP 服务（stdio 等待请求）；日志（stderr / diag 日志）出现 `vault unlocked via MCP keychain escrow (source="keychain-escrow")`。
4. 端到端确认（推荐）：Agent 侧（Claude Code / CodeBuddy / Codex）调用一次 `coffer` MCP 工具并成功返回——证解锁后的凭据真可用，而非仅「进程没死」。

| 判据 | 预期 | 实际 | 分级 | 状态 |
|---|---|---|---|---|
| 无 env 密码、`mcp_wrap.available=true` 时启动 `coffer mcp`，进程存活且日志含 `source="keychain-escrow"`；stderr **不含**「未启用 MCP 解锁托管」与「MCP 托管读取失败」 | 解锁成功（修复前：退出 1 + 「未启用托管」） | 待回填 | 真机 | ⬜ |

**失败时的排查点（按序，避免把环境问题误判成未修复）**：

1. 二进制是否真是新构建：对**该 helper** 跑 TC-B33-06（旧 helper 未替换是最高频误判）。
2. 签名/权限：`codesign -d --entitlements :- <helper>` 是否含两组；`security cms -D -i <embedded.provisionprofile>` 的 `keychain-access-groups` 是否为 `A6DS985SJJ.*`（若重签成仅新组 → 旧组读会 -34018）。
3. 条目是否真存在：App 内「重新启用托管」后再试作为对照（`security find-generic-password -s cn.coffer.mcp-escrow` 受 group 归属影响，不可作为唯一判据）。
4. 区分错误类别：-34018 = 缺 entitlement/profile 覆盖；-25308 = 交互被拒（终端无 GUI 会话）；`NotFound` 类 = 条目损坏（长度非 32）而非本次修复失败。
5. `mcp_wrap.available` 是否为 `true`（false 时根本不触 Keychain，属 INV-5 正常路径）。

## §5 历史条目兼容判据（TC-B33-08）

| 用例 | 判据（可判定） | 分级 | 状态 |
|---|---|---|---|
| **TC-B33-08** 旧组条目仍可读 | 存在**只**写在旧组 `A6DS985SJJ.app.coffer.Coffer` 下的托管条目时，`coffer mcp` 能解锁成功（日志 `source="keychain-escrow"`）；且成功时**不得**出现「请从 App 重新启用托管」类提示（不得要求用户重建） | 真机/人工 | ⬜ **未覆盖（本轮）** |

**可构造性说明（诚实边界）**：

- **无法在仓库内自动构造**旧组条目：`security add-generic-password` 不接受 access group 参数（条目落在调用工具自身身份对应的默认组），而产品代码**只会**往新组写（写入路径不改是本轮非目标）。因此需要一个「写入组 = 旧组」的签名二进制才能造出该条目。
- 可行的**人工**构造路径（二选一）：
  1. **历史用户路径（最真实）**：`app.coffer.Coffer` 时代的旧版 App + 当时启用的库 → 升级到本版 App/CLI 测解锁；
  2. **临时测试签名**：写一份 `keychain-access-groups` **仅列旧组**的临时 entitlements，签一个一次性写入工具，向 `cn.coffer.mcp-escrow` / `<vault_uuid>` 写入 32B，再用正式 CLI 测读回；测完删除该条目（不留残留）。
- **本轮处置 = 未覆盖（已登记）**。原因（两条路径本轮都不可行）：
  1. **本机 0 valid codesigning identities**（`security find-identity -v -p codesigning` 实测），无法签署「写旧组」的临时二进制 → 临时测试签名路径不可行；
  2. 本机无 `app.coffer.Coffer` 时代启用了托管的历史库（BUG-33 复现用的库是当前版 App 启用，条目落在新组）→ 历史用户路径不可行。
- **后续触发条件（三条任一即可解除未覆盖）**：① 本机恢复可用签名身份（Apple Development 证书就位）→ 走 §5 的临时 entitlements 写入路径；② 拿到改名前的旧版 App 产物 + 对应历史库 → 走历史用户路径；③ 有改名前启用托管的真实用户反馈旧条目不可读 → 直接以该用户环境核销（最高优先）。
- 未覆盖期间的口径：**不得**以「单元 02 已覆盖兜底逻辑」替代——02 证的是**读取代码**的兜底分支，不证**真实 entitlement 下**旧组可读（profile 若只授权新组，代码正确也会 -34018）。这个差异正是本用例存在的理由。
- 降级判定：真机实测旧组读回 **-34018**（profile 未覆盖旧组）→ 属环境/发版配置问题而非代码缺陷：登记环境项并给出处置（重生成覆盖两组的 profile，或明确「旧条目需重建托管」的用户文案），**不得**把 `Err` 静默当 `Ok(None)`（那会破坏 INV-3）。
