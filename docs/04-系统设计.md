## 1. 系统上下文

### 1.1 上下文图

```
                      ┌─────────────────────────────┐
                      │         用户（唯一）          │
                      └──────┬───────────────┬──────┘
                             │               │
                    操作     │               │  搬运加密文件
                             ▼               ▼
        ┌────────────────────────────┐   ┌──────────────────────┐
        │      Coffer App        │   │  用户自选的外部介质   │
        │  ┌──────────┐ ┌──────────┐ │   │  AirDrop / U 盘 /    │
        │  │ Android  │ │  macOS   │ │   │  网盘 / NAS / 移动硬盘│
        │  │  客户端   │ │  客户端   │ │   └──────────┬───────────┘
        │  └──────────┘ └──────────┘ │              │
        │        （互不通信）          │              │ 人工搬运
        └───────┬──────────────┬─────┘              │
                │              │◀───────────────────┘
        本地文件 │              │ 导入（只读，一次性）
                ▼              ▼
        ┌────────────┐  ┌──────────────┐
        │ 库目录      │  │ 导入源文件    │
        │ (密文)      │  │ .1pux/.csv/  │
        └────────────┘  │  .opvault    │
                        └──────────────┘
        ┌────────────────────────────────────┐
        │ 平台系统能力（只出不进）              │
        │ 生物识别 · 剪贴板 · 密钥库 · Autofill │
        └────────────────────────────────────┘

        ╔════════════════════════════════════╗
        ║  不存在：云服务 / 账号系统 / 服务器   ║
        ║  / 遥测 / 更新服务 / 任何网络端点     ║
        ╚════════════════════════════════════╝
```

**关键点**：

- 系统边界内**只有一个外部实体：用户**。没有服务端、没有第三方 API、没有遥测端点。
- "外部介质"不是系统的一部分，是用户的**人工操作**。App 不感知文件如何到达另一端。
- 平台系统能力是**单向调用**（App 调系统），不存在系统反向拉取数据的通道。唯一的例外是 Android 的 Autofill Framework 会主动回调 App——但这个回调发生在**同一设备内**、**同一进程内**，不涉及网络。

### 1.2 明确不存在的组件

| 组件 | 状态 | 说明 |
| --- | --- | --- |
| 后端服务 | **不存在** | — |
| 账号 / 认证服务 | **不存在** | 无注册、无登录、无令牌 |
| 同步服务 | **不存在** | 见需求 §1.4 |
| 遥测 / 分析 SDK | **不存在** | 不引入任何第三方 SDK |
| 崩溃上报服务 | **不存在** | 崩溃日志只写本地 |
| 更新检查服务 | **不存在** | 用户手动获取新版本 |
| 云配置 / 特性开关 | **不存在** | 所有行为由本地设置决定 |
| 第三方登录 | **不存在** | — |

> **开发流程 ≠ 产品**：本文档后续描述的 CI、代码托管、依赖下载等**开发环节**可以使用网络。产品本身不含网络能力，这两件事不能混淆。但需注意：**禁止在发行包中引入任何会主动联网的第三方 SDK**（如 Firebase、Sentry、Google Analytics），哪怕只在 Debug 构建使用——因为这容易在 Release 构建中因配置失误而残留。

## 2. 运行时视图

### 2.1 进程模型

| 平台 | 进程结构 | 说明 |
| --- | --- | --- |
| Android | **单进程**：主 App + AutofillService 在同一进程 | 保持简单。多进程会带来密钥共享与 IPC 复杂度，收益不足 |
| macOS | **单进程**：主 App + MenuBarExtra 在同一进程 | 不使用 XPC helper。App Sandbox 下单一进程足够 |

**明确不做的**：

| 方案 | 否决理由 |
| --- | --- |
| 把核心库跑在独立进程（守护进程） | 增加 IPC 攻击面；密钥需跨进程传输，违反最小暴露原则 |
| macOS 用 XPC Service 跑核心 | 同上。收益（崩溃隔离）不足以抵消成本 |
| Android 用独立进程跑 Autofill | 需 `isolatedProcess`，密钥无法共享，反而更难做 |

### 2.2 线程模型

```
┌──────────────────────────────────────────────────────┐
│ UI 线程（主线程）                                      │
│  · 只做 UI 渲染与用户输入                              │
│  · 绝不执行 KDF、导入、搜索等耗时任务                    │
└────────────────┬─────────────────────────────────────┘
                 │ 投递任务
                 ▼
┌──────────────────────────────────────────────────────┐
│ 工作线程池（固定大小，默认 = min(4, CPU 物理核数)）      │
│  · KDF 派生（单次 0.5–1.0 s，必须离开 UI 线程）          │
│  · 导入 / 导出 / 打包                                  │
│  · 搜索与批量解密                                       │
│  · Argon2id 内部会自己用多线程（p_cost），故外层池不宜过大 │
└────────────────┬─────────────────────────────────────┘
                 ▼
┌──────────────────────────────────────────────────────┐
│ SQLite 访问层                                          │
│  · 写：串行化（单写者），用 Mutex 保护连接               │
│  · 读：多读并发（WAL 模式支持）                          │
└──────────────────────────────────────────────────────┘
```

**明确不使用 async runtime（tokio / async-std）**，理由：

1. 本产品**没有任何网络 IO**，而 async 的主要收益来自高并发网络等待；
2. 全部 IO 是本地文件与 SQLite，延迟在微秒到毫秒级，线程池足够；
3. 去掉 async 可显著减少依赖树与代码复杂度，也让 FFI 边界更简单（UniFFI 对 async 的支持需要额外运行时集成）；
4. 密码学代码库（RustCrypto）本身是同步 API，混入 async 只会增加包装层。

**线程池大小的考量**：Argon2id 的 `p_cost` 参数本身会让实现内部使用多线程。若外层线程池同时跑多个 KDF 任务，会造成 CPU 过订阅。因此约定：**同一时刻只允许一个 KDF 任务执行**（用信号量保护）。

### 2.3 内存占用预算

| 场景 | 预算 | 主要构成 |
| --- | --- | --- |
| 空闲（已锁定） | < 30 MB | UI 框架 + 核心库 |
| 已解锁，未展开条目 | < 60 MB | 上述 + 域名索引缓存（1000 条目约 1–2 MB）+ SQLite 页缓存 |
| 展开条目详情 | < 80 MB | 上述 + 单条目明文 |
| 导入 1000 条目 | < 200 MB | 流式解析，不整体载入 export.data |
| 处理 100 MB 附件 | < 150 MB | **分块加密，每块 1 MiB**，不整体载入 |

> 以上为**设计预算**，非实测值。阶段 3 需实测并在本文档回填。

### 2.4 崩溃与异常

| 场景 | 处理 |
| --- | --- |
| Rust panic | 通过 panic hook 捕获；**禁止在 panic 消息中包含解密后的数据**；写本地崩溃日志（脱敏）后终止当前操作 |
| UI 层异常（Kotlin/Swift） | 标准异常处理；不回传敏感数据到崩溃处理器 |
| SQLite 损坏 | 解锁时执行 `PRAGMA integrity_check`；损坏则引导用户从备份恢复 |
| 磁盘满 | 写入前检查可用空间（预估写入量的 2 倍）；不足则中止并提示 |
| 强制杀进程 | WAL 保证事务原子性；下次启动做 WAL 恢复检查 |

## 3. 存储布局

### 3.1 Android

```
/data/data/<package>/files/
└── vaults/
    └── <vault_uuid>/
        ├── header.json
        ├── db.sqlite
        ├── db.sqlite-wal
        ├── attachments/
        └── thumbnails/

/data/data/<package>/files/logs/
└── cf-YYYYMMDD.log              # 本地日志，不含敏感数据

/data/data/<package>/files/exports/   # 用户导出位置（建议引导到外部存储）
```

**Android 备份策略：按数据类型分别处理**（ADR-13）

早期设想是 `allowBackup="false"` 一刀切，**该方案已放弃**——它同时否掉了用户的换机恢复能力，而本产品没有跨端同步，系统备份是用户唯一的自动恢复路径。

```xml
<application android:allowBackup="true"
             android:fullBackupContent="@xml/backup_rules"
             android:dataExtractionRules="@xml/data_extraction_rules" ...>
```

| 数据类型 | 位置 | 是否备份 | 理由 |
| --- | --- | --- | --- |
| **库文件** | `files/vaults/` | ✅ 允许 | 内容是密文。允许备份 = 换机/恢复出厂后数据能回来，对本产品是刚需 |
| **日志** | `files/logs/` | ❌ 排除 | 含操作时间线等元数据，无备份价值 |
| **导出文件** | `files/exports/` | ❌ 排除 | 用户自管产物，可能含明文 CSV |
| **密钥材料** | Android Keystore | 天然不参与 | Keystore 密钥不可导出，系统备份不包含 |

```xml
<!-- res/xml/backup_rules.xml（API 30 及以下） -->
<full-backup-content>
    <include domain="file" path="vaults/"/>
    <exclude domain="file" path="logs/"/>
    <exclude domain="file" path="exports/"/>
</full-backup-content>
```

> ⚠️ **必须纠正的一个常见误解**：`android:allowBackup` 是**开发者在 manifest 中声明的属性，用户无法在系统设置里针对单个 App 关闭它**。用户在系统设置里能关的是**整机备份**，关掉后影响设备上所有 App。
>
> 因此 App 内必须如实告知：
> - 系统备份会包含你的库文件，**内容是加密的**，没有主密码无法读取；
> - 若希望连密文都不上传，需在**系统设置中关闭整机备份**——App 自身无法做到"只排除自己"；
> - 换机后若开启了系统备份，库文件会自动恢复，但**仍需原主密码才能解锁**；
> - **卸载 App 会删除应用私有目录**，若系统备份未开启或尚未上传，库文件将一并丢失（见 §7.4）。

### 3.2 macOS

```
~/Library/Application Support/Coffer/
├── vaults/<vault_uuid>/
│   ├── header.json
│   ├── db.sqlite
│   ├── attachments/
│   └── thumbnails/
└── logs/
    └── cf-YYYYMMDD.log
```

**关键：`Application Support` 不在 iCloud Drive 同步范围内**，这是选择该目录而非 `~/Documents` 的首要理由。

**macOS 备份策略**（与 Android 对齐，ADR-13）：

| 数据类型 | 位置 | 备份状态 | 说明 |
| --- | --- | --- | --- |
| **库文件** | `~/Library/Application Support/Coffer/vaults/` | ✅ 会被 Time Machine 备份 | 密文，允许备份。**不主动排除** |
| **密钥材料** | 登录钥匙串中的 `K_bio` | ❌ 强制 `ThisDeviceOnly` | 密钥跨设备同步 = "零网络"承诺被系统通道绕过，必须显式禁止 |
| **日志** | `Coffer/logs/` | 含在 Time Machine 内 | 已脱敏 |

> **macOS 与 Android 的一处不对等**：Android 可以用 backup rules 精确控制 App 私有目录的备份范围，而 macOS 的 Time Machine 是**整卷备份，App 无法声明排除项**。用户若想排除库目录，需自行在 Time Machine 设置中添加。App 应在设置页提供该操作的引导。

**若用户选择把库放到别处**（需求允许用户自选库位置）：

| 目标位置 | App 行为 |
| --- | --- |
| `~/Documents`、`~/Desktop` | **明确告警**：该位置可能被 iCloud Drive 同步，与"完全本地"承诺冲突 |
| iCloud Drive 目录 | **强烈告警**，需二次确认 |
| 外置卷 / 网络卷 | 告警：网络卷不可靠，且在拔盘时会导致数据不可用 |
| 沙盒外任意路径 | 通过 security-scoped bookmark 获取访问权 |

同一逻辑适用于 Android：若用户把库放到外置 SD 卡或 `Downloads`，需提示风险。

### 3.3 库状态机（数据生命周期）

```
      ┌──────────┐
      │ 不存在    │
      └────┬─────┘
           │ create_vault
           ▼
      ┌──────────┐  unlock  ┌──────────┐
      │ 已锁定    │◀────────▶│ 已解锁    │
      │ Locked   │  lock    │ Unlocked │
      └────┬─────┘          └────┬─────┘
           │                     │
           │  delete_vault       │ export_vault_package
           ▼                     ▼
      ┌──────────┐          ┌──────────────┐
      │ 已删除    │          │ .lvvault 包   │
      │ (目录移除)│          │ （密文，可搬运）│
      └──────────┘          └──────┬───────┘
                                   │ import_vault_package
                                   ▼
                              ┌──────────┐
                              │ 新的库    │
                              └──────────┘
```

**状态转换的安全约束**：

| 转换 | 约束 |
| --- | --- |
| Locked → Unlocked | 需主密码或生物识别；失败次数触发指数退避 |
| Unlocked → Locked | 立即清零 DEK 与派生密钥；清空内存缓存 |
| Locked → 已删除 | 需输入主密码二次确认（防误删，也防他人删除） |
| Unlocked → 导出包 | 需输入主密码二次确认（导出即产生可搬运的完整副本） |
| 包 → 新库 | 新库有自己的主密码（可与源库相同，但**默认建议不同**） |

### 3.4 数据销毁

| 场景 | 销毁方式 | 局限（必须诚实说明） |
| --- | --- | --- |
| 删除单个条目 | SQLite 物理删除 + `VACUUM` | 闪存与 SSD 上，**旧数据块可能仍残留**，无法保证物理擦除 |
| 删除整个库 | 目录递归删除 | 同上 |
| 锁定清空密钥 | 内存 `zeroize` | 无 — 内存清零是可靠的 |
| 安全删除（防恢复） | v1.0 **不提供** | 在 SSD/闪存上无法可靠实现；正确做法是**全盘加密 + 依赖系统** |

> **诚实声明**：本产品**不承诺**"删除后可防止专业取证恢复"。在闪存介质上，任何声称能安全擦除单个文件的说法都不可靠。防护应依赖设备级全盘加密（Android 的 File-Based Encryption / macOS 的 FileVault）。这一点需写入产品文档。

## 4. 安全设计（STRIDE 完整威胁模型）

### 4.1 资产清单

| 资产 | 敏感度 | 存储位置 |
| --- | --- | --- |
| 条目密码 | **极高** | 库文件（密文） |
| TOTP 密钥 | **极高** | 库文件（密文） |
| 附件内容 | 高 | 库文件 + attachments（密文） |
| 条目标题 / 用户名 / URL / 备注 | 高 | 库文件（密文） |
| DEK / 子密钥 | **极高** | 仅内存 |
| 主密码 | **极高** | 仅内存（且不做持久化） |
| 生物识别封装密钥 | 高 | 平台密钥库 |
| 库结构元数据 | 中 | 库文件（明文，见详细设计 §3.5） |
| 库显示名 | 低中 | header.json（明文） |

### 4.2 STRIDE 分析

#### S — Spoofing（身份伪造）

| 威胁 | 场景 | 对策 | 残余风险 |
| --- | --- | --- | --- |
| 恶意 App 冒充 Coffer 的填充界面 | 用户以为在向 Coffer 输入主密码，实际输给了恶意 App | 锁定界面使用系统安全 UI（Android 的 Autofill 内嵌认证）；不提供任何"让用户在其他 App 里输入主密码"的设计 | 低。用户仍可能被钓鱼到假 App——需靠应用商店与签名机制防护 |
| 生物识别被绕过 | 伪造指纹 / 人脸 | 依赖平台 TEE / Secure Enclave；使用 `.biometryCurrentSet` / `setInvalidatedByBiometricEnrollment(true)` | 低（依赖平台可信度） |
| 库文件被替换为攻击者构造的库 | 用户打开他人提供的库文件 | header 中的 `vault_uuid` 参与 KEK/DEK 的 AAD | 中。若攻击者完整构造一个合法库并诱骗用户使用，无法防御——需靠用户判断文件来源 |

#### T — Tampering（篡改）

| 威胁 | 场景 | 对策 | 残余风险 |
| --- | --- | --- | --- |
| 单条密文被搬运 | 把 A 条目的密文复制到 B 条目 | AAD 绑定记录 UUID + 列名 | **低**（已消除） |
| 附件分块被重排 | 打乱附件分块顺序 | 每块 AAD 绑定 `attachment_uuid + chunk_index` | **低** |
| 记录被静默删除 | 删掉 SQLite 中若干行 | `meta.record_count` + `meta.root_mac` 校验 | 低 |
| 整个库被回滚到旧版本 | 用旧备份替换当前库 | **无法完全防御**（无服务端无时间戳权威） | **中**。缓解：定期做带日期的加密备份，用户可自行对比 |
| macOS 二进制被篡改 | 替换 App 可执行文件 | Developer ID 签名 + Hardened Runtime + 公证 | 低 |

#### R — Repudiation（抵赖）

| 威胁 | 场景 | 对策 |
| --- | --- | --- |
| 用户否认执行过导出 / 删除 | 单机单用户场景，此威胁**实际意义有限** | 提供本地审计日志（`audit_local` 表），记录解锁、导出、删除等事件 |

> 单用户单机产品中，抵赖威胁的优先级低。审计日志的主要价值是**用户自查**（"我什么时候导出过？"），而非法律举证。

#### I — Information Disclosure（信息泄露）★ 最核心

| 威胁 | 场景 | 对策 | 残余风险 |
| --- | --- | --- | --- |
| 库文件被复制 | 设备被盗、文件被拷走 | 全部敏感字段 AEAD 加密；主密码经 Argon2id | 低（依赖主密码强度与 KDF 参数） |
| 主密码被爆破 | 攻击者离线爆破 | Argon2id 高内存参数（目标 0.5–1.0 s/次） | 中。**无 Secret Key，爆破成本低于 1Password** —— 必须通过提高 KDF 参数与强制密码强度来补偿 |
| 剪贴板残留 | 复制密码后被其他 App 读取 | 定时自动清除（默认 30 s）+ 验证码不禁用清除 | 中。清除前的时间窗内，任何有剪贴板读取权限的 App 都能读到 |
| 截屏 / 录屏 / 最近任务预览 | 密码在屏幕上被截取 | Android `FLAG_SECURE`；macOS 侧需检测屏幕录制（`CGDisplayStream` 检测有限） | 中。macOS 无等效的全局防截屏能力 |
| 内存转储 | Root / 越狱设备 dump 进程内存 | 密钥 zeroize；缩短明文驻留时间 | **高**。有 root 权限的攻击者基本无法防御 |
| 系统日志泄露 | 敏感数据被写入 logcat / Console | 代码审查 + 禁止打印明文；CI 中加静态检查扫描 `println!`/`Log.` 后跟敏感变量 | 低（靠工程纪律） |
| 系统级备份外流 | Android 自动备份 / iCloud 钥匙串同步 | `allowBackup=false`；Keychain 用 `ThisDeviceOnly` | **低（但必须显式配置，否则完全失效）** |
| 应用快照 | Android 任务切换预览显示密码 | `FLAG_SECURE` | 低 |
| 键盘缓存 / 输入法 | 主密码被输入法记录 | 主密码输入框设置 `inputType=textPassword` + 禁用自动更正与建议；提示用户使用系统安全输入法 | 中。第三方输入法是系统级风险，App 无法完全控制 |
| 崩溃日志含敏感值 | panic 消息打印了明文 | panic hook 中过滤；**禁止对 `SecretString` 实现揭示明文的 `Debug`** | 低 |

#### D — Denial of Service（拒绝服务）

| 威胁 | 场景 | 对策 |
| --- | --- | --- |
| 恶意构造的导入文件 | 极深的 JSON 嵌套导致栈溢出；超多条目的 ZIP bomb | 解析器设深度上限与条目数上限；ZIP 解压前检查声明大小与实际大小；`serde_json` 用流式解析避免整体载入 |
| 超大附件 | 磁盘塞满 | 导入前检查可用空间；设单文件上限 |
| 暴力解锁导致 CPU 耗尽 | 连续尝试 | 失败后指数退避：1 s → 2 s → 4 s → … 上限 60 s |
| 损坏的库文件导致反复崩溃 | 打开即崩 | 打开失败走降级路径：只读模式 + 引导恢复备份 |

> **关于 ZIP bomb 的具体防护**：1PUX 是 ZIP，正常情况下 `export.data` 可能几十到几百 MB。防护措施：
> 1. 检查 `export.attributes` 与 `export.data` 的**声明大小**，超过阈值（如 1 GB）直接拒绝；
> 2. 解压时**实时累计**已解压字节数，超过阈值立即中止；
> 3. `files/` 目录的附件总量同样设阈值；
> 4. 每个附件单独检查压缩比（如压缩比 > 100:1 则告警）。

#### E — Elevation of Privilege（权限提升）

| 威胁 | 场景 | 对策 |
| --- | --- | --- |
| 未解锁状态下读取数据 | UI 层状态被绕过 | **Rust 侧强制 `require_unlocked()`**（详细设计 §4.3 的 `VaultLocked`）。UI 状态不可信 |
| 跨库越权访问 | 用 A 库的会话访问 B 库 | 会话绑定 `vault_uuid`；每笔操作校验目标库与会话库一致 |
| FFI 边界类型混淆 | 传入构造的 UUID 访问不存在或他人的数据 | 所有 ID 从 Rust 侧生成与校验；不接受 UI 侧构造的内部 ID |
| Autofill 越权 | 恶意 App 通过 Autofill 回调骗取其他条目的数据 | 域名匹配在 Rust 侧完成，**严格匹配才返回候选**；不匹配返回空 |

### 4.3 攻击面清单

| 攻击面 | 输入来源 | 防护重点 |
| --- | --- | --- |
| 1PUX / CSV / opvault 解析器 | **不可信**（用户从任何来源获得的文件） | 最高优先级的模糊测试对象 |
| 库文件本身 | 半可信（通常是自己生成的，但可能被篡改） | 格式校验 + AEAD 认证 + 完整性清单 |
| header.json | 半可信 | 字段范围校验（参数极端值需拒绝，如 `m_cost` 过大导致 OOM） |
| FFI 边界 | 半可信（同进程的 UI 代码） | 参数校验；不接受越界值 |
| Autofill 回调 | 半可信（系统发起，但目标 App 可构造） | 严格域名匹配 |
| 平台回调实现 | 可信（自己的代码） | 无 |
| 剪贴板 | **不可信**（其他 App 可读） | 只写入必要的单个值，定时清除 |

**`header.json` 参数校验的必要性举例**：若攻击者把 `m_cost_kib` 改成 `2^31`（2 TiB），解锁时会尝试分配 2 TiB 内存导致 OOM 崩溃。因此需设定合理上限（如 `m_cost_kib ≤ 4 GiB`、`t_cost ≤ 100`、`p_cost ≤ 64`），超限则拒绝并报错。

### 5.4 版本号与格式版本

**两套版本号，必须在文档与代码中明确区分**，否则会造成严重混乱：

| 版本 | 示例 | 含义 | 变更规则 |
| --- | --- | --- | --- |
| **App 版本** | `1.0.3` | 应用发布版本（语义化版本） | 每次发布递增 |
| **库格式版本** | `1` | `header.json` 的 `format_version` | **仅在容器结构发生不兼容变更时递增**，与 App 版本无关 |
| **导入映射版本** | `2026-09-23` | 1PUX/opvault 映射表的校准日期 | 每次校准样本后更新 |

**为什么必须区分**：App 可能发布 30 个版本而库格式一直是 `1`。若把两者混为一谈，会出现"升级 App 导致旧库打不开"的灾难，或"明明格式没变却提示需要迁移"的困惑。

## 6. 格式兼容与迁移策略

### 6.1 版本演进规则

| 变更类型 | `format_version` | 向后兼容 | 处理 |
| --- | --- | --- | --- |
| 新增可选字段 | 不变 | 是 | 旧版本忽略未知字段；新版本用默认值兜底 |
| 新增必填字段 | **递增** | **否** | 需要迁移 |
| 修改加密算法或参数结构 | **递增** | 否 | 需要迁移 |
| 调整 KDF 参数默认值 | 不变 | 是 | 参数本就随库文件走 |
| 新增条目类型 | 不变 | 是 | 未知类型降级为 `Custom` |
| 新增子密钥用途 | 不变 | 是 | 用新 label 派生即可 |

### 6.2 迁移机制

```
打开库时：
  读取 header.format_version
  ├── == 当前支持版本 → 正常打开
  ├── <  当前支持版本 → 进入【迁移流程】
  └── >  当前支持版本 → 拒绝打开，提示"请升级 App"（错误码 1006）

迁移流程（必须满足）：
  1. 【先备份】迁移前自动生成一份 .lvvault 包（命名含旧版本号），并告知用户位置
  2. 【原子性】写入新的临时目录，全部成功后替换旧目录；任一步失败则保留原库
  3. 【可回退】保留旧格式备份至少一次成功启动之后
  4. 【告知】迁移完成页明示：已备份、备份位置、可删除时机
```

> **迁移必须先备份**这一条不可省略。密码库的迁移失败意味着数据全部不可用，这是不可接受的单点风险。

### 6.3 降级不支持

**明确声明：不支持从新格式降级到旧格式。** 用户若用新版本 App 迁移过库文件，再用旧版本 App 打开将失败。这是行业通行做法，但**必须在发布说明中写明**，避免用户"降级 App 后发现打不开"的灾难。

## 7. 备份与灾难恢复

### 7.1 备份能力

| 能力 | 说明 |
| --- | --- |
| 手动导出 | 用户执行"导出加密备份" → 生成 `.lvvault` 单文件 |
| **系统级备份** | 库文件随系统备份（Android 云备份 / macOS Time Machine）自动保护，无需用户操作。**依赖设备设置，不保证开启** |
| 自动提醒 | 距上次导出超过 N 天（默认 30 天）时提醒 |
| 备份校验 | 导出后自动执行一次"能否打开并校验完整性"的验证 |
| 恢复 | 从 `.lvvault` 导入为新库；或由系统备份恢复库目录 |

**两种恢复路径的权衡**

| 路径 | 优点 | 缺点 |
| --- | --- | --- |
| 系统备份 | 自动、无需用户操作、时间点密集 | 依赖用户开启；**跨平台不通用**（Android 备份不能恢复到 macOS）；部分系统的云备份会跳过较大的附件 |
| `.lvvault` 手动导出 | 可控、可跨端、可多重备份、可校验 | 需用户主动执行 |

> **结论：两者互补，不可互相替代。** 系统备份是"兜底"，手动导出是"可控"。App 必须同时支持，并明确告知用户差别——**不能让用户以为"开了系统备份就万事大吉"**。

### 7.2 用户侧的备份建议（App 内应展示）

```
3-2-1 原则：
  · 保留 3 份副本（当前库 + 2 份备份）
  · 使用 2 种不同介质（如：移动硬盘 + 另一台设备）
  · 至少 1 份存放在异地

重要提醒：
  · 备份文件用你的主密码加密，忘记主密码 = 备份也无法打开
  · 建议同时把主密码记录在物理介质上（纸质、保险箱），
    而不是只存在另一台电子设备里
  · Android 与 macOS 的库互不相通，两端需分别备份
```

### 7.3 恢复演练

提供"恢复演练"引导功能：在**不破坏当前库**的前提下，让用户走一遍"从备份恢复"的流程，验证备份确实可用。

> 这个功能的理由是：**大多数用户从没验证过自己的备份能用**。等到真需要时才发现备份损坏或密码记错，那就晚了。演练功能是低成本高价值的信任建设。

### 7.4 灾难场景矩阵

| 场景 | 后果 | 恢复路径 |
| --- | --- | --- |
| 忘记主密码 | **数据永久不可恢复** | 无。这是设计的必然结果 |
| 库文件损坏 | 当前库不可用 | 从备份恢复 |
| 设备丢失/损坏 | 当前库丢失 | 从备份恢复到新设备；两端独立的库需分别恢复 |
| 备份也丢失 | 全部丢失 | 无 |
| 备份的密码记错 | 备份不可用 | 无 |
| App 卸载（Android） | 应用私有目录被删除致库文件丢失；**若系统备份已开启且已上传，重装后可恢复** | 见下方说明 |

> **Android 卸载会删除应用私有目录**，包括 `files/vaults/`。这是一个高频的、会造成真实数据损失的操作陷阱。
>
> 是否有救，取决于系统备份状态：
>
> | 系统备份 | 卸载后重装 | 结果 |
> | --- | --- | --- |
> | 已开启且已上传 | 从系统备份恢复 | 库文件回来，**仍需原主密码解锁** |
> | 已开启但未上传（如刚创建不久） | 无备份可恢复 | **数据丢失** |
> | 用户已在系统设置中关闭 | — | **数据丢失** |
>
> 因为结果不确定，App 必须在设置页显著提示，并在"删除库"流程中区分"仅删除库文件"与"卸载 App"两种操作。**不能假设系统备份会兜住。**

## 8. 测试策略

### 8.1 测试层次

| 层次 | 范围 | 工具 | 覆盖目标 |
| --- | --- | --- | --- |
| 单元测试 | 每个 Rust crate | `cargo test` | 行覆盖 ≥ 80%，密码学模块 ≥ 95% |
| 测试向量 | KDF / AEAD / TOTP | 标准向量 | **100% 通过**，不允许妥协 |
| 属性测试 | 加解密往返、序列化往返 | `proptest` | 任意输入下 `decrypt(encrypt(x)) == x` |
| 模糊测试 | 三个导入器 + 格式解析 | `cargo-fuzz` | 不 panic、不 OOM、不越界 |
| 集成测试 | 完整导入 → 查询 → 导出流程 | `cargo test` + 样本 | 端到端可用 |
| 跨端一致性测试 | 同一库文件两端打开比对 | 脚本 + 两端 CLI | 输出完全一致 |
| 平台测试 | Autofill / Touch ID / 密钥库 | 真机手动 + 自动化 | 关键路径无失败 |
| 安全测试 | 见 §8.3 | 手工 + 工具 | — |

### 8.2 必须通过的测试向量

| 测试 | 来源 | 向量数 |
| --- | --- | --- |
| Argon2id | RFC 9106 §5（测试向量） | 官方给出的测试向量全部 |
| TOTP | RFC 6238 Appendix B | **18 条**（SHA-1/256/512 × 6 个时间点），详见详细设计 §7.2 |
| XChaCha20-Poly1305 | draft-irtf-cfrg-xchacha / `chacha20poly1305` crate 自带的 Wycheproof 用例 | 全部 |
| Base32 | RFC 4648 | 全部 |
| HKDF | RFC 5869 Appendix A | 全部 |

### 8.3 安全专项测试

| 项 | 方法 | 通过标准 |
| --- | --- | --- |
| 零网络验证 | 反编译 APK 检查权限；`codesign -d --entitlements` 检查 macOS | 无 `INTERNET` 权限；无 network entitlement |
| 库文件明文扫描 | 对库文件跑 `strings` 与熵分析 | 检不到任何已知的测试密码、用户名、URL |
| 内存残留 | 解锁 → 锁定 → 内存 dump（需 root/调试器） | 检不到 DEK 与任何明文 |
| 日志脱敏 | 全流程操作后检查 logcat / Console / 日志文件 | 无明文敏感数据 |
| 篡改检测 | 手工修改库文件某字节 | 解密失败并报错，不产生静默错误 |
| 跨库密文搬运 | 把 A 库某条密文复制到 B 库 | 解密失败 |
| 导入器抗畸形输入 | 构造 1000 个畸形文件跑模糊测试 | 无崩溃 |
| 暴力破解退避 | 连续错误解锁 | 延迟严格递增且生效 |
| 系统备份排除 | Android：检查 `bmgr` 备份内容；macOS：检查 Time Machine 排除项 | 库文件与日志均不在备份范围内 |

### 8.4 测试数据管理

**这是本项目一个需要严肃对待的工程问题**：测试需要真实的 1Password 数据样本，但这些样本**本身就是敏感数据**。

| 要求 | 做法 |
| --- | --- |
| 不使用真实个人数据做测试 | 构造**合成样本**：手工编写覆盖全部 22 类、含各种边界值（空值、超长值、Unicode、emoji、特殊字符）的 1PUX/CSV/opvault |
| 合成样本纳入版本控制 | 样本本身不含真实信息，可安全入库，作为回归基线 |
| 真实样本的处置 | 若用户提供真实样本用于校准：**在本机离线使用，不提交到任何代码仓库；校准完成后删除；只把推导出的映射表（不含具体值）入库** |
| 样本指纹 | 映射表记录校准所用样本的 SHA-256 指纹，便于追溯校准依据（指纹本身不泄露内容） |

### 8.5 测试环境矩阵

| 平台 | 设备 | 说明 |
| --- | --- | --- |
| macOS | M 系列入门机型（如 M1 Air 8GB） | **主力验证设备**（首版交付目标）。KDF 已在 M0 标定，此处做内存预算与真机闭环验证 |
| macOS | M 系列高配机型 | 性能上限确认 |
| Android | 最低 API 26 设备（低端） | KDF 参数标定意义转为第二批验证（macOS 优先下 Android 为第二交付目标） |
| Android | 主流 API 33+ 设备 | 主要测试目标（第二批） |
| Android | API 34+ 设备 | Passkey 功能测试（第二批） |

**"最低端设备"（各平台各自的最低端设备）是必须真实持有的**：Argon2id 参数标定与内存预算的可行性，只有各平台的最低端设备能给出答案。用高端设备标定会导致低端用户解锁一次要等好几秒。

```

**不上报的代价必须诚实说明**：开发者不会自动获得崩溃信息，问题发现依赖用户主动反馈。这是"零网络"的必然成本。缓解措施是在设置页提供显眼的"反馈问题"入口（引导用户导出诊断包并手动发送）。

>

>

| `uniffi` | FFI 绑定 | — |
| `data-encoding` | Base32/Base64 | — |

**禁止引入**：任何 HTTP 客户端（`reqwest`、`hyper`、`ureq` 等）、任何遥测 SDK、任何 DNS 相关 crate。**这些禁止项应在 CI 中做自动化检查**：

```bash
# CI 检查：核心库依赖树中不得出现网络相关 crate
cargo tree --prefix none | grep -E '^(reqwest|hyper|ureq|isahc|surf|curl|tokio-rustls|native-tls)' \

### 12.2 数据互操作性

| 项 | 判断 |
| --- | --- |
| 读取用户自己导出的 1PUX / CSV | 无风险。这是用户自己的数据 |

### 12.3 开源（已定）

**决策：整体开源**（核心库 + Android App + macOS App），2026-09-24 定。

这个决定在逻辑上是必然的。本产品的核心卖点是"**没有联网能力**"，而用户验证这一点唯一可靠的方式就是**读代码并自己构建**。如果不开源，这句承诺就退化成"请相信我们"——与产品的立身之本直接冲突。

**开源范围**

| 内容 | 是否开源 | 说明 |
| --- | --- | --- |
| Rust 核心库 | ✅ 是 | 全部 |
| Android App | ✅ 是 | 全部 |
| macOS App | ✅ 是 | 全部 |
| **库格式规范** | ✅ 是，且**抽出为独立文档** | 便于第三方实现兼容读写器，扩大用户的数据可携带性 |
| 测试样本集 | ✅ 是（**仅合成样本**） | 真实样本不入库，见 §8.4 |
| 安全审计报告 | ✅ 公开 | 见 §12.5 |
| 发布签名密钥 | ❌ 否 | 私钥永不公开 |

**许可证：MIT**（2026-09-24 定）

| 项 | 说明 |
| --- | --- |
| 选定 | **MIT** |
| 特性 | 最宽松、最简短、生态兼容性最好 |
| 审计友好度 | **最高**。任何人可读、可改、可构建，不必考虑任何许可证义务 |

选型理由与本项目的核心诉求吻合：**它要的是"可被审计"，不是"防止被分叉"。** MIT 把审计门槛降到所有主流许可证里最低——审计者不需要读许可证、不需要判断兼容性，拿起代码就能验证"这个 App 是否真的没有联网能力"。

**选 MIT 需接受三件事**（决策时已确认）：

| 代价 | 说明 | 本项目的影响评估 |
| --- | --- | --- |
| **无显式专利授权** | Apache-2.0 含专利条款，MIT 没有。若贡献者持有相关专利，MIT 未提供明确的许可声明 | 风险较低。技术栈（Argon2id / XChaCha20 / SQLite / UniFFI）均为公开标准与成熟开源实现，无自研专利风险点 |
| **无法阻止闭源商业分叉** | 他人可拿本代码做闭源商业产品且不回馈 | 影响有限。分叉一个密码管理器并不比自己写省事，且分叉方会失去上游的持续安全更新——这在安全敏感产品上是重大劣势 |
| **后续变更许可证需全体版权人同意** | 未签 CLA 时，只要收过外部贡献就无法换证 | **必须从第一天建立 DCO 或 CLA** |

> ⚠️ **第三条是选 MIT 最容易埋的雷**：项目一旦合并了未签贡献协议的外部 PR，就**永久失去变更许可证的能力**。贡献授权机制必须在开放第一个 PR **之前**就位，不能事后补。这一点已列入 §13 交付物（`CONTRIBUTING.md` 须包含 DCO/CLA）。

**必须同步建立的机制**

| 机制 | 要求 |
| --- | --- |
| 依赖许可证清单 | 自动生成（`cargo-license` / Gradle 插件），发布前核对 |
| 许可证兼容性检查 | CI 自动检查，禁用与主许可证不兼容的依赖 |
| 贡献授权 | **采用许可授予型 CLA（`CLA.md`）** + CLA Assistant 自动化。**不用 DCO**——理由见下方"贡献者协议选型" |
| 安全披露流程 | 提供私密报告渠道（`SECURITY.md`）并承诺响应时限 |

**贡献者协议选型（已定：许可授予型 CLA）**

这是选 MIT 最容易埋雷的地方，单独展开。

| 方案 | 保留再许可权 | 专利授权 | 摩擦 | 结论 |
| --- | --- | --- | --- | --- |
| **许可授予型 CLA** | ✅ 能 | ✅ 有 | 低（PR 上点一次，可自动化） | ✅ **采用** |
| 版权转让型 CLA | ✅ 能（权利最完整） | ✅ 有 | 高（贡献者失去版权） | ❌ 对贡献者过苛 |
| **DCO** | ❌ **不能** | ❌ 没有 | 极低 | ❌ 不单独采用 |
| 什么都不做 | ❌ 不能 | ❌ 没有 | 无 | ❌ 等于自愿把许可证永久锁死 |

> ⚠️ **关于 DCO 的常见误解**：很多人以为签了 DCO 就能自由变更许可证。**不能。** DCO 是一份"证明"（certification）而非合同，其声明的对象是"**项目当前的许可证**"——它只证明贡献者有权按该许可证提交代码，**不授予任何超出该许可证范围的权利**，也不含专利授权。DCO 与 CLA 解决的是两个不同问题：DCO 管**代码来源是否合法**，CLA 管**项目有多少处置权**。两者可并存，但 DCO **不能替代** CLA。
>
> 该结论来自检索到的法律实践资料，原话包括 DCO "doesn't give the project the ability to relicense code"，以及它会 "make it very hard to change the licence of the project"。Apache ICLA 的定位也印证这一点：它是 **license grant 而非 copyright assignment**，明确授予"reproduce, modify, and distribute"以及**再许可**的权利。

**协议要点**（完整文本见 `CLA.md` v1.0）：

| 条款 | 内容 |
| --- | --- |
| 类型 | 许可授予，**非版权转让**——贡献者保留版权，且许可非独占 |
| 版权许可 | 永久、全球、非独占、免版税、不可撤销，**含再许可权** |
| **再许可范围** | 明示包含"专有 / 商业条款"。**刻意写在显眼位置**，不埋在细则里 |
| 专利许可 | 含**防御性终止**条款（对方对本项目发起专利诉讼则许可终止） |
| 项目方承诺 | 不变更为专有许可；变更前公告；已发布版本不追溯变更 |

> **关于"已发布版本不追溯变更"**：这一条不需要靠承诺实现——**开源许可证的授予在法律上本就不可撤销**。任何人在变更之前获取的版本，将永久保持在 MIT 条款下。"项目改证"对既有用户的实际影响，比听起来小得多。

**启用时机（重要）**：必须在**合并第一个外部 PR 之前**就位。该问题的触发条件是"合并了未签协议的 PR"，一旦发生即为**永久性权利缺口**——没有补救手段，只能逐个联系历史贡献者补签，而有些人可能已联系不上。当前项目尚无外部贡献者，是启用成本最低的时刻。

> **若项目长期为单人开发**，该问题不会实际发生。此时可以只保留 `CLA.md` 而不启用签署流程，等第一个外部 PR 出现时再启用——规则已写好，随时可用。

> ⚠️ **开源带来的"新风险"是一个伪风险**：代码公开后攻击者也能读。但按柯克霍夫原则（Kerckhoffs's principle），**安全性不应依赖实现的保密性，只依赖密钥的保密性**。本项目的安全性完全建立在"主密码 + 加密算法"之上，公开实现不降低安全性，反而因引入外部审查而提高。**真正需要防的是实现 bug，而藏起来的 bug 只会藏得更久。**

### 12.5 安全审计（已定）

**决策：做第三方安全审计**，2026-09-24 定。审计报告公开。

**为什么必须做**：自研加密容器格式是本项目风险最集中的地方（需求 R-04）。格式设计者评审自己的格式，**结构性地看不见自己的盲区**——这不是靠"多检查几遍"能解决的，只能靠外部独立评审。

**审计范围与优先级**

| 范围 | 具体内容 | 优先级 |
| --- | --- | --- |
| 加密实现 | Argon2id 参数与调用、HKDF 子密钥派生、AEAD 的 AAD 构造、nonce 生成策略 | **最高** |
| 密钥管理 | 信封加密的封装/解封装、verifier 设计、生物识别密钥封装、内存清零 | **最高** |
| 容器格式 | 目录结构与打包格式、版本识别与迁移路径、完整性校验机制 | 高 |
| 导入器 | 1PUX / CSV / opvault 解析的边界处理与资源限制（能否被畸形文件打崩） | 高 |
| FFI 边界 | 参数校验、错误处理、跨语言的内存与生命周期管理 | 中 |
| 平台实现 | Android Keystore / macOS Keychain 配置正确性、Autofill 与 Passkey 集成 | 中 |
| **零网络属性验证** | 依赖树、二进制、权限声明中无任何网络能力 | 中（但**结论对用户最有说服力**） |

**审计时机（两阶段）**

```
M0 技术预研
   │
   ▼
M1 核心库 ──▶ 【第一次审计：密码学与格式】
   │            范围：加密实现、密钥管理、容器格式
   │            时机：格式冻结后、UI 大量开发前
   │            目的：在改动成本还低时发现问题
   ▼
M2~M5 平台实现
   │
   ▼
M6 硬化 ────▶ 【第二次审计：全量复核】
                范围：全部 + 平台实现 + 零网络属性验证
                时机：v1.0 发布前、代码冻结后
                交付：公开报告
```

> **为什么分两次**：只在最后做一次，意味着格式缺陷要到项目末期才暴露，此时返工成本极高——格式一变，所有已导入的用户数据都要迁移。**第一次审计的价值就是让格式在还便宜的时候被推翻。**

**供应商选择**

| 类型 | 说明 |
| --- | --- |
| 专业密码学审计公司 | **首选**。需确认其有密码学与本地存储格式的审计经验 |
| 开源社区众审 | 补充，不能替代。开源带来更多眼睛，但没有明确责任主体与交付物 |
| 通用安全渗透测试 | **不足以覆盖主要风险**。本项目的风险在"格式设计是否正确"，不在"App 是否有越权漏洞" |

**审计产出与处置**

| 产出 | 处置 |
| --- | --- |
| 审计报告 | **公开**（可脱敏，但结论与未修复项必须保留） |
| 发现的问题 | 分级；高危必须发布前修复；中低危需公开处置计划 |
| 未修复项 | 必须在报告**与发布说明中同时披露**，不能只写在报告里 |

> **一条不可妥协的原则**：若审计发现高危问题而未能修复，**v1.0 不应发布**。这不是"可以带病上线后面再修"的场景——密码库数据一旦因加密缺陷泄露，后果不可逆。
