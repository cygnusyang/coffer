## 1. 文档定位

本文件是项目**唯一的进度事实源**，回答三个问题：

1. **每条需求做了没有？** —— 见 §6 / §7 状态矩阵；
2. **项目整体走到哪一步了？** —— 见 §3 里程碑状态；
3. **接下来做什么？** —— 见 §9 近期工作重点。

**职责边界**：需求"是什么"看 `01-需求分析.md`，方案"怎么做"看设计文档，进度"做没做完"只看本文件。设计文档不承载进度信息。

**维护规则（强制）**：

- 任何需求状态发生变化（⬜ → 🟡 → ✅）的提交，**必须同步更新本文件的对应行与修订记录**；
- 每个里程碑状态跃迁时更新 §3；
- 状态判定以**测试为据**：标 ✅ 必须有对应测试通过；无测试支撑的状态一律标 🟡 或 ⬜。

**状态图例**：

| 标记 | 含义 |
| --- | --- |
| ✅ | 已实现，有测试支撑，行为符合需求验收要点 |
| 🟡 | 部分完成（骨架 / 局部路径可用 / 缺验收） |
| ⬜ | 未开始 |
| ➖ | 不适用或明确排除（见 `01-需求分析.md` §2.2 / MoSCoW Won't） |

## 10. 数据快照说明

本文**最新修订**的状态判定基于 **2026-09-27** 的实测快照（一次性取样，非持续跟踪；数字随提交变动，以现场重跑为准）：

- core 工作区测试：全量 **422 个用例**。门禁命令（跳过 2 条）下**实际执行 420 条、全部通过**。被排除的 2 条是**两类不同问题，不可合并计数**：`极端kdf参数建库记录与解锁往返`（`cf-session/tests/adversarial.rs:792`）在 debug 档 1 GiB Argon2id 资源耗尽、会长时间挂起；`千条搜索基线`（`cf-session/src/usecase/search.rs:183`）是单次墙钟断言（1000 条 < 200 ms），独立实测 **p50 ≈ 77 ms、余量 2.6×**，**已确证为 flaky：20 次记录执行中 3 次失败**（361.8 / 339.0 / 273.5 ms，为 200 ms 预算的 1.37–1.81 倍）；**失败率不可给出**——现有执行采集于负载波动的非受控条件，足以确证 flaky、不足以量化速率；**计数口径**（分母的构成与逐条出处）见 `docs/09-版本路线图.md` §1.3 与附录 B.4——该分母是**被声明的边界**，换口径即变（把日常门禁运行一并计入则为 28 次）；且**至少一次失败发生在仅选中该 1 条时**（`41 filtered out`，机器记录）→ **与同 binary 兄弟测试的并发无关**，**隔离并不能避免**。断言测的是机器抖动，**与 load average 不相关，非功能回归，不影响 FR-11.4 的达成**。即 **422 = 420 执行通过 + 2 条排除**；**「421 通过 / 1 失败」不成立**；
- ⚠️ **现场重跑的注意事项**：`cargo test --workspace` 默认在首个失败目标即中止（须加 `--no-fail-fast` 才能一次跑完并观测），且工作区内含 1 GiB Argon2id 重载荷用例（debug 下单条 >20 分钟、单进程 RSS ≈1.0 GB，两实例即打满本机 swap）。门禁命令的重定义见 `docs/09-版本路线图.md` §1.2（v0.2-T00）——**权威命令不可由本行推断**：它须在 **`core/` 下**执行（仓库根无 `Cargo.toml`，直跑即非零退出）、带 `--no-fail-fast`、并跳过两条已知问题用例；本文不复述该命令以免多处维护；
