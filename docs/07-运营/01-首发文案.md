# 二、核心叙事（为什么再做一个）

## EN

Every password manager is optimised for one thing: putting a secret into a human's browser. That model breaks the moment an agent is in the loop — you want Claude Code to `npm publish`, or your coding agent to hit a private API. Today you do one of two things: paste the token into a file the agent reads, or hand it your 1Password session. Both mean the secret ends up somewhere it can be logged, summarised, or exfiltrated.

Coffer treats that as the primary design problem, not an afterthought:

1. **Secrets stay out of the model.** An agent asks Coffer to run a command with a secret injected into that subprocess's environment. The agent gets stdout; it never sees the value. There is no tool that can print a password.
2. **The vault never leaves your Mac.** No account, no sync, no telemetry. The only network call the app can make is an update check, to four GitHub hosts, when you click it. You can verify this with `codesign -d --entitlements -` and a network monitor — the policy document tells you how.
3. **It is auditable, not just open.** AGPL-3.0, 673 test assertions across 16 harnesses, and a design corpus of 60+ documents, including the decisions I would otherwise quietly break.

What it is not: not a service, not a subscription, no browser extension, passkeys are read-degraded, macOS only. It is a tool for a specific person: someone who already uses an agent and is uncomfortable with where their credentials currently live.

## ZH

现有密码管理器的设计前提是『把密码填进人的浏览器』。一旦工作流里出现 AI agent，这个前提就断了 —— 你想让 Claude Code 去 `npm publish`，或者让编码 agent 调一个私有 API。现在只有两条路：把 token 写进 agent 能读的文件，或者把你的 1Password 会话交给它。两条路都意味着密码会落到能被记录、被摘要、被外传的地方。

Coffer 把这个当成第一设计问题，而不是补丁：

1. **密码不进模型上下文。** agent 请 Coffer 用某个密钥执行一条命令，密钥只注入那个子进程的环境变量；agent 拿到的是 stdout，永远看不到值。产品里没有任何工具能把密码打印出来。
2. **库不离机。** 没有账号、没有同步、没有遥测。App 唯一的联网行为是你在点『检查更新』时访问 4 个 GitHub 域名。你可以用 `codesign -d --entitlements -` 和网络监控自己验证，隐私声明里写了步骤。
3. **可审计，不只是开源。** AGPL-3.0、16 个 harness 共 673 条断言、60+ 篇设计文档，包含那些我本来会悄悄破坏的决策。

它不是什么：不是服务、没有订阅、**没有浏览器扩展**、Passkey 只支持降级读取、只有 macOS。它是给一类具体的人用的：已经在用 agent、并且对『凭据现在放在哪』感到不安的人。

# 三、Show HN 版（英文）

**Title**: Show HN: A local-first password manager built for AI agents, not browsers

**Body**:

I built Coffer because I could not answer a simple question: when my coding agent needs a token, where should that token live?

Every option was bad. A `.env` file means the secret is in the repo's blast radius. An agent-accessible password manager means the secret ends up in the context window, where it can be summarised, logged, or leaked into a commit. Pasting it into the terminal each time means it is in my shell history.

Coffer takes the position that secrets should never be visible to the agent at all. The agent asks Coffer to run a command; the secret is injected into that subprocess's environment; the agent sees stdout. The MCP surface is read-only by design — there is no tool that returns a password value.

The rest of it is deliberately unexciting: a local encrypted vault (Argon2id + AEAD), no account, no sync, no telemetry. The only network entitlement in the signed binary is `network.client`, used by the update checker against four GitHub hosts; the privacy doc explains how to verify that with `codesign` and a network monitor rather than taking my word for it.

Honest limitations, because they matter more than the feature list:

- macOS 14+ only
- no browser extension (you copy from the app; TOTP is built in)
- passkeys are read-degraded, not full
- single maintainer, so issues are best-effort
- not notarised in this build — you will need to right-click → Open (the notarised build is coming)

Stack: Rust core (crypto, format, session, importer, MCP server) + SwiftUI shell, UniFFI between them. 16 test harnesses, 673 assertions, AGPL-3.0.

I am particularly interested in feedback on the MCP trust boundary — the design is in `docs/01-需求与架构/05-Agent凭据域.md` (Chinese). If you think read-only is too restrictive, or that injecting into a subprocess is the wrong primitive, I would like to hear the argument.

**First comment (post immediately)**:

Some context I would want as a reader:

- The MCP server speaks stdio or a Unix domain socket. It never listens on a TCP port.
- `run_with_secret` is the only write-ish primitive: it spawns a child process with an env var. There is no `get_password` tool, and the CLI has no read path either — by design, which also means backing up CI secrets by hand is annoying.
- The vault format, threat model, and every irreversible decision are in `docs/` (Chinese, with an English index at `docs/README.en.md`).

# 四、V2EX / 少数派 版（中文）

**标题**：我做了个密码管理器，专门给『会让 AI 用密码』的人

**正文**：

先说结论：这不是又一个 1Password 替代品。它只解决一个问题 —— **当你的 AI agent 需要用凭据时，钥匙放在哪。**

我自己的场景很简单：让 Claude Code 去发布一个包，或者调一个私有 API。以前只有三种做法，一种比一种糟：

1. 把 token 写进 `.env` —— 等于放在仓库的爆炸半径里
2. 让 agent 直接读密码管理器 —— 密码进了上下文窗口，可以被摘要、被写进 commit、被下一轮对话带出去
3. 每次手动粘贴 —— 进了 shell history

Coffer 的做法是：**密码永远不对 agent 可见。** agent 请求 Coffer 用某个密钥执行一条命令，密钥注入那个子进程的环境变量，agent 只拿到 stdout。MCP 面是只读设计，**没有任何工具会返回密码值**。

其余部分刻意做得很无聊：本地加密库（Argon2id + AEAD）、没有账号、没有同步、没有遥测。签名后的二进制里唯一的网络权限是 `network.client`，只被你点『检查更新』时的 4 个 GitHub 域名使用 —— 隐私声明里写了怎么用 `codesign` 和网络监控自己验证，不用信我。

**它明确不做什么**（这些比功能列表重要）：

- 只有 macOS 14+
- **没有浏览器扩展**（从 App 复制，TOTP 内置）
- Passkey 只有降级读取
- 单人维护，issue 是尽力而为
- 这个版本还没公证 —— 首次打开要右键 → 打开（公证版在做）

技术栈：Rust 核心（加密/容器/会话/导入/MCP 服务器）+ SwiftUI 外壳，中间是 UniFFI。16 个测试 harness、673 条断言、AGPL-3.0。

**我最想听的不是『功能够不够』，而是这个判断对不对**：agent 与凭据之间，应该是『注入子进程』还是『短时令牌』？我在设计文档里选了前者，理由写在那儿，但我不确定它对所有场景都成立。
