## 0. 结论摘要

1. **发布版本轴**为 `v0.1 → v1.0`，共 5 个发布版本 + 1 个补丁版本（`v0.1.1`）。Android 整体移出该轴。
2. **v0.2 必须是数据出口（导出/备份/恢复），不是 Touch ID**——BUG-2 是*人类签名的外部阻塞*，把随时可发的导出功能与它同版会一起卡死。**不把可控交付物耦合到外部阻塞项上。**
3. **Touch ID 不绑定任何版本**：BUG-2 未解除前，绑定它的版本会被无限期卡死。登记为「BUG-2 解除后即可发布的独立交付项」。
4. **附件存储必须与 1PUX 导入同版（v0.3）**：`FR-7.1` 解析 1PUX 的 `files/`，`FR-7.8` 又强制导入后提示删除源导出文件——跨版本拆分会导致**附件永久丢失**（详见 §2.3）。
5. **门禁命令必须重定义**，否则所有出口判据不可执行：现行 `cargo test --workspace` 会在第一个失败目标中止，且含一条**已确证 flaky（20 次记录执行中 3 次失败）、但失败率不可量化**的墙钟断言（采集条件非受控，见 §1.1 / §1.3），另有一条 debug 下 >20 分钟、单进程 RSS≈1.0GB 的用例。
6. **版本号词汇实测有六套**，其中第 4 套（文档修订号）与第 5 套（发布版本号）曾在同一文件内**字面撞车**。（**第 4 套的撞车本轮已消除**：`06` 已改用 `r<N>`，见 §3.1 / 附录 A-15；**其余文档的同型撞车仍在**，见 A-15）
7. **环回检验点**：v0.2「数据取得回来」→ v0.3「数据进得来 + 看得清风险」→ v0.4「用起来顺手」→ v0.5「无密码」→ v1.0「别人也信」。

## 1. 门禁定义（所有版本出口判据的地基）

### 1.1 现状问题

WI-1 独立核验结论（`/tmp/coffer-WI-1-verification.md`）：

| 问题 | 实测 |
| --- | --- |
| 首个失败即中止 | `cargo test --workspace` 在 `cf-session` 处中止，后续 crate 未被观测 |
| 随机红 | `cf-session::usecase::search::tests::千条搜索基线` —— **已确证 flaky**：**20 次记录执行中 3 次失败**（361.8 / 339.0 / 273.5 ms，为 200ms 预算的 **1.37–1.81 倍**，逐条可溯源见 §1.3）；**失败率不可给出**：现有执行采集于负载波动的**非受控**条件，足以确证 flaky、不足以量化速率。**单测隔离（bin 内仅该 1 条，机器记录 `41 filtered out`）下仍失败 2 次** → **与同 binary 兄弟测试的并发无关**；此外**并行运行时也失败 1 次**（42 条同跑，`0 filtered out`）→ **它会击穿常规全量运行**。**注意：`--test-threads=1` 不是第二个可区分条件**（本例是 no-op，且唯一佐证是手写标注，见 §1.3）。 |
| 成本爆炸 | `cf-session/tests/adversarial.rs:792`（m=1GiB / t=10 Argon2id）debug 下单条 >20 分钟、单进程 RSS≈1.0GB；采集时刻 `vm.swapusage` 为 **used 19914M / total 20480M**（swap 几近耗尽）。⚠️ **不可读作「两实例打满 swap」**：本机 RAM 是 **16 GiB**（`hw.memsize`=17179869184）、swap 总量是 macOS 的**动态值**而非机器规格（本机复测 `total=12288M`），**2×1.0 GB 的 RSS 不足以耗尽 12–20 GB 的 swap** —— 19914M 是**同期观测值**，不是这两条用例的后果；其成因现有证据不支持 |
| 环境敏感 | 同一用例在不同负载下耗时从数百 ms 波动到 >15 分钟量级——**这种巨大波动本身就是「该测试成本随环境剧变」的证据** |

### 1.2 门禁命令

```sh
# ⚠️ 前提 1：`cargo` 可能不在 PATH 上（非交互 shell / 新终端 / 脚本里 `~/.cargo/bin` 常缺失）
#    → 报 `command not found: cargo`、退出码 **127** —— 命令**根本没跑**。
#    直执行时 127 是响亮的；但**一旦接管道，`$?` 会变成 0**（见下方「管道吞退出码」）→ **静默假绿**。
#    rustup `--no-modify-path` 安装的情形与修复见 `README.md:138`。
command -v cargo >/dev/null 2>&1 || source "$HOME/.cargo/env"

# ⚠️ 前提 2：cargo 工作区根是 core/，不是仓库根（仓库根没有 Cargo.toml）。
#    不在 core/ 下执行，cargo 直接报 `error: could not find Cargo.toml` 并非零退出。
cd core

# 门禁 —— 确定性绿（当前推荐，排除 2 条问题用例）
cargo test --workspace --no-fail-fast -- \
  --skip 极端kdf参数建库记录与解锁往返 --skip 千条搜索基线
cargo clippy --all-targets -- -D warnings

# 门禁 —— 终态（两条问题用例修好后启用）
cargo test --workspace --no-fail-fast

# 门禁 —— 终态：重载荷 / 性能（release，串行；只跑 #[ignore] 标记的测试）
# ⚠️ `--all-targets` 必需：缺了它，`--ignored` 会把 doctest 一并选中，而以 `ignore`
#    标注的围栏片段无法独立编译 → 整条命令以 101 失败（实测 /tmp/coffer-ignored-run.log：
#    debug `:158` 与 release `:425` 均 `Couldn't compile the test.`，退出码见 `:166` / `:433`）。
# ⚠️ 本命令**今天选中 0 条**：全仓 `#[ignore]` 零命中。它是为终态预备的
#    （届时 `adversarial.rs:792` 拆出极端档并加 `#[ignore]`）。
cargo test --release --workspace --all-targets -- --ignored --test-threads=1

cd ..   # 构建门禁脚本的相对路径基于仓库根

# 构建门禁
./tools/build_macos_app.sh && codesign --verify --strict macos/build/Coffer.app
```

`--no-fail-fast` 是必需的：没有它，一次运行只能观测到第一个失败，无法判断整体状态。

**⚠️ 管道会吞掉退出码。** 管道后 `$?` 取的是**最后一个命令**的状态，不是 `cargo` 的，故 `cargo … 2>&1 | tail -3` 的 `$?` 是 `tail` 的：实测（纯 shell，不依赖 cargo）`false 2>&1 | tail -3` 之后 `$?` = **0**，而 `${pipestatus[1]}` = **1**。取真实退出码只有三条路：**不接管道**、用 zsh 的 `${pipestatus[1]}`（**1-indexed、小写**；bash 的 `${PIPESTATUS[0]}` 在 zsh 下取到空值）、或先 `set -o pipefail`。**这一段与代码块里的两条前提同源**——都是「观测到的信号 ≠ 想知道的信号」。**任一失败原因**（缺 PATH → 127 / 不在 `core/` 下 → 找不到 `Cargo.toml` / 测试真失败）**只要接了管道，读数都会被换成 0**。叠加起来就是**静默假绿**：命令根本没跑起来，门禁却显示通过 —— 这正是 §1.2 要消灭的东西。

**`ignored` 与 `filtered` 是两个不同的计数器，不可合并。** 主门禁的 `ignored` 读数形态是**两条各自 `1 ignored`**，且日志**按名点到**：`/tmp/wi4-gate.log:551` `test cf-crypto/src/kdf.rs - kdf::random_salt (line 261) ... ignored`（汇总在 `:553`）、`:571` `test cf-ffi/src/lib.rs - session_call (line 86) ... ignored`（汇总在 `:573`）——正是上面那两段**以 `ignore` 标注的围栏**所对应的 doctest，**它们本就设计为不编译，围栏是对的**，错的只是原命令缺 `--all-targets`。**而 `2 filtered` 是被 `--skip` 排除的两条问题用例。两个「2」来源不同、含义无关**（口径见 §1.1 与 §1.3）。

> 上述修正命令本身**尚未实测**（已实测的是缺 `--all-targets` 的原形）。「`--all-targets` 不含 doctest」是 cargo 的文档语义，修正命令的实跑通过仍待下一次门禁运行确认。

**门禁覆盖边界（强制声明）**：本节定义的「门禁」只覆盖 **Rust 侧**（`cargo test` / `cargo clippy` / release `--ignored`）与构建签名（`tools/build_macos_app.sh` 只作 `swiftc -O` **编译** —— 编译 ≠ 测试；`codesign --verify --strict` 验的是签名与包结构）。**Swift / UI 侧的行为没有自动门禁**：`tools/run_keychain_tests.sh` 与 `tools/run_touchid_status_tests.sh` 两个 runner 均不在本节命令块内，仓库也没有 `.github`（无 CI）。**故任何 Swift/UI 侧能力的 ✅ 标记，其证据都在门禁之外** —— 此处只声明「证据不在门禁内」这一关于门禁的事实，**不评估**门禁外证据的强度。§1.5 的 FR-11.4 是**该通则的一个实例**，不是唯一特例。

### 1.3 FR-11.4 的准确表述

> **需求满足（实测 p50 77ms / 2.6x 余量）；证据链不可用（测试 flaky，失败率不可量化）。**

仓库外只读探针（debug profile，**4 轮 × 40 样本 = 160**，查询串与正式用例完全一致）实测：

```
  批次（采集时 load）    p50      p90      max      ≥200ms
  探针 1（load 3.5）    77.444   80.636   88.381   0/40
  探针 2（load 3.5）    75.153   77.346   80.210   0/40
  探针 3（load 3.3）    75.421   78.868   79.584   0/40
  探针 4（load 3.1）    75.736   79.272   93.360   0/40
  余量倍数（200ms / p50）= 2.58x / 2.66x / 2.65x / 2.64x
```

> **数据来源（逐项可溯源）**：探针 2–4 的原始输出见 `/tmp/coffer-wi1-probe-repeat.log`（3 轮 × 40）；探针 1 的数值出自 WI-1 核验报告（同一探针工程的首次运行）。四轮合计 **160 样本，无一 ≥200ms**。此处按**逐轮**列出并随附采集条件，**不合并、不合成比率**。

**措辞纪律**：写成「性能降级」会错怪代码（代码没问题）；写成「✅」会掩盖测试缺陷。**需求本身满足，是测试不可靠。**

**3 次已记录的失败 —— 逐条可溯源（列的是观测事实，不是速率）**：

| # | 耗时 | 相对 200ms 预算 | 当时的执行形态 | 出处 |
| --- | --- | --- | --- | --- |
| 1 | **361.8 ms** | 1.81× | **并行运行**：完整测试二进制（与同 binary 其余 41 条同跑，`41 passed; 1 failed; 0 filtered out`） | `/tmp/coffer-wi1-test.log:351`（panic 于 `search.rs:198:9`；`:358` 结果行） |
| 2 | **339.0 ms** | 1.70× | **单测隔离**：bin 内仅该 1 条被选中（`41 filtered out`） | `/tmp/coffer-wi1-perf-rerun.log:34`（RUN 4；`:35` 结果行） |
| 3 | **273.5 ms** | 1.37× | **单测隔离**：同上（`41 filtered out`） | `/tmp/coffer-wi1-rest.log:255`（`:258` 耗时 / `:269` 结果行 / `:272` `EXIT_PERF_ISOLATED=101`） |

这三次记录给出两个方向性结论。这两个条件**是真正可区分的**，判据是两批**机器输出**的结果行本身（A 级）：#1 是 `0 filtered out`（42 条同跑），#2/#3 是 `41 filtered out`（只剩这 1 条）。

**① 单测隔离下失败**（#2、#3，共 2 次）——bin 内只剩这 1 条仍失败 ⇒ **与同 binary 兄弟测试的并发无关**（这是证伪「并发是原因」的那一条，也是唯一一条**必需**的）。
**② 并行运行时也失败**（#1）——完整二进制 42 条同跑时同样失败 ⇒ **它会击穿常规全量运行**，不是只在人为单跑时才红。这一条对路线图有独立价值：它正是**门禁必须排除该用例**的理由，缺了它就只剩「人为单跑才失败」的印象。

> **⚠️ `--test-threads=1` 在此不是第二个可区分条件（勿把它写成「两种隔离方式各失败一次」）**：`coffer-wi1-rest.log` 的段落标题写作 `PERF TEST ISOLATED (single thread)`，**但该行标题是日志作者手写的一段标注、不是机器输出** —— tester 本人已明确否认其来源：「`rest.log:250` 的段落标题……是**我自己当时手写的标注**，不是机器输出 —— **它不能独立佐证该 flag 被传入**」（WI-1 报告 §2.5.1）。该段**机器输出**的结果行是 `0 passed; 1 failed; …; 41 filtered out` —— **bin 内只有这 1 条被选中**；`perf-rerun.log` 五轮**同样**是 `41 filtered out`。**只选中 1 条时 `--test-threads=N` 是 no-op**（只剩一条测试，本来就用一条线程跑），故它并未在「仅该 1 条被执行」之上增加任何隔离强度。把这两批说成「两种隔离各失败一次」，是**给同一个条件起了两个名字**——一条证据被数了两遍，不是两条独立证据。

> **证据强度分级（下游只能引 A 级；本节照搬 WI-1 报告 §2.5.1，`/tmp/coffer-WI-1-verification.md:290-309`）**
>
> - **A 级 = 机器记录**：由测试框架 / OS 直接输出、可独立复核 —— `test result:` 行（`41 filtered out` / `0 filtered out`）、panic 行（`search.rs:198:9` 并带实测耗时）、`EXIT_*` 退出码、`uptime` 行。
> - **B 级 = 人手写标注**：日志里由作者手写的段落标题，**无法被机器输出独立佐证** —— 本仓库中即 `coffer-wi1-rest.log:250` 的 `########## PERF TEST ISOLATED (single thread) ##########`。
>
> 本文结论**只用 A 级证据**。`--test-threads=1` 既在本例是 no-op、其唯一佐证又属 B 级，故本文既不把它当条件，也不声称「串行即可避免」。
>
> **两个方向都要防**：libtest **不回显自己的 argv**，所以「按 flag 名 grep 不到」**不能**当否定证据；但它**也推不出「该 flag 被用了」**。**两个方向都只有 A 级证据才能下结论**。同族错误在本项目已出现四次：`--skip <写错的名字>` 静默零匹配、`grep` 关键词拼错、**glob 范围不足**、**给同一个条件起两个名字**。

失败与 CPU 负载**不相关**，最强证据是**同条件自然对照**：`/tmp/coffer-wi1-perf-rerun.log` 的 RUN 4 与 RUN 5，运行**前后 load 完全相同（13.64）**、命令相同、测试相同，**结果相反**（RUN 4 FAILED 339.0 ms / RUN 5 PASS）。旁证方向一致：另一轮 **12 次运行在 load 16.86–17.72（更高）下 12/12 全过**（`/tmp/coffer-wi1-perf-flake.log`）——**负载更高时全过、负载更低时反失败**。触发因素是约 250 ms 级的瞬时停顿（swap 换入换出 / 页错误 / 调度抖动），**该测试实测的是机器抖动，不是被测量的性能**。

> **计数口径（强制）**：**分子与分母都必须来自一个声明的口径。** 本文采用 WI-1 核验报告表格所定义的计数边界（`/tmp/coffer-WI-1-verification.md` 的条目 #1–#20，含 1 次全量、1 次单测隔离、5 次批次 A、12 次批次 B、1 次空载全量）：**20 次记录执行中 3 次失败**——即该表的 #1、#2 与批次 A 中失败的那一次。**不写百分比**：各次采集于负载波动的**非受控**条件，足以确证 flaky，**不足以给出速率**。**换口径就会换分母**（把日常门禁运行一并计入则为 28 次），故任何分母都必须**声明其边界**才可引用；逐条出处见附录 B.4。

### 1.4 配套测试处置（落在 v0.2-T00）

| 测试 | 现状 | 处置 |
| --- | --- | --- |
| `cf-session` 千条搜索基线 | 已确证 flaky（20 次记录执行 / 3 次失败，失败率不可量化），测机器抖动；并行与单测隔离下均失败 | 修 `search.rs` 断言；见 §1.5 |
| `cf-session/tests/adversarial.rs:792` | debug >20min、RSS 1.0GB | 标 `#[ignore]`；仅 release + 串行运行 |
| `--no-fail-fast` | 未使用，首个失败即中止 | 加入门禁，保证一次跑完可观测 |

**修 `search.rs` 的正确方式 = 照抄仓库既有范式**。这里的「范式」指 `cfg!(debug_assertions)` 这一**分档写法**，**不是照抄它的数值** —— 数值必须按本用例重新取（下段给出）。仍不引入 criterion 等新机制：

```rust
// core/cf-totp/src/lib.rs:626（既有先例，注释原文：
// "Target: < 1ms per generation. Debug builds are ~50x slower, so allow 50ms there."）
// ⚠️ 范式示意：下面的 50 / 1 是 cf-totp 的取值，**不是**本用例的取值。
let budget = if cfg!(debug_assertions) {
    std::time::Duration::from_millis(50)   // ← 搜索不可沿用此值
} else {
    std::time::Duration::from_millis(1)
};
```

### 2.2 分档理由

- **v0.2 不能是 Touch ID**：当前最大业务风险是「没有导出，库文件是唯一数据载体」。BUG-2 的修复路径是**人类签名决策**，属外部阻塞。把可控交付物（导出）与外部阻塞项放进同一出口，等于让导出无限期等签名。
- **每版都是一个能发给用户的可交付增量**，不含「无出口的功能开发版」。
- **v0.3 起点是「附件与导入同版」**，不是「导入」——见 §2.3。

### 2.3 强制修正：附件必须与 1PUX 导入同版（v0.3）

这是一处**跨版本边界的交互缺陷**，必须显式记录修正理由：

| 事实 | 出处 |
| --- | --- |
| `FR-7.1` 导入 1PUX 要解析 `export.attributes`、`export.data`、**`files/` 目录** | `01-需求分析.md:291` |
| `FR-7.8` **无条件**强制「导入后提示删除源导出文件（明文风险）」 | `01-需求分析.md:298` |

**缺陷链**：若附件存储晚于导入一个版本，用户在导入版按提示删掉了**唯一持有附件的源文件**，而附件尚无任何落库能力 → **附件永久丢失**。

**两条 Must 在同版内互斥**，故：

> **附件存储（FR-9.1/9.2）与 1PUX 导入（FR-7.1）同版落在 v0.3。**

⚠️ **注意区分**：v0.3 落地的是**附件存储（无 UI）**——附件**交互界面（FR-9.3/9.4）在 v0.4**。读者不应以为 v0.3 就能在 UI 里使用附件。

替代方案（若因故必须拆分）：v0.3 的删除提示必须**条件化**——附件未落库时不得提示删除源文件，或必须明示「附件尚未支持，删除源文件将永久丢失附件」；且导入侧必须明确定义 `files/` 的处置（计入预检报告并计数，**绝不静默丢弃**）。**本路线图采用「同版」方案，不采用此替代方案。**

**删源提示的开启条件（本节的推广，非仅附件）**：条件是「**预检报告已 surface 全部降级**」，**不是**「无未导入项」。附件只是降级的一种；§8 **E-4** 的类别歧义降级（`004`×1、`112`×1 → 「保守留空 + 归入 Notes」）**计为导入成功**，因此**不会**出现在 FR-7.6 的「未导入项」清单里 —— 若删源提示只看「未导入项」，这 2 条的真实类别会在用户按提示删源后**永久不可恢复**（类别信息只存在于源文件）。故 FR-7.8 的提示条件须写成：

> **当且仅当预检报告已 surface「未导入」与「已导入但降级」（含「类别未识别」）两类中的全部条目时，才提示删除源文件**；否则提示**保留**源文件，并逐条列出降级项。

这与附录 A-16 是同一处修正的两个侧面（A-16 管措辞是否数据驱动，本段管条件是否覆盖全部降级）。

### 2.4 Touch ID 不绑定任何版本

- BUG-2 是**人类签名决策**（cygnus 登录 Apple ID 生成开发证书）。把它绑进任何版本的出口判据，都会让那一版被无限期卡死。
- **登记为「BUG-2 解除后即可发布的独立交付项」**，代码已完成（`docs/08` T01–T04，`b3d7888`→`d8b4b72`）。
- 后续动作：在 `docs/KNOWN-ISSUES.md` 的 BUG-2 条目中补一行指向说明（本次工单未触及该文件，作为待办登记在 §10.4）。
- 由此，`docs/08` 的 T01–T05 **不映射到任何 `vX.Y-Tnn` 编号**（见 §4.3），它们保留设计文档的局部序号。

### 2.5 v1.0「冻结」= 冻结功能，不是冻结代码

审计会发现 CRITICAL/HIGH 问题，**修它们就是代码变更**。因此：

- v1.0 必然包含修复工作，必须**预算「修复 + 审计方复验」一轮**；
- 必须**提前 1–2 个月采购审计**，否则 v1.0 会卡在采购上；
- 措辞用「**报告不再覆盖当前代码**」（报告绑定 commit hash），**不要**写成「审计结论当天即失效」。

## 4. 全局任务编号方案

### 4.1 现状：两个命名空间撞车 + 一个孤儿

| 命名空间 | 位置 | 任务 | 状态 |
| --- | --- | --- | --- |
| A | `07` §任务表（`:348-352`） | T01~T05（macOS 纵切） | 全部 ✅ 关闭 |
| B | `08` §任务表（`:350-354`，**复用同样标签 T01~T05**） | T01~T05（Touch ID） | T01~T04 代码 ✅，T05 待真机 |
| 孤儿 | `06` 修订 r1.8/r1.9 | **T06**（TOTP 语义） | 已关闭，但**不属于 A 也不属于 B** |

**病根**：任务 ID 用**文档局部序号**，不同设计文档各自从 T01 起编 → 跨文档即撞车；T06 是因「续编 A 的序号」而产生的孤儿。

### 4.2 方案：发布版本作用域前缀 `vX.Y-Tnn`

格式 **`v0.2-T01`**。两条**强制规则**：

> **规则 1（不改号）**：任务一旦分配编号，**永不重编**。任务取消则编号作废留空，**不得回收给新任务**。`docs/06` 的修订记录、commit message、`KNOWN-ISSUES` 条目引用过的编号尤其不可改。
>
> **规则 2（禁止有歧义的裸引用）**：**跨版本、跨文档**引用任务，或该引用**将离开本文档**（commit message、`docs/06` 修订记录、`KNOWN-ISSUES` 条目、报告摘录）时，**必须带完整前缀**——禁止写「见 T03」，必须写「见 `v0.2-T03`」。理由是 `07` 与 `08` 都用 T01~T05（实测撞车见附录 B），且**摘录会丢掉章节上下文**，裸引用无法判定指向。
>
> **前缀的例外（①② 可省 / ③ 强制裸写）**：① **本版本自己的任务分解章节内**（§5/§6/§7）——版本已由该章标题与章首**带前缀的任务表**固定，歧义不产生，故依赖图与并行/串行说明可写 `{T01→T02}`；**但裸号仅可指本版本的 `vX.Y-Tnn`** —— 指 `07`/`08` 的局部序号时**必须带文档名**，否则正是本条要防的那次撞车；② **同一句内**已有带前缀的首次出现——如附录 A-8 先写 `v0.2-T01`、再写「进入 T02」；裸号**绑定到紧邻其前、且同一版本作用域内最近一次**带前缀出现，**跨版本时必须重新带前缀**；**若同句内另有按 ③ 裸写的序号，本情形不适用**；③ **复述或登记历史编号本身**（编号空间沿革、`07`/`08` 撞车事实、旧 ID 映射；如 §2.1 的「原孤儿 T06」、§4.1、§4.3、附录 B）时，**必须保持裸写**——此处的「裸写」指**不加 `vX.Y-` 前缀**，**非「不加任何限定」**，加前缀等于篡改历史；**指 `07`/`08` 局部序号时仍须带文档名**（如 `07` T02），与既有写法一致（§4.1「`06` 修订 r1.8/r1.9」、§4.3「`06` 孤儿 T06」）；**正文指路**历史编号时**按规则 2 处理** —— 历史编号无 `vX.Y-` 前缀可加，故以**文档名**代替（如 `07` T02）。
>
> 判断标准是**歧义风险，不是格式统一**：规则要能把「危险的省略」与「无害的省略」区分开，否则会被稀释成没人当真的条文。

配套约定：
- 一个任务只属于**一个**发布版本（其出口判据所在版本）；
- 版本内从 `T01` 起编；**`T00` 保留给该版本的「前置门槛」**（无用户可见功能的工作）；
- 设计文档（`07`、`08`）内的局部序号**保留不改**（那是章节序号），在本文 §4.3 统一映射。

> **术语对照（仅此一处说明，本文其余各处统一用「单测隔离」）**：WI-1 报告把 #2 与批次 A 的条件称作「**名称过滤隔离**」，指的是同一件事——**只按名字选中该 1 条测试、bin 内没有其它测试在跑**；本文统一称「单测隔离」。报告 §2.5.1 另把「单线程串行（`--test-threads=1`）」列为**待证**（B 级），本文同样不采用。
