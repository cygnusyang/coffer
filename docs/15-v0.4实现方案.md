## 0. 结论先行

1. **三项工作流全部可进 v0.4.0，无需顺延大项**。Rust 内核侧只剩一处真实缺口：**附件的 cf-session 门面方法不存在**（`AttachmentRepo` 只有 cf-importer 与 `copy_item` 内部可达，`VaultSession` 无任何附件方法）——这是工作流 A 的主体 Rust 工作。其余 Rust 侧（跨库复制、密码短语、模糊搜索）内核全部就绪。
2. **错误码零新增**。全部场景落在既有码空间（1001/1002/1005/1011/1012/5001/5002）；候选码 1013（AttachmentNotFound）仅在实现证明需要区分「附件行不存在」时启用，初始设计不引入（§4）。
3. **FR-11.2 实质已关闭**：UI 搜索框已经路由到 `session.search`，而内核 `search` 即 v0.2 提前交付的模糊多字段实现（标题+用户名+URL+标签、词级编辑距离 ≤1）——核对结论：**仅 `.searchable` 提示文案「按标题搜索」过时**，改一行文案即关项（§3.3.6）。
4. **多库不推翻 Q-2 单库裁决**：裁决原文是「架构支持、UI 只做单库（最近创建/最近打开的一个）」——v0.4.0 是 FR-1.2 的 UI 面（Must），即裁决的**到期升级**而非推翻。多库方案维持「**UI 层任一时刻至多一个解锁会话活跃**」不变量，切换 = 锁旧开新；Touch ID 的 K_bio 天然按库隔离（Keychain account=vault_uuid，docs/08 §3.2），零改造。
5. **FR-5.6 采用「序列复制」**：复制密码（走现有自动清除）→ 延迟 8 s 复制 TOTP 验证码（走 FR-5.5 不清除路径）。changeCount 守卫使交接天然安全；锁定即取消待复制（§3.3.4）。
6. **并行分组四组**：MA（附件内核门面）、MB（多库会话改造）、MC（菜单栏/快捷键）可两两并行（文件范围互斥，§6）；MW（FFI 收口批）**串行**独占 `core/cf-ffi/**`，在 MA 合入后一次收口全部 FFI 增量。Swift 热点 `AppModel.swift` 归 MB 独占，`MainView.swift` 归 MB 独占，`ItemDetailView.swift` 归 MA 独占；**MC 依赖 MB 合入后才能动 AppModel**（追加最小增量）。
7. **本方案无新增不可逆决策**：存储格式零变更（附件布局 v0.3.0 已冻结）、无 schema 变更、FFI 全部为增量方法。行为变更类决策（bootstrap 默认库选择、关窗驻留、FR-5.6 延迟值）**均已裁定**（2026-09-29 用户拍板，§10 留档），裁定后无新增不可逆决策。

## 2. 技术选型裁决

### 2.1 附件 FFI 的内容通道：整块 `Vec<u8>`，不做流式/分块回调

**备选**：

| 方案 | 做法 | 评估 |
| --- | --- | --- |
| **A. 整块字节跨 FFI（采用）** | `add_attachment(content: Vec<u8>)` / `read_attachment() -> Vec<u8>`（UniFFI ↔ Swift `Data`） | 100 MiB 上限内单次拷贝；与 D-3「不分块」对齐；UniFFI 原生支持 |
| B. UniFFI callback interface 流式读写 | Swift 侧实现 reader trait 逐块拉取 | 回调跨 FFI 的同步重入风险 + 绑定复杂度；v0.4 明确不做大文件优化，收益为零。否决 |
| C. 附件密文旁路：Swift 拿密文自己解 | 破坏「DEK/子密钥不出 FFI」根本纪律。**否决（安全红线）** |

**风险**：100 MiB 附件解锁一次 UI 内存峰值 ≈ 明文+密文+Data 拷贝 ~300 MB 量级——D-3 已裁决接受（v0.3.0 实测 100 MB 无内存问题）；Swift 侧纪律见 §3.1.4。

### 2.2 多库会话模型：单活跃会话不变量，不做多会话并存 UI

**备选**：

| 方案 | 做法 | 评估 |
| --- | --- | --- |
| **A. 单活跃会话 + 切换即锁旧（采用）** | AppModel 任一时刻只持一个「当前会话」；切换 = `lock()` 旧会话（密钥清零、UI 状态清空）→ `openSession(新)` | 与现有 `lock()` 语义零冲突；自动锁定/剪贴板档位/备份提醒全部只面向当前会话，改造面最小；内存密钥暴露面不随库数增长 |
| B. 多会话并存（每库独立解锁态，UI 切 tab） | factory 注册表本就支持多解锁会话 | 自动锁定计时、`clearOnLock`、备份横幅等**全部按会话展开**，改造面指数上升；两个解锁会话的剪贴板/审计边界语义不明。否决（YAGNI + 暴露面扩大） |

跨库复制是唯一需要「两个会话同时对象」的场景，但内核 `copy_item` 锁不双持 + 复制完即 `lock()` 目标库（§3.2.4），单活跃不变量在 UI 层保持成立。

### 2.3 菜单栏与全局快捷键：机制选型以调研报告为准，本文档钉死约束面

dev-researcher 产出 `docs/research-v0.4-menubar-hotkey.md`（任务 #1），**选型结论以该报告为准**。本方案预先钉死的约束（调研须在其中求解）：

1. **不得引入辅助功能（Accessibility）权限依赖**——docs/01 R-06 已裁定辅助功能模拟键盘方案不采用；若某机制（如 `NSEvent.addGlobalMonitorForEvents` 键事件）需要辅助功能授权则排除。
2. **零网络**：不新增任何 network entitlement；不引入带网络能力的依赖。
3. App 保持**常规应用**（Dock 可见，不设 `LSUIElement`）——菜单栏是叠加入口而非替代主窗口。纯 `LSUIElement` 形态随裁定 ③（关窗驻留采纳，2026-09-29）一并否决，留档备查。
4. 快捷键默认值（NFR-UX-03）：**已定稿 ⌥⌘P**（2026-09-29 用户裁定；备选 ⌥⌘K / ⌃⌥⌘Space 仅留真机验证记录）。调研仍须对 ⌥⌘P 做系统冲突面验证，冲突时回退备选并留档。

## 3. 各工作流设计

> 以下签名即并行开发的冻结契约。签名改动必须回到本文档走评审，不得在实现中静默变更。

### 3.1 工作流 A：附件 FFI 收口 + 交互 UI（FR-9.3 / 9.4）

#### 3.1.1 裁决：cf-session 新增附件门面（本版唯一 Rust 开发项）

`AttachmentRepo` 需要显式 `file_key` / `attach_mac_key` 与 `vault_dir`，这些只在解锁态 `UnlockedState` 内可得——门面必须落在 cf-session（镜像 `import_1pux` 的薄委托模式），**不是**把 `repos()` 提升为 pub（那会把整组仓库暴露给 FFI 层，违背最小暴露面）。

#### 3.1.2 接口签名（cf-session 门面 + FFI）

```rust
// core/cf-session/src/usecase/attachments.rs（新）
/// FFI 可见的附件元数据（镜像 cf_store::AttachmentMeta，i64 时间戳）。
pub struct AttachmentInfo {
    pub uuid: String,        // 附件行 UUID（旁路文件名同名）
    pub item_uuid: String,
    pub filename: String,    // 解密后明文
    pub size_bytes: i64,
    pub created_at: i64,     // Unix 秒
}

impl VaultSession {
    /// 列出条目附件（created_at 升序）。锁定 → 1001；条目不存在 → 1011。
    pub fn list_attachments(&self, item_id: &str) -> SessionResult<Vec<AttachmentInfo>>;
    /// 添加附件（filename 为 UTF-8 明文；content ≤ 100 MiB，超限 → 1012，
    /// 内核 add() 已有同判，门面预检快失败）。
    /// 事务内 INSERT 行（复用 with_tx），文件先行纪律由 AttachmentRepo::add 承担。
    pub fn add_attachment(&self, item_id: &str, filename: &str, content: &[u8])
        -> SessionResult<AttachmentInfo>;
    /// 读附件明文内容（一次一个、即用即弃；行不存在 → 1012，行在文件无 → 1005）。
    pub fn read_attachment(&self, attachment_uuid: &str) -> SessionResult<Vec<u8>>;
    /// 删除附件（AttachmentRepo::remove：先删行后删文件）。锁定 → 1001。
    pub fn remove_attachment(&self, attachment_uuid: &str) -> SessionResult<()>;
}
```

FFI（MW，挂 `VaultSession`）：

```text
object VaultSession:
  list_attachments(item_id)                          -> Vec<FfiAttachmentMeta>
  add_attachment(item_id, filename, content: Data)   -> FfiAttachmentMeta
  read_attachment(attachment_uuid)                   -> Data          # ≤100 MiB 明文
  remove_attachment(attachment_uuid)                 -> ()
```

类型（types.rs）：`FfiAttachmentMeta { attachmentUuid, itemUuid, filename, sizeBytes: Int64, createdAt: Int64 }`（usize 不跨 FFI → sizeBytes 用 Int64；UniFFI `Vec<u8>` ↔ Swift `Data`）。

**边界声明**：`add_attachment` 只校验条目存在（1011），**不限制条目状态**（Trashed/Archived 态在 UI 不可达，内核不强限——与 `update_item` 的状态门禁不对称，属有意收窄的 v0.4 边界，登记为已知边界）；同文件名不判重（1PUX 导入同语义）。

#### 3.1.3 硬删条目的附件文件级联（既有缺口修复）

现状：硬删只级联 DB 行，`attachments/<uuid>` 旁路文件永久孤儿。修复落**会话层编排**（items.rs 与事务闭包不动）：

```rust
// core/cf-session/src/vault.rs delete_item 路径（编排级改动，~15 行）：
// hard = true 时：事务前 list_for_item(item_id) 收集附件 uuid 列表
//   → with_tx 硬删成功返回后 → 逐个 unlink(vault_dir/attachments/<uuid>)
//   （缺失容忍：文件不存在跳过；删除失败不回滚 DB 行——孤儿由
//   cleanup_orphans 语义兜底，与 attachment.rs「先删行后删文件」纪律一致）
```

软删/恢复不动附件（回收站恢复后附件仍可用——现状语义，测试钉住）。

#### 3.1.4 Swift UI（MA 阶段二）

- **`Views/AttachmentSection.swift`（新）**：条目详情页附件区。列表行 = 文件名 + 大小（人读格式）+ 时间；操作 = 添加（`NSOpenPanel`，`user-selected.read-write` entitlement 既有）/ 保存（`NSSavePanel`）/ 删除（确认对话框：**文案明示「附件将从库中永久删除」**）。
- **明文暴露面（诚实声明，沿 docs/07 §4.2 体裁）**：
  1. **预览不落盘**：图片 ≤ 一定尺寸用 `NSImageView`（`Data` 直接构造 `NSImage`）、PDF 用 `PDFKit.PDFDocument(data:)`——**内存预览**，明文不写磁盘；预览 Data 仅 AttachmentSection 行内局部状态持有，关闭预览即释放，不进 AppModel。
  2. **打开 = 显式导出**：其他类型走 `NSSavePanel` 导出后 `NSWorkspace.open`；UI 固定提示「导出文件为**明文**，请用后删除」。大文件优化不做（D-3）。
  3. `read_attachment` 取回的 `Data` 不进 `@Published`、不进环境对象（与 `getFieldValue` 同纪律）。
- **FR-9.4 Document 条目**（最小形态）：`Support/ItemTemplates.swift` Document 模板详情渲染时附件区**置于字段区之上**；新建 Document 保存后自动弹出添加附件面板（可跳过）。不做「条目即单文件」的强绑定（一个 Document 条目可挂多个附件，与 1PUX 导入挂载语义一致）。
- 复制条目（库内复制/跨库复制）已由内核携带附件（copy_item 载荷含附件），UI 零额外处理。

#### 3.1.5 测试要点（TDD）

1. cf-session 门面（Rust）：add → list → read_content 回环逐字节相等；filename 中文/空格/emoji 往返。
2. 超限：101 MiB → 1012，且 `attachments/` 目录无残留文件（快失败先于任何 IO）。
3. 锁定态四方法全部 1001；条目不存在 add/list → 1011；行不存在 read/remove → 1012；文件被外部删除 read → 1005。
4. 跨 FFI（MW）：`add_attachment` 经 FFI → 密文落盘断言（旁路文件 ≠ 明文）；`read_attachment` 回环相等；panic 注入 → 5999 进程存活。
5. 硬删级联：条目挂 2 附件 → hard delete → 行消失**且两个旁路文件消失**；软删 → 文件仍在，恢复后可读。
6. UI（真机/手工清单进 docs/13）：添加 → 预览（图片/PDF）→ 保存 → 重开 App 仍在；1PUX 导入携带附件的条目详情页附件可见可打开。

### 3.2 工作流 B：多库 UI（FR-1.2）+ 跨库复制 UI（FR-2.10）

#### 3.2.1 AppModel 多库会话改造（MB-1）

**不变量（本方案的核心约束）**：UI 层任一时刻至多一个解锁会话活跃；`factory` 注册表可持多个**已锁定**会话对象（现状即如此，注册表持引用只为幂等）。

  3. 无库 → `noVault`（现状）。

```text
  copy_item(item_id, dst: VaultSession)              -> String   # 目标库新条目 uuid
  # 密码短语（FR-3.3）
  generate_passphrase(opts: FfiPassphraseOptions)    -> String
```

共 **6 个方法 + 2 个类型**，全部增量、无破坏性签名变更。纪律沿用 docs/07 §2.3：全同步、`session_call` panic 守卫、时间戳 i64 Unix 秒、DEK/SubKeys 不出现在任何签名、usize 不跨 FFI、UniFFI 不支持元组（本批无元组需求）；改 FFI 后必须 `tools/build_swift_bindings.sh` 重生成，**该批次内不再触 Rust**（交接清单 §4 纪律 4）。

#### 6.1 AppModel.swift 改动切片裁定（r1.1 补充：lead 核实其为三工作流共同热点）

**裁定：AppModel.swift 切不开，按「S1 重构主体先行 → 其余组零改动 → 强制需求串行追加」三段式串行链执行。** 不做文件内分片并行。

**理由**：AppModel 是 650 行的 `@MainActor` 状态机，方法体互相咬合——`openSession` 回放设置项、`lock()` 清 UI 状态与剪贴板、`bootstrap` 编排、`evaluateBackupReminder` 与两条解锁路径的收尾交织。对方法体的并行改动即使 git 合并成功也不等于语义正确（自动锁定/剪贴板/退避三处状态机的隐式耦合无法靠 diff 冲突检测暴露），故不采用「各组分方法体切片」方案，统一串行。

| 切片 | 执行组 | AppModel.swift 改动量 | 内容 |
| --- | --- | --- | --- |
| **S1** | MB-1 | **重构主体（唯一授权批次，预计 ≤ 40 行）** | `bootstrap` lastVaultUUID 优先 + `switchVault(to:)` + 库列表缓存；`openSession` 语义不变（复用） |
| **S2** | MA-2 / MB-2 | **零改动（设计强制）** | 附件区与跨库复制 sheet 自持状态：`session` / `vaultUUID` / `factory` 均为既有可读成员，经 environmentObject 只读消费；`read_attachment` 的 Data 只进行内局部状态（§3.1.4），不新增 AppModel 属性 |
| **S3** | MC-1 | **零改动（目标），允许最小追加** | 主窗口呼出自持逻辑（AppDelegate.summonMainWindow），经只读 phase 判定焦点；呼出走 `NSApp.activate` 不经 AppModel；菜单「锁定全部」走 `factory.lockAll()` + `model.lock()` 既有 API。若实现证明必须追加：**仅允许新增** `@Published` / 计算属性 / 方法，**禁止修改既有方法体**；追加发生在 S1 合入后的 MC 分支（串行） |

**违反处置**：任何组在 S1 合入前对 AppModel.swift 的改动一律 rebase 到 S1 之上；实现中发现方法体级需求的，回本文档登记后并入 S1 批次或排队 S3，不得就地修改。

**合并顺序**：

```
MA-1 ──→ MW ──┬─→ MA-2 ──→ MB-2
              ├─→ MC-2
MB-1 ──┬──────┴─→（rebase）
       └─→ MC-1 ──→ MC-2
```

MA-1 与 MB-1 全程并行；MW 在 MA-1 后立即启动（不等 MB）；MA-2 / MB-2 / MC-2 在 MW 后并行（ItemDetailView 的 MA-2→MB-2 串行除外）；MC-1 等 MB-1。每组合入前跑门禁四连（`cd core && cargo test --workspace --no-fail-fast` + clippy `-D warnings` + build_macos_app.sh + codesign；Swift 侧无自动门禁，按交接清单 §4 逐项闭环）。reviewer LOW 登记（r1.5）：门禁四连无脚本封装（docs/09 §3.2 T00 可选遗留 `tools/gate.sh` 未做），暂维持手工执行；封装列为顺手项不阻塞发版——封装须内置管道吞退出码防护（docs/09 §4 纪律 2，`${pipestatus[1]}` 或 `set -o pipefail`）。
