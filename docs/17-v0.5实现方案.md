## 0. 结论先行

1. **存储前提已满足，零 schema 迁移**：passkeys 表随 fmt-v1 冻结建齐（`cf-store/src/schema.rs:158`，含 `rp_id_hmac` 部分索引与 COSE `algorithm` 整型列），仓库层未实现——Rust 内核是纯增量，降级路径（导入/查看/删除）的存储前提自 v0.1 起就成立（回应调研 §6「须由 dev-architect 核实」）。
2. **双分支共用面先行**：无论 M0-⑤a 探针结果如何，内核（PasskeyRepo + cf-session 门面 + WebAuthn 原语 + 1PUX 导入解析）与查看/删除 UI 都是必做面——这是 D-5 降级面（FR-10.1/10.2/10.5/10.6）与全功能面的公共子集。**探针结果只裁剪上层，不改变内核设计**（lead 裁定）。
3. **私钥操作全部收在 Rust core**（ES256 签名、COSE/CBOR 序列化），扩展 Swift 层只见平台请求/响应——「私钥不出会话」是 DEK 不出 FFI 纪律的自然延伸。签名库选 p256（RustCrypto，MIT/Apache），CBOR 复用 workspace 既有 ciborium，**零新增序列化依赖**。
4. **两处不可逆候选，均标注待用户确认**（§11）：① `enc_private_key` 字节编码格式（用户库写入即事实冻结）；② 全功能分支的「自动填充启用」若走库迁移入 App Group 容器（用户数据路径变更）。除此之外无新增不可逆决策。
5. **错误码零新增预期**：复用 1001/1005/1011/1012/2001/2002；候选 3002（AssertionFailed）仅在 M0-⑤b 证明需要区分时登记 docs/03 §12（§5）。
6. **并行分组三组 + 串行 FFI 批**：PK1（内核）∥ 无并行 Swift（PK2/PK3 都依赖 FFI）→ PW（cf-ffi 独占串行）→ PK2 ∥ PK3；PK3 额外以 M0-⑤a+⑤b 通过为门禁（§7）。
7. **iCloud 不同步按特性声明**（lead 裁定）：第三方凭据提供者路径下 iCloud Keychain 同步从设计上不存在——「Passkey 不跨设备同步，跨设备靠库文件搬运」写进用户文档，是零网络的正向表述而非限制（调研 §3）。

## 3. 技术选型裁决

### 3.1 D-1 私钥编码格式（⚠️ 不可逆候选，待用户确认）

`enc_private_key`（BLOB，DDL 冻结）存什么字节格式——用户库一旦写入即事实冻结（类比 D-1 备份格式裁定）。

| 方案 | 做法 | 评估 |
| --- | --- | --- |
| **A. PKCS#8 DER（采用建议）** | ES256 私钥存标准 PKCS#8；`algorithm` 列存 COSE alg 编号（-7），DDL 已对齐 | 标准编码、p256/openssl/Swift CryptoKit 全生态可读、调试工具链成熟；WebAuthn 层需要 COSE 时由 Rust 侧按 algorithm 包装转换（单向、确定性、可测） |
| B. COSE Key 结构直接存 | WebAuthn 原生形态 | 少一次转换，但解析链长、生态工具少、跨语言调试困难。否决 |

**为什么现在必须定**：降级路径（导入 1PUX passkey）也会写入该字段——「分支裁剪」不影响此决策的不可逆性。

### 3.2 D-2 签名与序列化落点：Rust core（cf-crypto），扩展层零密码学

**备选**：

| 方案 | 做法 | 评估 |
| --- | --- | --- |
| **A. Rust core（采用）** | `cf-crypto/src/webauthn.rs`：ES256 keypair 生成（CSPRNG）、断言签名、COSE key 编码；扩展 Swift 层经 FFI 取「现成的响应载荷」 | 私钥永不离开会话（DEK 纪律延伸）；确定性 CBOR 可单测；与平台 API 解耦（M0-⑤b 只验接口形态，不重写密码学） |
| B. Swift CryptoKit P256 在扩展内签名 | 私钥跨 FFI 下发到 Swift | 违背「密钥材料不出会话」根本纪律。**否决（安全红线）** |

**依赖**：`p256`（RustCrypto，MIT/Apache——NFR-LEGAL-02 ✓）+ `signature` trait；CBOR 复用 workspace `ciborium`（cf-domain/cf-format 既有，零新增序列化依赖）。**平台 API 与 Rust 的对接形态（attestation/挑战载荷在谁手上组装）标注「待 M0-⑤b 真机复验」**——调研风险 5，本方案不冻结该细节。

### 3.3 D-3 rpId 检索：锁定态 HMAC 索引 + 解锁态全量

`rp_id_hmac`（DDL 部分索引）= `HMAC-SHA256(attach_mac_key 同族子密钥, rp_id)`——锁定态可判断「本库是否有某 rpId 的 Passkey」而不解密 rpId（与 docs/03 §8 AUD-02 指纹比对同型）。**子密钥标签 `cf/passkey-idx/v1`**：HKDF 派生运行时行为，不落盘、不改 DDL，但 SubKeys 增第 10 把子密钥属跨 crate 契约变更（v0.2 audit_key 先例）→ **列为待确认项**（§11；备选：在既有某把子密钥上 HKDF-expand，派生链多一跳）。

扩展查询路径（E1，待 M0-⑤b 复验）：`prepareCredentialList(for:requestParameters:)` 携带 rpId → 扩展经共享数据面 open 库（锁定态则先引导解锁）→ `rp_id_hmac` 索引命中 → 解密展示候选列表。

### 3.4 D-4 扩展与宿主的数据共享通道（全功能分支最大设计点）

**约束事实**（调研 §4）：扩展独立沙盒容器；宿主 security-scoped 授权不继承；钥匙串经 `keychain-access-groups` 同名组天然共享（既有）；库文件路径是问题本体。

| 方案 | 做法 | 评估 |
| --- | --- | --- |
| **A. App Group 容器（主选）** | 「为自动填充启用本库」= 将 vault_dir **原子移动**到 Group 容器（`~/Library/Group Containers/group.<team>.app.coffer.Coffer/vaults/<uuid>/`）+ 共享引导文件记录路径；主 App 后续从新路径打开（UserDefaults 记录 + 兼容旧路径检测） | 单一授权点、双进程同权；**库位置变更 = 不可逆候选**（§11）；原子目录移动 + 失败回滚协议在探针过后细化评审；免费账号 App Groups 可用性未验证——M0-⑤b 探针项 |
| B. 扩展内重选（兜底） | 扩展 UI 内 NSOpenPanel 让用户重选库目录 | 零迁移，但每次系统弹层都要选库的体验不可接受；仅作 A 失败时的降级。NSOpenPanel 在扩展内可用性同为探针项 |

**裁定**：A 主选、B 兜底；**启用自动填充是逐库显式动作**（非全库默认）——多库下只把用户明确启用的库迁入 Group 容器，与其余库隔离，攻击面与迁移范围最小。迁移协议细节（原子性、中途断电、路径别名）在 M0-⑤b 通过后单开设计小节评审，本方案不冻结。

### 3.5 D-5 ASCredentialIdentityStore 元数据明文（诚实声明）

`ASPasskeyCredentialIdentity`（rpId + 用户名等）以**明文**写入系统凭据身份存储——这是 AutoFill 建议列表工作的平台前提，不可加密。与 docs/03 §3.5 元数据泄露清单同类取舍（opvault 同设计）。`rp_id_hmac` 是**库内**加密索引；系统面 rpId 必然明文。**用户文档 + 设置页声明**，列 §11 知情确认。

## 4. 各工作流设计

### 4.1 PK1：Rust 内核（共用面 C1/C2/C3/C6）

#### 接口签名（冻结契约）

```rust
// core/cf-store/src/repo/passkey.rs（新；DDL 冻结，仓库纯增量）
pub struct PasskeyMeta {           // FFI 可见，无私钥
    pub uuid: String,
    pub item_uuid: String,
    pub rp_id: String,             // 解密明文
    pub rp_name: Option<String>,
    pub user_name: Option<String>,
    pub credential_id_b64: String, // base64（凭据 ID 非密钥，FR-10.2 允许展示）
    pub algorithm: i64,            // COSE alg（-7 = ES256）
    pub sign_count: i64,
    pub created_at: i64,
    pub last_used_at: Option<i64>,
}
impl PasskeyRepo<'_> {
    pub fn add(&self, item_uuid: &str, record: &PasskeyRecord, now: i64) -> CfStoreResult<String>;
    pub fn list_for_item(&self, item_uuid: &str) -> CfStoreResult<Vec<PasskeyMeta>>;
    pub fn list_by_rp_index(&self, rp_id_hmac: &[u8]) -> CfStoreResult<Vec<PasskeyRow>>; // 锁定态索引
    pub fn remove(&self, passkey_uuid: &str) -> CfStoreResult<()>;
}
// PasskeyRecord = 明文载荷结构（rp_id/user_handle/credential_id/private_key(PKCS#8)/…），
// 加密封装沿用全仓库层统一 AAD 约定：field_aad("passkeys", uuid, 列名)；
// rp_id_hmac 列写 HMAC（D-3 子密钥）。

// core/cf-crypto/src/webauthn.rs（新；D-2）
pub struct Es256KeyPair { /* PKCS#8 封装，ZeroizeOnDrop */ }
pub fn generate_key_pair() -> Result<Es256KeyPair, CfError>;
pub fn sign_assertion(key: &Es256KeyPair, auth_data: &[u8], client_data_hash: &[u8])
    -> Result<Vec<u8>, CfError>;
pub fn cose_public_key(key: &Es256KeyPair) -> Result<Vec<u8>, CfError>;
// ⚠️ auth_data/attestation 载荷的组装边界「待 M0-⑤b 真机复验」，本签名不冻结该入参语义。

// core/cf-session/src/usecase/passkeys.rs（新）
impl VaultSession {
    pub fn list_passkeys(&self, item_id: &str) -> SessionResult<Vec<PasskeyMeta>>;      // 1001/1011
    pub fn add_passkey(&self, item_id: &str, record: &PasskeyRecord) -> SessionResult<String>;
    // D-6：add 前校验条目存在（1011）；只增不改——不改条目字段/密码（FR-10.6）。
    // 注册产物走 create-or-attach：rp_id_hmac 命中既有条目 → 挂靠；否则新建 Login（无密码不强制）。
    pub fn remove_passkey(&self, passkey_uuid: &str) -> SessionResult<()>;               // 1001
    pub fn passkey_candidates_for_rp(&self, rp_id: &str) -> SessionResult<Vec<PasskeyMeta>>; // E1 查询路径
}

// core/cf-importer/src/pux/passkey.rs（扩展既有 1PUX 映射；iOS/Android 导出源）
// 预检报告增 passkey 计数与解析失败行（沿 FR-7.4「不静默丢弃」纪律）；
// 导入失败语义沿 2001/2002。
```

#### 文件清单（PK1）

`cf-store/src/repo/passkey.rs`（新）、`repo/mod.rs`（聚合体 + 重导出）、`cf-crypto/src/webauthn.rs`（新）、`cf-crypto/src/lib.rs`、`cf-session/src/usecase/passkeys.rs`（新）、`usecase/mod.rs`、`vault.rs`（挂接 + SubKeys 第 10 把子密钥，D-3）、`cf-importer/src/pux/passkey.rs`（新）+ `pux/mod.rs`、`precheck.rs`（passkey 计数）、各自 Cargo.toml（p256 依赖）、集成测试。

#### 测试要点（TDD）

1. Repo 回环：add → list_for_item 逐字段相等；私钥密文落盘断言（BLOB ≠ PKCS#8 明文；跨行搬运解密失败——沿 totp 仓库测试模式）；`rp_id_hmac` 命中/未命中。
2. D-3：同 rpId 不同子密钥 → 指纹不同（防跨库比对）。
3. WebAuthn：keypair 生成两次不同；签名可验（p256 verify 回环）；PKCS#8 编码可被标准解析（固定向量）。
4. FR-10.6：add_passkey 后条目 fields/urls/totp 逐字节不变（只增不改回归）。
5. 导入：iOS/Android 1PUX 样本（合成）passkey 解析回环；预检计数；坏 passkey 行不丢条目（并入告警）。
6. 删除：remove 后行消失；条目硬删 → passkeys 行级联消失（FK 已冻结）。

## 10. 明确不做（本版）

- Android / iOS（docs/09 v0.5.0 卡片）。
- iCloud 同步——**特性**：第三方提供者路径下同步从设计上不存在；「Passkey 不跨设备，跨设备靠库文件搬运」写用户文档（lead 裁定）。
- FIDO2 QR / iPhone hybrid 跨设备传输：第三方提供者不参与该流程（调研 §3 已知限制），零网络下亦无诉求。
- 浏览器扩展形态（Chrome/Firefox）：macOS 系统级凭据提供者已覆盖 Safari 及系统 AutoFill；其他浏览器不进本版。
- Passkey 条目历史 / 审计扩展（audit_local 已有 ItemPasskey 类事件与否随实现核对，不扩审计 schema）。
- 多库同时启用自动填充的批量迁移编排（逐库显式启用，§3.4）。
