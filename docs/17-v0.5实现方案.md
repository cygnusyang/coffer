## 0. 结论先行

1. **存储零迁移**：passkeys 表随 fmt-v1 冻结建齐（`cf-store/src/schema.rs:158`——rpId/credentialId/signCount 等结构化列 + `rp_id_hmac` 部分索引），仓库层未实现。调研 v2 §4.2 的「结构化字段而非 attachment 旁路」建议与既冻结 DDL 完全一致，无需任何 schema 动作。
2. **数据源两路 + 库文件免费第三路**：① 1PUX（仅 iOS/Android 导出含 passkey，桌面端无——`01` 已定论）；② **Bitwarden JSON 导出（调研 v2 新确认含 passkey，`fido2Credentials` 字段——官方文档确认但 schema 非互通承诺，【单源】，实现期须逆向核对字段）**；③ Coffer 备份恢复随 db.sqlite 整体搬运，零工作（§3.4 TCA-7 裁定 (a)）。
3. **错误码零新增**：复用 1001/1005/1011/1012/2001/2002；v0.5 降级版无断言路径，3002 候选**撤销**（随 ADP 重启时再议）。docs/03 §12 零登记。
4. **无新增不可变**存储面；唯一不可逆决策已落定：`enc_private_key` = PKCS#8（**2026-09-29 lead 批准**；导入即写入用户库、事实冻结的属性不变——§3.1）。**构建零签名影响**：无扩展、无双 profile、无 App Group、无跨进程写锁（全随 ADP 购买后重启，调研 v2 §6：降级版零签名新依赖）。
5. **并行三组**：PK1（存储+会话）∥ PK2（双格式导入，按冻结签名先行）→ PW（FFI 串行批）→ PK3（查看/删除 UI）。合计 ≈ 1–1.5 周（调研 v2 §6 成本口径）。
6. **FR-10.6 在降级版的落地 = 导入映射规则**：passkey 作为条目的**新增附属数据**挂靠（item_uuid 外键），导入映射**不触碰** login/password 字段——「保留原密码」由映射规则 + 回环测试保证（§4.2 D-6），与调研 v2「passkey 是条目的新字段，不动密码字段」同构。
7. **备份面裁定（TCA-7 两面删一）**：选 **(a) 导出/恢复含 passkey 数据**——备份 ZIP 打包 db.sqlite 整体，passkey 行（已加密）天然随库走，**零代码增量**，仅新增回环测试（§4.4）；(b) 作废。

## 2. 分支状态与边界声明

**分支 B（降级版）已激活**（2026-09-29 用户裁定 D-5：暂不购买 ADP，需求变更即视为批准）。本文档即分支 B 设计；分支 A（完整版）E1~E6 设计文本**原样保留**于 r1.0（commit a755ec2 可溯）+ 要点摘录 §9——**休眠，ADP 购买后重启，重启前不实现**。**出口判据①②（创建/断言）作废声明**（按 `18` TCB-4 / TC-D3 措辞）：创建与使用为能力 absent（无凭据提供者扩展，非隐藏菜单），降级分支核销以 TCB-1~6 为准。

### 2.1 边界声明（降级形态的三条诚实边界）

1. **创建/使用能力 absent（TCB-4）**：本版无凭据提供者扩展——系统设置里不会出现 Coffer 提供者，网站/App 无法选择 Coffer 创建或使用 Passkey。这不是「有菜单但禁用」，是能力不存在。用户文档明示。
2. **iCloud 不同步是特性**（lead 裁定沿用）：Passkey 私钥存 Coffer 自有加密库，不经 iCloud Keychain（第三方提供者路径下同步从设计上不存在）；跨设备 = 库文件搬运（加密备份/恢复）。用户文档主动声明。
3. **数据源边界**：桌面端 1PUX 无 Passkey——已用 1Password 桌面版的用户首建数据需 iOS/Android 导出或改用 Bitwarden JSON，或网站重新注册（ADP 后）。用户文档明示（调研风险 4）。

## 3. 技术裁决

### 3.1 D-1 私钥编码归一化（不可逆决策，**已裁定 2026-09-29 lead 批准 PKCS#8**）

`enc_private_key`（BLOB，DDL 冻结）统一存 **PKCS#8 DER**；`algorithm` 列存 COSE alg 编号（-7 = ES256，DDL 整型列已对齐）。导入时归一化：来源格式（Bitwarden/1PUX 的私有编码，**实现期逆向核对**）→ 解析校验 → PKCS#8 落库；非 ES256 拒绝（预检显式列出，不静默丢弃）。

**为何降级版仍不可回避**：导入路径从第一天就写用户库——格式事实冻结不因分支裁剪而推迟（r1.0 裁定沿用）。归一化解析用 `p256`/`sec1`（RustCrypto，MIT/Apache；仅做解析与校验，**无签名运行面**——断言签名随 ADP 重启时引入）。

### 3.2 D-2 密码学边界：本版无新增运行面

ES256 **签名/注册**代码路径整体不存在（FR-10.3/10.4 absent）。`p256` 仅用于导入归一化的私钥解析校验（§3.1）。CBOR 复用 workspace `ciborium`（若导入解析需要）。**不做 COSE/attestation 组包**（完整版范围，§9）。

### 3.3 D-3 rp_id_hmac 索引：写入保留，查询面本版不暴露

`rp_id_hmac = HMAC-SHA256(子密钥 `cf/passkey-idx/v1`, rp_id)` 在导入时写入（未来 ADP 扩展的锁定态查询索引，写好等用）；本版 FFI **不暴露** by-rp 查询（无消费方）。子密钥 = SubKeys 第 10 把（跨 crate 契约变更，v0.2 audit_key 先例）——**已批准（2026-09-29 lead）**；备选 HKDF-expand 作废留档。

### 3.4 D-4 备份面裁定（TCA-7 两面删一）：选 (a) 含 passkey

备份 = 工作目录 ZIP（header.json + db.sqlite + attachments/，v0.2 D-1 既有格式）——passkey 行在 db.sqlite 内且已字段级加密，**导出/恢复天然含 passkey、零代码增量**。交付物 = 回环测试（导入 passkey → export_backup → 删库 → restore → 逐字段一致含私钥密文，§4.4 测试 7）；(b)「导出不含 passkey」作废（那反而需要刻意排除代码）。TCB-6 引用本读数。

### 3.5 移除项（r1.0 → r2.0 随降级裁剪）

凭据提供者扩展全部（E1）、双 entitlement（E2）、数据共享通道（E3，App Group/迁移协议——**库迁移不可逆候选随之撤销**）、构建面 `.appex` 组装（E4）、`ASCredentialIdentityStore` 明文元数据（E5，连带其知情声明撤销）、0 socket 扩展 PID（E6，主 App 判据沿用 docs/16 口径）、M0-⑤a/⑤b 探针依赖（#14 结果不再阻塞本版任何任务；探针本身保留为 ADP 购买后的重启前置）。

## 4. 各工作流设计

### 4.1 PK1：存储 + 会话（cf-store + cf-session）

```rust
// core/cf-store/src/repo/passkey.rs（新；DDL 冻结，仓库纯增量）
pub struct PasskeyMeta {           // FFI 可见，无私钥
    pub uuid: String,
    pub item_uuid: String,
    pub rp_id: String,
    pub rp_name: Option<String>,
    pub user_name: Option<String>,
    pub credential_id_b64: String, // base64（凭据 ID 非密钥，FR-10.2 允许展示）
    pub algorithm: i64,            // COSE alg（-7 = ES256）
    pub sign_count: i64,
    pub created_at: i64,
    pub last_used_at: Option<i64>,
}
pub struct PasskeyRecord {         // 明文载荷（导入路径）
    pub rp_id: String,
    pub rp_name: Option<String>,
    pub user_name: Option<String>,
    pub user_handle: Vec<u8>,
    pub credential_id: Vec<u8>,
    pub private_key_pkcs8: Vec<u8>, // D-1 归一化后
    pub algorithm: i64,
    pub sign_count: i64,
}
impl PasskeyRepo<'_> {
    /// 加密封装沿用全仓库层统一 AAD 约定 field_aad("passkeys", uuid, 列名)；
    /// rp_id_hmac 列写 HMAC（D-3 子密钥）。 signer 校验（非 ES256 → 1012）。
    pub fn add(&self, item_uuid: &str, record: &PasskeyRecord, now: i64) -> CfStoreResult<String>;
    pub fn list_for_item(&self, item_uuid: &str) -> CfStoreResult<Vec<PasskeyMeta>>;
    pub fn remove(&self, passkey_uuid: &str) -> CfStoreResult<()>;
}

// core/cf-session/src/usecase/passkeys.rs（新）
impl VaultSession {
    pub fn list_passkeys(&self, item_id: &str) -> SessionResult<Vec<PasskeyMeta>>; // 1001/1011
    pub fn remove_passkey(&self, passkey_uuid: &str) -> SessionResult<()>;         // 1001
}
// add 路径不设独立 FFI 门面——唯一来源是导入编排（PK2 经 with_tx 内 repos.passkeys.add，
// 镜像 attachments 在 cross_copy/1PUX 导入的既有用法）。ADP 重启时再增注册产物回写门面。
```

**文件**：`cf-store/src/repo/passkey.rs`（新）、`repo/mod.rs`（聚合体 + 重导出）、`cf-session/src/usecase/passkeys.rs`（新）、`usecase/mod.rs`、`vault.rs`（挂接 + 第 10 把子密钥，D-3）、crate 内集成测试。

**测试要点**：① add → list_for_item 逐字段相等；② 私钥密文落盘断言（BLOB ≠ PKCS#8 明文；跨行搬运解密失败——沿 totp 仓库测试模式）；③ `rp_id_hmac` 写入且同 rpId 同子密钥指纹一致 / 跨库不同；④ 非 ES256 → 1012；⑤ 条目硬删 → passkeys 行级联消失（FK 已冻结）、软删/恢复不动；⑥ remove 后行消失且文件面无副作用（纯 DB 行）。

### 4.2 PK2：双格式导入（cf-importer）

**D-6 FR-10.6 落地规则（本版关键设计点）**：passkey 是条目的附属新数据（item_uuid 外键挂靠），导入映射**不读取也不改写** login/password 字段——含 passkey 的条目照常携带密码字段入库。预检报告给出「含密码且含 passkey 的条目数」（FR-10.6 的可测试证据）；回环测试断言密码字段逐字节不变（§4.4 测试 8）。

```rust
// core/cf-importer/src/pux/passkey.rs（新）：1PUX passkey 字段解析
//   桌面 1PUX 无 passkey——解析器对「无 passkey 字段」是恒空快速路径，零回归面。
// core/cf-importer/src/bitwarden/（新目录）：
//   parser.rs   —— JSON 解析（serde 既有依赖；DoS 上限沿 docs/07 §3.1 口径：
//                  文件 ≤ 50 MB、items ≤ 10 000、单字段 ≤ 64 KiB；超限报错指明条目）
//   precheck.rs —— 预检报告：条目数 / passkey 条目数 / 解析失败逐条列出（不静默丢弃）/ 
//                  非 ES256 列表 / 「含密码且含 passkey」计数（FR-10.6 证据）
//   mapping.rs  —— 条目映射：login{username,password,uris,notes} 走既有字段映射语义；
//                  fido2Credentials[] → PasskeyRecord（归一化 PKCS#8，D-1）；
//                  密码字段映射与 passkey 挂靠互不触碰（D-6）
// ⚠️ Bitwarden fido2Credentials 字段形态为【单源】（调研 v2 §4.1：官方明示非互通承诺），
//    **实现期以真实导出样本逆向核对为准**——parser 对未知字段容忍（记 warning 不丢弃）。
```

**导入事务语义**：镜像 1PUX（每条目单事务，任一条目失败回滚该条、已成功保留）；预检只读可反复调用。

**会话门面存在性声明（r2.3 补，设计遗漏留档）**：`import_bitwarden_json` / `precheck_bitwarden_json` 须经 `cf_session::VaultSession` 门面才能到 FFI（DEK/SubKeys 不跨 FFI，`vault.rs` 既有口径——`import_csv` / `import_1pux` 均有门面先例）。r2.0 §4.1/§4.2 只定义了 importer 层编排，漏列该门面——**PW 批获一次性扩权**在 `vault.rs` 镜像 `import_1pux` 模式补 ~6 行门面（`unlocked?` 门禁 + 薄委托，1001/2001/2002 语义同 import_csv）。遗漏发现经过：**FFI 层（PW）开工实核 grep 发现，非审查发现**——教训：本文档「按冻结签名先行 / 集成实测」类表述今后必须注明**实测所在层**（importer 层实测 ≠ 会话→FFI 链路实测），跨层集成点须在文件闭集中显式列出。

**文件**：`cf-importer/src/pux/passkey.rs`（新）、`pux/mod.rs`、`bitwarden/{parser.rs,precheck.rs,mapping.rs,mod.rs}`（新）、`precheck.rs`（计数面）、`lib.rs`（编排入口 `precheck_bitwarden_json` / `import_bitwarden_json`）、`Cargo.toml`（如需 p256/sec1 传递依赖）、测试 fixtures（合成 Bitwarden JSON：含密码+passkey 条目 / 纯密码条目 / 非 ES256 / 坏 passkey 行）。

**测试要点**：① Bitwarden 合成样本回环：条目数、逐字段（含密码）、passkey 逐字段一致；② **FR-10.6 回环：导入前后 password 字段逐字节不变**；③ 非 ES256 / 坏 passkey 行 → 预检显式列出、导入跳过该行不丢条目（沿 FR-7.8 不静默丢弃纪律）；④ DoS 超限报错；⑤ 1PUX 无 passkey 桌面样本恒空快速路径（既有测试零回归）；⑥ 导入中途注入失败 → 该条目回滚。

## 5. 错误码核对

| 场景 | 错误码 | 结论 |
| --- | --- | --- |
| 锁定态 passkey 操作 / 导入 | 1001 | 复用 |
| 私钥解封——**结构性损坏**（密文短于 nonce+tag 最小长度） | 1005 Corrupted | 复用（仓库纪律两级口径，totp 预检同款先例；PK1 实测读数） |
