## 2. 技术裁决

### 2.1 FR-8.2 1PUX 导出（EX）

#### 2.1.1 输出格式与兼容度（裁决 A）

**结论：输出官方 1PUX v3 结构**（`export.attributes` version=3 + `export.data` + `files/`），字段键用**官方形态**（`fieldType` / `overview.urls` / `details.loginFields` / `details.notesPlain` / `details.sections` / `details.documentAttributes`），不发射合成样本的双键变体。

| 备选 | 说明 | 裁定 |
| --- | --- | --- |
| A. 官方形态 | 严格按 1Password 官方 1PUX 结构发射；`fieldType`、`documentAttributes`、`files/<documentId>___<fileName>` | ✅ **采用**——互操作目标（FR-8.2「可被其他支持 1PUX 的工具读取」）唯一有意义的方向 |
| B. 合成样本形态 | 发射导入侧合成样本用的 `item.file` / `type` 键 | 否决——仅本仓自洽，外部工具无法读 |
| C. 双键兼容发射 | 同时写 `fieldType` 与 `type` | 否决——冗余字段污染官方结构，且 `fieldType` 为对象时无 `type` 别名意义 |

**categoryUuid 反向映射**（行为契约 ①）：复用 `03` §6.4.1 opvault 权威表（001~111），反向映射 `cf-domain::ItemCategory → 三位码`。**映射表落 `cf-importer/src/pux/mapping.rs`**（`pub fn category_to_1p_code`），cf-exporter 跨 crate 引用——与 CSV `HEADER_*` 同范式防漂移。未命中（Custom/自定义）→ 落 `003`（SecureNote），与导入侧「未知 categoryUuid 降级 SecureNote」对称，保证回环稳定。

**风险**：`03` §6.4.2 明言官方未给出 categoryUuid 数值表，本实现以 opvault 表为基线（导入侧已如此）。若他方工具读错分类，属该基线固有风险，非本版新增。**缓解**：回环测试钉住 + 真实 1Password 交叉打开列为真机验收项（§2.1.6 诚实边界）。

#### 2.1.2 附件（裁决 B）

**结论：导出官方形态 B**——`details.documentAttributes{fileName, documentId, decryptedSize}` + ZIP `files/<documentId>___<fileName>`；`documentId` 用 UUIDv7 生成。附件密文经 `AttachmentRepo::read_content` 解密后流式写入 ZIP（deflate），不整体载入内存。

| 备选 | 裁定 |
| --- | --- |
| A. 官方 documentAttributes | ✅ 采用（互操作） |
| B. 合成 `item.file` | 否决（外部工具不识别） |

#### 2.1.3 Passkey（裁决 C）

**结论：1PUX 导出不含 passkey，报告计数不静默**。理由：桌面 1PUX 无 passkey 字段形态（`01` §5-J 限制① + 导入侧恒空快速路径同源）；Coffer 库内 passkey 私钥无 1PUX 标准桌面承载形态可验证。`PuxExportResult::skipped_passkeys` 显式计数，UI 结果页提示「Passkey 不随 1PUX 导出，请用加密备份迁移」。

#### 2.1.4 TOTP（裁决 D）

**结论：全量导出**（含非 SHA-1），TOTP 登录字段 `designation="totp"` + `value={"totp": "<otpauth://URI>"}`（导入侧同款读取形态，回环自洽）；URI 由 `TotpMeta`（algo/digits/period/issuer/account）+ secret 重建，复用 `cf-totp` base32。**与 CSV 导出的差异理由**：CSV 单列无算法承载（非 SHA-1 回写会被静默按 SHA-1 解析——故不导出）；1PUX 的 URI 自带 `algorithm=` 参数，他方工具按参数解，Coffer 自身导入侧仅 SHA-1（`v0.1 裁定`）会降级——报告注明「非 SHA-1 TOTP 经本仓回环降级 SHA-1，第三方工具不受影响」。cf-exporter 需将 `cf-totp` 从 dev-dependencies 升为正式依赖。

#### 2.1.5 FR-8.4 明文二次确认适用（裁决 E）

**结论：适用，走 CSV 同款双门禁**。1PUX `export.data` 为**解密后的明文 JSON**（导入侧 docstring「1PUX 导出已解密为明文 JSON」同源），含全部密码/TOTP secret——FR-8.4「导出明文前强提示风险并二次确认」对 1PUX 导出同等成立。ExportView 新增 1PUX tab，复用 CSV 的双门禁状态机（强风险页勾选 + confirmationDialog 二次确认），内核不提供门禁（与 CSV 同纪律）。

#### 2.1.6 互操作诚实边界（裁决 F）

**声明：不能在本仓环境内自证「1Password 可读」**。本版验收锚点是**自回环**（导入 → 导出 → 再导入 → 逐字段一致）+ 结构对照 `03` §6.4/官方形态。真实 1Password 交叉打开 = **真机验收项**（`T06` 验收清单），未执行前文档/UI 不得声称「已验证与 1Password 互通」——对齐 BUG-11 发版文案约束的诚实纪律。

#### 2.1.7 导出范围

- 导出 **Active + Archived** 条目（与 CSV 一致），**回收站条目不导出**（`skipped_trashed` 计数，CSV 先例）；
- 未知 FieldType / 不可序列化字段：降级 Text 并入 report（不静默，导入侧容忍语义同源）。

### 2.2 FR-7.3 opvault 导入（OP）

#### 2.2.1 结构调研结论

`03` §6.3 已按官方 OPVault design 文档给出完整目录结构与密钥派生链（PBKDF2-HMAC-SHA512 → masterKey/overviewKey → SHA-512 派生加密/MAC 密钥 → item keys；Encrypt-then-MAC，AES-256-CBC + HMAC-SHA256）。**本版实现以其为基线，不重推**。待补两处实现缺口：

| 缺口 | 状态 | 处置 |
| --- | --- | --- |
| D-04 opdata 对象精确二进制布局 | 未闭环 | 按 `03` §6.3「[IV:16]‖[ct]‖[MAC:32]」推导实现，**OP 核心任务内交叉验证前置**：对照第三方开源实现（Go `opvault` / Haskell `opvault` 已知存在）核对；真实样本到手前实现按此布局 + 自洽往返测试，样本校验为 `T02` 验收门槛 |
| item details JSON schema（`d` 解密后字段结构） | 未定义 | 定义解析策略而非硬编码表（见 §2.2.3），字段码表**待样本校准** |

#### 2.2.2 密码跨 FFI

opvault 为密码保护的目录导入，与 1PUX/CSV（纯文件）不同。FFI 签名 `import_opvault(path: String, password: String, vault_dir: String)`——password 以 `String` 跨 FFI，**与 `unlock(password: String)` 既有范式一致**（无 SecretString 跨 FFI 先例，不新造）。

#### 2.2.3 字段类型支持矩阵与 out-of-scope 清单（裁决 G）

**结论：已知类型→类型化，未知类型→Text + 报告（不静默丢弃）**。候选类型码表（`t` 键，**待样本/交叉验证校准，实现期以真实样本核对后冻结**）：

| OPVault 类型 | Coffer FieldType | 说明 |
| --- | --- | --- |
| T（Text）/ P（Password）/ N（Notes）/ M（Multiline）/ U（URL）/ D（Date）/ B（Phone） | Text / Concealed / Multiline / Multiline / Text(URL 行) / Text / Text | 常用字段类型 |
| 未知/未列 | Text | 降级并记入预检报告「未映射字段」清单 |

designation（`k` 键）`username` / `password` / `totp` / `notesPlain` → Coffer Designation 同 1PUX 映射。TOTP 字段从 details 提取 otpauth（若有），复用 `parse_otpauth`。

**明确 out-of-scope（v0.7.0 首版，逐条入报告不静默）**：

| 项 | 理由 |
| --- | --- |
| OPVault 附件 | 附件在 OPVault 中的承载形态未在 `03` §6.3 覆盖，且无真实样本；首版**跳过并计数**，样本/交叉验证确认后随补丁加 |
| 密码历史 / 关联项（`reference` 类型字段）/ 自定义类型（如 secure note 的富文本） | 与 1PUX 导入同源丢弃决策（`docs/09` v0.3.0 冻结裁决：密码历史丢弃+计数） |
| OPVault 多 profile 目录 | 取 `default/`（`03` §6.3 目录结构基线），其余 profile 报告列出不导入 |
| opvault 导出（反向） | FR-8 无此需求，不做 |

**目录语义**：`precheck_opvault(path)` = **结构预检**（目录结构 + `profile.js` 元数据可解析 + KDF 参数读数），**不触密码**（与「预检不触密钥」纪律一致，`docs/17` TCB-1④ 同源）；**含条目数/分类分布的完整报告需密码**——由 `import_opvault` 内部解析后产出（两段式：先解锁密钥链 → 全量解析 → 报告 + 落库，单事务纪律与 1PUX 相同：每条目一事务 + 收尾清理孤儿附件——本版附件 out-of-scope，故无孤儿清理面）。此偏差（完整预检需密码）在文档显式标注。

#### 2.2.4 密码学依赖（新依赖清单，`T02` 引入，需 `cargo add` 校准版本）

| crate | 用途 | 备注 |
| --- | --- | --- |
| `pbkdf2` | PBKDF2-HMAC-SHA512（profile 密钥派生） | 复用 workspace 既有 `hmac` + `sha2` |
| `aes` + `cbc` | AES-256-CBC 解密（Encrypt-then-MAC 链） | RustCrypto；`03` §6.3 勘误已钉死非 GCM |
| `subtle` | MAC 常量时间比较 | workspace 已有 |

**明确不做**：不引入 opvault 第三方 crate 作为运行时依赖（格式逆向为主，第三方仅作交叉验证对照）。

### 2.3 FR-12.4 大字号（Swift-only，裁决 H）

**结论：纯 SwiftUI，零核心变更**。`ItemDetailView` 密码字段（含 Passkey 行以外的 Concealed 字段）增「放大」按钮 → 全屏 `LargePasswordSheet`（新文件）：密码单字符自适应缩放（monospaced，宽度自适应，上限 ~72pt，超长换行），含复制按钮（走既有 ClipboardManager，尊重剪贴板清除定时）与关闭。无 macOS 截屏防护面（FR-12.2 仅 Android）。不落库、无门禁。

### 2.4 FR-14.3~14.5 设置项（ST）

- **14.3 生成器默认参数（Swift-only）**：UserDefaults 持久化（AppModel 既有范式：`generatorDefaultsV1` 键，存 `FfiPasswordGenOptions` 六字段 + passphrase 选项）。生成器面板首次打开预填存档值；「另存为默认」回写。**零核心变更**（`cf_audit::generate_password` 纯函数不变）。
- **14.4 本地诊断**：核心最小增量 = 组合读取方法 `diagnostic_summary()`（`T03`）：条目数（`meta.item_count`）、附件数、库创建/最后备份时间、vault uuid 前缀（非敏感）；App 侧 `format_version()`（`cf_format::FORMAT_VERSION` 常量经 FFI 暴露）+ Bundle version。Swift `DiagnosticsView`（新）展示。**不含任何敏感数据**（FR-14.4 红线：无标题/无密码/无 secret）。
- **14.5 网络自证（Swift-only）**：`NetworkSelfCertView`（新）静态说明页——声明零网络架构（无网络 entitlement / 无 `std::net` 代码路径），给出用户自证方法（`codesign -d --entitlements` 检查无 `com.apple.security.network.*`；运行时 `lsof -nP -iTCP -iUDP` 无连接）。可选加分项：门禁脚本 grep 断言核心仓零 `std::net`/`reqwest` 引用（`T11`，不阻塞）。

### 2.5 FR-5.3 TOTP QR（已裁定 A，2026-10-04 用户裁定 / 42960b8）

**事实**：`01` §5-E FR-5.3 =「扫描 QR（otpauth://）+ 手动输入」= **TOTP 添加方式**；全仓无「passkey QR」。版本卡「FR-5.3 QR 判定」措辞与需求原文不符。

**两种解释与工作量**：

| 解释 | 内容 | 工作量 | 门禁 |
| --- | --- | --- | --- |
| A. TOTP QR（字面 FR-5.3） | macOS 相机 AVFoundation 扫 otpauth QR → 复用 `parse_otpauth` → 添加 TOTP 到条目；需 `NSCameraUsageDescription`（TCC 弹窗） | 中（纯 Swift + 少量 FFI/复用解析） | 添加 TOTP = 条目写 → ItemWrite |
| B. Passkey QR 传输（任务措辞） | 跨设备 passkey 以 QR 迁移（Google 系做法） | 大（新能力面，无设计文档支撑，与桌面 1PUX 无 passkey 数据源限制冲突） | — |

**裁定（A，42960b8）**：FR-5.3 = TOTP QR **相机实时扫描**（AVCaptureSession + TCC 相机权限，按需求原文 `docs/01` §5-E）；TCC 拒权降级为手动输入 URI 兜底（列入验收负路径）。「passkey QR」系版本卡措辞错误，已澄清。`T09` 解除阻塞、并入 G3。设计增量见 §2.5.1。

```

  → TotpScanView（sheet：AVCaptureSession 实时预览 + 取景框）
     → AVCaptureMetadataOutput 识别 QR → 原始 stringValue
     → model.parseOtpauthUri(uri)  // 复用 cf-ffi parse_otpauth_uri（api.rs:576，
                                   // 纯函数直调，无解锁/写门禁；失败统一 1012）
          ├─ Ok(FfiTotpDraft) → sheet 内预览 issuer/account/位数/周期
          │    +「使用此 URI」→ 回填 ItemEditView.otpauthText = 原始 URI → dismiss
          └─ Err(1012) → sheet 内提示「不是有效的 otpauth URI」→ 保持扫描/可手动输入
```

| --- | --- |
