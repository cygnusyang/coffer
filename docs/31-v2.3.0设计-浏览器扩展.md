# 31 · v2.3.0 设计——浏览器扩展（WebExtension + native messaging）

## 0. 结论先行

**路线（lead 建议、用户已指示继续、待 D- 批准）**：macOS 平台 Chrome/Edge/Firefox 一份 WebExtension + native messaging 宿主；Safari 顺延二期。Coffer 取「**App/daemon 持库持钥、扩展为薄客户端**」架构（比 1Password 更薄——零网络决定扩展无法自持加密库），且比 1Password 更安全一步：**解密全在 Coffer 侧，通道按需传解密值**，通道承载明文填充值 → **通道机密性 + 双向认证为本版最高优先级设计面**。

**8 项架构裁定建议**（核心结论，细节见 §3/§4/§5/§6，D- 逐条见 docs/31a）：

| # | 决策 | 建议（结论） |
| --- | --- | --- |
| D-1 | 通道认证机制 | **四层叠加**：① manifest `allowed_origins`/`allowed_extensions` 冻结扩展 ID（浏览器强制）；② host 验父进程 = 签名浏览器（`SecCode` by PID + **DR/TeamID 主 + runtime CDHash 次**，fail-closed，直击 CVE-2025-24169）；③ broker 验 peer host（PID + 代码签名 + `getpeereid` + challenge，复用 docs/20 §3.6）；④ E2E 会话双向认证（IKpsk2 风格，P-256/PSK，§3.3） |
| D-2 | 宿主进程模型 | **复用嵌套 bundle coffer 二进制**，新增两子命令：`browser-agent`（native messaging host，薄中继，浏览器 spawn）+ `browser-broker`（长驻 daemon，持解锁会话，App 解锁时 spawn、锁定时杀，锁态镜像）。manifest `path` → bundle 内 shim（`exec` 保父进程链，规避「manifest 不能传参」） |
| D-3 | origin 绑定格式 | 三型：**exact / subdomain / domain**，无 regex、无 prefix 通配；存储 = item 结构化 `origin_bindings` 字段（冻结）；匹配优先级 exact > subdomain > domain |
| D-4 | manifest 冻结点 | **首版发布前冻结** Chrome/Edge 扩展 ID（manifest `key` 字段钉死）+ Firefox GUID（`browser_specific_settings.gecko.id`）；dev 模式 App 扫描浏览器 profile 自动发现 dev ID |
| D-5 | Safari 策略 | **顺延二期**（无 stdin/stdout 宿主，须容器 App + SafariWebExtensionHandler，复用度低、成本高） |
| D-6 | 通道机密性 | 明文填充值**必经通道**（扩展零解密，结构性）；E2E = **P-256 ECDH + HKDF-SHA256 + AES-256-GCM + HMAC-SHA256**（扩展侧 WebCrypto 原生、零 JS 加密依赖；Rust 侧新增 `p256`+`aes-gcm`，vendored）；**每会话独立密钥 + 内存限时驻留** |
| D-7 | 捕获触发面 | 表单 **submit 事件监听 + 验证提交成功**（导航/响应）才提示保存；仅显式接受，不自动保存；`data-coffer-ignore` 退出属性 |

**明文暴露面（诚实声明，设计显式承认）**：解密值只在 4 处短暂出现——broker 进程内存（解密瞬间）、扩展 service worker/content script 内存（填充瞬间，随即覆盖）、页面 DOM（填充值对页面 JS 可见，浏览器扩展模型的结构性限制，非实现缺陷）、捕获流中页面自有的表单值（本就属页面）。其余任何环节（native messaging 管道、UDS、host 中继、日志）只见 E2E 密文。

**并行分组总览**（§10）：Wave-1 全并行 G-A∥G-C∥G-D∥G-F → Wave-2 串行 G-B → Wave-3 串行 G-E → Wave-4 G-T（tester 判据）+ G-R（reviewer 安全门禁）。互斥矩阵见 §10.2。

## 2. 总体架构

### 2.1 组件与进程模型

```
┌────────────────────────── 浏览器（Chrome/Edge/Firefox，macOS）──────────────────────────┐
│                                                                                        │
│  ┌────────────────────────── WebExtension（Coffer Browser）─────────────────────────┐  │
│  │  background（MV3 service worker）：native 端口管理、E2E 会话、状态                │  │
│  │  content script：捕获（submit）/ 填充（字段识别 + 写入 DOM）——与页面共享 DOM       │  │
│  │  inline menu（扩展源 iframe，同源隔离页面读取）/ popup（手动解锁/检索/手势确认）    │  │
│  │  crypto/e2e.ts（WebCrypto 原生：P-256 ECDH + HKDF + AES-GCM + HMAC）              │  │
│  └───────────────────────────────┬───────────────────────────────────────────────────┘  │
│                                  │ browser.runtime.connectNative("com.coffer.browser")   │
│              native messaging（4 字节 LE 长度前缀，本机浏览器内机制）                    │
└──────────────────────────────────┼──────────────────────────────────────────────────────┘
                                   │ 浏览器 spawn，stdio
                          ┌────────▼─────────┐
                          │ coffer browser-agent │  native messaging host（薄中继）
                          │ （嵌套 bundle 内 shim │  ——只搬字节，零授权、零解密、零持久状态
                          │    exec 后，验父进程    │  验父进程 = 签名浏览器（§3.2 ②）
                          │    = 签名浏览器）      │
                          └────────┬─────────┘
                                   │ UDS（本机回环，AF_UNIX，dir 0700 / file 0600）
                          ┌────────▼─────────┐
                          │ coffer browser-broker │  长驻 daemon（App/CLI 侧可信核心）
                          │  ——持解锁会话（escrow 免密解锁，docs/29 §6）                 │
                          │  ——唯一授权/解密执行点：origin 校验、用户确认、按需单值解密    │
                          │  ——E2E 会话端点（身份密钥 + 配对 PSK，§3.3）                 │
                          │  生命周期 = App 解锁→spawn / 锁定→kill（锁态镜像）            │
                          └────────┬─────────┘
                                   │ 进程管理（App 是 broker 的父进程，锁定/退出即杀）
                          ┌────────▼─────────┐
                          │      Coffer.app        │  设置页「浏览器集成」开关、配对确认 UI、
                          │  （既有主 App）         │  native messaging manifest 写入/删除
                          └────────────────────┘
```

**进程边界裁定（D-2 落地）**：**主 App 不宿主**扩展取密服务（沿用 docs/20 §6.2「主 App 不宿主服务器」立场）；真实授权/解密在 **broker 独立进程**（App 侧可信核心）。host 只中继不授权（硬约束）。三进程 + 浏览器 + 扩展为最小闭环。

### 2.2 依赖方向（硬约束，审计口径同 docs/11 §3.3）

```
extension/（WebExtension，独立于 Rust 依赖树，仅 WebCrypto）
   │ native messaging（浏览器机制，非 Coffer 依赖）
   ▼
core/cf-browser（新 crate，lib）——协议/E2E/origin/会话，crate 内自足
   ├──► cf-domain（SecretString/CfError/ItemCategory 复用）
   ├──► cf-crypto（AEAD/HKDF/HMAC/密钥材料纪律，§3.3 增量）
   └──► cf-session（VaultSession 复用 escrow 解锁通道）
   ▲
   │
core/cf-mcp（bin「coffer」：main.rs/cli.rs 增 browser-agent/browser-broker 子命令分发）
   └──► cf-browser（bin 依赖 lib，cf-browser 不依赖 cf-mcp）
macos/Coffer（Swift 侧：manifest 写入/删除、broker 进程管理、配对 UI）
   └──► 包内嵌套 bundle coffer 二进制（D-6 既有装配）
```

- **cf-browser 为纯 lib**，不产 bin；子命令在既有 `coffer` bin（cf-mcp 名下）分发——**零新二进制、零新签名面**（复用 D-6 嵌套 bundle，这是 D-2 采纳的核心理由）。
- **cf-browser 不得被 cf-session/cf-store/cf-ffi/cf-domain 反向引用**；cf-mcp 仅作组合根。
- 扩展侧无 Coffer 依赖（WebCrypto 内建）；`check_no_network` 新增 `p256`/`aes-gcm` 无网络能力，白名单维持 PASS（§7.4）。

### 2.3 数据流

**启用/配对流**（一次性，§5.3）：App 设置页开启「浏览器集成」→ 校验嵌套 bundle coffer 二进制（McpStatusProbe.cofferBinaryPath 先例）→ 写各浏览器 NativeMessagingHosts manifest（含冻结 allowed_origins）→ 扩展首连 → broker 向 App 弹配对确认（用户批准）→ 下发 PSK + broker 公钥 → 扩展持久化于 chrome.storage.local。

**解锁流**（§4）：扩展连 host → host 连 broker → broker 未解锁 → 返回 `broker_locked` → 扩展 popup 提示「打开 Coffer 解锁」→ App 解锁 → App spawn broker（escrow 免密）→ 扩展重连 → E2E 会话建立。

**填充流**（§6.1）：用户聚焦字段 → 点击 inline menu 条目（显式手势 → 手势令牌）→ `get_secret{request_id, entry, fields[], origin, gesture}`（一次手势=一次填充，request_id 关联；D-7 单次/TTL 30 s 不变）→ broker 校验 origin 绑定 + 手势 → 解密 → E2E 密文返回 → 扩展解密 → 写 DOM → 覆盖零化 → 令牌作废。

**捕获流**（§6.3）：content script 监听 submit → 验证提交成功（导航/响应）→ inline menu 提示「保存到 Coffer」→ 用户接受 → `capture_save{origin,user,pass,gesture}` → broker 校验 + 建/改条目并绑定 origin。

### 2.4 状态机（broker / extension 会话）

```
broker（App 生命周期绑定）：
  App 未解锁/未启用 ──App解锁+启用──► running(unlocked, E2E 端点就绪)
  running ──App 锁定/退出──► killed（session 密钥随进程销毁）
  注：broker 持有解锁会话期间 lock 命令（扩展侧 `lock`）→ 杀进程（同 App 锁定）

extension：
  idle ──native port 建立──► connecting ──E2E 握手──► paired
  paired ──broker_locked──► awaiting_unlock（popup 引导开 App）
  paired ──SW 终止──► idle（会话密钥随 SW 内存销毁，重连即重握手）
  任何状态 ──手势令牌过期/重放──► error(8007)
```

**MV3 service worker 随时可被杀**（调研 Q6 一手）：E2E 会话密钥**只存内存**、不落 chrome.storage（SW 重启 → 会话失效 → 重握手，成本低且是安全正收益）；仅非敏感重连状态（如「已配对」标记）可存 `chrome.storage.session`。

## 3. 通道与加密设计（本版最高优先级）

### 3.1 三段通道

| 段 | 载体 | 机密性 | 完整性/认证 |
| --- | --- | --- | --- |
| 扩展 ↔ host | 浏览器 native messaging（stdin/stdout，4 字节 LE 长度前缀；Chrome/Edge/Firefox macOS 全 LE 一致，spike 实证） | E2E 密文（host 只见密文） | 浏览器 enforced（allowed_origins）+ host 验父进程签名（§3.2 ②） |
| host ↔ broker | UDS（AF_UNIX，dir 0700/file 0600，专用私有父目录，docs/20 §3.1 MEDIUM-1 纪律） | E2E 密文 | peer PID 代码签名 + getpeereid + challenge + 单调 id（docs/20 §3.6 全套） |
| 扩展 ↔ broker（逻辑 E2E） | 跨上两段，host 为 blind transport | **AEAD 端到端**（§3.3） | **双向认证**（§3.3） |

### 3.2 四层认证链（D-1 落地）

每层防御不同攻击者，单层皆不足，**四层叠加为最终裁定**：

| 层 | 校验方 → 被校验方 | 机制 | 防谁 | 失败语义 |
| --- | --- | --- | --- | --- |
| ① 扩展 ID | 浏览器 → 扩展 | manifest `allowed_origins`（Chrome/Edge）/ `allowed_extensions`（Firefox GUID），D-4 冻结 | 非授权扩展到达 host | 浏览器拒绝连接（不 spawn host） |
| ② 浏览器 | host → 父进程 | `SecCodeCopyGuestWithAttributes(PID)` + **DR/TeamID 签名验证（主）**（`SecCodeCheckValidity`，TeamID + identifier 锚定，跨浏览器原地自更新稳定）+ **runtime CDHash 白名单（次）**（`kSecCodeInfoUnique` 现取；旧常量 `kSecCodeInfoCdhash` 已不在 SDK），fail-closed | CVE-2025-24169（host 无法验证拉起者）、同机进程冒充浏览器 | host 拒绝服务并退出（8001） |
| ③ host | broker → peer host | `LOCAL_PEERPID`→PID 代码签名（CDHash == 嵌套 bundle coffer 二进制）+ `getpeereid` 同用户 + 会话 challenge + 单调 id（docs/20 §3.6 机制注记对齐） | USENIX'18（同机冒充 host/server）、非授权本地进程连 broker | broker 拒绝连接（8002） |
| ④ 扩展↔broker | 应用层 E2E | IKpsk2 风格握手（§3.3）：broker 静态密钥 pin + 配对 PSK | 管道嗅探、host 被控、进程链被绕过 | 握手失败 → 会话不建立（8004） |

**关键机制注记（r0.2，P-S 实证修订）**：② 与 ③ 均基于 **PID→代码签名**（macOS `SecCodeCopyGuestWithAttributes` + `SecCodeCheckValidity`），同用户按 PID 查签名可行、不需额外 entitlement、无 TCC 弹窗（P-S 实证）。**② 层主校验 = DR/TeamID 签名验证**（TeamID + identifier 锚定，跨 Chrome 原地自更新稳定——P-S 发现：精确 CDHash 白名单会被自更新击穿，9 天前启动的旧进程 runtime CDHash ≠ 磁盘 CDHash 致误拒）；**次校验 = runtime 现取 CDHash**（`kSecCodeInfoUnique`；旧常量 `kSecCodeInfoCdhash` 已不在 SDK）。③ 层验 host 为**自有嵌套 bundle coffer 二进制**、无自更新，CDHash 比对稳定。spike（P-S）已实证 PASS（fail-closed：非白名单 / PID 不存在 / 冒充者 exit 1），G-B 放行。

### 3.3 E2E 协议（D-6 落地）

**协议族**：Noise `IKpsk2` 风格手工实现（不引 Noise 框架——扩展侧免 WASM/免框架，Rust 侧自控），映射 WebCrypto 可用原语：

| 原语 | 扩展侧（WebCrypto 原生） | Rust 侧（cf-browser，新增） |
| --- | --- | --- |
| ECDH | P-256（`subtle.deriveBits`）——**WebCrypto 唯一 ECDH，X25519 不支持 → 否决 X25519 方案** | `p256` crate（NIST P-256 ECDH） |
| KDF | `subtle.deriveKey` HKDF-SHA256 | 既有 `hkdf`/`sha2` |
| AEAD | AES-256-GCM（`subtle.encrypt/decrypt`，浏览器硬件加速、支持面最广） | `aes-gcm` crate |
| MAC/认证 | HMAC-SHA256（`subtle.importKey/verify`） | 既有 `hmac`/`sha2` |
| 随机 | `crypto.getRandomValues` | 既有 CSPRNG（getrandom） |

**为什么否决备选**（选型依据，详见 §11 风险 2）：
- **B. X25519 + ChaCha20-Poly1305**：Rust 侧已具 ChaCha20-Poly1305（chacha20poly1305），但 WebCrypto **无 X25519、无 ChaCha20 通用支持**（ChaCha20-Poly1305 WebCrypto 支持较新，Safari 18.4+/FF 132+）→ 扩展侧必须引入 WASM 加密库（CSP + 供应链 + CWS 审计负担），否决。
- **C. 纯对称 PSK（无 ECDH）**：无前向保密——PSK 一旦泄露，既往会话全部可解，否决。

**握手流程（IKpsk2 风格，host 全程 blind transport）**：

```text
前提：扩展已 pin broker 静态公钥 PK_b + 配对 PSK（配对流 §5.3，chrome.storage.local）
扩展(initiator)                       broker(responder)
  e, es           ──►                 （验证 PK_b 匹配 pinned 公钥）
  e, ee, s?, es   ◄──                 （msg2 签名 over e_init_pub‖e_resp_pub，身份密钥绑定）
  p = HMAC(PSK, okm) ──►              验证 p → 扩展身份确立
  okm = HKDF-SHA256(ikm = ee‖es, salt = e_init_pub‖e_resp_pub,
                    info = "cf/browser/session/v1", L = 64)
  每会话独立 ephemeral 密钥 → 前向保密 + 会话隔离
```

**E2E 契约（canonical，权威实现 = G-A/cf-browser Rust——lead 裁定 2026-10-07，r0.2）**：
token 图（含 `es`）为权威协议描述，下方简写行与契约表冲突时**一律以本表为准**；G-C（扩展侧）已按本表返工对齐，Wave-2 G-B 接线以 Rust 契约为基准。

| 项 | 冻结公式 |
| --- | --- |
| 会话密钥派生 | `okm = HKDF-SHA256(ikm = ee‖es, salt = e_init_pub‖e_resp_pub, info = "cf/browser/session/v1", L = 64)`；`enc_key = okm[0:32]`、`mac_key = okm[32:64]`（enc/mac 双密钥） |
| 每消息帧 | `plaintext = seq(8, LE)‖payload_json` → `AES-256-GCM(enc_key, nonce12, plaintext, aad="")` → 输出 `ct‖tag(16)`；`mac = HMAC-SHA256(mac_key, nonce‖ct_tag)`（`ct_tag = ct‖tag(16)`）→ `frame = nonce(12)‖ct‖tag(16)‖mac(32)`；seq 单调 → 防重放 |
| msg2 签名 | 签名对象 = `e_init_pub‖e_resp_pub`（SEC1 非压缩），broker 静态私钥（pk_b 对应私钥）签名，编码 P1363（r‖s） |
| msg3 确认 | `p = HMAC-SHA256(PSK, okm)`——扩展身份确立信号，broker 侧恒时比对 |
| 握手线格式（hex） | `Init{version, e_init}` / `Response{version, e_resp, pk_b, signature}` / `Confirm{version, p}` |

> **「双方 nonce」歧义注记（r0.2 消解）**：旧简写行「双方 nonce」本版**不以独立随机 nonce 字段实现**——Noise「nonce」语义 = 双方临时值，本版以双方 **ephemeral 公钥（SEC1 非压缩）** 充任，故 salt 与签名对象均为 `e_init_pub‖e_resp_pub`。各会话 ephemeral 独立 → 会话隔离 + 前向保密。

**明文暴露面（诚实声明）**：解密值仅 4 处短暂存在（§0 清单）；会话密钥仅存扩展内存（SW 终止即销毁）与 broker 内存（进程被杀即销毁），**不落 chrome.storage / 不落盘 / 不进日志**。扩展「零密钥材料」指**零库密钥**（DEK/KEK/mcp_key/子密钥一律不进扩展）；传输层材料（会话密钥/PSK/broker 公钥）明确属扩展持有边界，两者在文档与代码中显式区分。

### 3.4 会话密钥生命周期与内存驻留

- **每次会话独立**：E2E 握手每连接重跑（ephemeral ECDH），无跨会话密钥复用。
- **内存限时驻留**：broker 侧解密值——填充值下发后即 zeroize；扩展侧填充值——写 DOM 后立即覆盖（JS 层尽力覆盖 + 文档诚实声明 JS 无法真 zeroize）；手势令牌 TTL 30 s 单次。
- **锁态即销毁**：App 锁/退 → broker 被杀 → 会话密钥随进程销毁；SW 终止 → 扩展侧会话密钥随内存销毁。

## 4. 认证与解锁

### 4.1 解锁代理（委托 App/broker，扩展不碰生物/密码）

- 扩展**不持有**主密码/生物凭据，不自行解锁库（对齐 Bitwarden 桌面集成模式：生物认证委托桌面 App）。
- broker 解锁 = **escrow 免密路径**（docs/29 §6：托管优先 → env 兜底 → 退出 1，fail-closed），与 `coffer mcp --provider coffer` 同款取密语义。
- **锁态镜像（D-2 生命周期）**：broker 由 App 在「已解锁 + 浏览器集成已启用」时 spawn、App 锁/退时 kill → 扩展锁态恒等于 App 锁态（1Password 模型）。**不在 App 关闭时由 broker 自行 escrow 解锁**（防「后台无主进程长期持解锁会话」——扩大被攻破窗口；列为非目标，§9）。

### 4.2 配对信任（§5.3 细节）

扩展首连须用户在 **App 内显式批准**（App 显示浏览器名 + 扩展 ID + 权限说明）。批准后 broker 下发配对 PSK + 公钥。**PSK 独立于库密钥，可轮换**（重开「浏览器集成」即换新 PSK，旧扩展失配须重配对）；broker 身份密钥为**确定性派生**（HKDF(DEK, vault_uuid, "cf/browser/v1") → P-256 密钥对，镜像 mcp_key 设计，换库即自然重配对）。

## 5. 捕获/填充流

### 5.1 捕获流（D-7）

| 步骤 | 机制 |
| --- | --- |
| 监听 | content script 对 `submit` 事件监听（document_start 注入，懒激活），识别用户名/密码字段（label for / ARIA / autocomplete 启发式，A.10 同款） |
| 验证提交成功 | 导航事件（`pageshow`/`visibilitychange` 到新文档）或 fetch/XHR 完成判定**确实提交**；失败（表单重渲染/报错停留）则不提示（1Password 同款） |
| 提示 | inline menu 提示「保存到 Coffer」；**仅用户显式接受**才保存；无用户名不 autosave；`data-coffer-ignore` 退出 |
| 保存 | `capture_save{origin, username, password, title, gesture}` → broker 校验 origin 绑定权限 + 建/改条目 + 写入 `origin_bindings` |
| 暴露面 | 捕获的是页面自有值（本就属页面），无新增暴露；值经 E2E 通道传输 |

### 5.2 填充流（显式手势，点击劫持缓解）

| 步骤 | 机制 |
| --- | --- |
| 触发 | **仅用户点击 inline menu / popup 条目**触发；不自动填、不预填（DEF CON 33 教训） |
| 手势令牌 | UI 点击瞬间生成 `gesture`（随机 nonce，绑定该次 DOM 事件，TTL 30 s、单次、作废即弃）；`get_secret`/`capture_save`/`confirm_unbound_origin` 必须携带 → 页面 JS 无法脚本化触发 broker 动作 |
| origin 校验 | broker 校验条目 `origin_bindings` 匹配当前页 origin（§5.3）+ **表单 action 目标 origin 同源校验**（A.10.1 本地等价：action 指向异源 → 拒绝，除非用户显式 `confirm_unbound_origin`） |
| 取密 | `get_secret{request_id, entry, fields[], origin, gesture}` → broker 校验 origin 绑定 + 手势 → 解密 → `get_secret_result{request_id, values:{field→value}}`（E2E 密文返回；**多字段、一次性、无缓存**，一次手势=一次填充，request_id 关联；D-7 单次/TTL 30 s 不变） |
| 填充与销毁 | 扩展解密 → 写 DOM（页面对页面 JS 可见，结构性限制）→ 立即覆盖；内联菜单 = 扩展源 iframe（同源隔离页面读取） |

### 5.3 防钓鱼本地化（无云列表）

- **origin 绑定三型**（D-3）：`exact`（`https://example.com`，scheme+host+port 规范化）/ `subdomain`（`*.example.com`）/ `domain`（`example.com`，含 apex+全部子域）。**无 regex、无 prefix 通配**（regex = 用户误配 + 过宽匹配 = 钓鱼放大）。
- 匹配优先级 **exact > subdomain > domain**；填充仅当存在绑定匹配当前**有效 origin**。
- 任何不匹配 → 不填充；用户确认 ≠ 云列表，全部本地判定。
- 填充前 UI 恒展示目标 origin 与条目绑定（用户可见复核）。

### 6.1 扩展分发

| 渠道 | 要点 |
| --- | --- |

### 6.2 native messaging host 分发（D-6 复用）

- host = 嵌套 bundle coffer 二进制 `Coffer.app/Contents/Helpers/coffer.app/Contents/MacOS/coffer` 的 `browser-agent` 子命令（同 bundle 同身份同 profile，`keychain-access-groups` entitlement 既有）。
- **manifest 动态写入**（Bitwarden 实践）：App 启用「浏览器集成」时写入各浏览器 NativeMessagingHosts 目录（Chrome/Edge: `~/Library/Application Support/<Browser>/NativeMessagingHosts/com.coffer.browser.json`；Firefox: `~/Library/Application Support/Mozilla/NativeMessagingHosts/...`）；停用即删除。host_name = `com.coffer.browser`。
- **manifest `path` 不能传参** → `path` 指向 bundle 内 **shim**（**签名 Mach-O shim**：`tools/coffer-shim.c`、`/usr/bin/clang` 编译，无受限 entitlement、AMFI 不适用，与 coffer 同 Apple Development 身份签名，装配 `Contents/Helpers/coffer-shim`）。**argv 策略**：浏览器把扩展 origin 注入为 argv[1]，而 G-B `parse_agent_args`（cli.rs）只认 `--log`、未知 flag → Err → CONFIG_ERROR(1)——故 shim **丢弃 origin 类参数**（`chrome-extension://` / `moz-extension://`）、其余透传（`--log` 等）；② 层验父进程靠 `getppid()` 不靠 argv（origin 可由扩展伪造、host 不消费，丢弃无安全损失——P-S 交叉发现 #2 + G-B 消费面实证）。
- **拷出即 SIGKILL 纪律延伸**：host/broker 均只经包内路径运行（docs/20 §5.4 同源）。

### 6.3 签名门禁（与 v2.2.0 D-6 一致）

- host/broker 复用 `tools/build_macos_app.sh` step 3.5 嵌套 bundle 装配 + 同 Apple Development 身份 + 同 profile；keychain-access-groups entitlement 纪律不变。
- **entitlements 最小化**：shim 无受限 entitlement；broker/host 不新增 entitlement（只读 escrow Keychain 项走既有组 `A6DS985SJJ.app.coffer.Coffer`）。
- hardened runtime / 不退回 ad-hoc / 双 codesign --strict 校验（D-6 实证路径）逐项沿用。

### 6.4 零网络门禁

- 新 Rust 依赖 `p256`/`aes-gcm`（+其传递）无网络能力（非黑名单 crate，无 http/tls/socket/net 子串）；须 **vendored + 锁版本**（对齐 docs/29 G1c「零新外部网络依赖」纪律）→ `check_no_network.sh` 维持 PASS（G-E 验证项）。
- 扩展 WebCrypto 内建、无网络 fetch 路径；扩展不引入远程代码（MV3 禁）。

### 9.2 互斥核对（文件范围显式不相交）

- **G-A**：`core/cf-browser/**` + `core/Cargo.toml` + `core/Cargo.lock`。
- **G-B**：`core/cf-mcp/src/{main.rs,cli.rs}` + `core/cf-mcp/Cargo.toml` + `core/cf-mcp/tests/browser_subcommand.rs`。G-A ∩ G-B = ∅（cf-browser 与 cf-mcp 分属目录）；**但 G-A/G-B 同触 `Cargo.lock`（生成物）→ 必须串行（G-A→G-B），且 G-B 编译依赖 G-A crate 存在**。
- **G-C**：`extension/**`，与 core/、macos/、docs/、tools/ 全部不相交。
- **G-D**：`macos/Coffer/{Platform,Views,Support,AppModel.swift}` + `macos/Tests/BrowserStatusTests/**`；G-E 触 `macos/README.md`，G-D 不触 → 不相交。
- **G-F**：`docs/{03,09,10,KNOWN-ISSUES}.md`；G-T 触 `docs/32` 新文件，不相交。
- **G-E**：`tools/{build_macos_app.sh,check_no_network.sh}` + `macos/README.md`；与 G-D（macos/Coffer/**）不相交。
- **G-T**：`docs/32`（新）+ `tools/run_browser_smoke.sh`（新）+ `tests/acceptance_browser.rs`（新）+ `extension/tests/**`（新）——`tests/` 顶层、`tools/` 新脚本、`extension/tests` 均无人争用。

### 9.3 并行/串行合并顺序

```
Wave-1（全并行，文件互斥）：G-A ∥ G-C ∥ G-D ∥ G-F
  （P-S spike 与 G-A/G-C 并行，作 G-B 门禁）
Wave-2（串行）：G-B（依赖 G-A + P-S 通过）
Wave-3（串行）：G-E（依赖 G-B 二进制）
Wave-4：G-T（tester 起草判据，依赖 G-A..G-E 落盘）+ G-R（reviewer 安全门禁，依赖全部）
   → 门禁四连（cargo test / clippy / check_no_network / codesign）+ D-1~D-7 用户确认回填
```

**不标注「可并行」的边界**：G-B 与 G-A 同锁 `Cargo.lock` 且编译依赖 → **串行**；G-E 依赖 G-B 产物 → **串行**；G-T/G-R 依赖全部实现 → **串行尾段**。G-C/G-D 虽依赖 G-A 的协议/E2E 签名，但**文件互斥** → 可并行先行（按本文 §3/§5 冻结签名实现，docs/20 §9「按冻结签名先行」先例）。
