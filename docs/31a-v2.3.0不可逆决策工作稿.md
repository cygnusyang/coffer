## D-1 通道认证机制（四层叠加）

**决策内容**：扩展↔host↔broker 全链认证 = 四层叠加，一次性定死协议族：
① **扩展 ID 层**（浏览器 enforced）：manifest `allowed_origins`（Chrome/Edge）/ `allowed_extensions`（Firefox GUID）冻结扩展身份，D-4 钉死；
② **host 验浏览器层**：`coffer browser-agent` 验父进程 = 签名浏览器（`SecCodeCopyGuestWithAttributes(PID)` + **DR/TeamID 签名验证（主）+ runtime CDHash 白名单（次）**，fail-closed；**实现细节注记**：主 = `SecCodeCheckValidity` TeamID+identifier 锚定、跨浏览器原地自更新稳定，次 = runtime 现取 CDHash `kSecCodeInfoUnique`、旧常量 `kSecCodeInfoCdhash` 已不在 SDK）——直击 CVE-2025-24169「宿主无法验证拉起者」；
③ **broker 验 host 层**：`browser-broker` 验 peer host（PID→代码签名 + `getpeereid` 同用户 + 会话 challenge + 单调 id，复用 docs/20 §3.6 全套）——防 USENIX'18 同机冒充；
④ **应用层 E2E 双向认证**：扩展↔broker IKpsk2 风格握手（broker 静态公钥 pin + 配对 PSK）——防管道嗅探 / host 被控 / 进程链被绕过。

**改动代价**：认证链 4 层全部实现 + 真机 spike（P-S）实证 PID→代码签名机制；协议族一旦发布冻结，改协议 = 全量升级扩展与 host/broker（与 MCP D-1 冻结同类）。

**备选**：A1（仅 ①②，Bitwarden 级）——省 ③④，但 host 与管道成单点，不符合本版「通道机密性+双向认证最高优先级」硬约束；A2（仅 ④）——省 ①②，但 CVE-2025-24169/USENIX'18 未解。**建议 A（四层全上）**。

**风险**：②③ 依赖 macOS `SecCode` by PID 的同用户可用性——P-S spike 前置门禁（G-B 不放行），对齐 D-6 spike 先例。

## D-2 宿主进程模型（复用嵌套 bundle coffer 二进制）

**决策内容**：**复用**既有嵌套 bundle `Coffer.app/Contents/Helpers/coffer.app/Contents/MacOS/coffer`（D-6 已签同身份同 profile），新增两子命令：
- `coffer browser-agent` = native messaging host（浏览器 spawn，薄中继，零授权零解密零持久态，验父进程签名）；
- `coffer browser-broker` = 长驻 daemon（App 解锁时 spawn、锁定时 kill，锁态镜像；持 escrow 解锁会话，唯一授权/解密执行点）。
manifest `path` 不能传参 → bundle 内 **shim**（shell 脚本 `exec` 保父进程链 + PID 不变，验父进程仍成立）。

**改动代价**：两子命令 + shim 装配（G-A/G-B/G-E）；vs 独立 helper 二进制 = 新增一个待签名的独立可执行 + 独立嵌套 bundle 装配面 + 独立 profile 管理（D-6 教训：裸 Mach-O 受 AMFI 约束、需 bundle 包装）。

**备选**：B1（独立 helper，仿 1Password LoginItems / Bitwarden desktop_proxy）——隔离更纯，但重复签名/装配/维护面，且 manifest path 仍要解决；B2（host 直接持会话做全部，无 broker）——违反「宿主只中继不授权」硬约束，否决。**建议 A（复用二进制）**。

**风险**：broker 生命周期绑 App 锁态（不在 App 关闭时 escrow 自解锁）——「App 必须运行且解锁，扩展才能用」为用户可见约束（1Password 同款），落文档。

## D-3 origin 绑定格式（三型冻结，存储格式类）🔴 不可逆

**决策内容**：绑定类型只三型：`exact`（scheme+host+port 规范化全匹配）/ `subdomain`（`*.example.com`）/ `domain`（`example.com`，含 apex+全部子域）。**无 regex、无 prefix 通配**。匹配优先级 exact > subdomain > domain。存储 = item 结构化 `origin_bindings` 字段（additive，`#[serde(default)]` 兼容旧库，docs/29 D-3 先例）。

**改动代价**：item 数据模型新增字段 + 旧库兼容；**发布后改格式/改类型集 = 既有条目绑定需迁移**（存储格式类，不可逆）。

**备选**：C1（+regex）——灵活但用户误配 + 过宽匹配放大钓鱼（§5.3 论证），否决；C2（tag 临时约定 `coffer:origin:*`，U-4 先例）——可逆但本决策点就是要冻结格式，tag 编码 URL 脆弱，否决。**建议 A（三型 + 结构化字段）**。

## D-4 manifest 冻结点（首版发布前冻结）🔴 不可逆

**决策内容**：**首版发布前**冻结扩展身份：Chrome/Edge 用 manifest `key` 字段钉死扩展 ID；Firefox 用 `browser_specific_settings.gecko.id` 固定 GUID。所有 native messaging manifest 的 `allowed_origins`/`allowed_extensions` 引用冻结 ID。dev 模式 App 扫描浏览器 profile 自动发现 dev ID（Bitwarden 实践，不污染冻结 ID）。

**改动代价**：ID 一经发布即冻结——**改 ID = 所有已装扩展断连 + 全量重配**（1Password 2016 改 ID 先例）。**必须在首版上架前定稿**；一旦上架不可逆。

**备选**：D1（发布后再定）——上架后改 ID 灾难；D2（不冻结、每版可漂移）——manifest 恒失效。**建议 A（发布前冻结）**。

## D-5 Safari 策略（顺延二期）

**决策内容**：v2.3.0 **不含 Safari**。Safari 无 Chrome/Firefox 的 stdin/stdout native messaging 宿主机制，须容器 macOS App 打包扩展 + `SafariWebExtensionHandler`（`SFExtensionMessageKey`），content script 不能发 native 消息、CSP 剥 `ws://`，且扩展不能被 MDM 强制安装（调研 Q6 一手）。

**改动代价**：本版零投入；二期（v2.4.0+ 或独立版本）另立设计文档走容器 App 路径，与三浏览器 native messaging 架构不共享宿主代码。

**备选**：E1（本版含 Safari）——工作量大幅膨胀 + 双通道模型（native messaging + SafariWebExtensionHandler）并存，延误 macOS-first 主目标。**建议 A（顺延）**。

## D-6 通道机密性（明文值必经通道 + E2E 选型）🔴 安全契约

**决策内容**：
1. **明文填充值必经通道**（结构性）：扩展零解密能力（零网络决定无法自持加密库），broker 解密后按需单值经通道下发，扩展解密后填充。→ 通道机密性是最高优先级设计面。
2. **E2E 加密** = P-256 ECDH + HKDF-SHA256 + AES-256-GCM + HMAC-SHA256（IKpsk2 风格）：扩展侧 WebCrypto 原生（零 JS 加密依赖、CWS 审计友好）；Rust 侧新增 `p256`+`aes-gcm`（vendored + 锁版本）。
3. **每会话独立密钥 + 内存限时驻留**：握手每连接重跑（ephemeral ECDH，前向保密）；解密值 4 处短暂存在即销毁（§0 诚实声明）；会话密钥不落盘、不进日志、SW/进程终止即销毁。

**改动代价**：新 Rust 依赖 2 个（p256/aes-gcm，vendored）+ E2E 协议实现与 KAT 冻结向量（G-A）；check_no_network 复核（G-E）。

**备选**：F1（X25519 + ChaCha20-Poly1305）——Rust 侧已有 ChaCha20-Poly1305，但 WebCrypto **无 X25519/无 ChaCha20 通用支持** → 扩展须引 WASM 加密库（CSP + 供应链 + 审计负担），否决；F2（纯对称 PSK 无 ECDH）——无前向保密，PSK 泄露则既往会话全解，否决。**建议 A（P-256 + AES-GCM）**。

**界定**：「扩展零密钥材料」= 零**库密钥**（DEK/KEK/mcp_key/子密钥）；传输层材料（会话密钥/PSK/broker 公钥）属扩展持有边界，两者显式区分（docs/31 §3.3）。

## D-7 捕获触发面（submit 事件 + 验证提交成功）

**决策内容**：content script 监听表单 `submit` 事件（document_start 注入，懒激活），识别用户名/密码字段（label for / ARIA / autocomplete 启发式）；**验证提交确实发生**（导航事件 / fetch-XHR 完成）才提示保存；失败（表单重渲染/报错停留）不提示（1Password 同款）；仅用户显式接受才保存；无用户名不 autosave；`data-coffer-ignore` 退出属性。

**改动代价**：content script 注入范围 = `<all_urls>`（捕获需覆盖全部站点）→ **触发 CWS 人工深度审核 1-2 周**（排期预留）。

**备选**：G1（仅监听 submit、不验证成功）——误报保存（1Password 已改进为验证成功），否决；G2（`pagehide`/卸载推断）——不可靠。**建议 A（submit + 验证）**。
