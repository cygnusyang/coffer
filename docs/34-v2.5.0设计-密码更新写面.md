# 34 · v2.5.0 设计——密码更新写面（App 快捷动作 + CLI 写子命令）

## 0. 背景与目标

v2.5.0 新增需求（用户 2026-10-09 提出并讨论定稿）：为 Coffer 管理的密码提供**动态更新**能力。

- 现状：**消费线已闭环**（App 全 CRUD + MCP 只读工具 `list_secret_names / list_secrets / run_with_secret / get_secret_metadata`）；**输入线只有手动全量编辑**（编辑条目改密码字段 + CSV/1PUX/Bitwarden 重导入）；`coffer` CLI 只有 `mcp` 一个子命令，无任何写命令；docs/20 写面（grant/revoke/rotate）本就规划、MVP 明确 absent（AS-4/AS-7）。
- 目标：密码更新有**两条明确途径**——① **App 内**找到对应条目改（条目级「更新密码」快捷动作）；② **CLI** 写子命令。MCP 保持只读。

## 1. 用户裁定（本文档的定盘约束）

| # | 裁定 | 影响 |
| --- | --- | --- |
| R1 | **不做密码生成器** | 用户明确不喜欢生成密码（太长、不知道具体内容）。更新流程**值来源 = 用户输入/粘贴**，任何形态不得把「生成」作为主路径 |
| R2 | **密码绝不经过 Claude Code / LLM** | 哪怕模型构造含密码的工具调用参数也算进上下文。→ **MCP 写工具裁掉**（agent 仅顾问角色：「记得在 App 里更新 GitHub 的密码」），MCP 维持只读 |
| R3 | **直接写 + 历史回滚** | 不做审批弹窗（值由用户本人直输，信任锚点天然在用户侧）；错误靠 FR-2.9 条目历史版本回滚兜底 |
| R4 | **CLI 写子命令保留；MCP 写工具不保留** | 写面 = App 快捷动作 + CLI 写子命令两通道 |
| R5 | **动态更新 = 按需触发** | 零网络承诺 + 扩展线废弃 → Coffer 无法主动探测站点变更；触发者只有用户（App / CLI） |

## 2. 范围

### 2.1 In（本版）

- **App 通道**：条目详情页「更新密码」快捷动作（不进入全量编辑）。
- **CLI 通道**：`coffer set-password` 写子命令（stdin 取密）。
- 两通道共享既有 Rust 写内核（item update + FR-2.9 历史 append），**无 schema / 无 FORMAT_VERSION 变更**。

### 2.2 Out（明确不做）

- MCP 写工具（R2）；密码生成器（R1）；审批弹窗（R3）；站点变更主动探测（R5）；多值字段批量更新（本版仅密码字段）；条目新增/删除（App 已有，CLI 不在本版）。

## 3. 安全与纪律（两通道共用）

- **值不落 argv / 不进日志 / 不经协议帧明文外传**：CLI 密码走 stdin（TTY 下隐藏输入不回显）；App 走 SecureField。
- **强度门禁**：与 App 既有策略一致（zxcvbn ≥ 强，PasswordStrengthSection 同款），CLI 弱密码拒绝并给引导；CLI 提供显式 `--force` 逃生口（脚本/迁移场景，**用户 2026-10-09 批准保留**）。
- **历史版本化**：每次更新自动 append 一条历史版本（FR-2.9 既有），旧密码可查看/回滚。
- **审计事件**：写操作预留审计事件位（password-updated）；审计 JSONL 落盘仍待 D-3，本版不落地盘。
- **失败 fail-closed**：解锁失败 / 条目未命中 / 强度不达标 → 不写库、明确报错（CLI 退出码映射沿用 §5.3 纪律）。

## 4. App 通道——条目「更新密码」快捷动作

### 4.1 入口与交互

```
条目详情页 ──「更新密码」按钮
    │
    ▼ 弹出小 sheet（不进全量编辑）
    ├─ 「从剪贴板粘贴」主按钮（站点改密 → 复制 → 到 Coffer 一下粘贴）
    ├─ 手动输入框 + 密码强度条（zxcvbn，PasswordStrengthSection 复用）
    ├─ 显示当前版本时间（如「当前版本 2026-09-27」）
    └─ 「保存」→ 复用 update_item 仅改密码字段 → 自动 append 历史
         → 关闭 sheet + 提示「已更新 · 旧版本可在历史中回滚」
```

### 4.2 要点

- 意图聚焦：只动密码字段，不误触其它字段；比全量编辑更快更安全。
- 剪贴板优先：站点改密后最快路径（粘贴 → 强度 → 保存）。
- 强密码要求文案沿用（「密码强度需达到强或以上」）。
- 实现面：纯 SwiftUI（新 View + AppModel/ItemStore 既有 update 路径），**预期零 Rust 改动**（若有 FFI 便利接口需要，最小增量）。

## 5. CLI 通道——`coffer set-password`

### 5.1 命令签名

```
coffer set-password <条目名>            # 密码从 stdin 读一行；TTY 下隐藏输入提示
coffer set-password --id <条目UUID>      # 按 UUID 定位（名称歧义/改名场景）
coffer set-password --force <条目名>     # 绕过强度门禁（用户批准保留，§3）
```

- 条目定位：display name 精确匹配优先（未命中 / 歧义 → 明确报错，不写库）；`--id` 为 UUID 定位兜底。
- 取密链（与 `coffer mcp` 同构，D-4 纪律）：**MCP 解锁托管（escrow）→ `COFFER_VAULT_PASSWORD` env 兜底 → 都无 fail-closed 退出 1**。escrow 是库级能力（Keychain `cn.coffer.mcp-escrow` + header `mcp_wrap`），与 MCP 命名耦合但非 MCP 专属——CLI 写复用同一托管解锁，用户无需重复授权。

### 5.2 行为

- 成功：改密码 + append 历史 + 打印「已更新 <条目名> · 旧版本可在 App 历史中回滚」。
- 失败退出码：条目未命中 / 强度不达标 / 解锁失败等，按既有退出码映射纪律（§5.3）显式区分。
- 实现面：`core/cf-mcp` 新增子命令（Rust），复用 cf-store update + zxcvbn + escrow 取密；CLI 测试随 TDD。

## 6. 验收判据骨架（待 tester 起草补全）

1. App：条目详情「更新密码」→ 粘贴/输入新密码 → 保存 → 条目密码已变、历史新增一条旧版可回滚。
2. App：弱密码被拒并给引导（zxcvbn < 强）。
3. CLI：`coffer set-password <名>`（stdin）→ 密码更新 + 历史 append；argv/日志无明文。
4. CLI：未命中/歧义/强度不足 → 不写库、明确报错、非零退出。
5. CLI：escrow 未启用且无 env → fail-closed 退出 1（D-4 语义一致）。
6. 密码值不进审计日志 / 不进 CLI 历史 / 不进进程列表（ps 不暴露）。
7. MCP 工具面保持只读（无新增写工具）——非回归。
